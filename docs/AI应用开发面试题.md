# 一、LLM 接入与结构化输出

### Q1.1 LLM 调用为什么必须收口到一个统一入口？

- **难度**：基础 · **类型**：方案设计
- **考察点**：分层意识、可替换性、成本与可观测的统一采集点。
- **参考答案要点**：
  1. 业务代码不应感知供应商差异（URL 拼接、鉴权头、超时、响应结构）。
  2. 统一入口才能统一做：JSON 解析、异常分类（未配置/响应异常/网络异常）、用量统计、脱敏、限流与重试。
  3. Agent 节点只依赖一个 `CompletionClient` 协议，测试时可注入假模型，避免评测依赖真实供应商。
  4. 配置读取也应集中：运行时配置（数据库）优先，环境变量兜底，页面可改、可测。
- **追问**：如果供应商换成非 OpenAI 兼容协议，改动面应该落在哪里？——只改适配层，把 payload 构造与响应解析下沉，不动业务与图。

### Q1.2 如何保证大模型输出能被程序稳定消费？解析失败怎么处理？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：结构化输出、校验即合同、失败分类与降级。
- **参考答案要点**：
  1. 双保险：请求侧要求 JSON 对象（`response_format=json_object`），提示词中给出明确字段与约束；响应侧用严格 Pydantic 模型校验（`extra="forbid"`、长度/数量上下界）。
  2. 失败要分类：网络/超时属技术故障，可重试；JSON 不合法或字段校验失败属内容故障，重试收益低。
  3. 内容故障的处置顺序：记录结构化事件 → 有限次修复（把校验错误回灌 prompt）→ 规则兜底 → 转人工，而不是直接判整个任务失败。
  4. 所有产出标注来源（`llm` / `rules`）与 `provenance`，便于事后归因。
- **追问**：`extra="forbid"` 有什么副作用？——模型多返回字段即失败，提高了确定性但会增加兜底率，需要配合提示词与监控。

### Q1.3 哪些环节该用规则、哪些该用模型？判断依据是什么？

- **难度**：进阶 · **类型**：场景权衡
- **考察点**：成本/确定性/可解释性的取舍能力。
- **参考答案要点**：
  1. 判据四条：是否需要语义理解、是否要求确定性、是否对延迟敏感、是否可承受成本。
  2. 项目分工：上下文加载、权限、路由关键词、质量门、库存计算走规则；诊断、创意、文案、脚本走模型。
  3. 规则还承担"模型不可用时的兜底"，保证任务至少产出可用草稿。
  4. 关键设计：兜底不等于静默掩盖——用 `source` 字段和降级率指标让问题可见。
- **追问**：规则兜底率突然升高说明什么？——供应商故障、提示词回归、校验过严，三者要分开排查。

### Q1.4 多模型、多供应商的配置治理怎么做？

- **难度**：高级 · **类型**：方案设计
- **考察点**：配置分层、密钥安全、变更可控性。
- **参考答案要点**：
  1. 配置分两类：连接信息（base_url/key/model）与生成参数（temperature、max_tokens、是否关闭思考），后者可按 Agent 覆写。
  2. 存储优先级明确：数据库运行时配置覆盖环境变量；密钥加密存储，接口只返回脱敏值。
  3. 提供连通性测试接口，把"改完配置线上才炸"提前到保存前。
  4. 按用途分 target（文本/图片/视频），各自独立供应商与配额，互不影响。
  5. 变更要有审计与回滚；灰度可按 workspace 维度放量。
- **追问**：密钥轮换时如何不打断在跑的任务？——新旧 key 并存一个窗口期，新任务用新 key，旧任务自然结束。

# 二、多 Agent 架构与职责设计

### Q2.1 为什么拆成多个专用 Agent，而不是一个大 Agent 加一堆工具？

- **难度**：基础 · **类型**：方案设计
- **考察点**：多 Agent 的核心动机与代价，能否给出反例。
- **参考答案要点**：
  1. 单 Agent 的问题：工具一多系统提示词膨胀，模型容易混淆职责、调用无关工具，越权面也更大。
  2. 拆分的收益：职责收敛降低误调用；权限粒度可到角色级（库存 Agent 能看见库存调整，创意 Agent 完全看不见）；日志可定位到具体角色；工作流顺序可编排，增删角色不改大提示词。
  3. 代价必须说出来：注册表、多套提示词、跨角色一致性、评测成本都上升。
  4. 关键边界：不是让多个 Agent 自由对话，而是由上层工作流决定顺序。
- **追问**：什么情况下反而应该合并？——工具少、步骤强耦合、需要全局视角的短流程。

### Q2.2 多 Agent 协作：对话式协商与编排式执行怎么选？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：能否区分两类多 Agent 范式，并说明工程后果。
- **参考答案要点**：
  1. 对话式（Agent 互相发消息、自主决定轮到谁）：灵活，但轮次不确定、成本不可控、难审计、易死循环。
  2. 编排式（状态图/DAG 固定顺序，节点内部可有限工具循环）：可中断、可回放、可评测、成本有上界。
  3. 本项目选编排式，代价是新增流程要改注册表，灵活性换确定性。
  4. 折中：编排为主干，节点内允许有步数上限的小循环。
- **追问**：节点内的工具循环如何设上限？——最大步数 + token 预算 + 超限转人工，而不是直接抛异常。

### Q2.3 Agent、工具、工作流三张注册表的边界在哪？如何避免"注册了却不能执行"？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：声明与实现解耦的理解，以及漂移风险的控制。
- **参考答案要点**：
  1. Agent 注册表：角色 key、版本、描述、工具白名单——回答"这个角色能干什么"。
  2. 工具注册表：key、风险等级、是否仅 Owner、是否幂等——只是元数据，不含执行逻辑。
  3. 工作流注册表：角色顺序、必需上下文（满足其一即可）、默认风险等级——决定执行路径。
  4. 真正逻辑在 ToolGateway 的 handler；注册了但没 handler，网关必须直接拒绝，而不是运行到一半报错。
  5. 防漂移手段：启动自检（所有注册 key 都有 handler）、契约测试、CI 校验、能力目录只展示已实现且启用的项。
- **追问**：把 `version_manifest` 写进每次 Run 有什么用？——复盘时能确定当时用的是哪套角色/工作流版本，支撑归因与回放。

### Q2.4 平台要新增一个业务 Agent，完整改动面是什么？

- **难度**：高级 · **类型**：方案设计
- **考察点**：能否从"写提示词"上升到"平台级交付流程"。
- **参考答案要点**：
  1. 声明：注册 Agent（key/version/描述/工具白名单）。
  2. 能力：新增或复用工具 key，定风险等级，补 handler，复用底层 service 而不是重写业务。
  3. 编排：注册或修改工作流，声明角色顺序与必需上下文；确认需要人审的风险档位。
  4. 合同：输出 Pydantic 模型、提示词版本、规则兜底策略。
  5. 验证：单测（正常/边界/越权/质量失败）、离线评测用例、成本上限。
  6. 暴露：能力目录接口自动输出，前端无需硬编码；同步补权限矩阵。
- **追问**：如何不影响存量工作流？——版本化 + 灰度开关，新版本先小流量，旧 Run 继续用旧 manifest。

# 三、工具调用与权限边界（受控执行）

### Q3.1 "受控 Agent"到底控什么？

- **难度**：基础 · **类型**：概念辨析
- **考察点**：能否把"控制"拆成可验证的维度。
- **参考答案要点**：
  1. 控能力：工具白名单，角色只能调分配给自己的工具。
  2. 控风险：R0–R3 分级，高危强制人审，R3 仅 Owner。
  3. 控身份：每次调用校验用户、工作区、角色，不信任前端。
  4. 控成本：全局 token 预算 + 返修上限。
  5. 控输出：默认产出草稿，审批通过才写正式业务表。
  6. 控过程：每一步写结构化事件，可审计、可回放。
- **追问**：如果模型"绕过网关"直接调业务 service 会怎样？——架构上不允许：节点只拿得到注入的网关，service 不接受模型直连；靠代码评审与单测守住这条线。

### Q3.2 R0–R3 风险分级依据是什么？一个新工具怎么定级？

- **难度**：进阶 · **类型**：方案设计
- **考察点**：分级标准是否可复用，能否说清"为什么"。
- **参考答案要点**：
  1. 分级维度：可逆性、影响面（单条/批量）、是否对外可见、是否涉及资金或真实库存、能否自动回滚。
  2. 对应关系：R0 只读；R1 生成草稿/候选素材（不改变正式状态）；R2 写正式业务对象或创建实验；R3 真实资金/库存调整，owner_only。
  3. 定级流程：默认从严，新工具从 R2 起评；具备幂等 + 可回滚 + 影响面可控后再降级。
  4. `owner_only` 与风险等级是正交的两个维度，不能互相替代。
- **追问**：R2 是否一定人审？——可以按 workspace 配置放宽，但必须保留审计与默认安全，且放宽本身要留痕。

### Q3.3 一次工具调用的完整授权链路是什么？顺序为什么不能乱？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：防御纵深、校验顺序的工程含义。
- **参考答案要点**：
  1. 链路：认证（token → 用户）→ 工作区归属 → 工作流是否启用 → Agent 白名单是否含该工具 → 风险等级 vs 当前角色 → 是否需要审批 → handler。
  2. 顺序原则：先便宜后昂贵、先粗粒度后细粒度、能拒绝的尽早拒绝，减少无谓副作用与开销。
  3. 每层独立成立，不依赖上一层的结论——上层通过不代表下层可以跳过。
  4. 需要审批的在此中断图、写审批记录，而不是先执行再补审批。
- **追问**：为什么不能只在 API 层校验？——Agent 是异步执行，API 请求早已结束；执行时必须基于当时的角色与状态重新校验。

### Q3.4 多租户场景下怎么防越权？

- **难度**：进阶 · **类型**：故障排查
- **考察点**：租户隔离的常见漏洞与双来源校验。
- **参考答案要点**：
  1. 双来源：token 里的用户 + `X-Workspace-ID`，必须能查到有效 membership；不能只信 header。
  2. 执行期校验：Run 的 workspace 必须等于工具上下文的 workspace，防止跨租户拼接。
  3. 资源级校验：上下文里的 `product_id` / `store_id` 必须属于该 workspace，不能当权限凭据用。
  4. 上下文快照中的 id 一律视为"待校验输入"，而非"已授权对象"。
- **追问**：内部服务间调用如何防伪造？——内网 + 短期凭证/mTLS；本项目同进程依赖注入，风险面在参数校验。

### Q3.5 工具幂等怎么设计？"重复调用直接拿上次结果"具体怎么做？

- **难度**：高级 · **类型**：方案设计
- **考察点**：幂等键设计、并发冲突处理、副作用的收口。
- **参考答案要点**：
  1. 幂等键：`run_id + agent_key + tool_key`（必要时加入规范化入参 hash），落唯一索引。
  2. 执行前先查操作记录：已完成则直接返回结果快照，不再产生副作用。
  3. 并发双执行：靠唯一约束或行锁，冲突方读取结果而不是报错。
  4. 副作用外置：生成类工具先落"草稿/意图"，正式写入统一由 finalize 或审批后的动作完成。
  5. 外部生成类工具把 `request_id` 透传给供应商，利用供应商侧幂等。
- **追问**：幂等记录保留多久？失败记录能否重试？——按审计要求保留；失败进入可重试状态机，重试复用同一幂等键。

### Q3.6 工具注册与实现解耦，利大还是弊大？如何防上线事故？

- **难度**：高级 · **类型**：场景权衡
- **考察点**：架构权衡与工程防护的组合能力。
- **参考答案要点**：
  1. 利：可以先搭框架再补实现、对外提供能力目录、多团队并行开发、元数据可版本化。
  2. 弊：声明与实现漂移、出现"假能力"、问题暴露延迟到运行时。
  3. 防护组合：启动自检（注册必有 handler）、每个 key 的契约测试、CI 校验、catalog 只暴露已实现项、灰度开关。
  4. 判断标准：如果团队规模小且工具少，直接绑定实现更省事；解耦的收益随工具数量增长。
- **追问**：如何灰度上线一个新工具？——按 workspace 开启白名单，先只读验证，再放 R1，最后评估是否升 R2。

# 四、工作流编排（LangGraph）

### Q4.1 LangGraph 的核心概念分别解决什么问题？

- **难度**：基础 · **类型**：概念辨析
- **考察点**：State / Node / Edge / Checkpointer / interrupt 的准确定义。
- **参考答案要点**：
  1. State：贯穿全图的共享状态（TypedDict），节点返回增量字段而非整体覆盖。
  2. Node：一个执行步骤，通常是纯函数式边界，副作用通过受控依赖注入。
  3. Edge：普通边决定顺序，条件边按结构化状态路由（如质检通过/失败）。
  4. Checkpointer：按 `thread_id` 持久化每一步状态，支撑中断、恢复与回放。
  5. `interrupt()`：主动暂停并把待恢复点写入 checkpoint。
- **追问**：State 更新是覆盖还是合并？——按字段增量更新；列表类字段需要显式 reducer 才能追加。

### Q4.2 为什么选 LangGraph，而不是 LangChain Chain 或自研状态机？

- **难度**：进阶 · **类型**：场景权衡
- **考察点**：技术选型的对比维度。
- **参考答案要点**：
  1. 需求画像：多步骤、条件分支、循环返修、可中断、可恢复。
  2. Chain 是线性结构，不适合有环与中断；通用 Agent 框架自主性强，但难约束、难审计。
  3. 自研状态机可控，但持久化、恢复点、并发认领、可视化都要自己实现，成本不低。
  4. LangGraph 直接提供 State + checkpointer + interrupt，与本项目的"受控 + 可恢复"目标吻合。
  5. 代价：框架耦合、升级风险、调试门槛，需要通过版本锁定与集成测试来兜。
- **追问**：如果禁止引入框架，最小等价物怎么设计？——状态表 + 步骤定义表 + 幂等执行 + 恢复点，本质是把 checkpoint 自己做一遍。

### Q4.3 共享 State（黑板模式）会带来什么问题？怎么治理？

- **难度**：高级 · **类型**：方案设计
- **考察点**：能否识别"全局状态"这一常见架构债。
- **参考答案要点**：
  1. 问题：所有 Agent 输出堆在一个 dict，序列化体积、checkpoint 写入成本、prompt 拼装成本、调试难度都随业务线性增长；隐式耦合导致改一个节点影响别人。
  2. 治理一：只传引用——大对象落业务表或对象存储，State 里放 id 与摘要。
  3. 治理二：节点显式声明读哪些字段、写哪些字段，避免自由读写。
  4. 治理三：设 State 大小上限并监控，超限告警而非静默膨胀。
  5. 治理四：prompt 侧按需裁剪，不把整个 State 塞给模型。
  6. 长期方向：消息/黑板混合，节点间用结构化消息，减少共享可变状态。
- **追问**：State 变大对 checkpoint 有什么直接影响？——写入延迟、存储成本、恢复时间，都随体积上升。

### Q4.4 图里的返修循环如何避免死循环？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：多层限流思想（业务上限 + 框架兜底 + 语义判重）。
- **参考答案要点**：
  1. 业务层：`revision_count` 与 `max_revisions`（项目为 1 次），超限转人工而不是判失败。
  2. 框架层：`recursion_limit` 兜底，防止编排配置错误导致无限跳转。
  3. 规则层：只有 error 级问题拦截，warning 放行，减少无意义返修。
  4. 语义层：返修时注入结构化问题清单；若同一 issue code 重复出现，提前停止，避免原地打转。
  5. 成本层：返修同样消耗 token 预算，预算与次数双重约束。
- **追问**：超限后为什么要转人工而不是直接失败？——产出可能已经可用，交给人判断比丢弃更有业务价值，也便于收集 bad case。

### Q4.5 基础图与平台图为什么并存？这不是重复建设吗？

- **难度**：高级 · **类型**：场景权衡
- **考察点**：对演进式架构的理解，能否承认代价。
- **参考答案要点**：
  1. 基础图是单业务线的"样板间"：字段固定、节点定制深，用来把单条链路讲透、做深。
  2. 平台图由注册表驱动，一套编排代码装配全部工作流，解决规模化复制问题。
  3. 路由策略：命中商品诊断优化时平台图转调基础图，避免把已有能力重写一遍。
  4. 代价如实说：两套维护、行为可能不一致、评测要覆盖两条链路。
  5. 演进路径：能力收敛后把基础图降级为平台图的一个特化子图，或直接下线。
- **追问**：如何保证两条链路可靠性一致？——共享同一套 Outbox、租约、幂等与事件骨架，差异只留在业务节点内。

# 五、Human-in-the-loop 与状态恢复

### Q5.1 `interrupt` / `resume` 的实现原理与前提条件是什么？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：中断不是"抛异常"，恢复不是"重新跑"。
- **参考答案要点**：
  1. 原理：节点调用 `interrupt()` 时，图把当前 State 与待恢复点写入 checkpoint，`invoke` 正常返回而不是销毁上下文。
  2. 前提一：编译图时必须配置 checkpointer；前提二：每次调用必须传同一个 `thread_id`。
  3. 恢复：`Command(resume=payload)` 从断点继续，已完成的节点不会重跑。
  4. 业务侧配合：Run 状态置 `awaiting_review`、写审批记录、释放租约退出 Worker。
- **追问**：没有 checkpointer 会怎样？——中断无法恢复，只能从头重跑或直接失败，人工审批就退化成"重新生成"。

### Q5.2 审批通过后，工具就能直接执行了吗？审批的到底是什么？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：审批的语义边界，是否理解"授权不等于免检"。
- **参考答案要点**：
  1. 审批对象是"这次 Run 在特定上下文下的一个动作或草稿"，不是对该工具的永久授权。
  2. 恢复执行时仍要重新校验：租约是否有效、Run 状态是否合法、用户角色是否仍满足、工具是否仍在白名单、风险等级是否变化。
  3. 等待期间用户可能被降级或禁用，必须按执行时状态判断，而不是按提交时快照。
  4. 审批记录一次有效（Run 级唯一），防止重放与重复恢复。
- **追问**：审批后执行失败怎么办？——进入失败重试或人工介入，不能因为"已批准"就当作已成功。

### Q5.3 `edit_and_approve`（编辑后通过）的设计要点是什么？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：合同校验、二次质检、数据留痕。
- **参考答案要点**：
  1. 合同：决策三选一（通过/编辑后通过/驳回）；编辑后通过必须带编辑结果，其他决策不允许带——用校验器强制。
  2. 编辑后的内容必须重新过质量门，不通过则进入 `quality_failed`，不能直接落库。
  3. 同时保留原始草稿与人工编辑版，用于计算"编辑后通过占比"这类质量指标。
  4. 编辑结果同样要满足结构化合同，前端表单与后端模型共用一套约束。
- **追问**：编辑后质检不通过，应该回到审批还是判失败？——产品决策；更友好的是回到审批并展示问题，但状态机要支持二次审批。

### Q5.4 审批的并发、重复、超时问题怎么处理？

- **难度**：高级 · **类型**：故障排查
- **考察点**：状态机 + 唯一约束 + 异步投递的组合。
- **参考答案要点**：
  1. 重复：Run 级唯一约束，一个 Run 只接受一次最终决策；重复提交返回幂等结果。
  2. 并发：两个审批人同时提交，靠唯一键或乐观锁，先到者生效，后者收到冲突提示。
  3. 超时：审批设置过期时间，定时任务清理，避免 Run 长期占用活跃配额。
  4. 恢复不能同步跑图：审批接口只落决策 + 写 Outbox，由 Worker 重新认领，保持与首次执行同一条可靠链路。
  5. 状态机白名单：只有 `awaiting_review` 允许决策，其他状态一律拒绝。
- **追问**：过期后用户又点了通过怎么办？——拒绝并提示重新发起，不能复活已过期的执行上下文。

### Q5.5 Checkpointer 有哪些存储后端？为什么选 PostgreSQL？它和业务 Run 表的边界在哪？

- **难度**：进阶 · **类型**：场景权衡
- **考察点**：存储选型的对比能力，以及两类状态的职责划分。
- **参考答案要点**：
  1. 常见后端：内存（开发调试，进程退出即丢）、SQLite（单机）、PostgreSQL（多 Worker 共享、事务与运维成熟）、Redis（快但持久化与查询能力弱）。
  2. 选 PostgreSQL 的理由：多个 Worker 需要共享同一份图状态；需要真正持久化以支撑审批与崩溃恢复；与 MySQL 业务库隔离，避免 checkpoint 的写放大影响业务。
  3. 边界：Checkpoint 只负责图内部节点状态与技术恢复；Run 表负责用户可见的运行事实（状态、用量、错误、租约），二者不能互相替代。
  4. 四者一句话区分（常被连环追问）：Task 管目标、Run 管执行、Outbox 管投递、Checkpoint 管恢复。
  5. 运维：按 thread 归档清理，终态 Run 定期回收，控制表增长。
- **追问**：为什么不把 checkpoint 也放 MySQL？——能放，但会与业务事务争抢资源，且框架适配与迁移成本更高；按用途分离更清晰。

# 六、可靠异步与并发

### Q6.1 为什么长耗时 AI 任务必须异步化？API 层的职责边界在哪？

- **难度**：基础 · **类型**：方案设计
- **考察点**：同步/异步边界的基本判断。
- **参考答案要点**：
  1. 长耗时（分钟级）、依赖外部供应商、可能限流与重试，同步请求会占满连接、超时、无法重试。
  2. API 只做：鉴权、参数与归属校验、落业务记录、写投递事件，返回 `202` + `run_id`。
  3. 状态查询用轮询或订阅；前端只关心状态机，不关心执行细节。
  4. 用户体验兜底：立即返回"已受理"，配合进度事件与自动刷新。
- **追问**：为什么不用 WebSocket 直接推结果？——可以做，但长连接与 Worker 解耦更复杂；轮询 + 事件表在可靠性上更简单。

### Q6.2 Outbox 事务消息解决什么问题？不用它会怎样？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：双写不一致、最终一致性。
- **参考答案要点**：
  1. 问题：写业务库与发 MQ 是两个系统，无法原子；库成功而消息失败，就出现"有任务记录但永不执行"的静默丢失。
  2. 方案：同一事务写业务记录 + Outbox(pending)；独立投递器扫描 pending 投递，成功置 published，失败指数退避，超限置 failed。
  3. 语义：至少一次投递，因此消费端必须幂等。
  4. 代价：投递有延迟（轮询间隔），需要清理历史事件；因此通常再加一个"立即触发"来降低平均延迟，轮询只做兜底。
- **追问**：CDC（如 Debezium 订阅 binlog）方案对比？——更实时，但引入新的中间件与运维复杂度，本项目用轮询足矣。

### Q6.3 租约机制如何识别 Worker 宕机？它和 Celery 的 ack 是什么关系？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：消息确认与执行所有权是两件事。
- **参考答案要点**：
  1. ack 解决"消息是否被消费"，租约解决"执行者是否还活着、谁有权继续写结果"。
  2. 实现：认领时写 `lease_owner` 与过期时间，执行期间心跳续租；维护任务扫描超时的 RUNNING，重置为 QUEUED 并重新投递。
  3. 两者互补：`acks_late` + `reject_on_worker_lost` 覆盖进程崩溃；租约覆盖进程假死、网络分区、长任务卡住等 ack 感知不到的情况。
  4. 防脏写：写库前校验 `lease_owner` 仍是自己（fencing），旧 Worker 复活也不能覆盖新执行者的结果。
- **追问**：心跳续不上时应该怎么做？——主动终止本地执行并放弃写库，而不是继续跑完。

### Q6.4 "至少一次"投递下，业务幂等具体怎么做？

- **难度**：高级 · **类型**：方案设计
- **考察点**：幂等的层次（状态机、唯一键、结果复用、fencing）。
- **参考答案要点**：
  1. 状态机 CAS：`queued → running` 用条件更新，影响行数为 0 说明已被别人认领，直接退出。
  2. 唯一约束：`thread_id`、审批（Run 级唯一）、工具操作键，靠数据库兜底。
  3. 落库幂等：finalize 前先查是否已有产出，或对业务表建唯一键 / upsert，重复执行不产生第二份。
  4. 工具结果复用：幂等键命中直接返回上次结果快照。
  5. fencing：结合租约 owner 校验，防止旧执行者的迟到写入。
  6. 不可幂等的动作（真实扣减）必须拆成"记录意图 → 审批 → 单次执行"，并用幂等键约束。
- **追问**：幂等和重试冲突吗？——不冲突；幂等正是让重试安全的前提。

### Q6.5 并发保护该怎么做？锁的范围和限流维度如何选择？

- **难度**：高级 · **类型**：方案设计
- **考察点**：细粒度锁、租户级配额、供应商级限流的分层思维。
- **参考答案要点**：
  1. 任务认领用行锁 + `SKIP LOCKED`，锁范围缩到单行、事务尽量短，避免成为瓶颈。
  2. 租户级：按 workspace 限制活跃 Run 数量（项目为 10），防止单租户打满全局资源，超限快速失败（409）而不是排队。
  3. 供应商级：LLM 与图片/视频供应商按模型维度做令牌桶限流，避免触发对方配额。
  4. 业务热点：同一商品并发多任务时，用业务键互斥或合并任务，而不是只靠锁。
  5. 队列隔离：generation / agent / agent.workflow / maintenance 分开，避免长任务饿死维护任务；代价是 Worker 资源利用率下降，规模小时可合并。
- **追问**：行锁会不会成为吞吐瓶颈？——短事务 + 主键定位 + SKIP LOCKED 通常够用；更高并发可换乐观锁 + 重试。

# 七、质量门与评测

### Q7.1 规则质检与 LLM 质检怎么选？项目为什么用规则？

- **难度**：进阶 · **类型**：场景权衡
- **考察点**：两类质检的边界与组合方式。
- **参考答案要点**：
  1. 规则：确定性、零 token、可解释、低延迟；缺点是覆盖窄、易误杀、判不了语义。
  2. LLM：覆盖广、能判相关性/说服力；缺点是不稳定、贵、慢、可能被提示词绕过。
  3. 项目选择：质量门对象是结构化草稿（字段数量、角度是否重复、绝对化违禁词、证明点缺失），规则足够且可解释，成本为零。
  4. 组合策略：硬约束走规则（违禁词、结构完整性），软评价走 LLM（吸引力、匹配度），最终仍有人审。
- **追问**：LLM 当裁判如何防"自评偏高"？——换模型/独立提示词、校准集、抽样人工复核、与规则结论交叉验证。

### Q7.2 规则质检误杀太多，怎么系统治理？

- **难度**：进阶 · **类型**：故障排查
- **考察点**：从"感觉误杀"到"可度量治理"的方法论。
- **参考答案要点**：
  1. 先量化：每条问题带严重度与结构化编码，按编码统计命中量，定位误杀最集中的规则。
  2. 再分级：警告级只提示不拦截，只有错误级拦截。
  3. 拆粒度：过粗的规则拆细，例如"角度重复"从字符串全等升级为语义去重。
  4. 场景化：按品类配置规则集，策略版本化，可按品类选档。
  5. 兜底：返修上限 + 人审门，最坏结果只是多一次返修，不会硬否决业务。
  6. 验证：治理后同时看误杀率下降与漏放率，避免"放宽过度"。
- **追问**：如何证明治理有效？——误杀率、人审驳回率、首轮通过率三项联动看，单看一项会被误导。

### Q7.3 离线评测如何做到可重复？

- **难度**：高级 · **类型**：方案设计
- **考察点**：评测分层、随机性隔离、断言方式。
- **参考答案要点**：
  1. 固定评测用例集 + 结构化字段断言，不比对自由文本。
  2. 用"假模型/固定响应档位"隔离大模型随机性，保证同一用例结果可重复。
  3. 覆盖六类边界：路由、上下文、策略、质检、恢复、审批；7 条工作流逐条过。
  4. 分层：纯规则单测 → 图 + 假模型集成 → 小样本真模型回归 → 线上指标。
  5. 评测结果纳入 CI，作为合入门禁。
- **追问**：假模型测不出真实问题怎么办？——所以必须保留小样本真模型回归，并用线上指标做最终裁决。

### Q7.4 线上应该看哪些指标？为什么"编辑后通过占比"更关键？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：指标体系的分层与指标含义。
- **参考答案要点**：
  1. 任务层：完成率、失败率、P95 时延、平均 token。
  2. 质量层：首轮质检通过率、最终通过率、返修率、问题编码分布。
  3. 业务层：人审通过率、采纳率、编辑后通过占比。
  4. 编辑后通过占比高的含义：内容基本可用但需人改，是质量提升空间最大的区间，比"直接通过率"更能反映真实体验。
  5. 首轮与最终通过率要分开算，否则返修会被掩盖。
- **追问**：指标漂亮但业务不用，怎么排查？——看任务发起量、采纳率、使用频次与用户反馈，指标要绑业务动作而非只看模型。

### Q7.5 投放 AB 实验怎么设计成功标准？有哪些统计陷阱？

- **难度**：高级 · **类型**：方案设计
- **考察点**：实验设计基本功，能否主动说出偏差来源。
- **参考答案要点**：
  1. 先定假设与单一变量，明确分流单位（商品/店铺/人群）与样本量。
  2. 成功标准预注册，例如连续两天 ROI ≥ 2.5、CTR ≥ 4%、曝光 ≥ 1000，避免事后挑指标。
  3. 陷阱：早期偷看（peeking）、多重比较、辛普森悖论、分流不均、指标被其他活动污染。
  4. 观测周期要覆盖完整的转化滞后窗口。
- **追问**：小流量下如何决策？——序贯检验或贝叶斯方法，并延长周期看趋势，而不是提前下结论。

### Q7.6 多个 Agent 的输出互相矛盾，怎么处理？

- **难度**：进阶 · **类型**：故障排查
- **考察点**：冲突检测与兜底设计。
- **参考答案要点**：
  1. 把质量合规 Agent 放在最后一环，做跨角色规则交叉校验（如价格带与定位是否自洽、受众与卖点是否一致）。
  2. 冲突写成结构化问题（编码 + 涉及字段），进入返修反馈，而不是让人去猜。
  3. 规则判不了的语义冲突，标记后交人审，同时展示双方依据。
  4. 根因治理：上下文只保留一份事实源，每个 Agent 的输出合同明确边界，减少"各说各话"。
- **追问**：冲突反复出现说明什么？——多半是上下文缺失或职责重叠，应改注册表分工，而不是加规则硬压。

# 八、成本、上下文与记忆

### Q8.1 Token 预算怎么设计，才能兜底又不误杀？

- **难度**：进阶 · **类型**：方案设计
- **考察点**：预算的层次与终止策略。
- **参考答案要点**：
  1. 单次运行设全局上限（项目 12000），每次调用前按"已用 + 预估"判断余额。
  2. 单步再设 `max_tokens`，防止单次调用吃光预算。
  3. 超限终止并写事件，明确告知失败原因，不静默截断（截断会产出半成品，比失败更糟）。
  4. 配合返修上限与规则环节零消耗，控制总量。
  5. 双层配额：Run 级防单次爆炸，租户/天级防总量超支。
- **追问**：预算该按 Run 还是按租户？——两者都要，缺一层就会出现"单次正常、总量失控"或"总量正常、单次爆炸"。

### Q8.2 上下文超长时怎么做裁剪与压缩？

- **难度**：高级 · **类型**：方案设计
- **考察点**：优先级、压缩方式、压缩本身的可观测性。
- **参考答案要点**：
  1. 优先级：系统约束与安全规则 > 当前任务输入 > 近期产出 > 历史记忆 > 早期对话。
  2. 压缩方式：摘要、只保留关键字段、用 id 引用大对象、结构化槽位替代原文。
  3. 分层：本轮上下文 → 会话摘要 → 长期记忆，逐层降级。
  4. 触发条件：token 阈值或轮次阈值，避免每轮都压缩。
  5. 压缩要可观测：记录压缩前后 token、压缩率，并监控压缩后质量是否下降。
- **追问**：如何保证关键约束不被压掉？——约束走独立通道（system 固定段），永不参与压缩。

### Q8.3 长期记忆与短期记忆的区别？项目为什么只有长期记忆？

- **难度**：基础 · **类型**：概念辨析
- **考察点**：记忆分层，以及对项目现状的诚实认知。
- **参考答案要点**：
  1. 长期记忆：跨任务复用，结构化存储，带作用域、key、来源、生效时间，任务启动时加载注入。
  2. 短期记忆：单次会话/单次运行内的消息与中间结果，支撑多轮指代与追问。
  3. 项目现状：只有用户手动保存的长期记忆；没有对话循环，前端是表单驱动的"点击即委托"，会话表存在但未用于多轮。
  4. 缺少短期记忆的后果：用户不能追问"把第二个方案再改改"，只能重新发起任务。
  5. 补齐的最小改动：会话消息读写 + 槽位抽取 + 上下文拼装 + 滚动摘要。
- **追问**：记忆冲突怎么仲裁？——当前 `memory_key` 非唯一，多条同键并存且无仲裁；改进方向是唯一约束 + 更新时间/置信度取胜 + 人工确认。

### Q8.4 为什么要做 token 用量归一化？

- **难度**：基础 · **类型**：工程实践
- **考察点**：多供应商差异与成本核算的严谨性。
- **参考答案要点**：
  1. 不同供应商的 usage 字段命名与口径不同（输入/输出/总量，缓存命中是否计入），直接相加没有意义。
  2. 归一化成 `input/output/total/calls` 四个字段，缺失时估算或记 0 并标记，保证预算与报表可比。
  3. 归一化后才能做跨模型成本对比与预算熔断。
- **追问**：估算误差怎么处理？——留安全余量按比例上浮，并在指标里区分"实测"与"估算"。

# 九、可观测性与审计

### Q9.1 一次 Agent 运行应该记录哪些事件和字段？

- **难度**：基础 · **类型**：工程实践
- **考察点**：事件模型的完整性与可用性。
- **参考答案要点**：
  1. 生命周期事件：queued、claimed、context_loaded、agent_step_completed、quality_review_completed、approval_requested/resolved、resumed、finalized、failed。
  2. 字段：事件类型、Agent 名、状态、输入/输出快照（脱敏）、指标（token、耗时）、trace_id / span_id。
  3. 三类用途：前端进度展示、故障定位、评测与审计轨迹。
  4. 大对象只存摘要或引用，避免事件表膨胀。
- **追问**：事件表增长过快怎么办？——按 Run 归档、只存摘要、详情落对象存储，并设保留期。

### Q9.2 如何把链路追踪和业务 Run 关联起来？跨进程怎么传递？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：分布式追踪在异步任务中的落地细节。
- **参考答案要点**：
  1. `trace_id` / `span_id` 写入事件表，Run 作为业务维度属性打点到 span 上。
  2. 链路切分：API → Outbox 投递 → Worker 认领 → 每个图节点 → LLM/工具调用。
  3. 跨进程（Celery）需手动把 traceparent 放进消息头，Worker 侧提取并续接，否则链路会断。
  4. 采样策略：错误全采、正常低采样，但要保证同一 Run 的链路整条完整。
- **追问**：采样导致问题无法复现怎么办？——错误路径强制全采 + 关键节点保留快照。

### Q9.3 日志与快照如何脱敏？线上"这次结果很差"怎么定位到根因？

- **难度**：进阶 · **类型**：故障排查
- **考察点**：安全与可诊断性的平衡。
- **参考答案要点**：
  1. 必脱敏：api_key、password、token、手机号、邮箱等；快照递归处理，长文本截断。
  2. 定位链路：用户反馈 → run_id → 事件时间线 → 版本清单 → 上下文快照 → 提示词与模型参数 → 复现用例。
  3. 归因维度：是上下文缺失、提示词问题、模型波动，还是质检过松/过严。
  4. 可回放的前提：固定输入 + 固定版本 + 固定参数；必要时用录制响应做确定性重放。
- **追问**：脱敏后还怎么排查？——保留结构与长度特征，只替换敏感值，同时提供受控的解密审计通道。

# 十、生成式媒体链路

### Q10.1 文生图/文生视频的异步链路怎么设计？

- **难度**：基础 · **类型**：方案设计
- **考察点**：外部异步 API 的完整生命周期管理。
- **参考答案要点**：
  1. 创意方案确认后创建生成任务（pending），经 Outbox 投递到 generation 队列。
  2. Worker 提交供应商 → 拿到任务 id → 按间隔轮询（有最大次数）→ 取回结果 URL。
  3. 下载落本地/对象存储，写入素材库，状态默认"待评估"。
  4. 全程写任务与事件表；失败按退避重试（最多三次），超时由扫描任务兜底。
  5. 前端通过状态机展示进度，不直接依赖供应商。
- **追问**：为什么不直接把供应商 URL 存库？——URL 会过期、CDN 不可控、审核与留档需要自有副本。

### Q10.2 为什么质检发生在生成之前，而不是生成之后？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：能否准确说清链路顺序与能力边界。
- **参考答案要点**：
  1. 生成前对象是结构化文本草稿：可解析、可规则校验、返修成本极低。
  2. 生成后对象是像素/视频：没有 OCR 与视觉模型就无法校验违禁词与内容合规。
  3. 成本顺序：生成很贵，先过滤再调用能显著省钱。
  4. 现状：图片/视频产物只做人工审核（通过/弃用/复测），机器质检不覆盖成品。
- **追问**：如果要做成品质检，最小方案是什么？——视觉模型 + OCR 违禁词 + 人审抽样，并明确误判的兜底流程。

### Q10.3 要保证"生成图不改变商品原貌"，应该怎么改造？

- **难度**：高级 · **类型**：方案设计
- **考察点**：能否识别纯文生图的能力边界，并给出可落地的保真方案。
- **参考答案要点**：
  1. 现状限制：纯文生图/文生视频不带原始商品图，视频侧还显式拒绝参考图，因此"是否改动原图"在现有链路上不成立。
  2. 改造一：换成图生图/参考图接口，传入原图并加约束提示词。
  3. 改造二：增加视觉校验——特征向量相似度、感知哈希、关键区域（logo/颜色/结构）比对，设阈值。
  4. 改造三：阈值不通过自动重生成或转人工，并把相似度写进素材元数据。
  5. 视频：抽关键帧比对，并约束首帧使用原图。
- **追问**：供应商不支持图生图怎么办？——降级为"文生图 + 人工比对"，同时把限制写进产品说明，不要让用户误以为有保真保证。

### Q10.4 生成任务失败、超时、重复提交怎么处理？重试几次合理？

- **难度**：进阶 · **类型**：工程实践
- **考察点**：错误分类与成本意识。
- **参考答案要点**：
  1. 分类：提交失败（可重试）、审核拒绝（不可重试，应改提示词）、轮询超时（有限重试）、下载失败（可重试）。
  2. 重试上限三次 + 指数退避；超过则置失败并保留错误上下文。
  3. 去重：同一方案同一参数不重复提交，用幂等键/任务状态拦截。
  4. 成本：批量任务设并发上限与供应商配额，失败率异常要告警而不是无限重试。
- **追问**：重复提交如何避免重复计费？——把客户端生成的 request_id 透传供应商，并本地做"已提交"状态锁。

# 十一、架构选型与生产化

### Q11.1 为什么业务用 MySQL、Checkpoint 用 PostgreSQL、队列用 Redis？多存储的代价是什么？

- **难度**：进阶 · **类型**：场景权衡
- **考察点**：按用途选型的能力，以及一致性代价。
- **参考答案要点**：
  1. MySQL：业务表关系清晰、事务成熟、团队熟悉。
  2. PostgreSQL：checkpoint 需要多 Worker 共享、JSON 友好、与业务负载隔离。
  3. Redis：队列与缓存，低延迟；持久化能力弱，不适合作为事实源。
  4. 代价：三套运维、跨库无法同事务（checkpoint 与业务表的一致性靠幂等与状态机保证）、排障链路变长。
  5. 取舍：规模小的时候可以收敛到一套库，但要把"状态分层"的设计保留下来。
- **追问**：能不能全用 PostgreSQL？——技术上可以，但要评估迁移成本与团队栈；本项目按用途分离更利于讲清职责。

### Q11.2 熔断、降级、限流、重试四者怎么区分？在本项目分别落在哪？

- **难度**：进阶 · **类型**：概念辨析
- **考察点**：四个高频概念不混淆，并能落到代码位置。
- **参考答案要点**：
  1. 熔断：下游持续失败时"调不调"的开关，自动切断故障链路。
  2. 降级：调不通时"给用户什么"，返回缓存/默认值/规则兜底。
  3. 限流：入口流量超过容量时"宁可拒绝，不可打垮"，保护自身。
  4. 重试：针对偶发失败；下游已过载时盲目重试是雪崩加速器，必须配退避与抖动。
  5. 项目现状：重试（Celery/Outbox 退避）与降级（规则兜底）已有；限流与熔断不完整，是明确改进项。
  6. 落点：LLM 与媒体供应商调用层做熔断 + 令牌桶；入口按 workspace 限流；重试只对可重试错误生效。
- **追问**：四者顺序怎么配合？——入口限流 → 调用前熔断判断 → 失败后有限重试 → 仍失败则降级并记录。

### Q11.3 什么时候该把单体 FastAPI + Celery 拆成微服务？

- **难度**：高级 · **类型**：场景权衡
- **考察点**：拆分信号与代价的权衡。
- **参考答案要点**：
  1. 信号：独立伸缩需求（媒体生成 vs API）、故障隔离要求、团队边界、发布频率差异、资源异构（GPU/CPU）。
  2. 本项目已有逻辑隔离（四队列），物理拆分的首要收益在"媒体生成 Worker"与 API 之间。
  3. 代价：分布式事务、链路追踪、部署与配置复杂度、联调成本。
  4. 原则：先做模块边界与队列隔离，等出现明确的伸缩或故障隔离痛点再拆。
- **追问**：先拆哪个？——媒体生成：外部依赖重、耗时长、最容易拖垮主 API。

### Q11.4 这套平台的三条局限，改造优先级怎么排？

- **难度**：高级 · **类型**：方案设计
- **考察点**：能否基于影响面与成本做排序，而不是平均用力。
- **参考答案要点**：
  1. 局限：关键词路由意图识别弱；全局 State 随业务膨胀；记忆只按 scope 过滤、缺摘要与冲突仲裁。
  2. 排序依据：影响面 × 实现成本 × 可验证性。
  3. 建议顺序：State 治理（影响成本与稳定性，改动可控）→ 路由升级（小模型分类 + 置信度兜底，可离线验证）→ 记忆压缩与仲裁（依赖前两者）。
  4. 每项都要有度量：离线集、线上指标、单任务成本，否则无法证明有效。
- **追问**：路由换成 LLM 分类，如何防止"更贵且更慢"？——小模型 + 缓存 + 置信度阈值，低置信才升级大模型或转人工。

### Q11.5 与"员工自己用 AI"相比，这套系统的业务价值如何量化？没有埋点怎么办？

- **难度**：进阶 · **类型**：场景权衡
- **考察点**：价值表达能力与诚实度。
- **参考答案要点**：
  1. 五个维度：效率（单任务耗时/人均产出）、规模（批量并发）、质量（通过率/返修率/采纳率）、风险（越权拦截、审计覆盖）、成本（单任务 token 与生成费用）。
  2. 核心差异不是"省了写提示词的时间"，而是把个人工具变成组织级生产系统：能力固化、质量同一条线、结果可溯源。
  3. 没有埋点时，用可得的代理指标（任务发起量、人审反馈、编辑率），并明确说明这是代理指标，同时给出埋点方案。
  4. ROI 口径：节省人力时长 × 人力成本 vs 模型与运维成本，注明假设。
- **追问**：如何证明"质量提升"不是主观感受？——用首轮/最终通过率、编辑后通过占比、人审驳回率三条曲线对照版本变更。

# 十二、综合设计题（开放）

### Q12.1 设计一个支持多轮对话的运营助手，如何与现有任务体系融合？

- **难度**：高级 · **类型**：开放设计
- **考察点**：会话与任务的关系、短期记忆、上下文工程。
- **参考答案要点**：
  1. 概念分离：会话（conversation）是上下文容器，任务（task/run）是可执行单元；一次会话可派生多个任务。
  2. 短期记忆：消息表 + 滚动摘要 + 结构化槽位（product_id、store_id、intent、约束）。
  3. 上下文拼装：系统约束 → 槽位 → 会话摘要 → 最近 N 轮 → 命中的长期记忆。
  4. 工具结果压缩：大结果只回填摘要与引用 id，原文按需再取。
  5. 槽位缺失时主动澄清，不猜测；用户改需求时取消旧 Run、重新路由。
  6. 权限不变：所有工具调用仍经网关校验，多轮不产生"越聊权限越大"。
- **追问**：多轮里如何避免重复执行昂贵步骤？——复用已完成 Run 的产出引用，或做结果缓存与幂等键。

### Q12.2 如何为 Agent 平台设计版本灰度与回滚？

- **难度**：高级 · **类型**：开放设计
- **考察点**：版本治理、兼容性、可回滚性。
- **参考答案要点**：
  1. 版本维度：提示词版本、Agent 定义版本、工作流版本、代码版本，四者组合成 `version_manifest`。
  2. 记录：每次 Run 固化当次 manifest，事后可归因"是哪套组合产出的结果"。
  3. 灰度：按 workspace 或流量比例路由，开关放在注册表层而非散落在代码里。
  4. 回滚：新任务回旧版本；存量 Run 继续用其 manifest 对应版本，避免"回滚把在跑任务弄坏"。
  5. 兼容：State 字段只增不删、提供默认值；节点改名要有迁移函数或用别名。
- **追问**：旧 checkpoint 遇到新代码反序列化失败怎么办？——容错读取 + 迁移函数；无法迁移时拒绝恢复并明确重跑，而不是静默出错。

### Q12.3 从"预定义工作流"演进到"自主规划"，路径和风险控制怎么设计？

- **难度**：高级 · **类型**：开放设计
- **考察点**：演进分阶段与安全边界。
- **参考答案要点**：
  1. 四阶段：关键词路由 → LLM 路由（选工作流）→ 计划生成（从已注册能力里选步骤）→ 动态工具编排。
  2. 每个阶段都保留同一套护栏：工具白名单、风险分级、token 预算、审批门、事件审计。
  3. 风险：成本不可预测、副作用不可控、评测困难、失败模式复杂。
  4. 控制：计划先审后执行（plan approval）、最大步数与预算硬上限、每步可回滚、危险工具强制人审。
  5. 业务分层：低风险高频场景先放开，涉及资金/库存的保持预定义。
- **追问**：自主规划的效果怎么评测？——固定任务集 + 计划正确率 + 执行成功率 + 成本/时延，与人审通过率对照。

### Q12.4 成本、质量、延迟三角，给定预算砍半你会怎么调？

- **难度**：高级 · **类型**：场景权衡
- **考察点**：能否给出有优先级的取舍方案，而不是罗列手段。
- **参考答案要点**：
  1. 先保底线：人审门、权限、审计不能省；质量底线由"最终通过率"定义。
  2. 分层降本：非核心步骤降模型档位（摘要、改写用小模型），核心创意保留强模型。
  3. 提升复用：上下文与结果缓存、相同商品复用诊断结论、减少候选数量而不是降低单条质量。
  4. 异步化保延迟：交互层 5 秒内给"已受理 + 进度"，最终结果后台完成。
  5. 度量：单位任务成本、P95 延迟、采纳率三条曲线，做帕累托判断，而不是只看成本下降。
- **追问**：预算再砍一半呢？——转为"规则 + 小模型出草稿 + 人审精修"的模式，明确告知能力降级，而不是悄悄降低输出质量。

# 附录 D：常见失分点

1. **把多 Agent 说成"Agent 互相商量"**：本项目是工作流编排，顺序由注册表决定，不是自主对话。
2. **把中断说成抛异常/任务失败**：`interrupt` 是正常暂停并持久化，恢复后不重跑已完成节点。
3. **把审批当成永久授权**：审批的是特定 Run 的特定动作，执行前仍要重新校验角色与状态。
4. **把 Outbox 说成"重试机制"**：它解决的是"业务写入与消息投递的原子性"，重试只是实现手段。
5. **混淆 Checkpoint 与 Run 表**：一个管图内部状态，一个管业务事实，不能互相替代。
6. **把质检说成生成之后**：规则质检在调用生成模型之前，作用对象是文本草稿。
7. **夸大能力**：界面没有对话式交互、没有短期记忆、没有视觉质检、没有工具熔断限流，这些要如实承认并给出改进方向。
8. **只讲优点不讲代价**：每个设计都要能说出对应成本（复杂度、延迟、维护量），否则会被追问击穿。
