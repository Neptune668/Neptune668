# 《电商运营助手》项目面试串讲

> 前两部分讲清项目是什么、强在哪里，第三部分串起核心业务流程，第四部分按高频与实战两档整理可直接口述的问答。文中数量、模型名、配置键均与工程实现一致。

## 一、项目介绍

电商运营助手是一个受控的多 Agent 电商运营平台，把店铺、商品、库存、竞品、投放这些业务，和 AI 诊断、创意生成、图片视频素材整合到一套系统里，帮助运营人员用一句话完成从商品诊断、创意方案到素材生成、投放实验、经营复盘的整套运营动作。它解决的是面向电商运营场景过去运营数据散落在各个接口、要手工串联，以及直接用大模型生成内容质量参差、过程不可控的问题，把点状能力变成可管控、可复用的平台。

这套系统我采用前后端分离的架构(，独立开发完成)。`后端`用 Python FastAPI 搭建 RESTful 接口，SQLAlchemy ORM 管理 MySQL 业务库，Alembic完成数据库版本迁移，基于 Pydantic-Settings 实现集中式环境配置；认证上自研 Bearer-Token 体系，实现多角色权限控制。`异步部分`用 Redis 加 Celery 构建任务队列，处理媒体素材生成和 Agent 后台执行。业务上覆盖店铺商品、SKU 库存、竞品监控、经营绩效统计和 CSV 批量导入；整套服务通过 Docker Compose 容器化编排交付。

在这个底座之上，我基于 LangGraph 设计了受控多 Agent 平台，把已有服务编排成受控工作流，检查点持久化到 PostgreSQL。我定义了 9 个角色、16 项工具、7 条工作流，每个角色配独立提示词和工具白名单，工具按 R0 到 R3 分级，高危动作强制人审，配合租约和检查点做中断恢复；Agent 复用底层 service，不重写业务。

支撑这套结构的是我理解的 Harness 工程——不是框架也不是库，而是围绕 Agent 运行的一整套约束：谁能调什么工具、一次运行消耗多少 token、留下什么痕迹、失败能否恢复。它把不可控的生成拆成可检查、可暂停、可回放的受控步骤。

> 解决的痛点，
>
> `架构`:后端，异步，业务；（背）alembic数据库版本迁移
>
> `亮点`：多agent,`haness工程`（亮点是重点，背）

## 二、项目亮点分析

### 2.1 业务亮点

**目标级入口，把多步操作收敛成一句话。** 使用者表达的是"分析这款坚果的定位，给出主图方向，先让我审核"这样的目标，系统自动路由到对应工作流，不必自己排列接口调用顺序。

**产出是草稿，不是终稿。** 诊断、创意、素材默认进待审核状态，人工可编辑、驳回或采用，适配真实运营的审核流程；越权调用与数据破坏被挡在执行之前。

**优秀员工的能力可复用。** 诊断思路固化进提示词和节点约束，新手产出对齐老手水位；每次运行记录版本、上下文和结果，出现爆款能回查提示词与创意角度，沉淀成模板。

**批量并发与失败兜底。** 素材生成从串行手工变成批量并发，失败自动重试、任务不丢，直接支撑大批量上新场景。

### 2.2 技术亮点

**自研鉴权，后端强校验。** hmac-sha256 签名 Token，密码哈希存储，payload 只放用户 id、角色和过期时间；每次请求解析后回查数据库用户状态，避免账号禁用后旧 Token 仍可用；OWNER / OPERATOR / VIEWER 三级角色，权限全部在后端依赖注入处校验，不依赖前端。

**受控多 Agent，拒绝无约束自主调用。** 角色、工具、工作流三张注册表分离声明与实现；工具白名单约束到角色级，风险分级 R0 到 R3，R3 仅 Owner 可用；所有调用经 ToolGateway 统一校验身份、工作区、角色权限；高风险动作中断工作流写入审批记录，审计通过后才落正式业务表。

**可靠的后台任务系统。** Task、Run、Outbox 三表同事务提交，解决"数据库写入成功但消息投递失败导致任务丢失"；Worker 认领任务写租约、后台心跳续租，崩溃后租约到期自动回收重入队；幂等设计防止重复消费产生脏数据；拆分成 generation、agent、agent.workflow、maintenance 四队列隔离。

**成本与可观测。** 全局 token 预算 12000，累计耗尽直接终止；返修上限 1 次防止循环；非推理环节走规则不走模型；每一步写入结构化事件，可回放、可定位。

> 试简述，生成任务是独立worker进程中异步执行的，熊：如何整合到langgraph工作流中观测进度可配置：提示词,重试次数？

技术亮点：

1. 自研鉴权，后端强校验(用用户数据前做校验)
2. 受控多Agent，拒绝无约束自主调用（业务agent）
3. 可靠的后台任务系统（不存在任务创建成功没有投递出去，幂等(工具调用不再次调用，拿结果)）
4. 成本可观测（成本可控）

## 三、核心业务流程总结

### 3.1 运营业务主流程（能讲）

1. 商品建档：创建店铺、添加商品、添加SKU
2. 竞品录入与监控
3. 商品诊断
4. 创意方案：默认生成四个主图方案和三个视频脚本，默认为draft状态
5. 主图/视频素材生成：调用即梦模型
6. 推广链接与投放实验
7. 经营数据复盘
8. 库存建议

每一步都落结构化业务表，前一步的产出是下一步的输入，全链路可回溯。

### 3.2 Agent 受控执行流程（重点）必问

1. 使用者提交目标
2. 关键词规则匹配到已注册工作流
3. 同一事务创建 AgentTask、AgentRun、OutboxEvent，同时生成AgentRunEvent事件记录
4. maintenance Worker 扫描 Outbox，投递到 agent.workflow 队列
5. 业务 Worker 凭租约认领 Run
6. 加载上下文：商品、店铺、成员角色、长期记忆上下文
7. 按工作流定义依次执行诊断、创意、质检节点
8. 质检不通过且未超返修上限则带问题反馈重跑，超限转人工
9. 命中高风险工具时写入审批记录，工作流中断
10. 人工批准或编辑草稿后从 Checkpoint 恢复，继续收尾落库

### 3.3 素材生成流程（AI模型能力）

1. 创意方案确定后创建 GenerationJob
2. Outbox 投递到 generation 队列
3. Worker 调用即梦文生图（jimeng_t2i_v30）或文生视频（jimeng_t2v_v30），异步提交后轮询取回 URL
4. 下载到本地、写入素材库，状态默认"待评估"
5. 运营人工改为通过、弃用或复测

机器质检发生在调用即梦之前的文本草稿上，即梦产物本身只做人工审核；失败任务按退避重试，最多三次。

>
> 试简述，R2人工审批如何实现的，审批后工具就能执行吗？
>

### 3.4 可靠投递与恢复

Outbox 保证消息可靠性投递，Checkpoint 保存多 Agent 图内部节点状态，租约负责 Worker 宕机识别与任务回收，三者各司其职：消息不丢、中断能续、宕机可回收。基础图把单条业务线讲透，平台图由注册表驱动、用一套编排代码装配全部工作流；命中商品诊断优化时平台图转调基础图，两条链路共享同一套可靠性骨架。

## 四、常见面试题

### 4.1 高频面试题

#### Q1：介绍这个电商运营 AI 助手的整体架构

按四层答，别散着说。后端 FastAPI 出 REST 接口，SQLAlchemy 操作 MySQL 存业务数据，PostgreSQL 专存 LangGraph 的 Checkpoint，Redis 作 Celery 消息队列。异步层是 Celery Worker 消费任务，处理图片视频生成和 Agent 工作流，用 Outbox 事务消息加租约心跳保证任务不丢、不卡死。Agent 层是基于 LangGraph 的受控多 Agent 平台，有角色注册表、工具网关、风险控制、人工审批和记忆模块，底层调用已有业务 service。基础设施是 Docker Compose 编排、Alembic 迁移、Pydantic-Settings 统一配置、Pytest 测试。四层讲完，整体把握就清楚了。

#### Q2：为什么不用现成 JWT 库，自己实现 Token 鉴权

课程项目为了理解底层原理，做了基于 hmac-sha256 的签名 Token。要点有两个：

payload 只放用户 id、角色、过期时间，敏感信息不进 Token；每次请求解析后必须回查数据库确认用户状态，防止账号禁用后旧 Token 还能用。踩过的坑正是最初只验签名、没查用户状态，禁用账号的旧 Token 依旧有效，后来加了数据库校验。

生产环境会优先用成熟 JWT 库，不重复造轮子。

#### Q3：为什么要做受控 Agent，不让大模型自由调用工具

自由调用意味着可能随意改库存、删数据。

项目做了多层限制：

- 工具白名单，每个角色只能调分配给自己的工具；
- 风险分级 R0 到 R3，读数据 R0、草稿 R1、改业务数据 R2/R3，R3 仅限 Owner；
- 审批网关，高风险动作暂停等人审核；
- 所有调用经 ToolGateway 统一校验身份、工作区、角色；
- Agent 输出是草稿，审批通过才写正式表。

#### Q4：Outbox 事务消息解决什么问题，原理是什么🛫

发件箱机制是为了保证提交成功的任务一定能够投递。

创建 Agent 任务要写 Task 记录，同时发消息给 Celery；如果库写成功、发消息时网络异常，就会出现有记录但任务永不执行的丢失。

做法是同一事务里写业务记录加 Outbox 事件，成功一起落库、失败一起回滚；再由独立定时任务扫 Outbox 的 pending 事件投递到队列，失败就重试，保证最终一致性。

#### Q5：LangGraph Checkpoint 的作用，项目怎么用🛫

Checkpoint 是 LangGraph 的状态持久化机制，保存工作流每一步的状态。项目用 PostgreSQL 做持久化：执行到人工审批时保存全部上下文、暂停工作流；用户审批后从 Checkpoint 读回状态继续跑，不必从头重来；Worker 崩溃也能恢复，不丢中间计算上下文。它和业务 Run 表是分开的，一个管图内部节点状态，一个管业务运行状态。

#### Q6：Celery Worker 任务卡死怎么处理

用租约心跳机制。Worker 拿到任务时写入 lease_owner 和租约过期时间，正常运行期间持续续租；后台维护任务定期扫描 RUNNING 状态的 Run，租约超时说明 Worker 已宕机，就把状态重置为 QUEUED 重新入队；同时搭配 Outbox 事件重试和幂等设计，避免重复执行产生脏数据。

#### Q7：AgentTask、AgentRun、OutboxEvent、Checkpoint 四者区别

Task 是用户提交的高层目标，代表一次完整业务请求；Run 是 Task 的一次执行实例，存任务运行过程中的状态、token 用量和错误；Outbox 是可靠消息表，保证业务记录和投递消息原子；Checkpoint 是 LangGraph 层保存图内部节点状态的，用于中断和审批后恢复。一句话总结：Task 管目标、Run 管执行、Outbox 管投递、Checkpoint 管恢复。

### 4.2 实战面试题

> 这一档聚焦多 Agent 架构的选型、边界、故障与生产落地，附带连环追问。

#### Q1：为什么拆成多个专用 Agent，而不是一个大 Agent 加一堆工具

单 Agent 加工具实现简单，但工具一多系统提示词就膨胀，模型容易混淆职责、乱调无关工具。

项目拆成窄职责的专用 Agent，每个有独立提示词和工具白名单：

- 职责收敛，降低幻觉和误调用；
- 权限粒度更细，比如库存 Agent 能看到库存调整工具，创意 Agent 完全看不到；
- 可观测性更强，日志能定位到具体角色；
- 编排更灵活，工作流定义角色顺序，增删角色不用改大提示词。

代价是复杂度上升，要维护注册表和多套提示词。

（注意：不是让多个 Agent 互相聊天，而是由上层工作流驱动顺序执行）

追问 token 开销怎么控？——设全局预算上限 12000，耗尽直接终止；非推理环节走规则不走模型；记忆只加载有效记录、上下文做裁剪；返修上限 1 次，防止无限循环调用。

#### Q2：Agent、工具、工作流三张注册表的边界，会不会注册了却不能执行

> registry.py

Agent 注册表定义角色：版本、描述、允许的工具白名单，说明"这个角色能干什么"。工具注册表定义工具元信息：key、风险等级、是否仅 Owner、幂等标记，只做声明，不等于有执行代码。工作流注册表定义一条完整流程：需要哪些角色、什么上下文、默认风险等级，决定执行顺序。

注册不等于可执行——工具注册表只是元数据，真正逻辑在 ToolGateway 的 handler 里；存在注册了但没实现 handler 的情况，网关会直接拒绝。好处是元数据和实现解耦，可以先搭框架再逐步补实现，还能对外提供能力目录。

#### Q3：R0 到 R3 风险分级，完整授权链路是什么

> tool_gateway.py

每层独立校验、层层防御。

- 先看当前工作区是否启用该工作流；
- 再校验 Agent 白名单是否包含这个工具，注册了但不在白名单照样拒绝；
- ToolGateway 读取工具风险等级；校验登录用户在 workspace 内的角色，Viewer 只能调 R0 只读；R2/R3 标记需人工审批，R3 仅限 Owner；
- 全部通过才进 handler 执行；需要审批的，中断 LangGraph、写入 AgentApproval 记录，进人工网关。

#### Q4：人工审批怎么实现，审批后怎么恢复多 Agent 工作流

我们使用LangGraph构建工作流的执行流程，靠 Checkpoint 持久化整张图的状态。

【中断】：触发审批节点时不销毁状态，把完整 State 写入 PostgreSQL Checkpoint；工作流中断，对外返回 AWAITING_REVIEW，同时写独立的 AgentApproval 记录，Worker 释放租约退出；

【回复】：用户在前端批准、驳回或编辑草稿，API 存决策并创建 Outbox 事件；Worker 消费事件重新认领 Run，从 Checkpoint 恢复上下文，从中断节点往后执行，前面已跑完的 Agent 不重跑。

#### Q5：多 Agent 工作流耗时长，Worker 中途崩溃怎么保证不丢、可恢复

Checkpoint 、AgentRun、OutboxEvent三层各管一段。

Checkpoint 在图层保存每步节点状态和各 Agent 输出草稿，崩溃后恢复图内部状态，已完成的 Agent 不用重跑；

租约在业务层，Worker 认领写 lease_owner 和过期时间、持续续约，崩溃后租约超时，维护任务重置状态并重新生成 Outbox 事件；

OutboxEvent 在事务层，Task、Run、事件同事务提交，保证不会出现"任务存在但没消息触发"。

三者缺一不可：Outbox 保证消息可靠投递，租约解决宕机识别与回收，Checkpoint 解决恢复不重跑。

#### Q6：同一个商品并发发起多个 Agent 任务，怎么做并发保护

总体原则是加锁范围越小越精准越好。CeleryWorker在认领Agent时，查询时用 with_for_update 加行锁，避免多个 Worker 同时认领同一行；同时在 Workspace 维度设全局并发上限，单个工作区最多 10 个活跃 AgentRun，超出直接拒绝，防止一个租户占满资源。

#### Q7：多 Agent 系统有哪些典型故障，怎么处理

`LLM 调用超时`：靠 Checkpoint 只重试失败的当前节点，已跑完的不重复执行，并设最大重试次数。

`输出格式错误、Pydantic 解析失败`：捕获异常计入事件日志，到修订上限就转人工审批，把原始输出交给人，而不是直接判失败。

`多 Agent 输出互相矛盾`：质量合规 Agent 作为最后一环做规则校验，标记问题进修订或人审。

`Token 超限`：全局预算管控，累计超限直接终止并记录事件，防止持续调用产生高额账单。

#### Q8：这套多 Agent 平台有什么局限，上生产会怎么改进？

局限三条：

- 工作流是预定义编排，意图路由只用关键词规则，复杂自然语言意图识别弱；
- Agent 之间靠全局 State 交换数据，State 会随业务膨胀，没有做消息隔离；
- 记忆只按 scope 过滤，缺摘要压缩，量大仍有上下文风险。另外工具的限流、熔断还没完整实现，下游抖动可能连锁影响任务。

改进对应着做：意图路由换成轻量 LLM 分类；给 State 设大小上限、大上下文自动摘要压缩；ToolGateway 加限流熔断，LLM 调用加超时和退避重试；补每个 Agent 的调用次数、token、失败率指标并接入链路追踪；加工具调用审计日志，完整记录入参出参。

#### Q9：Agent 是怎么测评的，关注哪些指标🛫真题

测评分两层。

- 研发阶段是离线评测：有固定评测用例集，用假模型档位隔离大模型随机性，结果可重复；平台评测是 7 条工作流乘以路由、上下文、策略、质检、恢复、审批六类边界，每条对结构化字段断言。
- 运行阶段看三层指标：任务层看任务完成率，质量层看质检通过率和返修率，首轮与最终通过率分开算，业务层看人审通过率和采纳率，编辑后通过占比最能反映质量。广告实验有点击率、转化率、ROI 的 AB 对比，写死成功标准：连续两天 ROI 大于等于 2.5、点击率大于等于 4%、跑满一千次曝光。客户满意度没有埋点，如实说明，最接近的信号是人审反馈。

#### Q10：规则质检误杀太多怎么处理

（先辨析，别急着改规则）

质检规则：每条质检问题带严重度和结构化编码，警告级不拦截、只提示，真正拦截的是错误级；

先分析：先按编码统计命中量，定位误杀最多的那条，把感觉变成数据。

再治理：规则层把阈值做成可配置，误杀多的错误级降为警告级；粒度层把过粗的规则拆细，比如角度重复从字符串全等升级成语义去重；场景层按品类承载不同规则集，策略本身版本化，可按品类选档。

最后兜底：规则是辅助不是终审，有最多一次返修加人工审核门，误杀最坏只是多一次返修和一次人审，不会硬否决业务。

#### Q11：相比员工自己用 AI，这套系统的业务价值在哪

缩短提示词时间只是入口价值，真正的差别是把 AI 从个人手工工具变成组织级生产系统。

效率上一键出结构化结果；规模上从串行手工变批量并发，失败重试、任务不丢；能力复用上把优秀员工思路固化成提示词和节点约束，新手产出对齐老手；质量上每次都过同一条质检线和人审门；溯源上每次运行可追到 Agent 版本、上下文和产出，爆款能反查提示词沉淀模板；成本与风险上，越权和密钥泄露被确定性策略挡住。个人用 AI 提升单点效率，这套系统提升团队的能力水位和确定性。

#### Q12：生成主图方案能指定方向吗，有没有对话框和长短期记忆

方向不能事前指定。生成接口入参只有商品和诊断结果，提示词要求四个角度明显不同，方向是模型自选；唯一的人工干预是生成后编辑"测试角度"。系统没有对话式交互：前端是按钮和表单驱动的"点击即委托"，后端虽有会话表但缺消息读取、助手回复和多轮循环，前端未使用；用户目标走的是关键词路由。上下文只有技术性的 thread_id 加检查点，用于审批中断后恢复，图状态里没有消息列表。

记忆只有长期记忆、没有短期记忆：由用户在 Agent 中心手动保存一个结构化值，附带作用域、key、来源和生效时间；任务启动会加载进上下文，会在完成商品和店铺上下文加载之后，加载记忆上下文注入提示词。冲突也没有仲裁：memory_key 非唯一索引，多条同键记录并存。

#### Q13：即梦生成图片或视频后怎么质检，能返修吗

这里的次序要说对：

- 质检（主图方案和视频脚本的质检）在调用即梦之前，不在之后。
- 质量评审是纯规则，查诊断建议数量、创意角度重复、标题副标题和视觉重点里的绝对化违禁词、证明点缺失，对象是结构化的文本草稿，不是从图上识别的文字；
- 项目里没有 OCR 和视觉模型。即梦产物本身不做机器质检，返回 URL 后下载写素材库、状态默认待评估，靠运营人工改成通过、弃用或复测。
- 返修要分清两层：文本草稿的返修是把质检问题转成反馈注入提示词重跑，最多一次；生成任务失败或超时是技术重试，最多三次；
- 成品图不能基于质检结果自动返修。即梦用的是纯文生图和文生视频模型，请求参数里不带原始商品图，视频侧还显式拒绝参考图，所以"有没有改动原图"在这条链上不成立。真要做保真校验，思路是换成图生图接口传入原图，再加视觉模型做特征向量或感知哈希比对——这是改进方向，项目现状没有。
