## 0. 先看三种时长怎么讲

| 时长 | 讲什么 | 目标 |
| :-- | :-- | :-- |
| 1 分钟 | Situation + Task 各 2 句 + Result 1 句，Action 只报 3 个关键词：受控多 Agent、可靠任务、质量与成本 | 让面试官知道项目边界和技术含量，主动追问 |

## 1. Situation（背景与痛点，2–3 句）

电商运营每天的活儿是散的：商品信息在后台、库存和竞品在表格里、诊断靠经验、主图和视频外包，投放和复盘又是另一套数据，运营要手工把七八个环节串起来，一个新品上新就要耗掉大半天。

同时，直接让大模型干这些活又不可控——它可能改错库存、生成违禁词、过程无法追溯，出了问题没人能说明白是哪一步、用的哪个版本。

所以我做了一个面向中小电商运营团队的单品运营平台：把店铺商品、SKU 库存、竞品监控、创意素材、投放实验和经营复盘收进一套系统，再在业务底座上叠一层受控的多 Agent 能力，让运营用一句目标就能驱动整条链路，同时保证每一步可审核、可回放、可兜底。

---

## 2. Task（架构、流程与我的职责，4–5 句）

整体是前后端分离：后端用 FastAPI 出 REST 接口，SQLAlchemy 管 MySQL 业务库，Redis + Celery 做异步队列，LangGraph 负责多 Agent 编排，检查点单独放 PostgreSQL，前端是 Next.js 的服务端渲染工作台。

Agent 侧我按"注册表驱动"来设计：9 个角色、16 项工具、7 条工作流，角色定义工具白名单，工具定义 R0–R3 风险等级，工作流定义角色顺序和必需上下文，三者分离声明与实现。

执行链路是三段式：创建阶段在同一事务里写任务、运行实例和 Outbox 事件；投递阶段由维护任务扫 Outbox 投到 `agent.workflow` 队列；执行阶段 Worker 凭租约认领，加载商品、店铺、成员和长期记忆上下文，按工作流依次跑专家节点和质量门，命中高风险动作就中断等人审，审批后从检查点恢复收尾落库。

我负责的是从业务服务、异步任务到 Agent 平台这一整条后端链路：数据模型与迁移、权限与工作区隔离、四类队列的拆分、可靠性机制（Outbox、租约、幂等）、LangGraph 编排与人审中断、质量门与评测口径，前端只做配合联调。

如果只用一句话概括我的角色：不是"调大模型接口"，而是把不确定的生成能力工程化成一个可交付、可运维的系统。

## 3. Action（10 个细节，每个都是一个高频面试题）

### A1｜从"一个大 Agent"改成"多角色 + 注册表"（对应题库 Q2.1 / Q2.2 / Q2.3）

**出问题**：最初的想法很自然——一个 Agent，挂上所有工具，让它自己决定调哪个。真跑起来问题立刻出现：提示词越来越长，模型开始张冠李戴，明明该查库存却去生成主图；更麻烦的是，一旦给了它库存调整工具，它就有机会在没人注意的时候改数据。

**第一次尝试**：我把工具说明写得更细，希望在提示词里"讲清楚"。结果是提示词越长，模型越容易忽略其中某几条，维护成本也在涨——每加一个工具，所有角色的行为都可能被影响。

**碰壁**：我意识到这不是提示词问题，是边界问题。单 Agent 的本质是"用自然语言描述权限"，而自然语言约束不住权限。

**定位**：真正需要的是三件事分开——角色能干什么（白名单）、工具危不危险（风险等级）、流程按什么顺序走（工作流）。这三件事混在一个提示词里，就一定会互相污染。

**最终做法**：拆成 9 个窄职责角色，每个角色独立提示词、独立工具白名单；再把声明抽成三张注册表：Agent 注册表定义角色与白名单，工具注册表只定义元信息（key、风险、是否仅 Owner、是否幂等），工作流注册表定义角色顺序和必需上下文。执行逻辑仍然在工具网关的 handler 里，注册不等于可执行，找不到 handler 直接拒绝。每次运行把版本清单写进 Run，事后能查到当时用的是哪套角色和工作流版本。

**一句话结果**：职责收敛之后，误调用肉眼可见地少了，权限粒度能做到"库存 Agent 看得见库存调整、创意 Agent 完全看不见"，日志也能直接定位到是哪个角色出的问题。

---

### A2｜把"权限校验"从接口层挪到执行层（对应题库 Q3.2 / Q3.3 / Q3.4）

**出问题**：一开始我觉得权限在 API 层做就够了——用户点按钮时校验一次，没问题就放行。但 Agent 是异步执行的：接口早就返回 202 了，真正调工具是在几分钟后的 Worker 里，这中间用户的角色可能被降级，账号可能被禁用。

**第一次尝试**：只在 API 入口校验 token 和工作区，工具执行时直接信任上下文里的 `workspace_id` 和 `product_id`。

**碰壁**：这等于把"提交时的授权"当成了"执行时的授权"，而且上下文里的 id 是模型可影响的输入，拿它当权限凭据就是越权入口。

**定位**：权限必须在"真正产生副作用的那一刻"成立，并且每次都要重新成立，不能继承。

**最终做法**：做成一条完整链路——认证用户 → 校验工作区成员关系 → 校验该工作区是否启用这条工作流 → 校验 Agent 白名单是否包含该工具 → 按工具风险等级对比当前角色（Viewer 只能 R0，R3 仅 Owner）→ 需要审批的先中断 → 最后才进 handler。每一层独立成立，不因为上层通过就跳过。另外资源级也校验：商品、店铺必须属于当前工作区，上下文快照里的 id 一律当"待校验输入"。

**一句话结果**：越权请求被挡在产生副作用之前，而且不是靠前端按钮隐藏，是后端在异步执行时兜住的。

### A3｜任务创建成功却永远不执行：用 Outbox 补上双写漏洞（对应题库 Q6.2）

**出问题**：压测时发现一种很难查的"幽灵任务"：数据库里有 `queued` 的 Run，但队列里没有对应消息，任务就永远躺在那儿。

**第一次尝试**：在创建逻辑里"先写库、再发消息"，发送失败就重试几次。

**碰壁**：重试解决不了根本问题。如果进程在"写完库、还没发消息"的瞬间挂掉，重试代码根本没机会执行；如果消息发了但事务回滚，又会出现"队列里有、库里没有"的反向不一致。两个系统没法用一次提交保证。

**定位**：这是典型的双写问题，靠"更努力地重试"永远补不上，必须把"要不要发"这个事实和业务数据写进同一个事务。

**最终做法**：同一事务里写业务记录加一条 Outbox 事件（pending），提交成功两者都在，回滚两者都没有。再由独立的投递器扫描 pending 事件投递到队列：成功置 published，失败按指数退避重试，超过 10 次置 failed 并保留错误。投递器既由 Celery Beat 每 5 秒兜底轮询，也在创建成功后立即触发一次，兼顾可靠性和平均延迟。

**一句话结果**：从"任务创建成功可能丢"变成"创建成功就一定会有一次投递"，代价是接受"至少一次"语义，重复问题交给下一层的幂等解决。

---

### A4｜消息会重复、Worker 会假死：租约 + 幂等 + fencing（对应题库 Q6.3 / Q6.4）

**出问题**：上了 Outbox 之后，重复消费开始出现；更麻烦的是有时候 Worker 进程没死，但卡在一个外部调用上，Celery 的 ack 机制感知不到，任务就一直占着 running 状态。

**第一次尝试**：开 `acks_late`，让任务执行完再确认，靠队列重投解决崩溃。

**碰壁**：ack 只能回答"消息有没有被消费"，回答不了"这个执行者是不是还活着、还该不该由它写结果"。进程假死、网络分区、长任务卡住，这三种情况 ack 都覆盖不到。

**定位**：消息可靠性和执行所有权是两件事，得各用一套机制：消息层用 ack 防丢，业务层用租约防占死。

**最终做法**：认领任务时用行锁加 `SKIP LOCKED`，同时写 `lease_owner` 和 5 分钟过期时间；执行期间起一个心跳协程持续续租；维护任务每 30 秒扫一次超时的 running，把状态重置为 queued 并重新投递。写库前校验 `lease_owner` 还是自己，防止旧 Worker 复活后覆盖新执行者的结果。消费端再叠三层幂等：状态机 CAS（条件更新影响行数为 0 就直接退出）、唯一键（thread_id、Run 级审批、工具操作键）、finalize 前先查产出或做 upsert。

**一句话结果**：重复消息被吸收，Worker 宕机后任务能在租约到期后自动回收，迟到写入也覆盖不了新结果。

### A5｜审批要等半小时，不能让 Worker 干等：中断 + 检查点恢复（对应题库 Q5.1 / Q5.5）

**出问题**：高风险动作要人工审批，但运营不可能秒回。最初的做法是在节点里同步等待，结果 Worker 被长期占用，任务超时，审批回来的时候上下文已经没了。

**第一次尝试**：把等待改成轮询数据库，节点里 sleep 一段时间查一次审批状态。

**碰壁**：这本质上还是"占着线程等人"，并发一上来 Worker 就被审批任务占满，而且进程重启后等待中的状态全丢。

**定位**：审批不是"执行中的等待"，而是"执行的一次暂停"。暂停必须能把状态存下来、把资源释放掉，之后从原地继续。

**最终做法**：用 LangGraph 的 `interrupt()` 在审批节点主动暂停，把完整 State 和待恢复点写进 PostgreSQL 的 checkpoint；业务侧把 Run 置为 `awaiting_review`、写一条独立的审批记录、释放租约退出。用户批完，接口只落决策加写 Outbox，Worker 重新认领后用 `Command(resume=...)` 从同一个 `thread_id` 恢复，前面已经跑完的专家节点不重跑。

**一句话结果**：审批期间不占 Worker，恢复后不重跑已完成节点；这里有个必须讲清的前提——图必须配好 checkpointer，调用必须传同一个 thread_id，否则中断就恢复不了。

### A6｜"审批通过"不等于"永久放行"（对应题库 Q5.2 / Q5.3 / Q5.4）

**出问题**：我一开始把审批理解成"用户点了同意，后面就照着执行"。后来意识到，审批和恢复之间可能隔了几个小时，这期间角色可能被改、账号可能被禁用、工作流可能被关掉。

**第一次尝试**：恢复时直接读审批记录里的 decision，通过就继续跑。

**碰壁**：这相当于用"历史时刻的授权"去执行"当前时刻的动作"，而且审批记录如果不做唯一约束，还可能被重复提交、重复恢复。

**定位**：审批的对象是"这次 Run 在特定上下文下的某个动作或草稿"，是一次性授权，不是对工具的永久授权。

**最终做法**：恢复时重新走一遍校验——租约、Run 状态、当前工作区角色、工具白名单、风险等级，一个都不能省；审批记录做成 Run 级唯一，只有 `awaiting_review` 状态允许决策，重复提交返回幂等结果，并发提交靠唯一键让先到者生效，审批本身设过期时间由定时任务清理。对"编辑后通过"再补一条：编辑内容必须重新过质量门，不通过就进 `quality_failed`，不能因为人改过就直接落库。

**一句话结果**：审批是"放行一次动作"，不是"解锁一个工具"，重放和越权都被堵住了。

### A7｜规则质检误杀太多：把"感觉"变成"数据"再治理（对应题库 Q7.1 / Q7.2 / Q7.6）

**出问题**：质量门最初把所有问题都当拦截项，结果运营反馈"明明没问题也被打回"，返修次数飙升，反而拖慢了产出。

**第一次尝试**：想着"规则不够准就多加规则"，于是不断往质检里堆判定条件。

**碰壁**：规则越多，误杀越多，而且每条规则为什么命中、命中了多少，完全说不清——治理变成了拍脑袋。

**定位**：质检的问题不是规则数量，而是"没有分级、没有度量、没有兜底"。要先能统计，才能谈优化。

**最终做法**：第一，把问题分成 error 和 warning 两级，只有 error 拦截，warning 只提示；第二，每条问题带结构化编码，按编码统计命中量，让"误杀最多的是哪条"变成数据；第三，把过粗的规则拆细，比如角度重复从字符串全等升级成语义去重；第四，规则按品类配置、策略版本化，可以按品类选档；第五，兜底保留返修上限加人审门，最坏结果只是多一次返修，不会硬否决业务。

**一句话结果**：误杀从"运营抱怨"变成可度量的指标，规则调整有了依据，而且不再出现"一条规则卡死整条业务线"。

### A8｜模型调用不能无底洞：预算、返修上限和循环护栏（对应题库 Q8.1 / Q4.4）

**出问题**：早期只限制了"最多返修几次"，没限制 token。结果一次超长上下文就把预算吃光，而且质量门和返修之间理论上可以来回跳，存在死循环风险。

**第一次尝试**：加 `max_revisions = 1`，以为够了。

**碰壁**：次数限制只约束"轮数"，不约束"每轮多贵"。一次调用带上全部上下文和很长输出，照样能把成本打穿；另外框架层的 `recursion_limit` 没设，编排写错就可能无限跳。

**定位**：成本要三层同时管——单次调用、单次运行、循环结构。

**最终做法**：给每次运行设 12000 token 全局预算，每次调用前按"已用 + 预估"判断余额，超限直接终止并写明确事件，不静默截断；单步再设 `max_tokens`，防止一次吃光；返修用 `revision_count` 加 `max_revisions` 控制，超限转人工而不是判失败；图配置 `recursion_limit` 兜底；能走规则的环节（上下文加载、权限、质量门、库存计算）一律不走模型。

**一句话结果**：单次任务成本有上界，失败原因可解释，返修不会变成无限循环。

### A9｜模型输出不能直接进业务：结构化合同加规则兜底（对应题库 Q1.2 / Q1.3）

**出问题**：最开始直接把模型返回的文本 `json.loads` 一下就落库，结果线上出现字段缺失、类型不对、多返回字段，任务在落库阶段才崩，前面的调用全白费。

**第一次尝试**：在提示词里反复强调"只返回 JSON、不要多余字段"。

**碰壁**：提示词能降低概率，但不能保证。模型偶尔还是会带解释性文字，或者把数字写成字符串。

**定位**：模型输出是"不可信输入"，必须像对待外部接口一样做契约校验，而且要区分"技术故障"和"内容故障"——前者可重试，后者重试收益很低。

**最终做法**：请求侧要求 JSON 对象，响应侧用严格 Pydantic 模型校验（禁止额外字段、约束长度和数量）；失败分类处理：网络或超时走重试，解析或校验失败则记录结构化事件，先尝试有限次修复（把校验错误回灌提示词），还不行就降级到规则生成兜底草稿。所有产出都标 `source=llm|rules` 和 provenance，让降级可见、可统计。

**一句话结果**：模型故障时任务仍能产出可用草稿，而且降级率是可监控的，不会被"看起来正常"掩盖。

### A10｜生成链路与评测：质检要前置，效果要能证明（对应题库 Q10.1 / Q10.2 / Q7.3 / Q9.1）

**出问题**：做图片和视频生成时，直觉是"生成完再检查"。但真实链路里，生成一次又慢又贵，而且产物是像素，没有 OCR 和视觉模型根本判不了违禁词。

**第一次尝试**：先调供应商生成，再对结果做规则检查，不合格就重新生成。

**碰壁**：成本翻倍，而且"重新生成"并不能保证下一次更好；更关键的是，我的质量规则本来就是针对结构化的主图方案和视频脚本写的，对像素图完全失效。

**定位**：质检的对象应该是"可解析、可返修、成本低"的文本草稿，而不是昂贵且不可控的成品。

**最终做法**：把链路改成"创意方案确认 → 创建生成任务 → Outbox 投到 generation 队列 → 提交供应商 → 按间隔轮询取回 → 下载落素材库 → 状态默认待评估 → 人工改成通过/弃用/复测"；机器质检放在调用生成模型之前，检查方案数量、角度是否重复、绝对化违禁词、证明点是否缺失；生成失败按退避重试最多三次，超时由扫描任务兜底。评测上，用固定用例集加假模型隔离随机性，覆盖 7 条工作流 × 路由/上下文/策略/质检/恢复/审批 六类边界，每条对结构化字段断言，纳入回归门禁；运行期靠事件表记录每一步的输入输出快照（脱敏）、token 和 trace，出问题能从 run_id 一路追到版本清单和提示词。

**一句话结果**：生成成本花在"值得生成"的草稿上，产物质量交给人审；而"这套系统到底行不行"不再靠感觉，有离线断言和线上指标两条证据链。

## 4. Result（效果与指标，2–3 句）

最终交付的是一套能跑通单品运营闭环的系统：9 个角色、16 项工具、7 条工作流全部由注册表驱动，素材生成与 Agent 执行拆进 4 条独立队列；可靠投递、租约回收、断点恢复三条机制各自闭环，做到任务创建不丢、Worker 宕机可回收、审批中断可续跑且不重跑已完成节点。

质量与成本侧，单次运行 token 预算 12000、返修上限 1 次、单工作区活跃 Run 上限 10，评测覆盖 7 条工作流 × 6 类边界共 42 组结构化断言；线上按任务完成率、首轮/最终质检通过率、返修率、人审采纳率和编辑后通过占比分层观测，投放实验以连续两天 ROI ≥ 2.5、CTR ≥ 4%、曝光 ≥ 1000 作为预注册成功标准。

需要如实说明的是，这个项目没有接入真实商家，所以我没有生产环境的业务增长数据；我能给出的是工程可靠性口径和评测口径，以及一套已经设计好的埋点补齐方案——这部分的诚实比编一个百分比更重要。

## 7. 讲述时的三条禁忌

1. **不要把多 Agent 说成"Agent 互相商量"**：本项目是工作流编排，顺序由注册表决定，说错会显得没做过。
2. **不要把"审批"说成"执行完再确认"**：审批发生在副作用之前，中断点也在之前。
3. **不要只讲亮点不讲代价**：每个设计都准备一句成本（复杂度、延迟、运维量），否则会被追问击穿；承认局限比硬撑更加分。
