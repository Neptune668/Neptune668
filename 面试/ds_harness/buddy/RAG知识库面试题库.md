# 一、项目背景与使用情况（8 题）

### 1.1.1.1 简单介绍这个 RAG 知识库项目

**回答要点（总分总）：**
- **总**：面向企业产品文档的智能知识库系统，核心能力是「文档自动导入 + 智能问答」。
- **分（导入侧）**：PDF/Markdown → 解析成 Markdown → 处理图片表格 → 切片 → 识别商品名 → 生成 BGE-M3 混合向量 → 写入 Milvus。
- **分（查询侧）**：确认商品名 → 并行做向量检索 / HyDE 检索 / MCP 网络搜索 → RRF 融合 → Rerank 精排 → LLM 生成答案。
- **技术栈**：后端 FastAPI + LangGraph；存储 Milvus + MongoDB + MinIO；前端支持文件导入进度 + SSE 流式问答。

💡 记住「总分总」结构。

### 1.1.1.2 项目解决什么问题？整体设计难点是什么？

- **解决**：企业产品资料多、格式复杂、人工查找低效、客服回答不稳定；把非结构化文档变成可检索知识，让回答基于企业自有资料（RAG）。
- **四大难点**：
  1. 复杂 PDF 的解析和图片语义补全
  2. 文档切片粒度控制（切分导致语义缺失）
  3. 多路召回结果融合
  4. LLM 回答准确性控制
- **工程难点**：异步导入、任务进度、流式输出、向量库一致性。

💡 切片用 LangChain 自带的切分器不行，需要自定义；难点核心是「切分导致语义缺失」。

### 1.1.1.3 ⭐ 用户量大概是多少？

- 按**独立 AI 服务**规划，面向电商客服/运营场景。
- **压测估算**：注册用户 20~80 万、日活 2~3 万；AI 客服触达 25%~40%；日咨询 4000~7000 次，每次平均 8 轮。
- **问答调用**：约 3.2 万~5.6 万次/天，集中在 8 小时内，平均 QPS 约 1~2；预留 3~5 倍峰值，按 **5~10 QPS** 准备资源。

💡 流失用户约 6 万（可作为用户留存口径的补充）。

### 1.1.1.4 做完后是否有人用？效果怎么样？

- **有使用**。常见产品操作、参数说明、故障排查类问题能直接从知识库召回并生成答案，减少人工翻文档时间。
- **上线后重点观察**：召回命中率、答案正确率、用户追问率、人工转接率、bad case 数量。
- **持续优化**：通过问题集评测 + bad case 回流，优化切片、召回、重排、提示词。

💡 补充：筛选无用反馈、从日志排查问题。

### 1.1.1.5 ⭐ 知识库更新频率多高？

1. 产品手册一般不是高频更新。
2. 未来会做完善的后台管理页面 + 版本管理。

### 1.1.1.6 ⭐ 文档规模多大？是否全是 PDF？

1. 文档数量 **3000~6000 份**。
2. 格式：PDF、Word、Markdown 都有。
3. 每份从几页到上百页的手册都有。

### 1.1.1.7 是否参与技术选型？选型依据？

- **Milvus**：看重**存算分离**，MinIO 既存向量数据，又存图片和原始文件。
- **问数项目用 Qdrant + ES**：主要基于京东 DataAgent 项目的改造。
- **复盘**：再次选型可以统一，企业级用 Milvus 更稳。

💡 补充模型选型：BGE 两种检索、rerank v2 向量级别要够；LLM 用 Qwen3.5-35B-A3B-GPTQ-Int4，`max_model_len=16384`。

### 1.1.1.8 ⭐ 并发/体量/宕机应对？日千万级访问设计方案？

**高并发高访问：**
- 多级缓存，减少访问 LLM；
- 引导用户命中 FAQ；
- Nginx 多副本负载均衡；
- MQ 排队机制，削峰填谷。

**文档体量**：一般不成瓶颈，Milvus 存算分离、MinIO 可弹性扩容。

**大模型宕机**：降级策略——切换备用小模型、返回预设兜底话术。

💡 并发按「10 次/秒」口径；核心手段是「削峰填谷」。

# 二、数据来源与知识整理（5 题）

### 1.1.2.1 ⭐ QA 里的问题和答案由谁提供？

本项目是**文档型知识库**，不是以 Q&A 方式存储，而是把手册文档以**切片**形式存进知识库。

### 1.1.2.2 文档导入怎么做？人工还是自动化？

有人工导入页面，提供**批量导入**功能。

### 1.1.2.3 ⭐ 文档是否去重？如何保证唯一性？

- **当前**：按设备名称做幂等处理（删除原有，重新导入）。
- **进阶**：按文件 SHA 码识别，提醒导入用户已有重复文档。
- **未来**：不覆盖，做版本管理。

### 1.1.2.4 ⭐ 新增/更新文档后，切分和索引如何更新？

**当前（幂等更新）：**
1. 按商品名清理旧向量；
2. 重新切片、向量化、入 Milvus。

**更好方案（灰度）：**
1. 导入新内容，标记「未生效」，不删旧的；
2. 新内容完整导入后，标「有效」；
3. 旧切片标「作废」。
目的：避免导入一半时有人查询。

💡 用 `enable: false` 表示失效。

### 1.1.2.5 Milvus 和 ES 存多少数据？何时选 Milvus 而非 ES？

- 数据量本身不大，主要看重**业务功能**。
- Milvus 偏**向量/语义匹配**；ES 偏**全文精确匹配**。

💡 Milvus 数据量约 10G 级别。

# 三、文档解析与内容处理（13 题）

### 1.1.3.1 PDF 如何解析提取？

1. PDF **不直接检索**，先用 **MinerU 转成 Markdown**。
2. 转换后文本、标题、表格、图片引用结构化。
3. 后续所有格式统一走 Markdown 图片处理 + 切片链路。
- MinerU = 复杂 PDF → Markdown 的解析工具，解决「文本顺序乱、表格难抽、图片引用难保留」问题。

### 1.1.3.2 MinerU 和 VLM 图片识别区别？

- **MinerU**：把 PDF 拆出来转 MD，图片部分**只做引用、不做解读**。
- **VLM**：看懂图片、生成图片摘要，用户提问时引用图片并回答问题。

### 1.1.3.3 ⭐ 处理的文本复杂情况？

产品说明手册：长文档、有标题段落、有图片、有参数表格。

💡 难点补充：**表格跨页**。

### 1.1.3.4 ⭐ 表格如何提取处理？

1. MinerU 把 PDF 表格转为 HTML `<table>`；
2. 切片时把 `<table>` 用**行列交叉合并做线性化**，把表格变成自然语言，便于 LLM 识别。

### 1.1.3.5 ⭐ 图片内容如何处理？

1. 扫描 Markdown 里的图片引用；
2. 取图片前后的标题/上文/下文作上下文；
3. 调 VLM 生成图片标题/摘要，上传 MinIO；
4. 摘要作为文本参与检索；答案带图片 URL，前端可展示。

### 1.1.3.6 ⭐ 处理文件大概多长？

几十页到上百页常见，也会遇到两三百页长 PDF。长文档先按标题层级 + 内容长度切片，再检索相关片段。

### 1.1.3.7 从两三百页 PPT/PDF 精准提取关键信息？

1. 结构化：PDF → 带标题/表格/图片引用的 Markdown；
2. 切片：保留标题、父标题、商品名元数据；
3. 查询：商品过滤 + 多路召回 + RRF + Rerank；
4. 优化方向：故障码、参数表、警告可额外结构化抽取为**知识图谱**。

### 1.1.3.8 混合检索 BM25 与向量权重怎么定？

- 当前两种索引**权重各占一半**。
- 确定方法：准备测试集（常规问题 + 期望匹配切片），按多种权重测试，取分值更高者。

💡 BM25 是 ES 默认的相关性算法（BM25 打分）。

### 1.1.3.9 查询改写是什么？

把原始问题转成更适合检索的表达，并把前几轮对话信息提炼进本次问题。常见方式：
- **纠错**：修正错别字、口语表达；
- **标准化**：简称/别名转标准术语；
- **补充主语**：把追问得到的主语与原问题合并；
- **拆解**：复杂问题拆成多个子问题。

### 1.1.3.10 ⭐ HyDE 是什么？偏了怎么处理？

- **HyDE** = Hypothetical Document Embeddings（假设性文档检索）：先让模型根据问题生成一段假设答案/文档，再用它做向量检索。
- **防止偏**：
  1. 提示词限制必须围绕原问题生成假设答案；
  2. HyDE 只是一路，还会和原问题合并；
  3. 后面还有 rerank 节点重排兜底。

💡 关键：HyDE 是「可能」的假设文档，不是标准答案。

### 1.1.3.11 为什么需要多路查询和 RRF？

从不同角度召回，再用 RRF 评分把多路结果统一排序，召回更全、排序更稳。

💡 面试时强调 HyDE 的重要性：解决用户问题短、缺主语的问题。

### 1.1.3.12 RRF 和 rerank 是什么？重排怎么做？

- **RRF**（Reciprocal Rank Fusion，倒数排名融合）：按文档在多路结果里的排名算融合分，公式 `score(d)=Σ 1/(k+rank_i(d))`，k 常用 60，排名越靠前分越高。
- **rerank（精排）**：把 query 和候选文档成对输入 rerank 模型，输出相关性分数，再按分重排。

💡 rerank 是让「问题 + chunk」让模型打分，做断崖截断。

### 1.1.3.13 检索重排后返回 Top 多少？怎么减少中间信息丢失？

- TopK 参数包括：最多条数、最少条数、断层相对差值、断层相对比值。
- 参数先用经验值，再按 RAGAS 评估后微调。

# 四、文档切片与上下文完整性（15 题）

### 1.1.4.1 ⭐ 文档切片怎么做？

1. 先按 Markdown 1~6 级标题切；
2. 太长章节递归切，太短同父标题下合并；
3. 每个 chunk 保留标题、父标题、文件标题、商品名；
4. 向量化时拼 `item_name + content`，增强商品相关性；
5. 每个切片带 `item_name` 字段用于过滤，避免相似设备混淆。

### 1.1.4.2 ⭐ 切分长度阈值怎么控制？

- **最大长度** 1200 字符（之前 2000，发现 rerank 常忽略关键信息）；过长递归切分。
- **最小长度** 300 字符，过短向前后合并，避免缺上下文。
- **重叠**：保留少量句子重叠，当前 1 个 `overlap_sentences`。

### 1.1.4.3 段落超过最大块长度，如何保证语义完整？

**当前**：
1. 尽量按标题/段落/句子边界切，避免句子中间硬切；
2. 用 `overlap_sentences` 增加边界冗余。

**进阶**：
1. **文本回填**：保留 `parent_chunk_id`，命中子块后回填父章节/相邻块（缺点：可能增加噪音）；
2. **知识图谱**：实体关系建立跨切片语义关联，作为补充信息交给 LLM（缺点：需大模型提实体，增加 token 和时间）。

### 1.1.4.4 切分导致语义丢失时，怎么定位和优化？

1. 用 RAGAS 评估，`context_recall` 低即明显切片丢失；
2. 从 bad case 入手：看原文是否有答案 → 查召回结果是否含关键切片；
3. 若原文有答案但召回没命中，重点查 embedding / rrf / reranker 筛选前后日志。

**优化手段**：调小 chunk、增加 overlap、保留更多 RRF 候选、提高 rerank TopK、增加标题和商品名上下文。优化后复测 `context_recall`、`context_precision`、`answer_correctness`。

### 1.1.4.5 PDF/Word/图表/扫描件/低质量文档如何解析？

使用 MinerU；图片信息通过 VLM 生成说明文字（Caption）进入知识库。

### 1.1.4.6 多栏、图文错位、左文右图、「大片图片+简短编号」怎么处理？

MinerU 内部有 VLM，用于识别版面信息。

### 1.1.4.7 跨页大表格/图片切片后检索差怎么处理？

- MinerU 支持跨页表格合并；
- MD 的 HTML 表格做线性化处理；
- 图片用 VLM 生成说明文字。

### 1.1.4.8 ⭐ RAG 中的噪声如何处理？

- **导入预处理**：去页眉、页脚、乱码、无意义字符；
- **检索阶段**：相似度阈值过滤低分结果，重排提升相关性；
- **生成阶段**：Prompt 指示模型过滤噪声信息。

### 1.1.4.9 数千 Token 规章制度切块后简短提问只召回局部怎么办？关键信息跨块怎么办？

- 上下文被切碎不全 → 用**回填**补上下文；
- 长距离跨切片 → 用**知识图谱**提取核心实体关系。

### 1.1.4.10 拒答的触发条件和实现方式？

Rerank 评分低于 **0.3** 时淘汰上下文；上下文全被淘汰则拒答。

### 1.1.4.11 召回 chunk 超过 ReRanker 上下文窗口？重排后相关度仍不高？

- bge-reranker-large 上下文窗口 512 token，我们每个切片控制在 500 以内。
- 相关度仍不高 → 查具体原因，用 HyDE 或知识图谱增加信息匹配。

### 1.1.4.12 ⭐ 召回率低或大量不相关，从哪些方面排查优化？

**排查路径**：
1. 各路 embedding 的评分和筛选策略；
2. RRF 各路权重、平滑系数、筛选策略；
3. rerank 评分、TopK 筛选策略。

**原则**：召回率低 → 放宽门槛；精确率低 → 收紧门槛。

### 1.1.4.13 仅靠相关度排序导致切片重复、多样性不足？

用 **MMR（最大边际相关性）** 筛选：按相关度评分时，对与已选切片相近的切片做权重惩罚，删掉过于接近的切片以保留多样性。

### 1.1.4.14 向量相似度和语义相近是否等同？

**不完全等同**。向量模型把文章含义压缩成向量，会丢失大量细节——就像把两幅油画变成 8 位像素图再比较像素相似度。

### 1.1.4.15 RAG 向量化 + 切块的框架有什么问题？更好的方式？

- 问题：实现简单，但切块破坏上下文完整性、导致语义断裂，无法建立跨文档实体关系。
- 更好方式：**回填切片** 或 **知识图谱**。

# 五、检索召回与排序生成（16 题）

### 1.1.5.1 ⭐ 文档检索整体流程？

1. 先商品确认，再多路召回；
2. 召回 = 向量 + HyDE（本地），MCP 是可选网络补充；
3. 本地结果先进 RRF，之后统一交给 Rerank；
4. 截断后的上下文交给 LLM 回答。

### 1.1.5.2 dense 和 sparse 为什么都要？

- dense 擅长语义改写；sparse 擅长型号、参数、接口名、专有名词。
- 企业文档两类问题都有，BGE-M3 的 dense/sparse 混合更稳。

💡 数据话术：dense only Recall@5=78.4%；dense/sparse(0.8/0.2)=86.9%；HyDE+RRF 后 90.8%。

### 1.1.5.3 ⭐ 商品名确认机制怎么做？

1. LLM 从当前问题 + 历史对话抽商品名；
2. 商品名向量化，到商品名向量集合做混合检索；
3. 高分直接确认、中间分返回候选、低分让用户补充型号；
4. 确认后作为后续 Milvus 检索过滤条件。

💡 待优化：商品名做缓存，问题分词后与缓存匹配，命中直接确定，省去 LLM + embedding。

### 1.1.5.4 多轮后才确认商品名，历史缺失怎么处理？

1. 问题改写带上之前对话记录（含历史商品名）；
2. LLM 据本次问题 + 历史对话提取商品名，存入本次会话；
3. 把商品名回填到之前没确定商品的对话。

### 1.1.5.5 ⭐ 三路召回分别是什么？各解决什么？

1. **普通向量检索**：常规语义 + 关键词匹配；
2. **HyDE 检索**：解决用户表达不完整、缺实体主语；
3. **MCP**：额外网络补充。

💡 严格说本地是「两路」，MCP 是网络补充。

### 1.1.5.6 为什么多路召回，不只靠向量检索？

- 向量检索是常规按问题查答案；
- HyDE 解决表达不完整、缺主语；
- MCP 补充网络信息。
- 多路结果经 RRF + Rerank 统一排序，召回更全、答案更稳。

### 1.1.5.7 多路检索之间如何协同？

1. LangGraph 里一个虚拟 `multi_search` 节点并行发多路检索；
2. 每路只写自己的结果字段；
3. join 后本地两路进 RRF（无图谱则两路），网络结果在 Rerank 阶段合并；
4. 既并行提速，又统一排序。

### 1.1.5.8 HyDE 检索为什么能提升召回？

1. HyDE 先让模型写一段假想答案/技术文档；
2. 用户问题往往短或缺实体，假想文档更像真实手册表达；
3. 拿问题 + 假想文档去向量检索，更容易命中。

### 1.1.5.9 RRF 融合算法是什么？

倒数排名融合：融合多路检索结果，不依赖各路原始分数可比性，按各文档在各路的排名算综合分，`score(d)=Σ weight_i/(k+rank_i(d))`。同一文档多路靠前则综合分更高。

### 1.1.5.10 RRF 的 k 为什么选 60？

- 60 是 RRF 常用经验值。
- k 小 → 头部排名影响更大；k 大 → 排名差异更平滑。
- 可据验证集调参，观察不同 k 下的 `context_recall`、`context_precision`、`answer_correctness`。

💡 核心是「平滑」。

### 1.1.5.11 前两路 RRF 融合 + MCP 后走 rerank，能直接 rerank 吗？

- 能直接 rerank，但**不建议把所有原始召回都丢进去**。
- RRF 很便宜，先做去重和粗融合；Rerank 成本高，适合处理压缩后的候选。
- 网络结果没有本地 chunk_id，放 rerank 阶段统一精排更方便。

### 1.1.5.12 检索重排后返回 Top 多少给 LLM？

- 不是固定 TopK。
- RRF 默认先保留 20 条本地候选；
- Rerank 后默认最少 6 条、最多 15 条，中间用断崖检测截断。

### 1.1.5.13 ⭐ 什么是断崖检测截断？

Rerank 后文档按分数降序，动态确定保留数量。默认**绝对差 0.5 或相对差 25%** 作为阈值。属经验配置，更严谨做法是用验证集看 `context_recall`/`context_precision` 再调阈值。

### 1.1.5.14 断崖检测阈值怎么确定？

来自验证集 + bad case 分析，项目用绝对差 0.5 / 相对差 25% 经验阈值。调阈值观察两类指标：
- 截断太激进 → `context_recall` 下降；
- 截断太宽松 → `context_precision` 下降、幻觉风险增加。
最终结合 rerank 分数分布、文档长度、上下文预算、答案正确率定。

### 1.1.5.15 最终 Top15 都给模型，但模型重头部尾部，如何防中间丢失？

1. **排序**：Rerank 分数最高的放前面；
2. **提示词**：要求模型逐条阅读参考资料；
3. **摘要**：长文本材料用 LLM 提摘要放在靠前位置（有额外消耗）。

### 1.1.5.16 MCP 网络检索解决什么问题？

补充本地知识库缺失的信息以及实时信息。

# 六、模型、指标与评测（11 题）

### 1.1.6.1 ⭐ 用了哪些模型？分别在什么节点？

1. **文本 LLM**：千问 flash，用于商品名抽取、问题改写、HyDE、图谱抽取、答案生成；
2. **VLM**：图片摘要，走兼容 OpenAI/DashScope 配置；
3. **Embedding**：BGE-M3，生成 dense + sparse；
4. **Rerank**：BGE reranker 远端 HTTP 服务。

### 1.1.6.2 VLM 和文本大模型为什么没独立部署？

1. 初期访问量不高，调用频率可控，用成熟云端模型更稳定、省运维；
2. 独立部署需高显存、服务治理、推理优化，投入大；
3. 优先独立部署 BGE-M3 和 reranker（导入/检索调用频率高、本地部署成本可控）；
4. 后续调用量上升再评估独立部署。

💡 预算有限，且这两个模型不在同一时间使用。

### 1.1.6.3 ⭐ 召回率大概怎么样？

- 必须基于测试问题集评估，不能凭感觉。
- RAGAS 评估优化后 **93%+**；实测上线问题（含不在知识库的内容）召回率 **85%**。
- 口径：核心产品手册类问题召回稳定；bad case 集中在切片过大、表格/图片缺失、商品名识别错误、rerank 丢弃关键切片。

### 1.1.6.4 ⭐ 准确率怎么评测？

- 构建测试问题集，用 RAGAS 的 `context_precision` 分数求平均。
- `context_precision` = reranker 后上下文与参考答案的评分。
- 公式：`准确率 = Σ(precision@k × relevance_k) / 检索上下文数量`，`Precision@K` = 前 K 个结果中相关结果占比。该算法奖励排名靠前的命中上下文。

### 1.1.6.5 召回率怎么评测？

用 RAGAS 的 `context_recall` 评分观察。公式：`召回率 = 上下文支持的参考答案事实点 / 参考答案事实点`。

### 1.1.6.6 如何保证 LLM 回答准确性？

- 优化检索：保证切片被找到、噪音可控；
- 优化提示词：控制回答语术。

💡 每个环节都要处理，从后往前（生成→检索→召回→切片）逐层排除。

### 1.1.6.7 RAGAS 主要观察哪些指标？高低代表什么？

- **faithfulness**：答案是否被上下文支撑，低 → 可能幻觉；
- **answer_relevancy**：是否切题，低 → 理解或提示词问题；
- **context_precision**：召回上下文是否干净，低 → 噪声多；
- **context_recall**：证据是否召全，低 → 召回链路有问题；
- **answer_correctness**：与标准答案是否一致，整体效果指标。

💡 前期自测，后面收集 bad case、筛选反馈。

### 1.1.6.8 ⭐ 测试问题集怎么来？

1. 开发按文档先整理一批自测问题；
2. 业务补高频真实问题；
3. 上线后收集真实用户问题 + bad case。

### 1.1.6.9 ⭐ bad case 主要分析什么？步骤？

1. 先查评分，分情况分析；
2. 召回率低 → 先查原文是否有答案 → 再查会淘汰证据的节点（embedding / rrf / reranker）；
3. 上下文准确率低 → 调 TopK 保留数量；
4. 正确性低、其他都高 → 优先调提示词，其次换模型。

### 1.1.6.10 ⭐ 项目里有哪些优化案例？

1. **切片和重排优化**：答案在原文后半段但 rerank 不敏感 → 调小 chunk、加 overlap、提高候选保留量；
2. **提示词优化**：检索指标不差但答案发散 → 要求只基于参考资料回答、控制长度、按对象分组输出；
3. **脏数据优化**：MinerU 转换产生特殊符号/公式脏数据 → 增加规则过滤清洗；
4. **性能优化**：多用缓存和 FAQ，减少 LLM 使用。

### 1.1.6.11 是否有审计机制？观测怎么实现？

- 用 LangSmith / Langfuse / 自研日志记录全链路 Trace：User Query、检索 Chunks、ReRank 分数、Prompt、LLM 输出及耗时。
- 监控面板（Grafana）观测 QPS、P99 延迟、拒答率、用户负反馈率。

💡 本项目用 **Langfuse**。

# 七、前后端交互与流式响应（3 题）

### 1.1.7.1 ⭐ SSE 流式响应怎么实现？

1. 流式查询先生成 task_id，并创建一个 queue；
2. 后台跑查询图，答案节点调 LLM stream；
3. 每出一段就往队列放 delta 事件；
4. 前端通过 `/stream/{task_id}` 接收，最后收 final 事件。

### 1.1.7.2 SSE 和 WebSocket 区别？为什么选 SSE？

- **SSE**：服务端→客户端单向推送，基于 HTTP，浏览器原生支持、自动重连，适合进度通知和流式输出；
- **WebSocket**：双向通信，适合实时协作、在线聊天，交互成本高；
- 知识库问答是客户端提交后服务端持续推送，不需高频双向，SSE 更简单、成本低，易与 FastAPI `StreamingResponse` 结合。

### 1.1.7.3 文件导入长任务，前端如何感知进度？

1. 上传接口先返回 task_id；
2. 导入流程放后台任务跑；
3. 前端轮询 `/status/{task_id}` 看状态和节点列表。

# 八、性能、稳定性与部署（8 题）

### 1.1.8.1 响应时间从 3s 变 12s，如何排查节点耗时？

- 查询每个环节进度可见，日志都有节点耗时，可追踪。
- 延迟一般出在「用 LLM 的节点」和「MCP 节点」。
- MCP → 排查网络访问阻塞；LLM → 用缓存策略绕过 LLM。

💡 延迟 5s 以内一般不会找运维排查。

### 1.1.8.2 如何保证高可用？

1. 多路召回：单路出问题不影响主流程，增加容错；
2. 重试机制；
3. 多副本；
4. 兜底策略。

💡 监控：Prometheus + Grafana（后者图形化）；告警可推送 OA（钉钉）、邮件、Slack。

### 1.1.8.3 如何处理 Milvus 连接失败？

- 客户端做**单例 + 连接检查**，避免每次请求重复连接；
- 连接失败记录日志，返回可控错误/空结果，不让服务崩；
- 导入场景：任务标 failed，前端可见失败原因；
- 查询场景：降级到其他召回源（图谱、历史、MCP）；
- 生产配置健康检查、重试、超时、告警。

### 1.1.8.4 如何做模型接口控流？

设定并发 + 每分钟 token 参数，用**多线程 + 消息队列**解决。

### 1.1.8.5 服务如何部署？资源如何分配？

基于 0.5~1 QPS 规划：
1. 两台服务器：4C16G 应用机 + 8C32G 中间件机；
2. 大模型用千问服务；
3. Embedding + Reranker 部署在一台 4090（24G 显存）GPU 云服务器（或 Qwen Text Embedding + Reranker 服务）。

### 1.1.8.6 为什么拆 GPU 和 CPU 服务器？

- CPU 服务：API、流程编排、数据库读写、SSE；
- GPU 服务：embedding、rerank 模型推理；
- 拆开互不抢资源，方便单独扩容模型服务。

### 1.1.8.7 ⭐ 为什么没用 Kubernetes？

1. 当前服务规模不大，Docker Compose 更容易交付和排查；
2. K8s 适合多副本、弹性伸缩、灰度发布、复杂运维；
3. 先把链路跑稳，后续流量上来再迁移。

💡 Docker Compose 便于管理 docker 容器。

### 1.1.8.8 重新设计这个系统会做哪些改进？

1. 增加缓存（FAQ、item_name）；
2. 增加可维护的管理平台，文本存 MySQL，向量库只留索引；
3. 增加知识库数据看板；
4. 知识更新增加灰度发布，避免导入时有人查询。
