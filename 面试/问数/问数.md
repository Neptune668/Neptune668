- **1 张事实表**：`fact_order`（订单事实表，只存外键 + 度量值）

## 二、为什么这个「问数」项目必须建数仓

核心原因：**NL2SQL（自然语言转 SQL）的难点，恰好是维度建模解决的问题**。

### 1. 把「维度」和「度量」分开，LLM 才能正确生成 SQL

LLM 生成 SQL 时，必须分清两类字段：
- **维度（dimension）**：用于 `WHERE` 过滤、`GROUP BY` 分组（地区、商品、时间）
- **度量（measure）**：用于 `SELECT` 里的 `SUM/AVG` 聚合（销量、金额）

原始订单表通常是一张宽表，把"地区名、商品名"和"金额"混在一起，LLM 无法判断哪个字段该 `GROUP BY`、哪个该 `SUM`。数仓把事实表设计成"外键 + 度量值"，维度表设计成"主键 + 描述属性"，这种清晰的 role 标注（`primary_key/foreign_key/measure/dimension`）直接喂给 LLM，正确率大幅提升。

### 2. 度量与维度分离 → 统一指标口径

指标（GMV、AOV）通过 `relevant_columns` 关联到事实表的具体 measure 字段：

```175:186:conf/meta_config.yaml
metrics:
  - name: GMV
    description: 全称Gross Merchandise Value，表示所有订单的成交金额总和。
    relevant_columns:
      - fact_order.order_amount
    alias: [ 成交总额, 订单总额 ]
```

这样"销售总额"永远等于 `fact_order.order_amount` 求和，口径统一，不会出现"不同问法得到不同 SQL、不同结果"的问题。

### 3. 主外键关系让 LLM 能自动推理出 JOIN 路径

用户的问题大多是跨表的多维分析（如"各地区销量排名前三的商品"），需要事实表 JOIN 多个维度表。星型模型"事实表居中、维度表环绕"的结构，JOIN 关系清晰（`fact_order` 外键指向各维度表主键）。

项目里 `merge_recall` 节点甚至会**自动补充主外键字段**：

```101:112:app/agent/nodes/merge_recall.py
    # # 补充：相关表的主外键字段信息
    for table_id,column_list in table_column_dict.items():
        # 去查询meta库当前表的主外键字段信息
        key_column_infos: list[ColumnInfoMySQL] = await meta_mysql_repo.get_key_column_infos_by_table_id(table_id)
        for key_column_info in key_column_infos:
            # 将主外键的字段信息转成ColumnInfoQdrant对象
            key_column_info_qdrant = _convert_column_info_mysql_to_qdrant(key_column_info)
```

没有规范的主外键关系，这一步就无法实现，生成的 SQL 也就无法正确 JOIN。

### 4. 专门的 `dim_date` 时间维度表，支持相对时间问答

用户会问"3月 / 2025年 / Q1"这类问题。项目有独立的 `dim_date` 表（年/季度/月/日多粒度），且 `add_context` 节点会注入"当前日期 + 当前季度"：

```17:26:app/agent/nodes/add_context.py
    today = datetime.today()
    date = today.strftime("%Y-%m-%d")
    weekday = today.strftime("%A")
    quarter=f"Q{(today.month+2)//3}"
    date_info = DateInfoState(date=date, weekday=weekday, quarter=quarter)
```

配合时间维度表，LLM 才能把"3月"这个模糊表达解析成确定的过滤条件。

### 5. 结构稳定 → 元数据抽取和召回更可靠

知识库构建时，`MetaKnowledgeService` 依赖 `show columns` 拿字段类型、读取字段的 role/description/alias，再分别写入 MySQL（结构化）、Qdrant（向量）、ES（全文）。数仓规范化后的表结构稳定、字段含义清晰，元数据质量高，向量召回的命中率才高——这是整个 RAG 问数系统的基础。

---

**一句话总结**：这个项目建数仓，是为了把「维度/度量」「主外键关系」「时间粒度」「指标口径」这些 SQL 生成所需的结构化语义，用规范的表结构固化下来，从而让 LLM 能可靠地把自然语言问题转换成可执行、可 JOIN、口径统一的聚合 SQL。数仓不是这个系统的"附属品"，而是 NL2SQL 能跑通的前提。
