# 掌柜问数项目 · 面试题库

> 面向 Text2SQL / NL2SQL 智能问数系统的面试准备，按考察维度分类。
> 每道题包含：**面试官提问 → 回答思路/要点 → 可加分项**。

---

## 一、项目概述类（考察表达与全局理解）

### Q1. 用 3 分钟介绍一下这个项目

**回答框架（背景 → 痛点 → 方案 → 价值）：**

- **背景/痛点**：业务人员查数依赖数据开发或数据分析师写 SQL，交付慢、重复劳动多
- **方案**：面向数据仓库的智能问数系统，用户用自然语言提问（如"统计华北地区上月销售额"），系统自动完成问题理解 → 元数据召回 → SQL 生成 → 校验 → 执行 → 返回结果
- **技术核心**：以 Text2SQL 为核心，前后补充元数据知识库、多路召回、上下文精筛、SQL 校验、权限控制、bad case 评测闭环
- **价值**：业务层更快拿数据，技术层通过元数据/检索/校验/权限/评测机制控制 SQL 准确性与安全性

**加分项**：主动说明"这不只是一个 SQL 翻译器，本质是工程化可控的 NL2SQL 全链路系统"。

---

### Q2. 这个项目的整体架构是什么样的？

**回答要点：**

- **应用服务**：2 台 8C32G 云主机，Docker Compose 部署 FastAPI，Nginx 反向代理
- **模型服务**：1 台 GPU 服务器（32C128G + NVIDIA L20 48GB），vLLM 推理框架，OpenAI compatible API
- **主力模型**：Qwen3.5-35B-A3B-GPTQ-Int4；轻量路由模型 Qwen3.5-4B；Embedding 用 BGE-large-zh-v1.5
- **存储/检索**：MySQL 8.0（元数据中心）+ Qdrant（向量索引）+ Elasticsearch（全文索引）
- **编排**：LangGraph 编排 12 个节点的工作流
- **监控**：Prometheus + Grafana + 结构化 trace 日志

---

### Q3. 你主要负责哪些模块？

**回答要点（按参与度排序）：**

问数智能体链路，具体包括：
1. 元数据知识库建设（表/字段/指标三层元数据治理）
2. 表、字段、指标召回（多路召回 + 融合精筛）
3. SQL 生成（Few-shot + CoT 提示工程）
4. SQL 校验（EXPLAIN + LLM 语义校验）
5. 异常修正与防死循环
6. bad case 优化与评测闭环

---

## 二、Text2SQL 链路类（考察核心技术细节）

### Q4. Text2SQL 链路是怎么实现的？分几步？

**回答要点（六步/十二节点）：**

1. **问题理解**：抽取时间范围、指标、过滤条件、分组维度、核心实体
2. **关键词提取**：jieba TF-IDF + LLM 语义扩展
3. **多路召回**：字段（Qdrant）、指标（Qdrant）、字段取值（ES）
4. **上下文组装**：指标补依赖字段、字段值挂示例、按表分组、精筛成最小充分上下文
5. **SQL 生成**：用户问题 + 精筛上下文 → LLM 生成
6. **SQL 校验**：SQL 解析 → EXPLAIN → 权限校验 → 安全校验
7. **执行与返回**

**加分项**：说明"召回 → 补全 → 精筛"三层过滤的设计意图——控制最小充分上下文。

---

### Q5. 自然语言转 SQL 是直接丢给 LLM 吗？做了哪些前置处理？

**核心观点**：**不是直接交给 LLM**。直接生成容易表选错、字段选错，必须与元数据对齐。

前置处理：
1. 关键词抽取（jieba + LLM 扩展）
2. 三路召回（字段/指标走 Qdrant，字段值走 ES）
3. 上下文合并 + 精筛

**加分项**：指出"不稳定的自然语义 + 大量元数据上下文"若不处理会大幅降低准确率，这正是必须引入 RAG 的原因。

---

### Q6. 用户问题涉及哪些表和字段，是怎么确定的？

**回答要点**：表和字段来自元数据知识库，不是模型凭空猜。

1. MySQL 存表/字段/指标信息，同步到 Qdrant（字段+指标）和 ES（字段值）
2. 查询时从 Qdrant 召回字段/指标、ES 召回字段值
3. 根据字段所属表、指标依赖字段、字段值命中结果补齐表结构

模型拿到的是**结构化上下文**，知道表、字段、含义和示例值。

---

### Q7. 表过滤和字段过滤是怎么做的？

**回答要点（召回 → 补全 → 精筛三层）：**

- **召回**：语义召回字段/指标，关键词召回字段取值
- **补全**：指标依赖补字段、字段所属关系补表、字段取值补示例
- **精筛**：判断表字段与当前问题是否真正相关，过滤无关信息，生成 SQL 上下文

---

## 三、召回与检索类（考察 RAG 深度）

### Q8. 三路召回策略是什么？如何融合和重排？

**回答要点：**

三路召回：
- 字段召回（找表字段）
- 指标召回（找业务指标）
- 字段值召回（找 WHERE 条件里的具体值）

**关键点**：三路召回的是**不同类型**的上下文，所以做的**不是 RRF**，而是直接组合合并。

融合过程：字段值挂回对应字段 → 指标依赖字段补进字段集合 → 按表分组 → 补表描述和关键字段 → 再精筛 → 形成 SQL 上下文。

**加分项**：明确说明"为什么不用 RRF"——因为召回对象异构，不是同一候选集的打分排序问题。

---

### Q9. 关键词提取和语义理解用了哪些技术？

**回答要点：**

1. **统计分词**：jieba TF-IDF 提取初始关键词 + 词性过滤（只留名词/动词/形容词）
2. **LLM 语义扩展**：按字段/指标/字段值三种目标做差异化扩展策略，三者并行
   - 字段：推断"最小必要字段集合"
   - 指标：同义与缩写生成（销售额→GMV→成交额→交易额）
   - 字段值：提取实体名称和枚举值
3. **混合检索**：BGE-large-zh-v1.5 向量语义匹配 + ES IK_MAX_WORD 中文全文检索

---

### Q10. 如何解决中文语义到英文字段名的 GAP（如"收入"→order_amount）？

**这是难点，体现思考深度：**

- 通过元数据里的**字段别名、业务描述、取值示例**建立语义桥梁
- 指标扩展专门做同义/缩写生成，覆盖用户说法
- 用 AI + 人工维护**扩词表**（如"苹果笔记本"→Macbook）

**但也要诚实承认**：通用模型不一定能把中文说法映射到英文字段，这是召回失败的常见原因之一。

---

## 四、SQL 生成与准确性类（考察工程质量）

### Q11. 如何保证生成的 SQL 是用户想要的？

**回答要点（分层）：**

1. **意图理解层**：先解析成结构化意图（维度/指标/过滤条件），有歧义主动反问（如"上个月"=自然月 or 最近 30 天）
2. **生成控制**：写入 2-3 条最相似历史正确 SQL 作 Few-shot + 强制 CoT（先析意图→匹配 Schema→写 SQL→自检）
3. **语义校验（最核心）**：LLM 校验节点查五件事——指标口径、GROUP BY 粒度、过滤条件、JOIN、时间范围；再加**反向校验**（让另一个 LLM 解释 SQL，与原问题对比）
4. **结果合理性校验**：空结果/万行/聚合值异常都主动提示
5. **反馈闭环**：附"查询对吗"入口，错误 SQL 分析原因，纠正 SQL 进 Few-shot 库，形成飞轮

---

### Q12. 如何校验 SQL 的语法、权限和业务正确性？

- **语法**：SQL 解析 + EXPLAIN（可解析、表字段存在、执行计划能生成）
- **权限**：生成前把用户 id + 数据表传给权限审查接口（扩展）
- **业务正确性**：数据生成后让 LLM 对数据与原问题反思（扩展）

---

### Q13. EXPLAIN 能发现什么？发现不了什么？

- **能发现**：语法错误（SQL 能不能执行），可对执行计划做性能审查
- **发现不了**：业务需求是否对齐、约束是否遗漏——需加数据反思环节

**加分项**：举例"SUM(order_quantity) 当 GMV 算，EXPLAIN 说完全没问题"——说明 EXPLAIN 只能查"存在性"，查不了"语义正确性"。

---

### Q14. SQL 生成失败怎么纠错？如何防止死循环？

**回答要点：**

纠错：把原始问题 + 生成 SQL + 错误信息 + 元数据上下文一起交给修正节点，重新生成或局部修复。

防死循环三件套：
- 最大重试次数限制
- 错误类型判断（语法/字段错误可自动修复；权限/危险 SQL 直接中断）
- 兜底策略（澄清问题或转人工）

---

### Q15. JOIN 的表选错了怎么发现和处理？

**诚实回答 + 分层：**

- 语法通过但 JOIN 选错，只能靠**数据反思环节**发现，再交校正节点修复（扩展）
- 更根本的是**事前预防**：通过问题集做结果对账和 bad case 分析提前避免

---

## 五、安全与权限类（考察工程意识）

### Q16. 数据权限怎么做的？在哪个阶段鉴权？

- **表级权限 + 行级权限**两级
- 生成 SQL 前：元数据表 + 用户 id → 权限审查接口 → 得到访问标志（表级）+ 过滤条件（行级）
- 行级过滤条件**强制追加到 SQL**，保证只查有权限范围
- 敏感字段做字段级控制 + 脱敏（扩展）

---

### Q17. 如何防止 SQL 注入、越权、全表更新？

- **SQL 注入**：生成用的数值都与元数据匹配，恶意数值匹配不到元数据或匹配到正常元数据，不产生注入
- **越权**：表级+行级权限过滤条件强制追加
- **全表更新**：从执行函数层面定死，不允许写操作

---

### Q18. LLM 调用和部署如何保证数据安全？

三层：**私有化部署**（数据不泄漏）+ **数据脱敏**（敏感信息不直接展示）+ **数据权限**（只展示放开字段）。

## 六、性能与优化类（考察数据意识）

### Q19. 压测表现如何？瓶颈在哪？

| 并发 | QPS | TTFT P50 | TTFT P95 | TPOT P95 | GPU 利用率 |
| --- | --- | --- | --- | --- | --- |
| 16 | 14.8 | 310ms | 620ms | 38ms/token | 61% |
| 32 | 25.6 | 420ms | 880ms | 46ms/token | 78% |
| 64 | 38.9 | 690ms | 1.42s | 63ms/token | 91% |

**瓶颈**：随并发提升，TTFT/TPOT 上升、GPU 利用率拉到 91%，瓶颈在模型推理和 SQL 生成时获取字段/表关系。

---

### Q20. 查询语句优化做过哪些？

1. jieba + LLM 语义扩展双关键词策略
2. set 去重减少上下文噪音 + prompt 分层约束（安全/方言）
3. EXPLAIN 校验 + LLM 自校正闭环
4. 历史最相似 3-5 条 SQL 作 Few-shot
5. 高频查询结果集缓存
6. 慢查询日志监控 + 补索引

**刻意没做的**：暂未让 LLM 根据 EXPLAIN 自动改写 SQL，怕影响业务逻辑正确性。

## 七、数据规模与评测类（考察量化能力）

### Q21. 项目数据规模多大？

- 4 个主题域（订单/客户/商品/区域）、67 张表、913 个字段、128 个指标
- 字段枚举值 18.6 万条，事实表最大 3200 万行
- 向量：字段 913 + 指标 128；ES 索引 18.6 万条

---

### Q22. 准确率和通过率怎么评测？

- **准确率** = 数据正确个数 / 总个数
- **通过率** = SQL explain 通过 / 总个数

效果：常见查询准确率 90%+，复杂多表关联 80%+；端到端响应 3-10 秒。

---

### Q23. SQL 正确率达不到 100% 的原因？怎么优化？

**原因**：
1. 召回失败（中文→英文 GAP、固定阈值一刀切）
2. 上下文质量（LLM 裁剪误删/误留）
3. SQL 生成局限（语法对逻辑错）
4. 校验盲区（EXPLAIN 查不了语义）

**优化**：
1. 建 benchmark 让优化有数据依据
2. Few-shot 动态示例（性价比最高）
3. CoT 推理步骤
4. EXPLAIN 后加 LLM 语义校验
5. 阈值改动态
6. bad case 术语提炼进元数据
7. 数据反思节点纠偏 + 引导用户标准话术

## 八、难点与思考类（考察技术判断力，最易拉开差距）

### Q24. NL2SQL 的核心难点是什么？为什么不是"翻译"难？

**核心观点**：最大难点不是 NL→SQL 翻译，而是**把业务语义准确映射到正确的库/表/字段**。

自然语义不稳定不规范 + 元数据量大，两者叠加必须靠 RAG 对齐，否则准确率大幅下降。

---

### Q25. 调研过业内哪些方案？为什么借鉴京东 Data Agent？

- 权威开源有限，多是 BI 厂商闭源
- 大厂开源：阿里 SpringAI DataAgent、京东 Data Agent
- **本项目借鉴京东 Data Agent 做 Python 化改造**
- 阿里方案过度依赖 Java SpringAI 生态，流程长，用 plan-execute 多轮理解

---

### Q26. 为什么不做大宽表，而要设计多表关联？

- 数据表已是**轻度聚合宽表**，但部分维度表单独保存以**提高灵活度、控制冗余**
- JOIN 不多，主要是事实表 + 维度表 JOIN
- 涉及几十张表，最大表千万级以内

---

### Q27. 为什么没建语义层，而是让 LLM 直接生成 SQL？

语义转 SQL 对大模型不是难点，难点是**把用户语言拆解并与标准语义/元数据对齐、实现精确召回**。所以重心放在召回而非语义层。

---

### Q28. 为什么用较小的模型，考虑过更大模型吗？

- 准确率瓶颈在**前期召回流程**，不在模型能力
- 数据安全需本地部署，大模型增加部署难度

---

### Q29. 怎么解决"苹果笔记本"这种实体歧义（产品 vs 水果）？

- ES 多关键词匹配，"笔记本"会提高名称含"笔记本"商品的优先级
- AI + 人工维护**扩词表**（"苹果笔记本"→Macbook）

---

### Q30. 这个项目为什么不能只靠 Text2SQL？

用户自然语义不稳定 + 元数据量大，不做 RAG 会让"不稳定问题 + 大量上下文"双重作用，准确率大幅下降。RAG、工具调用、规则校验是让 NL2SQL 工程化可控的关键。

---

### Q31. 有没有涉及算法？项目定位是什么？

不涉及 AI 算法，定位是**大模型应用工程**——通过工程手段让"自然语言→数据"更可控稳定。

---

## 九、延伸追问（面试官可能的深挖）

### Q32. 为什么 Skill 没有嵌入项目？

Skill 优势是提炼通用高复用能力 + 让模型自主决定是否使用。但问数场景复用主要在项目内、流程固定，暂不需提炼为 Skill。未来通用能力（如文档生成）可考虑。

### Q33. 数据导入维护工作量大吗？

主要是元数据而非实际数据，工作量可控，可 AI 整理 + 人工审查微调，网页平台维护。
