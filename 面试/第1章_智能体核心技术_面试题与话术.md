# 1.1 Python基础

## 1. list 和 tuple 有什么区别？

**一句话回答**：list 可变，tuple 不可变；tuple 可哈希、能当字典的键，list 不能。

**展开话术**：
1. **可变性**：list 支持 append / remove / 改元素；tuple 创建后内容不能改。
2. **哈希性**：tuple 只要元素都不可变就整体可哈希，能做 dict 的 key 或 set 的元素；list 不可哈希。
3. **内存与性能**：tuple 结构固定、没有预留容量机制，所以更省内存、创建更快；list 为了支持动态扩容会有 over-allocation（预留空间）。
4. **语义**：tuple 常用来表达"固定结构"（如坐标、记录、多返回值），list 表达"动态集合"。
5. **坑**：tuple 的"不可变"是浅层的——如果 tuple 里放的是 list 这种可变对象，那个对象本身照样能改。

**加分点（追问预判）**：
- 为什么 tuple 比 list 省内存？→ 固定大小，无预留扩容。
- namedtuple 了解吗？→ 给 tuple 字段命名，可读性更好。
- 什么时候一定得用 tuple？→ 做字典 key、表示不可变常量集合。

> 列表是可变的，可以做增删改；元组是不可变的，不能做增删改；
>
> 哈希：**把任意长度的数据，通过哈希函数映射成一个固定长度的整数/摘要，用来快速查找、比较或定位**

## 2. 什么是闭包？定义和形成条件？

**一句话回答**：内层函数引用了外层函数的变量，且外层函数返回这个内层函数，就形成了闭包。

**展开话术**：
三个条件缺一不可：
1. 存在函数嵌套（内层函数定义在外层函数里）；
2. 内层函数引用了外层函数的**非全局**变量；
3. 外层函数**返回内层函数的引用**。

补充一点容易被追问的：闭包 = 函数 + 它捕获的环境（自由变量）。内层默认**只能读**外层变量，想改必须用 `nonlocal` 声明，否则 Python 会把它当成新的局部变量，直接报错。

**示例**：

```python
def outer(x):
    def inner(y):
        nonlocal x        # 想修改外层 x 必须加 nonlocal
        x += y
        return x
    return inner

f = outer(10)
print(f(1))   # 11
print(f(1))   # 12  ← 状态被保留
```

> 闭包是一种特殊的函数嵌套结构；
>
> 在闭包中，内部函数默认只能读取外部函数的变量，若直接修改会被 Python 判定为 “定义局部变量”，导致报错。需使用**nonlocal**关键字声明变量，明确其来自外部函数的作用域

## 3. 闭包为什么能保留外部函数的变量？

**一句话回答**：内层函数持有对外层变量的引用，外层变量的引用计数不为 0，所以不会被销毁。

**展开话术**：
1. 正常情况下，函数执行结束后，其内部变量会被销毁。但闭包中，内部函数引用了外部函数的变量，形成了 “变量捕获”，使得这些变量不会随外部函数的结束而销毁，而是被内部函数 “保留” 在内存中，直到内部函数被销毁。
2. 这种机制依赖 Python 的**作用域链**：内部函数在查找变量时，会先在自身作用域查找，若未找到则向上级（外部函数）作用域查找，闭包通过这种链式查找保留了对外部变量的引用。
3. 查找机制依赖作用域链（LEGB 规则：Local → Enclosing → Global → Built-in），内层找不到就逐级向上找。

**加分点**：可以主动提 `__closure__` 属性、cell 对象，以及 `nonlocal` 本质就是往 cell 里赋值，能让面试官觉得你懂底层。

> **Local（局部） → Enclosing（外层函数/闭包） → Global（模块全局） → Built-in（内置）**

## 4. 闭包有哪些实际应用场景？

**一句话回答**：核心价值就八个字——**保留状态、封装数据**。

**展开话术**：

1. **装饰器**：装饰器本质就是闭包，在不改原函数代码的前提下加功能（日志、计时、重试）。
2. **数据封装与隐藏**：模拟类的私有变量，把内部状态藏起来，只暴露操作接口，实现类似"私有属性"的效果。
3. **函数工厂**：动态生成带不同参数的函数，避免重复代码。
4. 还可以补充：**回调函数带上下文**、**缓存/记忆化（memoization）** 也是闭包的典型用法。

**示例（函数工厂）**：
```python
def make_multiplier(n):
    def multiply(x):
        return x * n
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)
print(double(5))   # 10
print(triple(5))   # 15
```

## 5. 闭包可能导致什么问题？如何避免？

**一句话回答**：可能内存泄漏，尤其是闭包长期持有大对象或形成循环引用时。

**展开话术**：
1. **内存泄漏**：闭包会保留外层变量，若变量是大对象且闭包长期存活，内存就一直不释放。
2. **循环引用**：闭包引用外层、外层又引用内层时，纯靠引用计数回收不掉，只能靠分代 GC 兜底。

**如何避免**：
- 不再使用时手动把引用置 `None`，断开引用触发回收；
- 避免在闭包里捕获过大对象，只捕获必要的最小状态；
- 频繁创建闭包的场景考虑用类替代（类的 `__del__` 可主动释放资源）；
- 必要时用 `weakref` 弱引用。

**加分点**：能讲清"引用计数 vs 分代垃圾回收（gc 模块）"的区别，说明循环引用只能靠 GC 解决。

## 6. 什么是 Python 中的迭代器？🛫

**一句话回答**：同时实现了 `__iter__()` 和 `__next__()` 的对象。

**展开话术**（重点讲清一个易混点）：
1. **可迭代对象（Iterable）≠ 迭代器（Iterator）**。可迭代对象实现 `__iter__`（能被 `for` 遍历），迭代器在此基础上还要实现 `__next__`。list / str / dict 是**可迭代对象**，但不是迭代器，要用 `iter()` 转换。
2. **for 循环的本质**：① 调用 `iter()` 拿迭代器 → ② 不断调 `next()` 取值 → ③ 抛 `StopIteration` 自动结束。
3. **特点**：懒加载（用到才取）、单向（只能往前）、一次性（取完不能自动重来）。

**Agent 工程里的使用场景**（加分）：
- 超大文件 / 百万行日志逐条读，避免一次性加载导致内存溢出；
- SSE 流式传输，把大模型生成的文本实时推给前端，可以提升用户体验；
- 工作流执行中实时拿每个节点的状态——LangGraph 的 `stream()` 返回的就是典型的状态迭代器，`for event in workflow.stream(state)` 每迭代一次就是一个节点完成。

**加分点**：为什么迭代器的 `__iter__` 要返回 self？→ 让迭代器本身也可迭代，保证 `for` 里统一调 `iter()` 不报错。可用 `isinstance(obj, collections.abc.Iterator)` 判断。

> 1. **LangGraph `stream()` 实时拿节点状态**：`workflow.stream(state)` 返回迭代器/生成器，`for` 每迭代一次就调用一次 `next()`，推动工作流往下执行并产出一个节点完成后的状态/事件，所以能边执行边拿状态，而不是等最终结果。
> 2. **迭代器 `__iter__` 返回 `self`**：让迭代器本身也可迭代，`iter(iterator)` 直接返回自己，保证 `for` 统一调用 `iter()` 不报错，并保持同一份迭代状态。`isinstance(obj, collections.abc.Iterator)` 可判断对象是否实现了 `__iter__` 和 `__next__`，即是否是迭代器。

## 7. 什么是 Python 中的生成器？🛫

**一句话回答**：用 `yield` 实现的、能惰性生成数据的特殊迭代器。

**展开话术**：
1. 含 `yield` 的函数叫生成器函数，调用它**不会执行函数体**，而是返回一个生成器对象；用 `next()` 才触发执行，到 `yield` 暂停并保留状态。
2. 本质就是迭代器，自动实现了 `__iter__` / `__next__`。
3. 特点：每次只生成一个值、不一次性加载全部数据，适合大数据、大范围、流式场景。
4. 还有生成器表达式 `(x for x in ...)`，注意和列表推导 `[x for x in ...]` 的区别：一个惰性、一个立即求值。

**对比示例（核心考点）**：
```python
# 普通函数：一次性返回 100 万个元素，占约 16MB 内存
def get_all():
    return [i * 2 for i in range(1000000)]

# 生成器：惰性生成，内存占用几乎为 0
def get_gen():
    for i in range(1000000):
        yield i * 2
```

**Agent 工程里的使用场景**：SSE 流式传输（核心）、LangGraph 工作流监控——`print(type(app.stream(state)))` 输出 `<class 'generator'>` 就是证明。

**加分点**：`send()` / `throw()` / `close()` 方法、`yield from` 委托子生成器；生成器是协程的底层基础。

## 8. 什么是 Python 中的装饰器？🛫

**一句话回答**：不修改原函数代码、给函数增加功能的语法糖，本质是闭包 / 高阶函数。

**展开话术**：
1. 本质：接收函数、返回函数的高阶函数。`@decorator` 等价于 `func = decorator(func)`。
2. 特点：不改原函数、复用性强、可叠加（多个装饰器**自下而上**执行）。
3. **一句记忆**：迭代器解决遍历问题，生成器解决内存问题，装饰器解决监控问题。

**Agent 工程里的使用场景**（重点加分）：日志、性能计时、重试机制、权限校验、缓存、限流，以及 Agent 里最常见的**工具注册**（`@tool`）。

**示例（计时器）**：
```python
import time, functools

def timer(func):
    @functools.wraps(func)   # 保留原函数的 __name__/__doc__
    def wrapper(*args, **kwargs):
        t0 = time.time()
        result = func(*args, **kwargs)
        print(f"{func.__name__} 耗时 {time.time() - t0:.3f}s")
        return result
    return wrapper
```

**加分点（追问预判）**：`functools.wraps` 的作用；带参数的装饰器（三层嵌套）；`functools.lru_cache`；类装饰器。

## 9. 同步和异步是什么意思？

**一句话回答**：同步是"发起 → 等待 → 继续"，异步是"发起 → 不等 → 结果好了再处理"。

**展开话术**（用点菜比喻很形象，直接讲）：
- 同步：你点完菜站在柜台等厨师做完端给你，期间啥也不干。
- 异步：你点完菜拿个小票回去刷手机，做好了叫号你再去取。

对照表：

| 概念 | 一句话 | 适合场景 |
|------|--------|----------|
| 同步 | 发起任务-等待结果-再往下走 | 逻辑简单、步骤必须顺序执行 |
| 异步 | 发起任务-不等结果-结果好了再处理 | 网络请求、文件读写、消息处理 |

**加分点**：强调"异步 ≠ 多线程"——异步是单线程内的**协作式并发**，靠事件循环调度；并发的实现方式有回调、Promise/Future、async/await 三代的演进。

## 10. 进程、线程、协程有什么区别？

**一句话回答**：进程是资源分配单位，线程是 CPU 调度单位，协程是用户态协作式执行单元。

进程：**操作系统分配资源的独立单元**。 每个进程有自己独立的地址空间（代码、数据、堆、栈），进程之间默认完全**隔离**

线程：**进程内部的操作系统调度的执行流**。 同一进程的多个线程**共享地址空间**，各自有独立的调用栈和寄存器上下文。

协程：**用户态程序自己管理的协作式执行单元**。 不依赖操作系统调度，由程序**显式让出控制权**（yield / await）

**展开话术**（按维度对比）：

| 维度 | 进程 | 线程 | 协程 |
|------|------|------|------|
| 资源隔离 | 完全隔离（独立地址空间） | 共享地址空间 | 共享线程 |
| 调度者 | 操作系统 | 操作系统 | 程序自己（用户态） |
| 切换开销 | 大 | 中 | 极小 |
| 内存占用 | 大 | MB 级 | KB 级 |
| 通信方式 | IPC | 共享内存（需锁） | 直接共享变量 |

**加分点**：协程为什么切换快？→ 不陷入内核态，保存的是轻量级上下文，由程序显式 `yield` / `await` 让出控制权。

## 11. 什么是 GIL（全局解释器锁）？

**一句话回答**：CPython 解释器里的一把全局锁，同一时刻只允许一个线程执行 Python 字节码。

**展开话术**：
1. **存在原因**：CPython 的内存管理（引用计数）不是线程安全的，用一把 GIL 锁来简化实现。
2. **影响分两种情况**：
   - I/O 密集型：影响不大——线程在等网络/磁盘时会**主动释放 GIL**，多线程仍有价值；
   - CPU 密集型：影响严重——多线程没法真正并行跑在多个 CPU 核上。
3. **绕过方案**：多进程（multiprocessing）、C 扩展里释放 GIL、换解释器（PyPy/Jython）。

**加分点**：提一嘴 Python 3.12/3.13 的 PEP 703 在推进"可选移除 GIL"，会显得你关注前沿。

## 12. 线程、协程、多进程分别适合什么场景？

**一句话回答**：CPU 密集 → 多进程；高并发 I/O → 协程；简单后台并发 → 线程。

**展开话术**（给一个判断思路，比背表格更有说服力）：
1. 先看任务性质：CPU 密集还是 I/O 密集；
2. 再看并发量级：几十上百用线程，成千上万用协程；
3. 最后看约束：是否依赖同步库、改造异步成本高不高。

| | 适合 | 不适合 | 典型任务 |
|---|------|--------|----------|
| 线程 | I/O 密集、需共享内存、任务量中等 | CPU 密集（GIL 限制）、超高并发（内存爆炸） | 文件读写、接口调用、后台轮询 |
| 协程 | 高并发 I/O、连接数成千上万 | CPU 密集（堵住事件循环）、依赖大量同步库 | HTTP 客户端、WebSocket、SSE、大模型流式输出 |
| 多进程 | CPU 密集、需绕开 GIL、需强隔离 | I/O 密集（杀鸡用牛刀）、需频繁共享数据 | 图像/视频处理、批量特征计算、模型并行 |

---

## 13. 为什么 I/O 操作常用协程而不是线程？

**一句话回答**：I/O 任务大部分时间都在"等"，协程最擅长的就是"等待"。

**展开话术**（对比着讲）：

| 对比维度 | 协程 | 线程 |
|----------|------|------|
| 调度开销 | 用户态自己切换，极低 | 内核态切换，较高 |
| 内存占用 | 一个协程 ~KB 级 | 一个线程 ~MB 级 |
| 并发效率 | 等 I/O 时主动让出，事件循环调度其他任务 | 等 I/O 时靠 OS 调度，切换成本高 |

所以海量连接（成千上万）时，线程会"内存爆炸 + 切换成本高"，协程则轻松应对。但**线程没被淘汰**：依赖同步库、任务量不大、改造异步成本太高时，线程仍是好选择。

**加分点**：可以引出 C10K / C10M 问题背景。

## 14. async 和 await 在 Agent 实现中起什么作用？

**一句话回答**：async 定义异步函数（协程），await 等待异步任务完成并释放当前协程的执行权。

**展开话术**（结合 Agent 工程，这是最能拉开差距的一题）：
Agent 系统里 async/await 主要用于五类场景：

| 场景 | 作用 |
|------|------|
| 并发工具调用 | 同时调搜索、数据库、RAG 检索 |
| 流式输出 | 边生成边返回 token 或事件 |
| 超时控制 | 对外部工具和模型请求设置等待时间 |
| 多 Agent 协作 | 并发执行多个子任务后汇总 |
| WebSocket/SSE | 保持连接期间持续推送中间结果 |

**示例（并行多个 Agent）**：
```python
import asyncio

async def run_agent(query):
    docs = await retrieve(query)     # 检索
    answer = await call_llm(docs)    # 调模型
    return answer

results = await asyncio.gather(
    run_agent("问题 A"),
    run_agent("问题 B"),
    run_agent("问题 C"),
)
```

**加分点**：`asyncio.gather` vs `TaskGroup`；用 `asyncio.Semaphore` 控制并发数防止打爆下游；事件循环（Event Loop）是 asyncio 的心脏。

## 15. FastAPI 启动的是什么服务？

**一句话回答**：FastAPI 是 ASGI Web 应用框架，本身不监听端口，由 ASGI 服务器（Uvicorn 等）启动运行。

**展开话术**：
1. 常见启动命令 `uvicorn main:app --host 0.0.0.0 --port 8000 --reload`：`main` 是 Python 文件名，`app` 是 FastAPI 实例，Uvicorn 负责监听端口、接收 HTTP/WebSocket 请求并调用 ASGI 应用。
2. **ASGI vs WSGI**：WSGI 是同步的、只支持 HTTP；ASGI 支持异步和 WebSocket，更适合现代 AI 应用的流式/长连接场景。
3. 常见服务器：Uvicorn、Hypercorn，或 Gunicorn + Uvicorn Worker（多进程部署）。

**加分点**：ASGI 三要素 scope / receive / send；`--reload` 只用于开发，生产环境不能开。

## 16. AI 工程中 conda 和 uv 有什么区别？

**一句话回答**：conda 管"复杂科学环境"（CUDA/PyTorch），uv 管"纯 Python 项目 + 快速依赖锁定"。

**展开话术**：
1. **conda**：跨语言包管理 + 环境管理，能装非 Python 依赖（CUDA、底层库），适合 PyTorch 等科学计算复杂环境。
2. **uv**：Rust 写的极快的 Python 包管理器（替代 pip/poetry），有锁文件、速度快，适合纯 Python 项目、FastAPI 服务、Agent 工程。
3. **现实层面（很接地气）**：大模型工程的依赖包都非常巨大，如果用 uv 每个工程都要单独一套 `.venv`，比较冗余；而 conda 可以让多个项目共享同一个环境。

**加分点**：uv 速度快是因为 Rust 实现 + 并行下载；uv 也能管 Python 版本（`uv python install`）；本质权衡是"环境隔离" vs "环境复用"。

## 17. 如何实现 SSE？

**一句话回答**：SSE 是基于 HTTP 的服务器单向推送，服务端返回 `Content-Type: text/event-stream`，持续写响应即可。

**展开话术**：
1. **原理**：普通的 HTTP 长连接，服务端不关闭连接，持续把数据写入响应体，浏览器通过 `EventSource` 接收。
2. **消息格式**：以 `data: <内容>\n\n` 为一个事件块，还支持 `event:`、`id:`、`retry:` 字段。
3. **FastAPI 实现**：用 `StreamingResponse` + 异步生成器。
4. **对比 WebSocket**：SSE 单向、基于 HTTP、可自动重连、更简单；WebSocket 双向。大模型"流式输出"场景用 SSE 就够了。

**示例**：
```python
import asyncio
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def event_stream():
    for i in range(10):
        yield f"data: {i}\n\n"
        await asyncio.sleep(1)

@app.get("/stream")
async def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**加分点**：前端 `EventSource` API；断线重连用 `Last-Event-ID`；什么时候该上 WebSocket（双向、低频高交互）。

# 1.2 LangChain & LangGraph

## 18. 什么是 LangGraph？State / Node / Edge / 条件边分别是什么？

**一句话回答**：LangGraph 是"面向 Agent 和复杂工作流的状态机框架"，把流程建模成「图」，适合多步骤、可分支、可循环、可恢复的流程。

**展开话术**（四个核心概念逐个说）：
1. **State（状态）**：整个流程共享的数据上下文，用 `TypedDict` 定义，在节点之间流转、被各节点读写。
2. **Node（节点）**：一个执行步骤，可以是模型调用、工具执行、检索、判断逻辑等。
3. **Edge（边）**：节点之间固定的流转关系（A 执行完必然去 B）。
4. **Conditional Edge（条件边）**：根据状态或节点输出，动态决定下一步走向（A 执行完后看结果决定去 B 还是 C）。

**一句话定位**：如果说 LangChain 更像"链"，LangGraph 更像"图"。它适合复杂编排，支持分支、循环、重试、暂停和恢复；而且 LangGraph 里可以直接复用 LangChain 的组件。

**加分点**：
- State 用 `TypedDict` + `Annotated` reducer 定义，解决多节点并发写同一字段的合并问题；
- `checkpointer` 做状态持久化，支持"暂停/恢复"和"时间旅行"回放；
- `Send` API 实现 map-reduce 式并行分支。

---

## 19. 什么是 LangChain？有哪些核心组件？在项目里起什么作用？

**一句话回答**：LangChain 是面向 LLM 应用编排的开发框架，解决提示词组织、模型调用、工具调用、检索增强、输出解析和链式执行这些问题。

**展开话术**（核心组件 7 类）：
1. **Models**：统一封装不同大模型的调用（OpenAI、Qwen 等一个接口）；
2. **Prompts**：管理提示词模板和变量注入；
3. **Output Parsers**：把模型输出转成结构化结果（如 JSON）；
4. **Tools**：让模型可以调用外部能力；
5. **Retrievers / VectorStores**：接检索、向量库、做 RAG；
6. **Chains**：把多个步骤串起来；
7. **Memory**：管理对话上下文。

**在项目里的作用**：更适合线性流程、单次问答、RAG 链路、工具封装这类结构较稳定的场景，

优势是上手快、组件化强、开发效率高。

**加分点**：
- 提 LCEL（`|` 运算符的链式表达式），是 LangChain 现代化写法；
- 说明 `MessagesPlaceholder`、few-shot 模板等 Prompt 细节体现用过。

## 20. LangChain 和 LangGraph 的区别是什么？分别适合什么场景？

**一句话回答**：核心区别在抽象层级和流程复杂度——LangChain 偏"线性 + 组件封装"，LangGraph 偏"状态驱动 + 复杂编排"。

**展开话术**（对照着讲）：
- **LangChain**：线性流程、组件封装、快速搭 RAG / 工具链 / 问答链，适合流程固定、分支少的场景。
- **LangGraph**：状态驱动、多分支多轮决策、Agent 工作流，适合需要循环、回退、重试、暂停恢复的场景。

**选型原则**：简单链路优先 LangChain，复杂工作流、Agent 编排优先 LangGraph。

**举例（讲得越具体越加分）**：电商小二这种偏单轮问答、工具链固定的场景，用 LangChain 就够；而掌柜智库这种涉及多路检索、判断、反复修正、状态流转的场景，用 LangGraph 更合适。

**加分点**：点明两者的关系——LangGraph 底层复用 LangChain 的组件，且现在 LangChain 官方也把 Agent 能力逐步迁移到 LangGraph 上（旧的 AgentExecutor 逐渐被取代），说明你关注框架演进。

## 21. LangGraph 和 YAML 配置工作流有什么不同？🛫

**一句话回答**：YAML 更适合"固定流程编排"，LangGraph 更适合"有状态的动态决策流程"。

**展开话术**：
1. **YAML**：声明式、固定 DAG、无状态，适合流程确定、无复杂条件分支的场景；易读易维护，非开发人员也能改流程。
2. **LangGraph**：代码驱动、状态机，支持条件边、循环、动态决策，适合 Agent"看情况决定下一步"的场景。
3. **本质区别**：YAML 是"静态编排"，LangGraph 是"动态编排 + 状态管理"。

**加分点**：什么时候选哪个——固定 pipeline（数据清洗、固定 RAG 流程）用 YAML 够用且更好维护；需要模型自主决策、循环、重试、多轮修正时用 LangGraph。可顺带提 Dify/Coze 这类平台的可视化/YAML 编排也属静态编排阵营。

> 不是一个层面的东西

## 22. 怎么避免 LangGraph 死循环？

**一句话回答**：给循环设置边界，给失败设置出口。

**展开话术**（几个层面，层层递进）：
1. **设置最大轮次**：加一个 `max_iterations` 计数，达到上限就强制结束或走兜底；
2. **把改进结果/失败结果反馈给下次处理**：把上一轮失败原因带回给模型，避免它在原地重复同样的错误；
3. **给模型明确的退出条件**：在 prompt 里写清楚"信息足够就输出最终答案"，服务挂掉也要有明确的终止路径；
4. **对工具失败设置兜底分支**：工具调用失败时走"拒答 / 降级"分支，不让流程卡死。

**一句话收尾**：循环必须有边界，失败必须有出口。

**加分点**：
- 具体做法：在 State 里放一个 `iteration_count` 字段，条件边里判断 `>= max_iterations` 就跳转到结束节点；
- 结合 `checkpointer` 做状态快照、支持超时中断；
- 把"已尝试次数 + 历史失败原因"注入 prompt，从根上减少原地打转。

# 1.3 Agent 与 RAG

## 23. Agent 是什么？和纯提示词、RAG、套壳大模型有什么区别？

**一句话回答**：Agent 是带有目标、规划、工具调用和状态管理能力的 LLM 应用，能围绕目标拆任务、调工具、读写状态，并根据执行结果继续决策。

**展开话术**（逐个对比）：
1. **纯提示词**：只靠一轮输入输出，没有外部执行能力；
2. **RAG**：重点是检索增强回答，核心是"找资料"，复杂决策能力要依赖额外流程编排；
3. **套壳大模型**：只是把聊天界面接到模型上，没有完整执行闭环。

**一句话定位**：成熟 Agent 的核心是「模型、工具、状态、流程控制、记忆、校验和兜底」这七个要素。

**加分点**：判断是不是"真 Agent"的标准——有没有「自主决策 + 外部执行 + 状态流转」的闭环。能举一个反例（只有聊天界面 = 套壳）最加分。

> 

---

## 24. 一个成熟的 Agent 架构通常包含哪些部分？

**一句话回答**：脑、手、记忆、流程四个部分。

**展开话术**（四要素）：
1. **脑（LLM / ChatModel）**：理解问题、推理下一步该做什么；
2. **手（Tools）**：可调用的外部能力，如搜索、数据库、API、计算器、RAG 检索；
3. **记忆（Memory / State）**：保存上下文、历史对话、中间步骤或业务状态，让 Agent 连续处理任务；
4. **流程（Agent Executor / Runtime）**：负责执行循环——接收任务 → 调模型思考 → 选工具 → 执行工具 → 观察结果 → 再次决策 → 输出答案。

**加分点**：把「think-act-observe」执行循环讲清楚是关键；并补充一句：成熟架构还必须有「校验 + 兜底」，避免结果不可控。

---

## 25. RAG 是什么？完整链路是什么？

**一句话回答**：RAG（Retrieval-Augmented Generation，检索增强生成）把外部知识库内容检索出来作为上下文，交给大模型生成答案。

**展开话术**（完整链路，建议张口就来）：
文档解析 → 清洗 → 切分 → 向量化 → 索引入库 → 

查询处理 → 召回 → 融合重排 → 上下文组装 → 答案生成 → 评测监控。

**加分点**：把链路拆成"离线建库（解析→入库）"和"在线检索（查询→召回→重排→生成）"两条线来讲，显得更有体系；最后补一句"评测监控是闭环，不是一次性动作"。

> 

---

## 26. 大模型为什么需要外挂知识库？RAG 和微调有什么区别？

**一句话回答**：外挂知识库补充时效性、私有领域知识和可追溯来源，同时降低训练/微调成本；RAG 解决"外部知识接入"，微调解决"改变模型行为与能力"。

**展开话术**：
1. **为什么外挂**：补充时效性知识、私有领域知识、提供可追溯来源，也降低训练和微调成本。
2. **RAG**：主要解决外部知识接入问题，知识保存在数据库、向量库或文档库中，更新知识时更新知识库即可
3. **微调**：改变模型行为、表达风格、任务格式或垂直任务能力，知识和模式进入模型参数，更新成本更高。

**加分点**：点明两者不互斥——"微调定能力、RAG 供知识"常组合使用；RAG 优势是快/可解释/易更新，微调优势是稳定风格与领域能力。

## 27. Workflow、ReAct 和 Plan-and-Execute 有什么区别？

**一句话回答**：ReAct 是"边想边做"，Workflow 是"预设流程"，Plan-and-Execute 是"先规划再执行"。

**展开话术**：
1. **ReAct**：推理和行动交替进行，适合动态工具调用、逐步探索；
2. **Workflow**：预定义节点和边，适合确定性强、稳定性要求高的业务链路；
3. **Plan-and-Execute**：先生成任务计划再逐步执行，适合较长任务、可拆解目标。

**一句话总结**：ReAct 适合开放探索，Workflow 适合稳定生产流程，Plan-and-Execute 适合复杂长任务。

**加分点**：每种配一个具体业务例子（如 ReAct 用于客服查单、Workflow 用于固定审核流、Plan-and-Execute 用于多步报告生成）。

## 28. ReAct 的结构是什么？Action 的职责是什么？

**一句话回答**：ReAct 让模型围绕"思考 → 查找 → 执行 → 观察"持续推进任务，结构是 Thought → Action → Observation 的循环。

**展开话术**：
1. **Thought**：当前如何理解问题；
2. **Action**：决定调用哪个工具（查知识库、调接口、跑 SQL、做检索）；
3. **Observation**：工具返回的结果；
4. 再进入下一轮 Thought，直到能给出最终答案。

**加分点**：强调两点——① ReAct 的价值在于"持续推进"，所以更依赖工具质量和循环控制；② Action 的职责是**输出要调的工具名 + 参数**，它本身不执行，真正执行由程序完成（呼应 Function Calling）。

## 29. Function Calling 是什么？执行机制是什么？

**一句话回答**：让模型按约定格式"选择并声明要调用的函数"，模型只输出函数名和参数，真正的执行由程序完成。

**展开话术**：
1. **本质**：模型不会执行外部函数，只会输出"要调哪个函数 + 什么参数"；
2. **执行机制** = 装饰器 + 工具映射表（把函数注册进 `tools` 字典，模型返回的函数名去映射表里找到真实函数执行）；
3. 完整闭环：模型声明调用 → 程序解析 → 执行真实函数 → 结果回填给模型 → 模型继续生成。

**示例（核心考点）**：
```python
tools = {}

def tool(func):
    tools[func.__name__] = {
        "function": func,
        "name": func.__name__,
        "description": func.__doc__,
        "parameters": func.__annotations__,
    }
    return func

@tool
def add(a: int, b: int) -> int:
    """计算两个数的和"""
    return a + b
# 等价于把 add 注册进工具表：tools["add"] = add
```

**加分点**：能讲清"声明（name + arguments）→ 解析 → 执行 → 回填"四步闭环，说明你懂的是机制不是 API。

## 30. Function Calling、MCP 和 Skill 有什么区别？

**一句话回答**：Function Calling 是"一次工具调用机制"，MCP 是"一组工具/资源的标准接入协议"，Skill 是"一类可复用能力封装"。

**展开话术**：
1. **Function Calling**：单次工具调用机制（模型选一个函数并传参）；
2. **MCP**：Model Context Protocol（模型上下文协议），一组工具或资源的标准接入方式；
3. **Skill**：一类可复用的能力封装，可以是文本、脚本、应用程序或网络服务。

**加分点**：讲清层级——Function Calling 是"调用粒度"、MCP 是"接入标准"、Skill 是"能力包"；可类比"函数 vs 协议/包 vs 插件"。

## 31. 普通 HTTP 接口怎么包装成 MCP？🛫

**一句话回答**：按能力拆接口 → 定义工具 schema → 服务端处理认证/超时/重试 → MCP server 统一暴露 → 客户端加载。

**展开话术**（五步）：
1. 按能力拆分 HTTP 接口；
2. 为每个工具定义名称、描述、参数 schema 和返回结构；
3. 在服务端处理认证、超时、重试和错误；
4. 通过 MCP server 统一暴露工具；
5. 在客户端或 Agent 运行时加载 MCP 工具。

**核心要点**：模型侧看到的是**标准化工具**，接口细节（认证、重试、URL）全部被 MCP server 屏蔽。

**加分点**：能结合代码讲——服务端用 `FastMCP` + `httpx` 封装，调用端用 `MultiServerMCPClient` 的 `get_tools()` 拿工具再挂到 Agent 上，体现"真做过"。

## 32. 单个 Agent 挂载大量工具时，如何解决上下文超限和工具误调用？

**一句话回答**：把大 Agent 拆成多个小 Agent，每个只带自己的工具，通过意图识别路由选择不同 Agent。

**展开话术**：
1. **问题根源**：工具太多 → 工具描述占满上下文窗口 + 模型选错工具的概率上升；
2. **主解法**：大 Agent 拆小，每个小 Agent 只挂自己的工具，意图识别路由分发；
3. **补充手段**：工具分组、按需动态加载工具描述、检索式工具选择（先根据任务召回相关工具，而不是全量塞进 prompt）。

**加分点**：主动点明"路由式多智能体"就是天然解法，呼应多智能体章节，体现整体思路。

## 33. 大模型无法稳定输出结构化 JSON 时如何解决？

**一句话回答**：三招——预定义结构做填空、用官方 JSON schema 输出、加校验退回重试。

**展开话术**：
1. **预定义结构**：给模型一个骨架让它"做完形填空"，而不是自由生成；
2. **官方结构化输出**：部分模型支持 JSON schema 输出（`response_format` / structured output），注意配置；
3. **校验 + 重试**：加校验环节，校验不通过就把错误和上下文重新发给模型改正。

**加分点**：结构化输出的本质是「约束 + 校验 + 重试」的闭环，不是靠祈祷；可提 `json_repair`、Pydantic 校验等落地手段。

## 34. Agent 记忆怎么设计？短期记忆和长期记忆分别解决什么问题？

**一句话回答**：短期记忆存对话状态对象（当前窗口 + 最近几轮），长期记忆存 MongoDB/MySQL/向量库（用户偏好、历史事实、画像）。

**展开话术**：
1. **短期记忆**：保存当前对话窗口和最近几轮上下文，解决代词指代、条件延续、当前任务连续性；
2. **长期记忆**：保存用户偏好、历史事实、长期画像、可复用知识，支持跨会话复用。

**加分点**：讲清存储选型——短期放内存/状态对象（随会话销毁），长期放持久化存储 + 向量库做语义召回（跨会话持久）。

## 35. LangChain 中常见记忆类型有哪些？

**一句话回答**：五种——Buffer、BufferWindow、Summary、VectorStoreRetriever、KnowledgeGraph。

## 36. Token 优化怎么做？

**一句话回答**：少塞、少存、少重复、少调用。

**展开话术**：
1. 去除寒暄、重复内容和无效确认（通过改写问题完成）；
2. 控制历史对话数量，长期记忆通过向量总结 + 向量召回；
3. 优化提示词模板，减少无用冗余词句；
4. 在保证召回率的前提下优化 topK测率（注意有风险）；
5. 利用 FAQ 和缓存减少调用 LLM 的次数。

**加分点**：把优化归结为两条线——「减少输入 token（清洗/摘要/截断）」+「减少调用次数（缓存/FAQ/小模型路由）」，比零散罗列更有体系。

## 37. 提示词如何管理和热更新？

**一句话回答**：提示词放配置中心 + 缓存读取，更新后失效缓存。

**展开话术**：
1. 提示词放在变量或缓存中，没有再走配置读取；

3. 更新数据库中的提示词后，立即失效缓存，下次读取即生效。

**加分点**：配置中心 + 缓存 + 失效机制 = 热更新；可补提版本管理、灰度发布、A/B 测试提示词。

## 38. 怎么避免幻觉、复读机和格式不稳定？

**一句话回答**：按"原因 → 对策"逐个排查，而不是笼统说"加约束"。

**展开话术**：
1. **幻觉**（按可能原因排查）：① 证据没召回 → 查 RAG 流程，定位证据丢失节点；② 证据太多稀释真相 → 优化切片保留长度和个数；③ 提示词约束不足；④ 模型能力不足。
2. **复读机**：与模型能力有关，现在的大模型出现概率不高；小模型频繁出现时，加重复词检测、及时终止。
3. **格式不稳定**：① 用官方模型的 JSON 格式选项；② 加提示词约束 + 给出明确示例；③ 加 JSON 校验，格式有问题就退回重试。

**加分点**：强调"先定位原因再对症"——幻觉要区分是召回问题、切片问题、约束问题还是模型问题，这是面试官最想听的分析框架。

## 39. 什么是多智能体？什么场景下需要多智能体？

## 41. 多智能体如何做任务规划、协调和编排？

**一句话回答**：分两层看——"谁协调任务"和"任务怎么执行"。

**展开话术**：
1. **谁来协调**：
   - 路由式：按任务类型分配给合适的 Agent；
   - 主控式：主 Agent 拆解分派任务，子 Agent 执行后返回，主 Agent 汇总；
   - 交接式：当前 Agent 把处理权交给另一个 Agent，接收方继续负责。
2. **怎么执行**：
   - 流水线：有依赖的任务顺序执行（如"收集 → 撰写 → 审核"）；
   - 并行汇总：独立任务同时执行，最后合并结果。

**加分点**：核心是明确"任务怎么拆、谁来做、先后关系、结果交给谁"，并由程序管理状态、异常和结束条件；三种协调方式可组合使用。

## 44. 子 Agent 故障如何隔离和降级？

**加分点**：选型维度——数据规模、是否已有 PG、运维能力、数据安全合规；能按项目体量给结论最加分。

## 54. 什么是向量？维度和相似度怎么理解？

**一句话回答**：向量 = 文字的"语义坐标"，维度 = 坐标长度，相似度 = 坐标间的距离。

**展开话术**：
1. **向量**：把一段文字变成一串数字，相当于文字的"语义坐标"，意思越接近坐标越接近；
2. **维度**：这串数字的长度（如 768 维），维度越高表达通常越细致，但计算和存储成本也越高；
3. **相似度**：衡量两个向量多接近，分数越高表示两段文字含义越相似。

**加分点**：相似度的算法——余弦相似度、点积、欧氏距离；embedding 模型维度选择是精度与成本的权衡。

## 55. 自动化评估怎么做？准确率怎么计算？

**一句话回答**：准备问题集 → 写 RAGAS 评估程序 → 跑指标 → 分析 bad case → 优化 → 再评估。

**展开话术**（五步闭环）：
1. 准备问题集；
2. 基于 RAGAS 编写评估程序；
3. 运行评估，观察指标；
4. 找到 bad case 分析优化；
5. 再次评估。

**指标公式**：
- 准确率 = 上下文中与期望答案相关的条数 / 总上下文条数；
- 召回率 = 期望答案且被上下文覆盖的事实点个数 / 期望答案的事实点个数。

**加分点**：准确率 vs 召回率要分清；强调评估是闭环、不是一次性动作。

## 56. 测试集怎么来？

**一句话回答**：真实历史对话 + 业务人员编写 + AI 生成自测。

**展开话术**：
1. 真实历史对话记录（最可靠）；
2. 专业业务人员编写；
3. AI 生成可用于自测。

**加分点**：AI 生成只能自测、不能当权威评测集；真实数据最贴近线上分布。

## 57. bad case 怎么收集、分析和优化？

**一句话回答**：线上靠用户负反馈，测试靠 RAGAS 低分，然后追日志定位环节、修改。

**展开话术**：
1. **线上**：通过用户交互动作收集（AI 拒答、点"无帮助"、转人工）→ 模拟重跑问题 → 分析召回情况 → 追日志定位流程 → 修改；
2. **测试**：RAGAS 评分低（正确性/召回率低）的作为 bad case → 分析原因 → 追查各环节日志 → 定位修改。

**加分点**：定位时区分"召回问题 / 排序问题 / 生成问题"，分别对应不同环节，而不是笼统说"改提示词"。

## 58. RAGAS 是什么？RAG 评估指标有哪些？

**一句话回答**：RAGAS 是开源 RAG 评估框架，评检索质量、生成质量、答案与上下文的一致性。

**展开话术**（常见指标）：
1. **Context Recall**：标准相关内容是否被召回；
2. **Context Precision**：召回内容中有多少是真正相关的；
3. **Answer Relevance**：生成与用户问题的相关程度；
4. **Faithfulness**：答案是否忠实于给定上下文。

```
	Context Recall：标准相关内容是否被召回
	Context Precision：召回内容中有多少是真正相关的
	Answer Relevance：生成与用户问题的相关程度
	Faithfulness：答案是否忠实于给定上下文
	Answer Relevance：答案是否回答用户问题

```

**核心观点**：RAG 评估要同时看检索、重排、生成，只看最终回答准确率，定位不了是召回问题、排序问题还是生成问题。

**加分点**：把指标归成三类——检索质量（Recall/Precision）、生成质量（Relevance）、一致性（Faithfulness），并说出"定位到环节"的价值。

## 59. AI Agent 权限控制机制如何设计？

**一句话回答**：知识管理平台做权限管理，对知识单元按人员/角色/部门分配权限，Agent 查询时校验。

**展开话术**：
1. 知识管理平台具备权限管理能力，对知识单元实现人员、角色、部门的权限分配；
2. Agent 查询知识单元内容时做权限校验（数据行级权限）。

**加分点**：RAG 场景下"权限 + 召回"的结合是关键——检索时注入权限条件或检索后做权限过滤（post-filter），防止越权读到不该看的知识。

## 60. Agent 系统延迟高时如何优化？

**一句话回答**：按链路拆分统计耗时，定位瓶颈后处理。

**展开话术**（优化项）：
1. **模型调用**：减少模型调用次数、充分用缓存和 FAQ、用大小模型路由；
2. **工具调用**：慢工具设超时和降级；
3. **上下文**：优化历史消息和上下文长度（谨慎，别伤质量）；
4. **交互体验**：流式输出、增加处理进度。

**加分点**：先测再优——对链路打点统计各环节耗时，定位到具体瓶颈；提 TTFT（首字延迟）概念，流式输出主要降的是"感知延迟"。

## 61. 系统上线前如何判断符合生产要求？上线后如何迭代？

**一句话回答**：上线前看效果、稳定性、安全性、可观测性；上线后看板监控 + 复盘 bad case + 更新知识库和测试集。

**展开话术**：
1. **上线标准**：RAGAS 评分、TTFT 压测、任务完成率；
2. **上线后迭代**：看板监控、复盘 bad case、更新知识库和测试集。

**加分点**：生产四维度（效果 / 稳定 / 安全 / 可观测）能展开讲，并强调"上线不是终点，靠数据闭环持续迭代"。
