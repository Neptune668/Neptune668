## 1. 项目介绍与背景（Q1–Q8）

### Q1 用 30 秒介绍一下这个项目

> 考察：表达结构、项目全貌 ｜ 频率：必问

**参考答案（直接背）**

> 掌柜智库是一个面向电商商品资料的知识库问答系统，服务客服、运营和业务人员。用户上传 PDF、Word、Markdown 后，系统用 MinerU 解析成 Markdown，处理图片和表格，按标题层级切片，再用 BGE-M3 生成稠密和稀疏向量写入 Milvus。查询时先做商品名确认和问题改写，再并行走向量检索、HyDE 和 MCP 网络检索三路召回，经过 RRF 融合、BGE-Reranker 精排和断崖截断，最后由大模型基于检索上下文生成答案，通过 SSE 流式返回。我负责后端 RAG 核心链路。

**追问**：你说的「核心链路」具体包括哪些节点？→ 直接接 Q2。

### Q2 用 2 分钟讲一下项目和你负责的部分

> 考察：结构感、个人贡献边界 ｜ 频率：必问

**参考答案（四段式）**

> 我按背景、方案、职责、结果四块讲。
>
> **背景**：商品资料分散在 PDF、Word、图片和表格里，客服查一个参数要翻几十页手册，新人上手慢，回答口径还不统一。
>
> **方案**：系统分存储和查询两条链路。存储侧把非结构化文档统一成 Markdown，做图片摘要、表格线性化、标题切片、商品名识别和 BGE-M3 向量化，落到 Milvus 和 MinIO；查询侧先做商品名确认和问题改写，再多路召回、RRF 融合、Rerank 精排、断崖截断，最后交给大模型生成并流式返回。
>
> **职责**：我主要负责后端 RAG 链路，包括导入编排、DocumentSplitNode、商品名识别、切片向量化、Milvus 入库、商品名确认、多路召回、RRF、Rerank、答案生成和 SSE。接口层和任务状态也参与了一部分。
>
> **结果**：核心手册类问题的召回和答案稳定性达到可用水平，形成了一套可以持续用 bad case 迭代的工程链路。

**加分**：最后补一句「这个项目对我最大的锻炼，是把 RAG 从 demo 做成了有状态、可观测、可回滚的工程系统」。

**踩坑**：不要一上来讲模型参数，面试官不关心 35B 还是 72B，先讲问题和链路。

### Q3 这个项目解决什么问题？用户是谁？

> 考察：业务理解 ｜ 频率：高

**参考答案**

- **用户**：客服、运营、业务/售后人员，以及需要查产品手册的内部员工。
- **痛点**：
  1. 资料分散：PDF、Word、图片、表格、扫描件混在一起；
  2. 检索靠人：按目录翻页、Ctrl+F 找关键词，长文档效率低；
  3. 回答不一致：不同客服对同一参数说法不同，新人培训成本高；
  4. 知识难复用：文档更新后，经验留在个人手里。
- **系统做的事**：把非结构化资料沉淀成可检索、可追溯、可复用的知识库，用自然语言提问，答案带出处。

**追问**：为什么不用关键词搜索？→ 用户问的是「这个型号报 E3 怎么处理」，关键词匹配不到「故障代码」和「处理方法」之间的语义关系；而且用户经常不带型号，需要先确认商品。

### Q4 业务价值怎么衡量？上线后看哪些指标？

> 考察：是否只关注技术指标 ｜ 频率：高

**参考答案**

分三层：

| 层级 | 指标 | 说明 |
|---|---|---|
| 检索层 | Recall@K、context_precision、context_recall | 证据有没有被召回、噪声多不多 |
| 答案层 | answer_correctness、faithfulness、answer_relevancy | 答得对不对、有没有幻觉、切不切题 |
| 业务层 | 追问率、转人工率、首次解决率、平均处理时长、bad case 数、用户负反馈率 | 是否真的省了人工 |

**话术**：「技术指标用于定位问题，业务指标用于证明价值。上线后我重点看追问率和转人工率，因为这两个最能反映答案有没有解决问题。」

**踩坑**：不要编「效率提升 60%」这种没有口径的数字；如果要说，必须能说清对比基线、样本和时间范围。

### Q5 这个项目最大的难点是什么？

> 考察：技术深度、是否真踩过坑 ｜ 频率：必问

**参考答案（四类难点 + 一类工程难点）**

1. **复杂 PDF 的解析与图片语义补全**：阅读顺序、多栏、跨页表格、扫描件，图片本身不进文本，需要 VLM 生成 caption。
2. **切片粒度控制**：切大了关键信息被稀释、rerank 忽略；切小了上下文断裂、指代丢失。
3. **多路召回结果的融合**：不同召回源分数不可比，还要去重、控制成本、保证多样性。
4. **答案准确性控制**：检索到了不等于答对，要处理幻觉、拒答、引用和口径。
5. **工程化**：异步导入、任务进度、失败重试、幂等更新、SSE 流式、Milvus 一致性。

**加分**：补一句「最难的其实不是单个算法，而是让整条链路可观测——出了问题能定位到是解析、切片、召回还是生成。」

### Q8 这个项目最大的亮点是什么？

> 考察：总结能力、能否说到点上 ｜ 频率：高

**参考答案**

> 亮点不是用了多少模型，而是把 RAG 做成了工程闭环，具体有三点：

## 2. 架构与技术选型（Q9–Q18）

### Q9 画一下整体架构，分几层？

> 考察：系统全貌 ｜ 频率：必问

**参考答案**

```
接入层    FastAPI（导入接口 / 查询接口 / SSE / 状态查询）
编排层    LangGraph（ImportGraph / QueryGraph）
能力层    MinerU 解析｜VLM 图片摘要｜BGE-M3 向量化｜BGE-Reranker 精排
          LLM 生成/改写/HyDE｜MCP 网络检索
存储层    MinIO（原文件、图片）｜Milvus（商品名向量、chunk 向量）
          MongoDB（会话历史、任务记录）
观测层    Prometheus + Grafana + 结构化 trace 日志
```

**讲法**：先讲「两条链路、三层存储」，再讲「编排层把长任务和在线请求分开」。

**追问**：为什么任务记录放 MongoDB 不放 MySQL？→ 见 Q15，承认初期选型偏灵活，后续管理台会迁 MySQL。

### Q10 为什么用 FastAPI？

> 考察：Web 框架理解 ｜ 频率：中

**参考答案**

- **异步 IO**：RAG 链路大量等待 Milvus、MongoDB、LLM HTTP、MCP，`async/await` 能用少量线程撑住并发。
- **SSE 友好**：`StreamingResponse` 直接对接流式生成。
- **工程效率**：Pydantic 做请求校验，自动生成 OpenAPI，前后端联调成本低。
- **生态**：LangGraph、Milvus、MongoDB 的 Python SDK 都是一等公民。
- **对比**：Flask 偏同步、生态老；Django 重，ORM/Admin 用不上。

**加分**：主动说坑——「同步阻塞调用（比如某些 SDK）要放线程池，否则会卡住 event loop；我们给 Milvus 和 Mongo 的调用都做了 async 封装或 `run_in_threadpool`。」

---

### Q11 为什么用 LangGraph？普通函数串起来不行吗？

> 考察：编排框架理解 ｜ 频率：高

**参考答案**

- **显式状态**：`ImportGraphState` / `QueryGraphState` 定义清楚每个节点读写什么，避免隐式全局变量。
- **条件路由**：按文档类型分流 PDF/Markdown，按商品名确认结果分流「确认/候选/追问」。
- **并行 fan-out/fan-in**：`multi_search` 同时发三路召回，再 join。
- **可观测**：每个节点有输入输出和耗时，bad case 能定位到节点。
- **可恢复**：配合 checkpoint，导入失败可以从节点重试，不用整单重跑。

**对比**：手写 pipeline 也能做，但状态传递、异常处理、并行、重试这些会重复造轮子；Airflow 这类 DAG 是批调度，不适合秒级在线请求。

**追问**：LangGraph 的 checkpoint 用的什么？→ ⚙️ 开发期 MemorySaver，生产可换 Redis/Postgres；导入任务把关键状态落 MongoDB，避免进程重启丢任务。

### Q12 为什么导入和查询要拆成两个图？

> 考察：架构边界 ｜ 频率：中

**参考答案**

| 维度 | ImportGraph | QueryGraph |
|---|---|---|
| 触发 | 用户上传，后台异步 | 用户提问，在线同步/流式 |
| 耗时 | 分钟级 | 秒级 |
| 状态 | 有任务状态、可重试、可断点 | 基本无状态，一次请求内完成 |
| 失败语义 | 标记 task failed，可重跑 | 返回兜底/降级，不污染任务 |
| 资源 | GPU 解析、embedding 批量 | LLM、向量检索、rerank |

拆开以后，导入高峰不会挤占在线查询，查询的延迟优化也不会被导入的长事务拖累。

**追问**：两条图共用什么？→ 共用 Milvus、MinIO、MongoDB 和模型服务；商品名识别逻辑可以复用，但 prompt 和批量策略不同。

### Q13 为什么选 Milvus，而不是 ES、Qdrant 或 pgvector？

> 考察：选型判断 ｜ 频率：必问

**参考答案**

选 Milvus 主要四个原因：

1. **原生向量 + 稀疏向量 + 标量过滤**：BGE-M3 的 dense/sparse 可以放在一个集合里做混合检索，`item_name` 直接做标量过滤。
2. **存算分离**：底层用 MinIO 持久化，计算节点无状态，扩容和备份都简单。
3. **规模与生态**：百万到亿级向量有成熟的索引（HNSW/IVF），分区、分区键、多副本都支持。
4. **团队与业务匹配**：商品资料以语义匹配为主，Milvus 更聚焦；MinIO 还能同时存原文件和图片。

对比：

- **ES**：全文/BM25 强，向量是后加的能力，混合排序和资源开销不如 Milvus 自然；如果业务以关键词精确匹配为主，ES 更合适。
- **Qdrant**：轻量、API 好用，但存算分离和生态不如 Milvus，团队已有 Milvus 经验。
- **pgvector**：事务和运维最简单，但百万级以上索引构建、过滤后召回的性能和扩展性有限。

**加分**：主动说代价——「Milvus 组件多（etcd、MinIO、消息队列），运维比 pgvector 重；数据量不大时其实是过度设计，我们看中的是长期演进。」

**追问**：什么时候会换 ES？→ 当业务需要复杂的全文检索、聚合分析、权限过滤组合时，可以考虑 ES 或 Milvus + ES 双写。

### Q14 MinIO 在项目里做什么？为什么不用本地磁盘？

> 考察：对象存储理解 ｜ 频率：中

**参考答案**

- 存三类对象：原始 PDF/Word/Markdown、解析出的图片、Milvus 的底层 segment/索引文件。
- 用 S3 兼容接口，应用通过 URL 访问，前端展示图片不用经过后端转发。
- 本地磁盘的问题：多副本难、容器漂移后路径丢失、备份和扩容麻烦、Milvus 也不好做存算分离。
- MinIO 支持生命周期、版本、预签名 URL，适合这种「文件多、单文件大、读多写少」的场景。

**追问**：图片 URL 是公开还是预签名？→ ⚙️ 内部知识库用预签名 URL，设置过期时间；如果前端要长期展示，走网关代理或 CDN，避免 bucket 公开。

### Q15 MongoDB 存什么？为什么不用 MySQL 或 Redis？

> 考察：存储选型 ｜ 频率：中

**参考答案**

- 存会话历史：`session_id`、`task_id`、`role`、`content`、`item_names`、`created_at`，按 `session_id + created_at` 建索引。
- 也存任务记录/节点进度（或部分放 MySQL，按实际）。
- **为什么 MongoDB**：多轮对话是文档型数据，字段会演进（比如后来加的 `item_names` 回填），schema 灵活；按 session 查询也自然。
- **为什么不用 Redis**：Redis 是缓存，持久化、审计、复杂查询弱，历史要可追溯。
- **为什么不用 MySQL**：不是不能，初期快速迭代选了 Mongo；后续做管理台、统计报表会迁 MySQL，Milvus 只留索引。

**加分**：主动说「这是初期选型，不是最优解；如果重做，元数据用 MySQL，会话热数据放 Redis，冷数据归档。」

### Q16 怎么理解 Milvus 的存算分离？

> 考察：向量库架构 ｜ 频率：中

**参考答案**

- Milvus 的计算节点（Proxy、Query Node、Data Node）基本无状态，数据持久化在对象存储（MinIO/S3），元数据在 etcd。
- 扩容计算节点不影响数据；存储可以独立弹性扩容；故障恢复靠对象存储重新加载。
- 好处：容量大、成本低、备份简单、计算按需扩。
- 代价：冷启动/首次加载慢，查询依赖网络 IO，需要把热点索引驻留内存；一致性上要接受「写入后短暂不可查」。

**追问**：你们遇到过量数据延迟吗？→ ⚙️ 导入后做 flush/load 并轮询 `load_state`，确认可查再标记任务完成；查询侧对刚导入的数据做短暂兜底提示。

### Q17 为什么没用 Kubernetes？

> 考察：工程判断，不盲目追新技术 ｜ 频率：高

**参考答案**

- 当前规模就 2 台应用机 + 1 台中间件 + 1 台 GPU，Docker Compose 足够，交付和排障成本最低。
- K8s 的价值在多副本、弹性伸缩、灰度发布、复杂服务治理；这些在当前 QPS 下不是瓶颈。
- 团队没有专职运维，上 K8s 的隐性成本（网络、存储、监控、升级）比收益高。
- 迁移触发条件：QPS 上来、发布频率变高、需要弹性扩缩容、服务数量变多。

**加分**：「我们先用 Nginx 做多副本负载均衡，用 Compose 的 healthcheck + restart 做基础自愈，等这些不够了再上 K8s。」

---

### Q18 如果让你重新设计这个系统，会改什么？

> 考察：反思能力、架构演进 ｜ 频率：高

**参考答案（按优先级）**

1. **元数据与索引分离**：文档、切片、任务、版本存 MySQL/PostgreSQL，Milvus 只存向量和必要标量，管理台好做。
2. **版本管理与灰度**：新版本先导入为「未生效」，全量成功后原子切换，旧版本标记「作废」，避免导入中途被查询。
3. **缓存体系**：FAQ 缓存、商品名缓存、语义缓存，减少 LLM 和 embedding 调用。
4. **异步任务队列**：用 Celery/RQ/Kafka 替代 FastAPI BackgroundTasks，支持重试、死信、削峰。
5. **模型网关**：统一路由、限流、超时、降级、成本统计。
6. **评测自动化**：每次改动跑固定问题集，输出 RAGAS 指标和 diff。
7. **可观测**：OpenTelemetry 全链路 trace，节点级耗时和 token 统计。

**话术**：「这些不是推翻重来，而是把现在的临时方案工程化。」

## 3. 文档导入与解析（Q19–Q30）

### Q19 文档导入的完整流程是什么？

> 考察：链路熟悉度 ｜ 频率：必问

**参考答案（按顺序背）**

1. 前端上传 PDF/Word/Markdown，FastAPI 创建 `task_id`，返回给前端。
2. `ImportFileService` 把原文件存到本地任务目录，再归档到 MinIO。
3. `TaskService` 记录任务状态：上传中 → 处理中 → 完成/失败。
4. 后台启动 LangGraph，把 `task_id`、`file_dir`、`import_file_path` 放进 `ImportGraphState`。
5. 入口节点判断类型：PDF 走 MinerU 转 Markdown；Markdown 直接读取。
6. 图片节点：扫描 Markdown 图片引用，取上下文，调 VLM 生成摘要，上传 MinIO，替换链接。
7. `DocumentSplitNode`：按标题层级切片，表格线性化，长切短并，保留元数据。
8. 商品名识别：取前几个 chunk + 文件标题，调 LLM 抽 `item_name`，生成商品名向量写入商品名集合，并回填到 chunk。
9. 切片向量化：`item_name + content` 拼成 embedding 内容，batch 调 BGE-M3 生成 dense/sparse。
10. Milvus 入库：创建/复用 chunks 集合和索引，批量插入，更新任务状态为完成。

**追问**：哪一步最容易失败？→ MinerU 解析（超时/格式异常）和 embedding（GPU OOM/超时）；所以任务要按节点记录状态，支持从失败节点重试。

---

### Q20 导入任务的状态机怎么设计？失败怎么恢复？

> 考察：长任务工程化 ｜ 频率：高

**参考答案**

- 状态：`pending → uploaded → parsing → splitting → embedding → indexing → success`，任一环节失败置 `failed` 并记录 `failed_node`、`error_msg`。
- 进度：任务表里存节点列表和当前节点，前端轮询 `/status/{task_id}` 展示。
- 幂等：以 `task_id` 为幂等键；重复提交同一文件用 sha256 识别。
- 重试：失败任务支持「从失败节点重试」，已完成的节点不重跑；MinerU 产物落盘，重试不用重新解析。
- 清理：失败任务保留原文件和中间产物一段时间，方便排查；成功后可清理临时目录。

**追问**：进程重启了怎么办？→ 任务状态在 MongoDB/MySQL，启动时扫「处理中」的孤儿任务，标记失败或重新入队；不能只靠内存里的 BackgroundTasks。

---

### Q21 PDF 为什么要用 MinerU？和 PyPDF、pdfplumber 有什么区别？

> 考察：PDF 解析的坑 ｜ 频率：必问

**参考答案**

- **PyPDF**：只能按内容流抽文本，阅读顺序、分栏、表格、图片位置都很难保证；产品手册里经常出现「左文右图」，抽出来是乱的。
- **pdfplumber**：表格和坐标能力强，但整篇文档的结构化（标题层级、阅读顺序、图片引用）要自己写大量规则。
- **MinerU**：面向文档解析，做版面分析、阅读顺序、表格识别（输出 HTML）、公式识别、OCR，直接产出 Markdown + images + content_list，省掉大量后处理。
- 代价：需要 GPU、解析慢、复杂公式/表格仍会出错，所以后面要有清洗和抽检。

**话术**：「MinerU 不是万能，但它把 80% 的脏活干了，我们只需要处理剩下的 20%。」

---

### Q22 MinerU 和 VLM 图片识别有什么区别？为什么不用 VLM 直接解析整份 PDF？

> 考察：工具边界 ｜ 频率：高

**参考答案**

- **MinerU 负责结构**：把 PDF 拆成文本、标题、表格、图片引用，图片只保留引用，不做语义解读。
- **VLM 负责语义**：看懂图片内容，生成标题/摘要，让图片能以文本形式参与检索。
- **不用 VLM 解析整份 PDF 的原因**：
  1. 成本和延迟高，几百页文档不现实；
  2. VLM 会「脑补」，长文档容易漏内容、改数字；
  3. 版面顺序、表格结构还是专用解析器更稳。
- 组合方式：MinerU 出结构，VLM 只处理图片和极复杂版面。

**追问**：图片摘要会不会引入幻觉？→ 会，所以 prompt 要求「只描述图中可见信息，不推测」，摘要里保留型号/参数原文，低置信度图片标记人工复核。

---

### Q23 图片内容是怎么处理的？上下文怎么取？

> 考察：多模态入库细节 ｜ 频率：必问

**参考答案**

1. 扫描 Markdown 里的 `![...](images/xxx.png)` 引用。
2. 取上下文：图片所在章节标题、前一段、后一段，拼成 context；如果图片有图注，优先用图注。
3. Prompt 要求 VLM 输出：图片类型（示意图/接线图/参数表/故障图）、关键对象、型号/参数/警告信息，2–4 句话。
4. 图片上传 MinIO，得到 URL；Markdown 替换为 `![摘要](URL)`，摘要同时作为文本保留。
5. 后续切片时，图片摘要作为所在段落的一部分参与 embedding 和检索；答案里带 URL，前端可以展示原图。

**追问**：一张图有多重要？→ 维修手册里的接线图、故障图，文本往往只有「如下图所示」，不补 caption 等于这段知识丢了。

---

### Q24 Markdown 里的图片链接怎么替换？URL 怎么管理？

> 考察：存储与引用 ｜ 频率：中

**参考答案**

- 路径：`bucket/task_id/images/xxx.png`，按任务隔离，方便清理和追溯。
- 替换：本地相对路径 → MinIO 对象 URL；alt 文本用 VLM 摘要。
- 访问：内部系统用预签名 URL（有过期时间），或通过后端网关代理；不建议 bucket 公开。
- 一致性：先上传成功再改 Markdown，失败则保留本地引用并记录告警，避免出现死链。

**追问**：URL 过期了怎么办？→ 前端每次从接口拿最新签名 URL，或后端代理；不要把过期 URL 写进长期存储的答案里。

---

### Q25 表格是怎么提取和处理的？为什么要线性化？

> 考察：表格处理 ｜ 频率：必问

**参考答案**

- MinerU 把 PDF 表格转成 HTML `<table>`，保留行列和合并单元格信息。
- 切片前做**线性化**：解析 DOM，展开 `rowspan/colspan`，用表头映射每一行，转成自然语言。

示例：

```html
<table>
  <tr><th>型号</th><th>电压</th><th>功率</th></tr>
  <tr><td>X100</td><td>220V</td><td>1500W</td></tr>
</table>
```

线性化后：

> 型号 X100：电压 220V，功率 1500W。

- 为什么要做：
  1. LLM 对 HTML 表格的 token 消耗高，且容易看错行列；
  2. 向量检索对「型号 + 参数」的自然语言更敏感；
  3. 合并单元格展开后，语义不会丢。
- 长表格按行分组切，每组重复表头；表格标题保留在 chunk 开头。

**追问**：合并单元格怎么展开？→ 解析时记录每个单元格的 `rowspan/colspan`，生成二维矩阵，再按列取表头；跨行表头做层级拼接（如「电压/额定」）。

---

### Q26 跨页大表格、跨页图片怎么处理？

> 考察：边界情况 ｜ 频率：中

**参考答案**

- MinerU 支持跨页表格合并；解析后检查表头是否重复、列数是否一致。
- 如果没合并成功：按「相同表头 + 相邻页 + 列数一致」做规则合并；合并后在表格前标注「跨第 X–Y 页」。
- 图片跨页：保留首现页的引用，caption 里注明跨页；必要时用 VLM 对整页重新识别。
- 切片时表格不按字符硬切，按行分组，每组重复表头，避免「后半张表没有列名」。

**追问**：合并错了怎么办？→ 记录解析置信度，低置信度的表格进人工复核队列；线上答案里保留页码，方便回查原文。

---

### Q27 扫描件、低质量 PDF 怎么解析？

> 考察：OCR 与兜底 ｜ 频率：中

**参考答案**

- 先判断是否扫描件：文本层为空或字符数异常少。
- 走 OCR（MinerU 内置 PaddleOCR）：先做图像预处理（去噪、纠偏、增强），再识别。
- 识别质量用置信度和字符分布评估；低置信度的页用 VLM 兜底，或标记「识别质量低，建议人工复核」。
- 入库时保留页码和原图，答案里引用时提示「来自扫描页，建议核对原文」。
- 对关键参数（型号、电压、故障码）做正则校验，识别结果和词典比对。

**追问**：为什么不全部用 VLM？→ 成本和稳定性；OCR 对规整印刷体更便宜，VLM 只处理复杂页。

---

### Q28 多栏、图文错位、左文右图怎么保证阅读顺序？

> 考察：版面理解 ｜ 频率：中

**参考答案**

- 依赖 MinerU 的版面分析模型：检测标题、正文、表格、图片、页眉页脚，再按阅读顺序排序。
- 多栏：先按列切分，再按栏内从上到下、从左到右排序；跨栏标题单独处理。
- 图文错位：用 bbox 坐标判断图片和段落的相对位置，把图片挂到最近的段落/标题下，而不是按文件流顺序。
- 工业文档「大片图片 + 简短编号」：优先保留编号和图片的对应关系，caption 里带上编号。
- 建立一批「版面复杂」的回归样本，每次换解析器版本都跑一遍。

**追问**：怎么评估阅读顺序对不对？→ 人工抽检 + 用「段落首尾是否连贯」做自动指标；更实际的是看下游检索命中率。

---

### Q29 导入阶段的脏数据怎么清洗？

> 考察：数据质量 ｜ 频率：高

**参考答案**

- **页眉页脚/页码**：重复出现的短行，按位置和频率识别后删除。
- **水印/乱码**：控制字符、零宽字符、重复标点、异常空格，正则清洗。
- **公式/特殊符号**：MinerU 转换后经常出现乱码，建立规则白名单，保留型号、单位、希腊字母，其余替换或删除。
- **重复段落**：连续重复行去重；跨页重复的标题只保留一次。
- **断行/连字符**：英文单词断行合并，中文断行按标点判断是否拼接。
- **目录/封面**：目录页对检索价值低，可单独标记或跳过。

**话术**：「清洗规则不是拍脑袋，是拿 bad case 反推的；每加一条规则，都用同一批文档做 diff，避免误删。」

---

### Q30 文档怎么做去重？更新时切片和索引怎么处理？

> 考察：幂等与版本 ｜ 频率：必问

**参考答案**

- **当前做法（幂等更新）**：以 `item_name` 为业务键，更新时先删除该商品名下的旧向量，再重新切片、向量化、写入。好处是简单，坏处是导入中途查询会看到空窗。
- **去重**：文件 sha256 识别完全相同文件，提醒用户「已存在」；商品名相同但内容不同，走覆盖更新。
- **进阶（版本管理）**：
  1. 新版本导入时标记 `staging`，不参与查询；
  2. 全量成功后原子切换 `active`，旧版本标记 `obsolete`；
  3. 查询只过滤 `status = active`；
  4. 支持回滚到上一版本。
- **再进阶**：按 chunk 做增量 diff，只重算变化的切片，减少 embedding 成本。

**追问**：删除旧向量时查询正好进来怎么办？→ 当前是双写/短空窗，靠「先写新、再切别名、最后删旧」解决；Milvus 可以用 partition 或 alias 做切换。

## 4. 切片与上下文（Q31–Q40）

### Q31 文档切片是怎么做的？

> 考察：RAG 基本功 ｜ 频率：必问

**参考答案**

1. **按标题切**：解析 Markdown 的 1–6 级标题，先切成章节树。
2. **按长度递归切**：章节超过最大长度（1200 字符），按段落 → 句子递归切。
3. **短块合并**：小于最小长度（300 字符）的块，在同父标题下和相邻块合并。
4. **重叠**：块之间保留 1 句 overlap，缓解边界语义断裂。
5. **表格特殊处理**：线性化后按行分组，超长表格重复表头。
6. **元数据**：每个 chunk 保留 `chunk_id`、`title`、`parent_title`、`file_title`、`item_name`、`page`、`parent_chunk_id`。

**追问**：为什么先按标题而不是先按长度？→ 标题是作者给的语义边界，先按标题能保证一个 chunk 不跨主题；长度只是兜底。

---

### Q32 切片长度阈值为什么是 1200 和 300？

> 考察：参数依据 ｜ 频率：必问

**参考答案**

- **上限 1200 字符**：控制单个 chunk 的信息密度，避免检索和 rerank 时关键信息被稀释。之前设过 2000，发现 rerank 经常忽略关键句，答案质量下降。
- **下限 300 字符**：避免 chunk 太碎、缺上下文；小于阈值的块和同父标题下的相邻块合并。
- **overlap 1 句**：只在边界补一句，避免重复率过高导致 RRF 后都是相似块。
- 这些值是经验值 + 评测调出来的，不是理论最优；不同文档类型（手册/FAQ/制度）应该允许配置不同阈值。

**追问**：1200 字符大概多少 token？→ 中文约 1–1.5 token/字，1200 字约 1200–1800 token，已经超过 bge-reranker-large 的 512 窗口，所以 rerank 端会截断（见 Q40）。

---

### Q33 overlap 只留 1 句够吗？会不会丢上下文？

> 考察：边界处理 ｜ 频率：中

**参考答案**

- 对手册类文本，段落边界比较清晰，1 句 overlap 主要解决「定义句被切断」的问题。
- 如果文档是长论述、跨段指代多，1 句不够，应该用**句窗**（命中句子 ± 前后 N 句）或**父子块回填**。
- overlap 不是越大越好：重复块会挤占 TopK，增加 rerank 成本，还会让答案重复。
- 判断依据：看 context_recall 和 bad case，如果错误集中在「缺少前文」，再加大 overlap 或回填。

**追问**：overlap 会导致重复召回吗？→ 会，所以 RRF 按 chunk_id 去重，必要时用 MMR 控制多样性。

---

### Q34 chunk 保留哪些元数据？分别有什么用？

> 考察：元数据设计 ｜ 频率：中

**参考答案**

| 字段 | 用途 |
|---|---|
| `chunk_id` | 唯一标识、RRF 去重、引用 |
| `title` / `parent_title` | 检索时补上下文、答案引用章节 |
| `file_title` | 定位文档、展示来源 |
| `item_name` | Milvus 标量过滤，避免相似型号串答案 |
| `page` | 回查原文、引用页码 |
| `parent_chunk_id` | 父子块回填 |
| `content` | 原文 |
| `dense_vector` / `sparse_vector` | 检索 |

**加分**：「元数据不是越多越好，Milvus 的标量字段太多会影响 schema 和维护；只保留过滤、引用、回填三类刚需。」

---

### Q35 超长段落、代码块、公式怎么切？

> 考察：特殊内容处理 ｜ 频率：中

**参考答案**

- **超长段落**：按句号、问号、分号切句，再按最大长度组合；不从一个句子中间硬切。
- **代码块/配置**：整体保留，超长时按函数/段落切，并在块首注明「接上文」。
- **公式**：尽量和前后解释放在一起，不单独成块；MinerU 的 LaTeX 公式保留原文，避免转义丢失。
- **表格**：按行分组，重复表头，不按字符切。
- **列表**：保持列表项完整，不把一个条目拆到两个 chunk。

**追问**：怎么保证切完语义完整？→ 切分点优先落在标题、段落、句子边界；切完用「块首是否缺主语」做抽检。

---

### Q36 什么是父子块回填？为什么不默认开启？

> 考察：上下文补全 ｜ 频率：高

**参考答案**

- **做法**：切片时同时保留父块（章节）和子块（段落）；检索命中子块后，返回子块 + 父块/相邻块，给 LLM 更完整的上下文。
- **好处**：解决「子块命中但缺上下文」，尤其是定义、参数表、步骤类内容。
- **不默认开启的原因**：
  1. 父块可能很长，挤占上下文窗口，增加 token 成本；
  2. 引入无关内容，降低 context_precision；
  3. 手册类文本段落清晰，大部分问题不需要父块。
- **折中**：只回填父块的标题路径 + 前后各 1 块；或用 sentence window，按需扩展。

**追问**：怎么评估回填有没有用？→ 固定问题集对比 context_recall / context_precision / answer_correctness，看净收益。

---

### Q37 切片导致语义丢失，怎么定位和优化？

> 考察：排查思路 ｜ 频率：必问

**参考答案**

1. **先确认原文有没有答案**：没有就是知识缺失，不是切片问题。
2. **看召回结果**：答案所在切片有没有被召回；没有，查 embedding 相似度、RRF 候选、rerank 前后排名。
3. **看切片本身**：答案是否被切断、指代是否丢失、表格是否缺表头。
4. **优化手段**：
   - 调小 chunk / 增加 overlap；
   - 保留标题和商品名上下文；
   - 提高 RRF 候选数、rerank TopK；
   - 父子块回填；
   - 表格线性化/图片 caption 补全。
5. **复测**：同一批问题集看 context_recall、context_precision、answer_correctness。

**话术**：「先用 RAGAS 判断是召回问题还是生成问题，再回日志定位到具体节点，不要一上来就调 prompt。」

---

### Q38 几千字的制度文档，用户只问一句话，只能召回局部怎么办？

> 考察：长文档召回 ｜ 频率：高

**参考答案**

- **结构先行**：按标题层级切，保留章节路径，让「第 3 章 第 2 条」这种结构信息进入 chunk。
- **父子块/句窗**：命中细粒度块后回填所在章节，补全上下文。
- **查询侧**：对复杂问题做拆解，生成多个子查询，分别召回后再融合。
- **多路召回**：HyDE 补全用户没说的实体和表述；关键词/稀疏向量补型号、条款号。
- **知识图谱**：跨章节的实体关系（如「A 条款引用 B 条款」）用图谱补，这是增强方向。
- **不要**简单加大 TopK：会把噪声一起带进来，context_precision 下降。

**追问**：回填父块会不会太长？→ 会，所以只回填标题路径 + 命中块前后各一块，或者让 LLM 先做摘要再回答。

---

### Q39 MMR 是什么？什么时候用？

> 考察：多样性控制 ｜ 频率：中

**参考答案**

- MMR（Maximal Marginal Relevance）：在相关性排序的基础上，惩罚和已选文档太相似的候选，公式：

```
MMR = argmax [ λ * sim(q, d) - (1-λ) * max sim(d, d_selected) ]
```

- `λ` 控制相关性和多样性的权衡，常用 0.6–0.8。
- 使用场景：TopK 里出现大量重复/近重复切片，答案信息单一；或者用户问题涉及多个方面。
- 代价：计算两两相似度，增加延迟；λ 太小会牺牲相关性。

**话术**：「我们默认不用 MMR，只有在发现召回结果高度重复时才开；开关和 λ 都用评测集验证。」

---

### Q40 chunk 1200 字符，但 reranker 只有 512 token，矛盾吗？

> 考察：是否真的理解模型限制 ｜ 频率：高 ｜ ⚠️ 原稿存在这个冲突

**参考答案（先承认，再给方案）**

> 确实存在张力。1200 字符是切片上限，不是每个 chunk 都到 1200；实际分布 P50 大约 500 字，P95 接近上限。rerank 时 bge-reranker-large 的 512 token 窗口会对长 chunk 截断，可能丢掉后半段的关键信息。
>
> 我们的处理是：
> 1. 切片时把标题、商品名放前面，关键句尽量靠前；
> 2. rerank 输入做截断，优先保留标题 + 前 512 token；
> 3. 对超长块用父子块，rerank 子块、回填父块；
> 4. 评估过换 `bge-reranker-v2-m3`（8192 窗口），但成本和延迟要权衡。

**加分**：主动说「这是当前实现的一个优化点，不是完美方案」，比硬说「不矛盾」更加分。

## 5. 向量化与 Milvus（Q41–Q50）

### Q41 为什么选 BGE-M3？它有什么特点？

> 考察：Embedding 模型理解 ｜ 频率：高

**参考答案**

- **多语言**：中英文混排的产品手册、型号、术语都能处理。
- **多粒度**：支持 dense、sparse、multi-vector（ColBERT）三种输出；我们用 dense + sparse，一次推理拿两种向量。
- **长上下文**：最大 8192 token，适合较长段落。
- **稀疏向量**天然带词权重，对型号、参数、专有名词比纯 dense 更稳。
- **成本**：自部署在 GPU 上，导入和查询都用同一个模型，避免多模型对齐问题。

**追问**：为什么不用 OpenAI embedding？→ 数据合规、成本、中文术语效果；而且 BGE-M3 能同时出 sparse，省一套 BM25。

**追问**：ColBERT 用了吗？→ 没用，多向量存储和检索成本高，当前 dense+sparse 足够；后续如果长文档细粒度匹配不够，再评估。

---

### Q42 dense 和 sparse 分别解决什么问题？权重怎么定？

> 考察：混合检索理解 ｜ 频率：必问

**参考答案**

| 类型 | 擅长 | 不擅长 |
|---|---|---|
| dense | 语义改写、同义表达、跨语言 | 精确型号、参数、罕见术语 |
| sparse | 型号、接口名、单位、专有名词的精确匹配 | 同义改写、语义泛化 |

- 企业文档两类问题都有：用户既会问「E3 故障怎么处理」，也会问「X100 的额定电压是多少」。
- 权重：Milvus 里用 `WeightedRanker(0.8, 0.2)`（dense 0.8 / sparse 0.2）⚙️；也有资料说各一半，面试时只讲一套。
- 定权方法：构造测试集，网格搜索不同权重，看 Recall@K / context_precision，选最优。
- 话术数据：dense only Recall@5 78.4%，dense/sparse 0.8/0.2 到 86.9%，加 HyDE + RRF 到 90.8%（内部评测集口径）。

**追问**：稀疏向量和 BM25 有什么区别？→ 本质都是词权重，但 BGE-M3 的 sparse 是模型学出来的、带上下文，BM25 是统计的；前者对同义/词序更鲁棒，后者可解释、无需 GPU。

---

### Q43 Milvus 的索引怎么选？参数是多少？

> 考察：向量库实操 ｜ 频率：高

**参考答案**

- **dense**：HNSW，`M=16`、`efConstruction=200`，度量 `COSINE`；查询 `ef=64` 起调。百万级以内内存可接受。
- **sparse**：`SPARSE_INVERTED_INDEX`，`drop_ratio_build=0.2`。
- **标量**：`item_name`、`status`、`doc_id` 建 `INVERTED` 索引，过滤走标量索引。
- **分区**：按业务线或文档类型分区；商品名太多不适合做 partition，做标量过滤更灵活。
- 选型逻辑：HNSW 召回高、延迟低，但内存占用大；IVF 省内存但要调 `nlist/nprobe`；数据量再大考虑 IVF_PQ/磁盘索引。

**追问**：HNSW 内存怎么估？→ 100 万 × 1024 维 × 4 字节 ≈ 4.1GB 原始向量，加上图结构和 overhead 约 1.5–2 倍，6–8GB；再算 sparse 和标量。

### Q44 chunks 集合的 schema 怎么设计？

> 考察：数据建模 ｜ 频率：高

**参考答案**

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | VARCHAR (PK) | 唯一 ID，可用 `task_id + seq` |
| `item_name` | VARCHAR | 商品名，标量过滤 |
| `file_title` | VARCHAR | 文档标题 |
| `title` | VARCHAR | 当前章节标题 |
| `parent_title` | VARCHAR | 父章节 |
| `content` | VARCHAR | 切片原文 |
| `page` | INT | 页码 |
| `dense_vector` | FLOAT_VECTOR(1024) | BGE-M3 dense |
| `sparse_vector` | SPARSE_FLOAT_VECTOR | BGE-M3 sparse |
| `status` | VARCHAR | active/staging/obsolete |
| `version` | INT | 文档版本 |

**加分**：主动说「`content` 放 Milvus 是为了少一次查询，但长期看应该 MySQL 存正文、Milvus 只存索引，避免双份存储和一致性问题。」

**追问**：VARCHAR 长度多少？→ 65535 上限；chunk 最大 1200 字符，够用；标题短字段单独设更小长度。

### Q45 商品名向量集合和 chunk 集合是什么关系？

> 考察：实体对齐设计 ｜ 频率：高

**参考答案**

- **商品名集合**：存标准商品名、别名、dense/sparse 向量，用于「用户说的是哪款」的实体对齐。
- **chunk 集合**：存切片，`item_name` 是过滤字段。
- 关系：查询时先在商品名集合确认 `item_name`，再用它过滤 chunk 集合。
- 为什么单独建：商品名数量少（几千到几万），检索快；可以独立更新别名；chunk 集合不用重复存商品名向量。
- 一致性：导入时先写商品名集合，再写 chunk；更新时两边一起更新。

**追问**：商品名和 chunk 的 item_name 怎么保证一致？→ 用标准名做 key，导入时统一 normalize（去空格、统一大小写、别名映射），写入前校验。

---

### Q46 向量写入怎么做批量、重试和一致性？

> 考察：数据写入工程 ｜ 频率：中

**参考答案**

- **批量**：embedding batch 16–32（看显存），Milvus insert batch 500–1000；太大容易超时/OOM。
- **重试**：embedding 和 insert 都做指数退避重试；`chunk_id` 幂等，重复插入用 upsert 或先删后插。
- **一致性**：一个任务的全部 chunk 写完后，再 `flush` + `load`，轮询 `load_state`，确认可查再把任务置为成功。
- **失败处理**：部分写入失败时，按 `task_id` 清理已写入数据，避免半成品；任务标记 failed，支持重试。
- **顺序**：先写 chunk，再更新商品名/任务状态；避免「任务完成但数据没写完」。

**追问**：Milvus 写入后为什么查不到？→ 数据先进 growing segment，未 flush/load 前不可查；需要 `flush` 并等待 load，或接受最终一致。

---

### Q47 文档更新时，旧向量怎么处理？

> 考察：幂等与在线一致性 ｜ 频率：必问

**参考答案**

- **当前**：按 `item_name` 删除旧向量 → 重新切片/向量化 → 写入。简单，但有查询空窗。
- **改进**：新版本写 `status=staging`，不参与查询；全量成功后用别名/状态切换为 `active`，旧版本置 `obsolete`；查询过滤 `status=active`。
- **更细**：按 chunk 做 diff，hash 没变的复用旧向量，只重算变化部分，省 embedding。
- **回滚**：保留上一版本，切换失败可以切回。

**追问**：删除和写入之间用户查询怎么办？→ 双写新版本 + 原子切换；或者查询时同时查 active 和 staging 的旧版本，保证有数据。

---

### Q48 混合检索是在 Milvus 里做，还是在应用层做？

> 考察：融合层次 ｜ 频率：高

**参考答案**

分两层：

1. **集合内 dense + sparse**：用 Milvus 的 `hybrid_search`，两个 `AnnSearchRequest`，`WeightedRanker(0.8, 0.2)`，一次拿到混合结果。
2. **多路召回之间**：普通向量、HyDE、MCP 在应用层做 RRF。因为 HyDE 是另一次查询，MCP 结果根本不在 Milvus 里，无法用 Milvus 内置融合。

**话术**：「Milvus 负责向量内部的融合，应用层负责跨召回源的融合，两层不要混。」

**追问**：为什么不用 Milvus 的 RRFRanker 做全部？→ 跨源结果没有统一的 Milvus 主键，MCP 也没有 chunk_id，必须在应用层统一。

---

### Q49 相似度度量选 COSINE 还是 IP？向量要归一化吗？

> 考察：向量细节 ｜ 频率：中

**参考答案**

- BGE-M3 输出做 L2 归一化，归一化后 COSINE 和 IP 等价；用 COSINE 语义更清晰。
- 不归一化时，IP 受向量模长影响，长文本可能占优，排序会偏。
- sparse 用内积，分数没有固定范围，所以跨源融合不能直接加权求和，要用 RRF 按排名融合。
- 换模型/换维度必须重建索引，不能混用。

**追问**：归一化在哪做？→ embedding 服务输出时统一做，入库和查询同一条预处理，避免训练/推理不一致。

---

### Q50 向量库容量怎么估算？什么时候需要扩容？

> 考察：容量规划 ｜ 频率：中

**参考答案**

- 向量：`chunk 数 × 维度 × 4 字节`。100 万 × 1024 × 4 ≈ 4.1GB，HNSW 索引约 1.5–2 倍，6–8GB。
- 标量 + 正文：100 万 × 1KB ≈ 1GB；稀疏向量按非零项估。
- 副本：多副本翻倍；Milvus 还有 segment、日志、临时空间。
- 原始文件：5–25GB；图片另算；MinIO 按年增长预留 2–3 倍。
- 扩容触发：查询 P95 上升、load 时间变长、内存使用率持续 >70%、Segment 数量过多。

**话术**：「我们的量级一台 8C32G 中间件够用，扩容更多是可用性考虑，不是容量焦虑。」

## 6. 查询链路（Q51–Q62）

### Q51 用户提问后，系统完整做了什么？

> 考察：查询链路熟悉度 ｜ 频率：必问

**参考答案**

1. 前端提交问题，`QueryService` 生成 `task_id` 和 `session_id`；流式查询创建 SSE 队列。
2. 组装 `QueryGraphState`：`original_query`、`session_id`、`task_id`、`is_stream`。
3. **商品名确认节点**：读最近历史，LLM 抽 `item_names` 并生成 `rewritten_query`；商品名向量到商品名集合对齐。
4. 分支：
   - 确认成功 → 进入召回；
   - 只有候选 → 返回「您问的是哪款」；
   - 没识别到 → 让用户补充商品名。
5. **多路召回**：普通向量检索、HyDE 检索、MCP 网络检索并行。
6. **RRF**：本地两路按 `chunk_id` 融合去重，保留前 20。
7. **Rerank**：本地 chunk + MCP 结果拼 query-doc pair，BGE-Reranker 精排。
8. **断崖截断**：按分数分布保留 6–15 条。
9. **答案生成**：上下文 + 历史 + 商品名 + 问题组装 prompt，LLM 生成。
10. **流式返回**：SSE 推 delta，结束推 final；最后写 MongoDB。

**追问**：哪一步最影响端到端延迟？→ 商品名确认的 LLM 调用、HyDE 的 LLM 调用、MCP 网络请求；这三处是优化重点（缓存、并行、超时）。

---

### Q52 商品名确认是怎么做的？三级判定怎么定？

> 考察：实体对齐、阈值设计 ｜ 频率：必问

**参考答案**

- **抽取**：把最近几轮历史 + 当前问题交给 LLM，输出 JSON：`item_names`、`rewritten_query`；prompt 里给商品名列表/别名规则，减少编造。
- **对齐**：对每个候选商品名用 BGE-M3 生成 dense/sparse，在商品名集合做混合检索。
- **三级判定** ⚙️：
  - 高分（≥0.85）：直接确认，写入 state；
  - 中间（0.60–0.85）：返回候选列表，让用户选；
  - 低分（<0.60）：让用户补充型号/商品名。
- **确认后**：`item_name` 作为 chunk 检索的标量过滤条件；`rewritten_query` 用于召回。
- **多候选**：可以并列返回 3–5 个，按分数排序，不要只给一个。

**追问**：阈值怎么定？→ 用标注样本扫阈值，看确认准确率、误确认率、澄清率；宁可多问一句，也不要把相似型号答串。

**追问**：LLM 抽不出来怎么办？→ 规则兜底（型号正则、别名表）+ 让用户选；不要硬猜。

---

### Q53 商品名抽取的 prompt 怎么设计？历史怎么带？

> 考察：Prompt 工程 ｜ 频率：中

**参考答案**

- **输入**：最近 N 轮（如 6 轮）对话，只保留 user/assistant 内容和已确认的 `item_name`；太长就摘要。
- **输出**：严格 JSON，`{"item_names": [...], "rewritten_query": "..."}`；要求「不确定就返回空数组」，禁止编造。
- **规则**：
  1. 优先使用本轮明确出现的型号；
  2. 本轮没有，继承最近一轮已确认的商品名；
  3. 代词/省略（「它」「这个」）结合历史补全；
  4. 别名/简称映射到标准名。
- **校验**：JSON 解析失败重试一次；抽出的名字必须在商品名候选库里能匹配，否则丢弃。

**追问**：为什么不直接拿用户原话去向量库匹配？→ 用户可能说「上次那个」「这个型号」，必须先结合历史改写；而且口语和标准名之间有别名鸿沟。

---

### Q54 多轮对话里历史消息缺商品名，怎么回填？

> 考察：会话状态管理 ｜ 频率：高

**参考答案**

- 问题改写时把历史对话一起带上；如果历史里已有商品名，附在对应轮次里。
- 本轮确认成功后，把 `item_name` 回填到本会话之前缺失商品名的消息上（MongoDB update）。
- 回填只在高置信度确认时做，避免把错误商品名扩散到历史。
- 后续轮次直接继承，减少重复 LLM 抽取。
- 会话结束时可以固化「会话级商品名」，作为默认上下文。

**追问**：用户中途换商品怎么办？→ 以本轮明确提到的为准，覆盖会话级商品名；历史回填不覆盖已确认的其他商品名。

---

### Q55 查询改写具体改什么？会不会改偏？

> 考察：Query 理解 ｜ 频率：高

**参考答案**

- **纠错**：错别字、口语、语音识别错误。
- **标准化**：简称/别名 → 标准术语（「空开」→「空气开关」）。
- **补主语**：结合历史补全「它」「这个型号」。
- **拆解**：复杂问题拆成多个子问题，分别召回。
- **扩展**：补充同义词、英文缩写，提升召回。
- **不改**：型号、参数、故障码等关键实体保持原样。

**防跑偏**：

1. 保留 `original_query`，原问题和改写问题都参与召回；
2. prompt 限制「只做表达规范化，不改变意图」；
3. 改写结果和原问题做 token 重叠校验，差异过大就回退；
4. 最终有 rerank 兜底。

**追问**：改写和 HyDE 会不会重复？→ 改写解决「表达」，HyDE 解决「缺内容」；两者互补，但都调用 LLM，要注意延迟和成本。

---

### Q56 为什么要多路召回，不只做向量检索？

> 考察：召回设计 ｜ 频率：必问

**参考答案**

单路向量的问题：

1. **召回角度单一**：dense 偏语义，型号/参数类精确匹配弱；
2. **用户表达不完整**：短问题缺实体，向量空间里离答案远；
3. **知识库有边界**：本地没有的实时信息、外部资料召不到。

三路分工：

- **普通向量**：常规语义 + dense/sparse 混合，覆盖大部分问题；
- **HyDE**：先生成假设文档，补全表达和实体，提升短问题召回；
- **MCP**：外部网络补充，解决本地缺失和实时信息。

最后 RRF + Rerank 统一排序，兼顾召回率和准确率。

**追问**：三路都开会不会很慢？→ 并行发；MCP 可配置开关和超时；HyDE 对明确问题可以跳过（⚙️ 按 query 长度/是否含型号决定）。

---

### Q57 HyDE 是什么？为什么能提升召回？有什么风险？

> 考察：HyDE 原理与边界 ｜ 频率：必问

**参考答案**

- **做法**：让 LLM 根据用户问题生成一段「假设性的答案/技术文档」，再把原问题 + 假设文档一起向量化去检索。
- **为什么有效**：用户问题通常短、口语、缺实体；假设文档更像手册里的正式表达，向量空间里更接近真实切片。
- **风险**：
  1. LLM 编造参数/型号，假设文档本身是错的；
  2. 假设文档把原问题带偏，召回不相关的内容；
  3. 多一次 LLM 调用，增加延迟和成本。
- **控制**：
  1. prompt 要求「只围绕原问题生成，不编造具体参数」；
  2. 原问题单独一路召回，不只用 HyDE；
  3. 后面 Rerank 精排兜底；
  4. 对明确、含型号的问题可以跳过 HyDE。

**追问**：HyDE 和 query expansion 的区别？→ 扩展是加词，HyDE 是生成一段完整文档，表达更充分，但幻觉风险更高。

---

### Q58 MCP 是什么？为什么查询链路要接网络检索？

> 考察：外部工具集成 ｜ 频率：中

**参考答案**

- MCP（Model Context Protocol）：标准化工具调用协议，把外部能力（搜索、数据库、API）封装成工具，模型/编排层按统一接口调用。
- 我们通过 MCP 客户端调 `bailian_web_search`，拿网页标题、摘要、URL。
- 解决：本地知识库没有的资料、产品最新公告、外部故障案例。
- 风险：结果质量不可控、延迟高、网络不稳定、合规问题；所以它是**可选补充**，有超时和开关，不主导答案。

**追问**：MCP 结果怎么和本地 chunk 一起排序？→ 统一转成 `{id, content, source, score}`，在 Rerank 阶段合并；MCP 没有 chunk_id，用 URL/hash 生成临时 ID。

---

### Q59 三路召回在 LangGraph 里怎么并行？

> 考察：编排实现 ｜ 频率：高

**参考答案**

- 用一个虚拟节点 `multi_search` 做 fan-out，内部 `asyncio.gather` 并发调三路；每路写自己的 state 字段（`vector_docs`、`hyde_docs`、`web_docs`），避免互相覆盖。
- state 用 `Annotated[list, operator.add]` 这类 reducer 合并结果。
- 每路独立 try/except + 超时（如向量 2s、HyDE 5s、MCP 5s）⚙️，单路失败返回空列表，不阻塞其他路。
- join 后进 RRF；MCP 结果直接带到 rerank。

**追问**：为什么用虚拟节点而不是三个真实节点？→ 三个真实节点也可以，但 fan-out/fan-in 的边更多、状态合并更难；虚拟节点把并行收在一个节点里，逻辑更清楚。

---

### Q60 某一路召回挂了，整个查询怎么办？

> 考察：容错 ｜ 频率：高

**参考答案**

- 每路隔离：超时、异常捕获、返回空结果，记录日志和指标。
- 降级顺序：普通向量是主路，必须保；HyDE 挂了不影响；MCP 挂了直接跳过。
- 如果主路也挂：降级到缓存/FAQ/历史，或返回兜底话术并提示稍后重试。
- 熔断：连续失败触发 circuit breaker，一段时间内直接跳过该路。
- 监控：每路成功率、P95 延迟、空结果率。

**话术**：「多路召回本身就是一种容错设计，单路故障不应该让整个问答不可用。」

---

### Q61 商品名确认很慢，有什么优化？

> 考察：性能优化 ｜ 频率：中

**参考答案**

- **缓存**：`query 中的型号/别名` → `item_name` 的映射缓存（Redis/本地），命中直接跳过 LLM 和向量检索。
- **规则前置**：型号正则、别名表先匹配，命中率高且零成本。
- **历史继承**：同一 session 已确认商品名，本轮没提就沿用，不再抽。
- **并行**：商品名确认和问题改写可以部分并行，但确认结果是过滤条件，要先拿到。
- **小模型**：抽取用更小的模型/更短 prompt。
- **失效**：商品库更新时清缓存。

**追问**：缓存会不会把新品漏掉？→ 缓存只存「已确认过的映射」，新品走正常链路；设置 TTL 和版本号，导入后失效。

**⚠️ 口径**：原稿把「商品名缓存」写在「待优化」里，面试时说「计划做/正在做」，不要说得像已经上线；除非你确实实现了。

---

### Q62 用户一句话问多个商品，怎么处理？

> 考察：复杂 Query ｜ 频率：中

**参考答案**

- 抽取多个 `item_names`，确认后按商品分别召回，结果按商品分组。
- 如果问题是比较型（「X100 和 X200 有什么区别」），prompt 要求分组对比，不要混在一起答。
- 如果商品太多（>3），先让用户缩小范围，避免上下文爆炸。
- Milvus 过滤用 `item_name in [...]`，每路召回分别做，再合并。
- 答案里明确标注每个结论对应的商品，避免张冠李戴。

**追问**：两个商品参数冲突怎么办？→ 以原文为准，分别列出来，不要合成一个；如果原文冲突，提示用户核对版本。

## 7. 融合与重排（Q63–Q72）

### Q63 RRF 是什么？公式和参数怎么定？

> 考察：融合算法 ｜ 频率：必问

**参考答案**

- RRF（Reciprocal Rank Fusion，倒数排名融合）：用文档在各路结果中的排名算融合分，不依赖原始分数。

```
score(d) = Σ_i  weight_i / (k + rank_i(d))
```

- `rank_i(d)` 是文档 d 在第 i 路中的排名（从 1 开始）；`k` 常用 60；`weight_i` 是各路权重。
- 我们本地两路（向量、HyDE）权重都是 1.0，`k=60`，按 `chunk_id` 去重，保留前 20。
- 直觉：在多路里都排前面的文档，融合分高；只在一路排第一的，不如两路都排前十的稳。

**追问**：k=60 怎么来的？→ RRF 论文的经验值；k 小头部差异大，k 大排序更平滑。可以用验证集扫 10/30/60/100，看 context_recall 和最终答案。

---

### Q64 为什么用 RRF，不直接对分数加权求和？

> 考察：分数可比性 ｜ 频率：高

**参考答案**

- 不同召回源的分数不可比：dense 余弦相似度在 0–1，sparse 内积无界，rerank logits 可正可负，MCP 没有分数。
- 归一化也不能完全解决：分布不同、长尾不同，min-max 会被异常值影响。
- RRF 只用排名，天然尺度无关，鲁棒、无需调参，适合多源融合。
- 代价：丢掉分数幅度信息，两个分数很接近的文档可能被排名差放大；所以后面还要 Rerank 精排。

**追问**：RRF 和加权分数能结合吗？→ 可以，先 RRF 粗融合，再用 rerank 分数精排；或者在 RRF 里加权重，但权重要用验证集调。

---

### Q65 为什么先 RRF 再 Rerank？能直接 rerank 所有召回吗？

> 考察：成本与效果权衡 ｜ 频率：必问

**参考答案**

- **能直接 rerank，但不建议**：三路召回可能有 100+ 条，cross-encoder 要逐对计算，延迟和 GPU 成本高。
- **RRF 很便宜**：只按排名算分，先去重、粗融合，把候选压到 20 条左右。
- **Rerank 贵但准**：只对压缩后的候选做精排，性价比最高。
- **MCP 特殊性**：网络结果没有本地 `chunk_id`，放在 rerank 阶段统一合并更方便。

**话术**：「RRF 负责『别漏、别重』，Rerank 负责『排得准』，两级分工。」

---

### Q66 Rerank 怎么做的？输入怎么构造？

> 考察：精排细节 ｜ 频率：必问

**参考答案**

- 模型：BGE-reranker-large，cross-encoder，输入 `(query, document)`，输出相关性分数。
- 输入构造：`query` 用改写后的问题；`document` 用 `title + item_name + content`，标题和商品名放前面，帮助模型抓主题。
- 批量：20 条候选一次或分批送 GPU，batch 8–16 ⚙️。
- 排序：按分数降序；MCP 结果也转成同样格式参与。
- 截断：模型窗口 512 token，超长截断（见 Q40）。
- 输出：分数 + 排序后的文档，交给断崖截断。

**追问**：rerank 分数能直接当置信度吗？→ 不能直接当概率，但可以做相对排序和阈值；阈值要按模型和验证集校准。

---

### Q67 什么是断崖检测截断？阈值怎么定？

> 考察：动态 TopK ｜ 频率：必问

**参考答案**

- Rerank 后按分数降序，观察相邻分数的落差；如果某处出现明显「断崖」，说明前面是高相关、后面是长尾，从这里截断。
- 规则 ⚙️：相邻分数绝对差 > 0.5，或相对跌幅 > 25%，触发截断；同时受最少 6 条、最多 15 条约束。
- 好处：不用固定 TopK——简单问题少给上下文，复杂问题多给；减少噪声和 token。
- 阈值来源：验证集 + bad case 分析，看 context_recall / context_precision 的权衡。
- 风险：断崖太早会漏掉第二条相关证据；所以设最少保留条数兜底。

**追问**：如果分数是平缓下降呢？→ 不触发断崖，取最大条数 15；如果都很低，走拒答逻辑。

---

### Q68 最终给大模型多少条上下文？TopK 怎么设？

> 考察：上下文预算 ｜ 频率：高

**参考答案**

- 不是固定 TopK，分三段：
  1. RRF 后保留 20 条本地候选；
  2. Rerank 后最少 6 条、最多 15 条，中间由断崖截断；
  3. MCP 结果按分数保留 0–5 条 ⚙️，总算力允许时再压。
- 还要看 token 预算：15 条 × 500 字 ≈ 7500 字，加历史、prompt，控制在模型窗口内。
- 参数用验证集调：TopK 太小 context_recall 下降，太大 context_precision 下降、幻觉增加。

**追问**：为什么最少 6 条？→ 保证多证据问题（步骤、参数、注意事项）不至于只召回一半；6 是经验和评测的折中。

---

### Q69 什么时候拒答？怎么实现？

> 考察：幻觉控制 ｜ 频率：高

**参考答案**

- **触发条件**：
  1. 所有候选 rerank 分数低于阈值（如 0.3）⚙️；
  2. 召回为空，或商品名确认失败且用户不补充；
  3. 上下文之间互相矛盾，无法判断。
- **实现**：
  1. rerank 后过滤低分，若为空直接返回兜底话术，不调 LLM；
  2. prompt 里要求「资料不足时明确说不知道，不要编造」；
  3. 答案生成后做一次 grounded 校验（可选）。
- **兜底话术**：说明没找到依据，建议换关键词/补充型号/转人工。
- **平衡**：阈值太高会误拒，太低会幻觉；用验证集看拒答率和正确率。

**追问**：用户坚持问知识库没有的，怎么办？→ 明确告知边界，可以走 MCP 或转人工，不要硬答。

---

### Q70 Top 5 给模型，但模型只关注头尾，中间信息丢了怎么办？

> 考察：Lost in the Middle ｜ 频率：中

**参考答案**

- **排序**：rerank 分数最高的放最前；如果必须放很多条，把最重要的放头尾。
- **提示词**：要求「逐条阅读参考资料，引用编号」，强制模型覆盖中间内容。
- **压缩**：长上下文先做摘要/抽取，把关键句放前面，减少中间噪声。
- **减少条数**：断崖截断本身就是控制长度，宁少勿滥。
- **结构化**：按「结论/步骤/参数/警告」分段，别堆成一大段。

**加分**：提一句「这是 LLM 的 known issue（lost in the middle），工程上只能缓解，不能根治；所以检索精度比堆上下文更重要。」

---

### Q71 召回结果重复、多样性不足，怎么解决？

> 考察：多样性 ｜ 频率：中

**参考答案**

- **先去重**：按 `chunk_id`、内容 hash、父块 ID 去重；RRF 本身按 ID 去重。
- **控制来源**：同一个文档最多保留 N 条，避免一个文档霸榜。
- **MMR**：在相关性基础上惩罚相似候选，`λ` 0.6–0.8。
- **分组**：按商品/章节分组，每组选 top 条，再合并。
- **评测**：看 context_precision 和答案覆盖度，别为了多样性牺牲相关性。

**追问**：MMR 会影响延迟吗？→ 要算两两相似度，候选多时明显；只在小候选集（20 条内）用。

---

### Q72 不同 query 的 rerank 分数分布不一样，阈值怎么统一？

> 考察：分数校准 ｜ 频率：中

**参考答案**

- rerank 输出是 logits，不是概率；不同模型、不同 query 类型分布不同，固定阈值确实不稳。
- 做法：
  1. 按 query 类型分桶（参数类/故障类/操作类），分别定阈值；
  2. 用 sigmoid/softmax 归一化后再看相对分数；
  3. 更稳的是看「断崖」和「相对排名」，少依赖绝对分数；
  4. 线上监控拒答率、低分率，漂移时重新校准。
- 拒答阈值宁可保守，误拒可以引导用户补充，幻觉代价更高。

**追问**：换 reranker 模型阈值要重调吗？→ 一定要，logits 尺度变了，旧阈值直接失效。

## 8. 生成、流式与前端交互（Q73–Q80）

### Q73 答案生成的 prompt 怎么组织？

> 考察：Prompt 结构 ｜ 频率：高

**参考答案**

```
System:
你是商品资料助手。只依据【参考资料】回答，不要编造。
资料不足时明确说明，并建议用户补充型号或转人工。
回答要分点、给出来源编号；涉及参数时保留单位和型号。

Context:
[1] 文档：X100 说明书 / 章节：故障代码 / 页码：12
内容：...

[2] ...

History:
最近 3 轮对话摘要...

Question:
用户问题（改写后）+ 商品名

Output:
- 结论
- 依据（引用 [1][2]）
- 下一步建议
```

- 关键：资料编号、只依据资料、引用、不足时拒答、格式约束。
- 历史和上下文要控制长度，超了先摘要。

**追问**：为什么把商品名也放 prompt？→ 强化主题，避免模型答成相似型号；同时和上下文里的型号互相校验。

---

### Q74 怎么保证 LLM 回答准确、不幻觉？

> 考察：生成控制 ｜ 频率：必问

**参考答案**

分四层：

1. **检索层**：提高召回率、rerank 精排、断崖截断，保证上下文相关且干净。
2. **Prompt 层**：只依据资料、要求引用、资料不足拒答、控制回答长度和格式。
3. **生成层**：temperature 调低（如 0.1–0.3）⚙️；关键场景用更强模型；流式时也要保留完整上下文。
4. **后处理**：引用校验、关键数字/型号和原文比对、低置信度提示人工复核。

**话术**：「幻觉不能靠 prompt 根治，检索质量是上限；prompt 只是让模型在给定资料里老实回答。」

**追问**：怎么发现幻觉？→ 离线用 RAGAS faithfulness，线上看用户负反馈和人工抽检；对关键数字做规则校验。

---

### Q75 SSE 流式响应是怎么实现的？

> 考察：流式工程 ｜ 频率：必问

**参考答案**

1. 前端发起查询，后端生成 `task_id`，创建 `asyncio.Queue`，注册到任务表。
2. 后台跑 QueryGraph；答案节点调用 LLM 的 stream 接口。
3. 每生成一段，往队列 `put` 一个事件：`event: delta`，`data: {"text": "..."}`。
4. 接口返回 `StreamingResponse`，`media_type="text/event-stream"`，循环从队列取事件并 `yield`。
5. 结束推 `event: final`，带完整答案/引用；异常推 `event: error`。
6. 前端用 `EventSource` 或 fetch stream 接收，逐段渲染。

**关键响应头**：

```
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

**追问**：为什么要队列，不直接在接口里跑图？→ 查询图可能包含多个节点，接口只负责推流；队列解耦生产（图）和消费（SSE），也方便断线后重连。

---

### Q76 SSE 和 WebSocket 有什么区别？为什么选 SSE？

> 考察：通信协议 ｜ 频率：高

**参考答案**

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 服务端 → 客户端单向 | 双向 |
| 协议 | HTTP | 独立协议，握手升级 |
| 重连 | 浏览器自动重连 | 自己做 |
| 代理/防火墙 | 友好 | 可能被拦 |
| 复杂度 | 低 | 高 |

- 知识库问答是「提交问题 → 服务端持续推答案」，不需要高频双向通信，SSE 足够。
- FastAPI 的 `StreamingResponse` 直接支持，前端 `EventSource` 原生支持。
- WebSocket 更适合实时协作、在线聊天、频繁双向交互。

**追问**：SSE 能传二进制吗？→ 只能文本，图片用 URL；SSE 有连接数限制（HTTP/1.1 同域 6 个），HTTP/2 好一些。

### Q77 多副本部署时，SSE 队列在进程内，不会出问题吗？

> 考察：是否踩过分布式坑 ｜ 频率：高 ｜ ⚠️ 原稿没提，是加分项

**参考答案**

> 会。队列在进程内时，如果 Nginx 把查询请求和 `/stream/{task_id}` 分到不同副本，就取不到队列。
>
> 常见规避：Nginx 按 `task_id`/session 做一致性哈希或粘性会话，保证同一任务落同一副本。但这只是绕过，不是根治。
>
> 更稳的方案：
> 1. 队列外置到 Redis Pub/Sub 或 Stream，所有副本都能订阅；
> 2. 查询和推流拆成独立服务；
> 3. 前端直接用任务 ID 轮询结果，SSE 只做可选加速。
>
> 这是当前实现的一个限制，量上来会改成 Redis。

**加分**：主动暴露限制，比被问住好。

---

### Q78 SSE 断线、超时、客户端取消怎么处理？

> 考察：流式健壮性 ｜ 频率：中

**参考答案**

- **心跳**：每隔 15s 发 `: ping` 注释帧，防止代理断开。
- **超时**：服务端设置总超时（如 120s）⚙️，LLM 卡住就推 error 并结束。
- **客户端取消**：监听 `request.is_disconnected()`，取消后台任务，清理队列。
- **重连**：`Last-Event-ID` + 服务端保留最近事件缓冲，重连后从断点续推；做不到就推完整答案。
- **幂等**：同一 `task_id` 重复连接，返回同一结果或当前进度。

**追问**：LLM 已经生成一半，连接断了，答案会丢吗？→ 后台任务继续跑完并落库，重连后取最终结果；流式只是展示层。

---

### Q79 流式和非流式怎么共用一套逻辑？

> 考察：代码复用 ｜ 频率：中

**参考答案**

- `QueryGraphState` 里带 `is_stream` 标志。
- 答案节点：
  - 非流式：`llm.invoke()`，拿到完整答案，写任务结果；
  - 流式：`llm.stream()`，逐段 `queue.put(delta)`，最后汇总完整答案。
- 两者都走同一套检索、rerank、prompt 组装；只有生成和输出方式不同。
- 最后都写 MongoDB，保证历史一致。

**追问**：流式下怎么做引用？→ 生成时带编号，final 事件里返回 `references` 列表（chunk_id、标题、页码、URL），前端渲染。

---

### Q80 文件导入是长任务，前端怎么感知进度？

> 考察：异步任务交互 ｜ 频率：高

**参考答案**

- 上传接口立即返回 `task_id`，不阻塞。
- 导入放后台任务（BackgroundTasks/队列）。
- 前端轮询 `/status/{task_id}`，返回状态、当前节点、节点列表、进度百分比、错误信息。
- 也可以对任务状态做 SSE，但轮询更简单，导入不是秒级，轮询足够。
- 完成后前端刷新文档列表；失败展示失败节点和原因，支持重试。

**追问**：轮询频率多少？→ 2–3s，完成后停止；任务多时加缓存/合并查询，避免打爆任务表。

## 9. 评测、指标与 bad case（Q81–Q90）

### Q81 测试问题集是怎么建的？

> 考察：评测体系 ｜ 频率：必问

**参考答案**

三类来源：

1. **开发自测**：按文档章节整理问题，覆盖参数、操作步骤、故障排查、注意事项。
2. **业务补充**：客服/运营的真实高频问题，带业务口径。
3. **线上回流**：真实用户问题 + bad case，定期去重后加入回归集。

建集要求：

- 每题有**标准答案**和**证据切片**（文档、章节、页码），否则无法算 context_recall。
- 按商品、问题类型分层，避免只测某一类。
- 规模 ⚙️ 200–500 题起步，核心场景每类至少 20 题。
- 版本化，改一次检索/切片/prompt 都跑同一套，保证可比。

**追问**：标准答案谁写？→ 开发写初稿，业务审核；有争议的题标记，不纳入自动评分。

---

### Q82 RAGAS 的五个指标分别是什么？高低说明什么？

> 考察：评测指标理解 ｜ 频率：必问

**参考答案**

| 指标 | 衡量 | 低说明什么 |
|---|---|---|
| faithfulness | 答案是否被上下文支撑 | 幻觉、模型自由发挥 |
| answer_relevancy | 答案是否切题 | 答非所问、prompt 或理解问题 |
| context_precision | 召回上下文是否干净 | 噪声多、TopK 太大、rerank 不准 |
| context_recall | 证据是否召全 | 切片/embedding/召回链路漏 |
| answer_correctness | 和标准答案是否一致 | 整体效果，定位需结合前四项 |

**话术**：「先看 recall 判断有没有找到，再看 precision 判断噪声，最后看 faithfulness 判断有没有瞎编；三个都高但 correctness 低，才是模型/ prompt 的问题。」

---

### Q83 context_precision 怎么算？

> 考察：公式与直觉 ｜ 频率：高

**参考答案**

RAGAS 的 context precision 是「按排名加权的精度」：

```
Context Precision@K = Σ_{k=1}^{K} (precision@k × relevance_k) / 检索到的上下文数量
```

其中：

- `precision@k` = 前 k 条里相关条数 / k；
- `relevance_k` = 第 k 条是否相关（0/1）。

直觉：相关切片排得越靠前，分数越高；把相关切片埋在后排会被惩罚。

**追问**：分母为什么是「检索数量」而不是「相关数量」？→ 不同实现有差异，RAGAS 原始实现分母是 topK 中相关项数量；面试时说清你用的是哪种口径即可，重点是「奖励前排命中」。

---

### Q84 context_recall 怎么算？

> 考察：召回评测 ｜ 频率：高

**参考答案**

```
Context Recall = 上下文能支撑的参考答案事实点 / 参考答案的事实点总数
```

- 先把标准答案拆成事实点（claims）；
- 再判断每个事实点是否能被召回上下文支撑；
- 比值就是 recall。

**追问**：事实点怎么拆？→ 人工拆 + LLM 辅助，业务审核；参数、步骤、条件各算一个点。拆得太细会低，太粗会虚高，要有标注规范。

---

### Q85 召回率到底是多少？为什么有 93% 和 85% 两个数？

> 考察：指标口径、诚实度 ｜ 频率：高

**参考答案**

> 两个数口径不同：
>
> - **93%+** 是离线评测集上的 context_recall，题目来自文档、有标准证据，属于「知识库内」的问题；
> - **85%** 是上线后真实问题的抽样，里面包含知识库没覆盖的问题、表述特别口语的问题，所以更低。
>
> 面试时我会说「核心手册类问题离线 93%，线上全量抽样 85%，差距主要来自知识库覆盖和表达差异」，不会只报一个数。

**加分**：主动说「这两个数不能直接对比，测试集分布不同；如果要对比，必须用同一批题、同一套判定」。

---

### Q86 bad case 怎么分析？步骤是什么？

> 考察：排查方法论 ｜ 频率：必问

**参考答案**

1. **看指标**：先判断是 recall 低、precision 低，还是 faithfulness/correctness 低。
2. **回原文**：标准答案在不在文档里？不在 → 知识缺失，补文档；在 → 继续。
3. **看召回**：证据切片有没有被召回？排名多少？被哪个节点淘汰（embedding 相似度、RRF、rerank 阈值、断崖）？
4. **看切片**：是否被切断、缺表头、缺上下文、图片没 caption。
5. **看生成**：上下文对了但答案错 → prompt、模型、上下文长度、引用。
6. **修复 + 回归**：改一个变量，跑同一批题，看指标净变化。

**话术**：「bad case 不是直接调 prompt，而是先定位它在链路的哪一段丢的。」

---

### Q87 离线评测和线上监控怎么配合？

> 考察：评测闭环 ｜ 频率：中

**参考答案**

- **离线**：固定问题集 + RAGAS，改切片/召回/prompt 前后对比；作为发布门禁。
- **线上**：采样真实问题，看负反馈率、追问率、转人工率、拒答率、P95 延迟、token 成本；对低分样本做人工标注。
- **回流**：线上 bad case 去重后进回归集，形成「发现 → 修复 → 防回归」闭环。
- **灰度**：新版本先小流量，对比核心指标再放量。

**追问**：线上没有标准答案怎么评？→ 用用户行为（是否追问、是否复制、是否转人工）+ 人工抽检 + LLM-as-judge 辅助，不能只看点赞。

---

### Q88 用 LLM 当裁判（LLM-as-judge）有什么偏差？怎么缓解？

> 考察：评测严谨性 ｜ 频率：中

**参考答案**

- **位置偏差**：偏爱排在前面的答案 → 交换顺序多次评。
- **长度/格式偏差**：偏爱长答案、分点答案 → 控制格式，或用 rubric。
- **自我偏好**：偏爱同族模型输出 → 多模型交叉评。
- **知识盲区**：裁判也不知道答案 → 提供参考答案，要求逐条比对。
- **缓解**：人工抽检校准、多裁判投票、固定 rubric、报告一致性（Kappa）。

**话术**：「LLM-as-judge 适合做大规模粗筛，关键结论还要人工复核。」

---

### Q89 讲一个你做的优化案例

> 考察：真实经历、数据意识 ｜ 频率：必问

**参考答案（STAR）**

> **问题**：上线后发现部分问题答案漏关键参数，bad case 集中在长章节。
>
> **定位**：日志显示证据切片被召回了，但 rerank 分数不高，且切片长度接近 2000 字；reranker 512 窗口截断，关键句在后半段。
>
> **动作**：
> 1. 切片上限从 2000 降到 1200，超长按句子递归切；
> 2. 标题、商品名放块首；
> 3. 增加 1 句 overlap；
> 4. RRF 候选从 10 提到 20，rerank 保留上限提到 15。
>
> **结果**：context_recall 和 answer_correctness 上升，长文档 bad case 明显减少；代价是 chunk 数量增加、embedding 成本略升。

**追问**：怎么证明是切片导致的？→ 对比实验：同一批题，只改切片参数，其他不变；看证据切片是否完整、rerank 分数排名。

### Q90 用户负反馈怎么闭环？

> 考察：运营意识 ｜ 频率：中

**参考答案**

- 前端提供「有帮助/没帮助」和点踩原因（答错、没找到、不完整、太慢）。
- 负反馈样本自动落到 bad case 池，按商品/问题类型聚类。
- 每周 review Top 问题，分派给文档、切片、召回、prompt 四类。
- 修复后进回归集，跟踪同类问题是否再出现。
- 对高频问题考虑做 FAQ 缓存/快捷入口，减少 LLM 调用。

## 10. 性能、稳定性与部署（Q91–Q100）

### Q91 响应时间从 3s 变成 12s，怎么排查？

> 考察：链路排查 ｜ 频率：必问

**参考答案**

1. **看 trace**：每个节点耗时（商品名确认、三路召回、RRF、rerank、生成），先定位是哪个节点。
2. **看时间分布**：P50 还是 P95 变慢？单节点还是全局？是否某个商品/文档特别慢？
3. **常见原因**：
   - LLM 节点：模型服务排队、限流、prompt 变长、输出变长；
   - MCP：网络阻塞、超时重试；
   - Milvus：segment 过多、load 未完成、过滤条件导致全扫；
   - rerank：候选变多、GPU 排队；
   - 应用：event loop 被同步调用阻塞、连接池耗尽、GC。
4. **对照变更**：最近有没有改切片、prompt、模型、索引、部署？
5. **修复**：超时、缓存、降级、扩容、异步化。

**话术**：「先看 trace 再猜，不能一上来就说模型慢。」

---

### Q92 压测数据怎么解读？瓶颈在哪？

> 考察：性能分析 ｜ 频率：高

**参考答案**

| 并发 | QPS | TTFT P50 | TTFT P95 | TPOT P95 | GPU |
|---|---|---|---|---|---|
| 16 | 14.8 | 310ms | 620ms | 38ms/token | 61% |
| 32 | 25.6 | 420ms | 880ms | 46ms/token | 78% |
| 64 | 38.9 | 690ms | 1.42s | 63ms/token | 91% |

解读：

- QPS 随并发上升，但边际递减；64 并发时 GPU 91%，说明接近瓶颈。
- TTFT 和 TPOT 随并发上升，是典型的 batching 排队效应。
- 生产按峰值 5–10 QPS 预留 3–5 倍，当前容量足够。
- 优化方向：限制并发、模型量化、prefix caching、减少输出长度、缓存。

**⚠️ 口径提醒**：这组数要能自圆其说。16 并发 14.8 QPS 意味着平均请求耗时约 1.08s；按 TTFT 310ms + TPOT 38ms 推算，平均输出只有约 20 token，和 RAG 长答案不符。面试时要么说明「压测用固定短输出测吞吐上限」，要么补一组真实输出长度的数据（见附录 B）。

---

### Q93 容量怎么规划？

> 考察：容量估算 ｜ 频率：中

**参考答案**

- **流量**：日常 0.5–1 QPS，峰值 5–10 QPS，按 3–5 倍预留。
- **应用**：2 台 8C32G，无状态，Nginx 负载均衡；单台可扛 10+ QPS（主要是 IO 等待）。
- **GPU**：1 张 L20 48G，跑 BGE-M3 + reranker；embedding 批量、rerank 20 条/请求，按 QPS × 候选数估。
- **Milvus**：100 万 chunk、单副本 8C32G 够用；副本和扩容看可用性。
- **LLM**：走 Qwen-Flash API，按 TPM/RPM 限额申请；峰值排队要有限流。
- **存储**：MinIO 5–25GB 原始文件 + 图片 + 索引，按年增长预留 2–3 倍。

**追问**：怎么算 GPU 够不够？→ 压测单卡 embedding/rerank 的 QPS 上限，再乘峰值系数；embedding 是导入期集中，rerank 是在线每请求一次，要分开算。

---

### Q94 怎么限流、排队、削峰？

> 考察：流量治理 ｜ 频率：高

**参考答案**

- **入口限流**：Nginx/网关按 IP、用户、接口限 QPS；超过返回 429。
- **并发控制**：信号量限制同时处理的查询数，避免 GPU/LLM 打满。
- **队列**：高峰期请求进 MQ，按优先级消费；同步接口给排队位次/预计等待。
- **token 限流**：按 TPM 限制，长 prompt 单独配额。
- **降级**：队列过长时关闭 HyDE/MCP，只走主路。
- **监控**：队列长度、等待时间、拒绝率、GPU 利用率。

**话术**：「限流不是把用户挡在外面，而是保证已经进来的请求能按时完成。」

---

### Q95 项目里有哪些缓存？怎么失效？

> 考察：缓存设计 ｜ 频率：高

**参考答案**

先说清楚「已落地」和「规划」，别把待优化说成已上线：

| 缓存 | 内容 | 状态 | 失效 |
|---|---|---|---|
| FAQ/高频问题缓存 | 高频问题 → 标准答案 | 部分场景已用 | 文档更新、人工下架 |
| 商品名缓存 | 型号/别名 → item_name | 规划/待优化 | 商品库更新、TTL |
| 语义缓存 | query 向量 → 相似问题的答案 | 规划 | TTL + 相似度阈值 |
| 检索缓存 | query → chunk 列表 | 规划 | 文档版本变更 |
| Prompt/前缀缓存 | 固定 system prompt | 模型侧能力 | 模型/版本变更 |

- 语义缓存要设相似度阈值（如 0.95）⚙️，否则会把不同问题答串。
- 文档更新时按 `item_name` 清相关缓存。
- 缓存命中率、误命中率都要监控。

**追问**：语义缓存的风险？→ 相似但意图不同（「X100 怎么开机」vs「X100 怎么关机」）会被误命中；阈值要高，关键操作类问题不走缓存。

---

### Q96 系统怎么做降级和兜底？

> 考察：可用性设计 ｜ 频率：高

**参考答案**

- **模型降级**：主模型超时/限流 → 备用小模型；再不行 → 抽取式答案/FAQ。
- **链路降级**：关闭 HyDE、MCP，只保留向量主路；减少 rerank 候选。
- **数据降级**：Milvus 不可用 → 缓存/FAQ/历史；返回「稍后重试」。
- **兜底话术**：明确告知服务繁忙/资料不足，给转人工入口。
- **开关**：所有降级项做成配置开关，能快速打开。
- **演练**：定期做故障演练，确认降级真的可用。

**话术**：「降级的目标不是答得好，而是不挂、不瞎答。」

---

### Q97 Milvus 连接失败怎么处理？

> 考察：依赖治理 ｜ 频率：高

**参考答案**

- **客户端单例**：全局复用一个 client，避免每请求建连接。
- **健康检查**：启动时检查，运行中定期探活。
- **超时 + 重试**：设置连接/查询超时，有限次重试 + 退避。
- **熔断**：连续失败打开熔断，一段时间内直接降级，避免雪崩。
- **错误处理**：导入任务标记 failed，记录原因；查询返回空结果并降级到其他源。
- **告警**：连接失败率、查询 P95、load 状态。

**追问**：重试会不会放大故障？→ 要限次数 + 退避 + 熔断，不能无限重试。

### Q98 大模型服务挂了/限流了怎么办？

> 考察：LLM 依赖治理 ｜ 频率：高

**参考答案**

- **超时**：设置首 token 超时和总超时，别无限等。
- **重试**：幂等请求有限重试；流式已输出部分内容时，不要重复整段。
- **切换**：备用模型/备用厂商，prompt 兼容。
- **降级**：跳过 HyDE/改写，直接用检索结果做抽取式回答；或返回 FAQ/缓存。
- **排队**：高峰期进队列，前端提示等待。
- **兜底**：明确告知服务不可用，给转人工。

**加分**：「流式场景要特别处理：已经推给前端的 delta 不能撤回，重试要从断点续，或者直接推 error 让前端重试。」

### Q99 如果日访问量到千万/亿级，架构怎么改？

> 考察：规模化设计 ｜ 频率：高

**参考答案**

先拆解：千万 DAU 不等于千万 QPS。按 10% 渗透、人均 5 次、峰值集中 4 小时估算，QPS 量级在几千，仍可通过水平扩展解决；真正贵的是 LLM 调用。

改造方向：

1. **接入层**：CDN、API 网关、多地域、限流鉴权。
2. **缓存**：FAQ/语义缓存/结果缓存，目标是把 LLM 调用压到 20% 以下。
3. **异步化**：MQ 削峰，长任务排队，SSE 走独立推流服务。
4. **存储**：Milvus 集群分片、读写分离、按租户/业务分区；MongoDB 分片；MinIO 多集群。
5. **模型**：模型网关、多厂商路由、批推理、量化、prefix cache。
6. **可观测**：全链路 trace、容量水位、自动扩缩容。
7. **成本**：缓存命中率、token 预算、按业务分级。

**话术**：「当前架构撑 10 QPS 没问题，千万级要重做接入、缓存和模型服务，不是加机器就行。」

### Q101 多租户/文档权限怎么做？

> 考察：企业级设计 ｜ 频率：中

- 元数据加 `tenant_id`、`doc_id`、`acl`（部门/角色/用户）。

**追问**：权限过滤会不会影响召回性能？→ 会，过滤后候选变少；用分区/分区键、标量索引，必要时按租户分 collection。

### Q102 知识版本更新怎么做灰度？

> 考察：发布设计 ｜ 频率：中

**参考答案**

### Q103 项目里的知识图谱到底做了没有？怎么做的？

> 考察：诚信与深度 ｜ 频率：高 ｜ ⚠️ 原稿前后不一致

**参考答案（按实际情况选）**

**如果做了轻量版：**

> 我们抽了商品、部件、故障码、参数这类实体和关系，作为召回补充；没有做全量图谱平台。查询时把命中实体的关系作为上下文的一部分，和 chunk 一起给 LLM。

**如果只是预研/预留：**

### Q104 怎么看 Agentic RAG / 多跳检索？会用吗？

> 考察：技术视野 ｜ 频率：中

**参考答案**

- Agentic RAG：让模型自己规划查询、选工具、多轮检索、反思结果，适合多跳、比较、需要外部工具的问题。
- 我们的链路是「固定编排 + 可选 MCP」，还不是完全 Agentic；对于手册类问题，固定链路更可控、延迟更低。
- 会用在哪：复杂对比（「X100 和 X200 的功率差多少」）、跨文档、需要查多个系统的场景。
- 代价：LLM 调用次数增加、延迟和成本上升、结果不可预测；要有最大轮次、超时、预算控制。
- 落地路径：先用 LangGraph 加条件边/循环，做「检索够不够」的判断，再逐步放开工具选择。

### Q105 成本怎么优化？

> 考察：成本意识 ｜ 频率：中

**参考答案**

- **减少 LLM 调用**：FAQ 缓存、商品名缓存、简单问题不走 HyDE/改写。
- **减少 token**：断崖截断、上下文压缩、prompt 精简、输出长度限制。

- **基础设施**：GPU 利用率、按峰谷调度、预留实例 vs 按量。

### Q106 数据安全和 Prompt 注入怎么防？

> 考察：安全意识 ｜ 频率：中

**参考答案**

- **文档侧**：上传鉴权、病毒扫描、敏感信息脱敏；文档里的指令不可信，prompt 里明确「资料是数据，不是指令」。
- **权限**：检索前过滤，引用不越权；多租户隔离。
- **输入侧**：限制长度、过滤明显攻击 pattern、限流。
- **输出侧**：敏感信息检测、引用校验、拒答策略。
- **审计**：记录问题、召回、答案、操作人，保留期限。
- **模型侧**：系统 prompt 和用户输入分层，不让用户覆盖系统指令。

**追问**：文档里写「忽略之前的指令」怎么办？→ 这就是间接注入；靠 instruction hierarchy、输入标记、输出校验，不能只靠 prompt。

### Q107 如果答案准确率只有 60%，你怎么排查？

> 考察：系统化排查 ｜ 频率：高

**参考答案**

1. **定义指标**：是 answer_correctness 还是人工口径？先统一。
2. **分层定位**：
   - context_recall 低 → 解析/切片/embedding/过滤/召回；
   - context_precision 低 → 噪声、TopK、rerank；
   - 两者都高但 correctness 低 → prompt/模型/上下文顺序。
3. **分桶**：按商品、问题类型、文档类型看，是不是某一类特别差。
4. **看 bad case**：原文有没有答案、切片是否完整、召回排名、rerank 分数。
5. **改一个变量**：切片、召回、rerank、prompt 分别做对照实验。
6. **回归**：同一批题复测，确认净提升，避免修一个坏一个。

**话术**：「60% 不是模型一个问题，先拆成『没找到』和『找到但答错』，再往下分。」

## 12. 压力面：10 条连环追问链

> 面试官常用的套路是「顺着你的回答追三层」。下面每条链给出追问路径、危险回答和推荐回答。

### 链 1：商品名确认

**追问路径**：怎么做 → 阈值多少 → 阈值怎么定 → 误确认怎么办 → 历史回填错了怎么办 → 为什么不用 NER

- **危险回答**：「阈值 0.8，经验值。」（追一句就穿）
- **推荐回答**：
  - 阈值用标注样本扫出来的，看确认准确率/误确认率/澄清率的平衡；
  - 误确认的代价比多问一句高，所以阈值偏保守；
  - 回填只在高置信度做，且只回填本会话；

### 链 2：RRF

**追问路径**：公式 → k 为什么 60 → 权重为什么 1.0 → 为什么不用分数加权 → Milvus 自带 RRF 为什么不用

- **推荐回答**：

### 链 3：HyDE

**追问路径**：原理 → 会不会幻觉 → 偏了怎么办 → 为什么还留着 → 什么时候关

- **危险回答**：「HyDE 不会偏，模型很准。」
- **推荐回答**：

## 13. 手写/白板题（H1–H6）

> 二面、三面常让现场写伪代码。重点不是语法，而是边界、去重、参数可配置。

### H1 手写 RRF 融合

**题目**：给多路召回结果（每路是按相关性排序的文档列表），按 RRF 融合，返回 TopN。

```python
def rrf_fuse(rank_lists, weights=None, k=60, top_n=20):
    """
    rank_lists: List[List[dict]]，每个 dict 至少有 chunk_id
    weights:   每路权重，默认 1.0
    """
    if weights is None:
        weights = [1.0] * len(rank_lists)

    scores = {}
    best_rank = {}

    for weight, docs in zip(weights, rank_lists):
        seen = set()
        for rank, doc in enumerate(docs, start=1):
            cid = doc["chunk_id"]
            if cid in seen:          # 同一路内去重
                continue
            seen.add(cid)
            scores[cid] = scores.get(cid, 0.0) + weight / (k + rank)
            best_rank[cid] = min(best_rank.get(cid, rank), rank)

    ranked = sorted(scores.items(), key=lambda x: (-x[1], best_rank[x[0]]))
    return [{"chunk_id": cid, "rrf_score": score} for cid, score in ranked[:top_n]]
```

**边界**：空列表、重复 chunk、权重为 0、`k<=0`、同一路重复文档。

**追问**：为什么用 `best_rank` 做第二排序键？→ 分数相同时，优先取在多路中排名更靠前的文档。

### H2 手写断崖截断

**题目**：rerank 结果按分数降序，按绝对差/相对差断崖截断，最少 6 条、最多 15 条。

```python
def cliff_cut(docs, min_k=6, max_k=15, abs_gap=0.5, rel_gap=0.25):
    docs = sorted(docs, key=lambda d: d["score"], reverse=True)
    n = len(docs)
    if n <= min_k:
        return docs

    limit = min(n, max_k)
    for i in range(1, limit):
        gap = docs[i - 1]["score"] - docs[i]["score"]
        base = max(abs(docs[i - 1]["score"]), 1e-6)
        if gap > abs_gap or gap / base > rel_gap:
            return docs[:max(min_k, i)]
    return docs[:limit]
```

**边界**：分数相同、负分、只有 3 条、断崖出现在第 1 位（用 `min_k` 兜底）。

**追问**：为什么不是「绝对差且相对差」同时满足？→ 两个条件取「或」更敏感，宁可多截；如果误截，靠 `min_k` 和评测回调。实际项目要明确用 AND 还是 OR，别含糊。

### H3 手写 Markdown 标题切片

**题目**：按 1–6 级标题切 section，超长递归切，过短合并。

```python
import re

HEADING = re.compile(r"^(#{1,6})\s+(.*)$")

def split_markdown(md, max_len=1200, min_len=300):
    # 1) 按标题切 section，保留层级
    sections, cur = [], {"level": 0, "title": "", "lines": []}
    for line in md.splitlines():
        m = HEADING.match(line)
        if m:
            sections.append(cur)
            cur = {"level": len(m.group(1)), "title": m.group(2).strip(), "lines": []}
        else:
            cur["lines"].append(line)
    sections.append(cur)

    # 2) section 内按段落/句子递归切到 max_len
    chunks = []
    for sec in sections:
        text = "\n".join(sec["lines"]).strip()
        if not text:
            continue
        for piece in recursive_split(text, max_len):
            chunks.append({"title": sec["title"], "content": piece})

    # 3) 同标题下合并过短块
    merged = []
    for c in chunks:
        if merged and len(c["content"]) < min_len and merged[-1]["title"] == c["title"]:
            merged[-1]["content"] += "\n" + c["content"]
        else:
            merged.append(c)
    return merged
```

**要说明的**：`recursive_split` 优先按 `\n\n`、再按句号/问号、最后才硬切；切完保留 `parent_title` 和 `chunk_id`。

**追问**：标题层级怎么保留？→ 维护一个栈，遇到低级别标题弹栈，chunk 里存 `title_path`。

### H4 手写 FastAPI SSE 接口

**题目**：查询接口返回 task_id，`/stream/{task_id}` 持续推送 delta，结束推 final。

```python
import asyncio, json
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()
QUEUES: dict[str, asyncio.Queue] = {}

@app.post("/query")
async def query(payload: dict):
    task_id = new_task_id()
    QUEUES[task_id] = asyncio.Queue()
    asyncio.create_task(run_query_graph(task_id, payload, QUEUES[task_id]))
    return {"task_id": task_id}

@app.get("/stream/{task_id}")
async def stream(task_id: str):
    queue = QUEUES[task_id]

    async def gen():
        try:
            while True:
                event = await queue.get()
                if event["type"] == "delta":
                    yield f"event: delta\ndata: {json.dumps(event, ensure_ascii=False)}\n\n"
                elif event["type"] == "final":
                    yield f"event: final\ndata: {json.dumps(event, ensure_ascii=False)}\n\n"
                    break
                elif event["type"] == "error":
                    yield f"event: error\ndata: {json.dumps(event, ensure_ascii=False)}\n\n"
                    break
        finally:
            QUEUES.pop(task_id, None)

    return StreamingResponse(
        gen(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",
        },
    )
```

**追问**：多 worker 怎么办？→ 队列外置 Redis；或粘性会话；或独立推流服务。

### H5 手写 Milvus 混合检索

**题目**：dense + sparse 混合检索，按 item_name 过滤。

```python
from pymilvus import AnnSearchRequest, WeightedRanker

def hybrid_search(collection, query, item_name, top_k=20):
    dense_vec = embed_dense(query)
    sparse_vec = embed_sparse(query)

    reqs = [
        AnnSearchRequest(
            data=[dense_vec],
            anns_field="dense_vector",
            param={"metric_type": "COSINE", "params": {"ef": 64}},
            limit=top_k,
        ),
        AnnSearchRequest(
            data=[sparse_vec],
            anns_field="sparse_vector",
            param={"metric_type": "IP", "params": {}},
            limit=top_k,
        ),
    ]

    res = collection.hybrid_search(
        reqs,
        rerank=WeightedRanker(0.8, 0.2),
        limit=top_k,
        expr=f'item_name == "{escape(item_name)}"',
        output_fields=["chunk_id", "content", "title", "file_title", "page"],
    )
    return res[0]
```

**要说明的**：`expr` 要做转义，防止注入；过滤字段要有标量索引；`limit` 是每路候选数，不是最终数。

### H6 设计一个幂等导入流程

**题目**：同一文档重复导入、导入中途失败、导入时有人查询，怎么保证正确？

**参考答案**

```
1. 计算文件 sha256
2. 查重：
   - 完全相同 → 提示已存在，可覆盖
   - 同 item_name 不同内容 → 走版本更新
3. 创建 task_id，状态 uploaded
4. 解析 → 切片 → 向量化，产物写临时命名空间（task_id 前缀 / status=staging）
5. 全量校验：chunk 数、抽样内容、关键问题召回
6. 原子切换：alias 指向新版本，或 status active 切换
7. 旧版本置 obsolete，保留 N 天
8. 任一步失败：任务 failed，临时数据清理，旧版本继续服务
9. 重试：从失败节点重试，已完成的解析/embedding 复用
```

**追问**：Milvus 怎么原子切换？→ collection alias 或 `status` 字段 + 查询过滤；alias 更彻底，status 更灵活。

### 30 秒版

> 掌柜智库是商品资料 RAG 知识库。导入侧 MinerU 解析、图片 caption、表格线性化、标题切片、商品名识别、BGE-M3 混合向量入 Milvus；查询侧商品名确认、向量 + HyDE + MCP 三路召回、RRF、BGE-Reranker、断崖截断、LLM 生成、SSE 返回。我负责后端 RAG 核心链路。

### 导入 10 步

> 上传 → task_id → 本地 + MinIO → 状态机 → LangGraph → 类型分支（MinerU/Markdown）→ 图片 caption → 切片 → 商品名 → 向量化 → Milvus

### 查询 10 步

> 提问 → task_id/session → 商品名确认（历史 + LLM + 向量对齐）→ 分支（确认/候选/补充）→ 三路并行召回 → RRF（k=60，20 条）→ Rerank（6–15 条）→ 断崖 → Prompt → LLM → SSE → MongoDB

### 六个关键参数

1. chunk：1200 / 300 / overlap 1 句
2. RRF：k=60，权重 1.0，保留 20
3. Rerank：最少 6，最多 15
4. 断崖：绝对 0.5 或相对 25%
5. 拒答：rerank < 0.3
6. 商品名：0.85 确认 / 0.60 候选

### 三个 trade-off

1. **RRF 先融合 vs 直接 rerank**：成本 vs 精度
2. **chunk 大 vs 小**：上下文完整 vs 信息稀释
3. **多路召回 vs 延迟**：召回率 vs 成本

### 三个不要

1. 不要说「做了完整知识图谱」，除非真能讲 schema 和多跳。
2. 不要只报一个召回率，要说清离线/线上口径。
3. 不要把压测 QPS 和 TPOT 硬凑，先说明输出长度。
