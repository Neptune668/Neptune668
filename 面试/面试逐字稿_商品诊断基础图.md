# 面试逐字稿：商品诊断基础图

> 面向面试的口语化逐字稿，围绕「商品诊断与优化基础图」这一条线的执行流程、依赖注入、观测包装、Token 归一化、中断恢复五个核心点展开。第一人称，可直接照着讲。
> 配套浓缩提纲见 `复习与面试笔记.md`。

---

## 一、开场总述（20 秒）

> 这个模块是电商运营 Agent 里「商品诊断与优化」这条业务线的固定工作流，我用 LangGraph 的状态图实现。它一共七个节点，中间带一个受上限约束的返修环，还有一个人工审核暂停点。整套设计就一个原则：**节点只通过结构化状态和受控工具交换数据，不直接碰数据库**，所有副作用都收口到依赖注入的 `deps` 和运行器里。

---

## 二、执行流程（1 分钟）

> 正常路径是：读商品资料 → 诊断 → 创意 → 质量检查 → 人工审核 → 落库。前三个节点出业务草稿，质量检查是纯规则、不调模型。
>
> 有两个特殊结构。第一个是返修环：质量检查不过，不是直接失败，而是进一个 `prepare_revision` 节点，把问题清单写进 `revision_feedback`、返修次数加一，然后回到诊断节点重跑。图上只有这一条回边，它跟死循环的区别就是受 `max_revisions` 上限约束，次数用完强制交人工；而且这一轮的问题会注入到下一轮提示词里，让重跑有方向。
>
> 第二个是人审暂停：到人审节点我用 `interrupt()` 把流程挂起，草稿、质量报告、返修次数打包给前端，检查点落盘。审核完用**同一个 `thread_id`** 调 `Command(resume=...)` 恢复，从挂起点接着跑，不是从头再来。有个细节，`interrupt` 之前不允许有任何副作用，否则恢复时节点重执行会重复写入。

**边说边画：**

```
START → 读资料 → 诊断 → 创意 → 质量 ─┬─ 返修(回边) → 诊断
                                     └─ 人审 → 落库 → END
```

## 三、依赖注入 `deps`（30 秒）

> 这张图不认识数据库、也不认识运行器，它只认一个 `deps` 对象，里面是四个可替换的函数：读上下文、调模型、记事件、落库。我把这四类副作用全部抽成函数注进去，图里只负责编排。
>
> 这么做的目的有两个：一是**可测试**，测试的时候不用起真实数据库和模型，传个测试替身、用内存检查点就能把整张图跑起来；二是**关注点分离**，权限、租约、幂等这些边界，都能在 `deps` 背后的实现里统一拦住，而不是散在七个节点里。

**四个能力对照：**

| 字段 | 干什么 | 谁在用 |
|---|---|---|
| `load_product_context` | 按 product_id 查库组装商品+竞品上下文 | 读资料节点 |
| `completion_client` | 调 LLM 出结构化结果（含规则兜底） | 诊断、创意角色 |
| `record_event` | 写观测/审计事件 | `_run_observed`、返修、人审节点 |
| `finalize_run` | 幂等落库：诊断、创意计划、状态 | 落库节点 |

---

## 四、观测包装 `_run_observed`（30 秒）

> 有副作用的节点我都包了一层 `_run_observed`，它干三件事：起一个 OpenTelemetry span 拿 trace id，执行前记一条 `agent_step_started`，执行后记 `agent_step_completed`，失败了记 `agent_step_failed` 再把异常原样抛出去——只留痕、不吞错。所有快照都过一遍脱敏，防止密钥或超长文本泄进事件表。
>
> 这样任何一个节点都是「开始、完成、失败」三步留痕，任何一次运行我都能回放它现在走到哪、为什么停在这。而且记事件这个动作本身还顺带做了租约校验和续期，等于每个节点执行时都在做心跳和进度同步。

## 五、Token 归一化（30 秒 + 1 分钟展开）

**核心（30 秒）：**

> 我做了一层 token 归一化，原因是不同 LLM 供应商返回的用量字段长得不一样——OpenAI 用 `prompt_tokens`/`completion_tokens`，Anthropic 用 `input_tokens`/`output_tokens`。如果节点直接读某个字段，换个供应商就崩。所以我在模型返回的地方统一收口，归一成一个标准 `ModelUsage` 结构，后面记账和预算都只认这一套，供应商差异就隔离在入口了。

**展开（1 分钟）：**

> 具体分三步。第一步定义标准结构 `ModelUsage`，四个字段：输入、输出、总 token、调用次数，全部非负。第二步归一化做字段兼容，`input` 优先读 `prompt_tokens`、没有就回退 `input_tokens`；`total_tokens` 供应商没给就用输入加输出自己算，所有值再过非负整数防御，脏数据不污染账本。第三步归一化之后贯穿整个预算体系：每次节点调完模型用 merge 累加进运行级账本；每次调之前用「总预算减已累计」算本次还能用多少，和申请量取较小值，耗尽直接抛异常熔断。

**收口：** 换供应商不改节点，只改入口；成本精确到每次调用；预算硬约束，单节点无法绕过全局预算。

## 六、中断恢复（30 秒 + 1 分钟展开）

**核心（30 秒）：**

> 我的 Agent 工作流里有人工审核，需要跑到一半停下来等人再原样续跑。我用 LangGraph 的 `interrupt` 机制：到人审节点把草稿、质量报告、返修次数打包后挂起，状态写进 PostgreSQL 检查点，用 `thread_id` 定位。恢复时用**同一个 `thread_id`** 调 `Command(resume=...)`，从挂起点接着跑，而不是从头重来。

**展开（1 分钟，三个阶段）：**

> 第一阶段暂停：人审节点调 `interrupt`，图停在原地、检查点落盘。硬约束是 `interrupt` 之前不能有副作用，否则恢复时节点从头重执行会重复写。
>
> 第二阶段等待：暂停后运行记录置 `AWAITING_REVIEW`，同时把租约清空——没有 worker 在跑它了，可以停很久，卖家看到的就是「待审核」。
>
> 第三阶段恢复：卖家提交决定后运行置 `RESUME_QUEUED` 重新进 Celery。worker 认领时用状态卡——恢复只认 `RESUME_QUEUED`、首启只认 `QUEUED`，状态不对就拒绝，防重复消费。然后带同一个 `thread_id` 调 `Command(resume=...)`，`interrupt` 返回审核决定，从挂起点继续走到落库。

**三个关键约束（收口）：** `interrupt` 前无副作用；租约暂停时释放、恢复时重取；落库用幂等键防重投。这样「暂停」就成了一等公民的状态，而不是异常或 hack。

**完整闭环图：**

```
首次: graph.invoke(初始状态, thread_id=T) → ... → interrupt() 挂起
      → checkpoint 落盘 + 运行置 AWAITING_REVIEW + 释放租约
等待: 卖家看到「待审核」
提交: submit_agent_review → 运行置 RESUME_QUEUED
恢复: Celery → graph.invoke(Command(resume=...), thread_id=T)
      → interrupt 返回决定 → 继续 → finalize 落库
```

## 七、六道防线收尾（20 秒，主动抛）

> 整张图被六道闸门框住：操作白名单、预算熔断、返修上限、人审暂停、幂等落库、租约。它们对应的就是 Agent 最容易失控的五类问题——越界读取、死循环、重复副作用、成本失控、不可追溯。我做的不是让模型随便跑，而是把不可控的生成关进可检查的边界里。

| 防线 | 落点 |
|---|---|
| 操作白名单 | 每个节点开头 `require_tool_permission` |
| 预算熔断 | `remaining_model_tokens`，耗尽抛异常 |
| 返修上限 | `revision_count < max_revisions` 封顶 |
| 人审暂停 | `interrupt()` + checkpoint |
| 幂等落库 | `finalize-v1` 操作键 |
| 租约 | 认领写 `lease_owner`，写事件前校验 |

## 八、高频追问 Q&A（口语版）

- **为什么质量检查不调模型？** 因为它要的是确定性和可回放，规则能覆盖的（建议条数、创意数量、角度去重、绝对化词、证明点）就不该赌 LLM。模型不可用时诊断和创意节点还有规则兜底，流程不会断。

- **返修会不会死循环？** 不会，回边只有一条，且受 `max_revisions` 硬约束，图还设了 `recursion_limit` 兜底。

- **暂停后 worker 挂了怎么办？** 状态在检查点里，靠 `thread_id` 定位，恢复用同一个 id 找检查点；落库那步有幂等键，重投直接返回旧结果，不会存两遍。

- **怎么保证不会重复执行？** 两层。认领用状态机卡 + `with_for_update` 加锁，两个 worker 只有一个抢到；落库用幂等键 `finalize-v1`，重投返回旧结果。

- **为什么节点不直接碰库？** 为了可测试和可恢复，副作用收口后审计和权限才拦得住。

- **`thread_id` 是干嘛的？** 检查点的定位键，首启生成 UUID，首次 invoke 和恢复 `Command(resume)` 都用同一个，换一个就是全新运行。

- **为什么暂停要释放租约？** 租约表示有 worker 在处理，暂停后没有 worker 了，占着会被维护任务当「卡住」回收；暂停清空、恢复重取，语义才正确。

- **这张图和平台图的区别？** 基础图一条线写死、节点固定、白名单细到操作级，把「一次受控运行」讲透；平台图按注册表动态组装七条线，一套代码覆盖。坚果场景两条图都能跑，基础图是精细版。

## 九、临场技巧

1. **总-分-总**：先一句话定位 → 讲流程和两个分支 → 六道闸门收尾，让面试官始终知道讲到哪。
2. **边说边画**：流程一定画出来，面试官不会跟丢。
3. **主动抛权衡**：「为什么质量过了还要人审」「为什么返修只回诊断不回创意」，会讲取舍比背流程高一个档次。
4. **术语克制**：每个术语落地到一个具体函数或一行代码，显得是真懂不是背书。
