# Agent / LangChain / LangGraph 面试复习题库

> 来源：个人笔记系统整理。每题含【考察点】与【参考答案要点】，标 ★ 为高频必考题，标 + 为在笔记基础上的合理扩展。

---

## 模块一：LangChain 与 LangGraph

### Q1 ★ 什么是 LangGraph？State、Node、Edge、Conditional Edge 分别是什么？

**考察点**：对 LangGraph 核心抽象的精准理解，能否用一句话讲清框架定位。

**参考答案要点**：
- LangGraph 是面向 Agent 和复杂工作流的**状态机框架**，适合多步骤、可分支、可循环、可恢复的流程。
- **State**：整个流程共享的数据上下文，所有节点读写它。
- **Node**：一个执行步骤（模型调用、工具执行、检索、判断逻辑）。
- **Edge**：节点之间的固定流转关系。
- **Conditional Edge**：根据状态或节点输出**动态决定**下一步走向。
- 一句话对比：LangChain 像"链"，LangGraph 像"图"；LangGraph 中可以直接使用 LangChain 的组件。

### Q2 ★ 什么是 LangChain？核心组件有哪些？在项目中起什么作用？

**考察点**：框架定位 + 组件清单 + 适用场景的判断力。

**参考答案要点**：
- 定位：面向 LLM 应用编排的开发框架，解决提示词组织、模型调用、工具调用、RAG、输出解析、链式执行。
- 核心组件：**Models**（统一封装不同模型调用）、**Prompts**（模板与变量注入）、**Output Parsers**（结构化输出）、**Tools**（外部能力）、**Retrievers/VectorStores**（检索与向量库）、**Chains**（串联步骤）、**Memory**（对话上下文）。
- 适用：线性流程、单次问答、RAG 链路、工具封装等结构稳定的场景；优势是上手快、组件化、开发效率高。

### Q3 ★★ LangChain 和 LangGraph 的区别？分别适合什么场景？

**考察点**：抽象层级与流程复杂度的匹配判断，几乎必考。

**参考答案要点**：

| 维度 | LangChain | LangGraph |
|---|---|---|
| 流程形态 | 线性流程 | 状态驱动的图 |
| 核心能力 | 组件封装、快速搭链 | 多分支、多轮决策、循环/回退/重试/暂停恢复 |
| 适用场景 | 流程固定、分支少（单轮问答、固定工具链、RAG） | 复杂工作流、Agent 编排 |

- 选型原则：简单链路优先 LangChain；涉及多路检索、判断、反复修正、状态流转（如"掌柜智库"类场景）用 LangGraph。

### Q4 LangGraph 和 YAML 配置工作流有什么不同？

**考察点**：静态编排 vs 动态决策的本质区别。

**参考答案要点**：
- YAML 适合**固定流程编排**：节点和流转预先写死，运行期无决策能力。
- LangGraph 适合**有状态的动态决策流程**：可根据运行时状态条件跳转、循环、回退。
- +扩展：YAML 胜在可读性、低代码、易审计；LangGraph 胜在灵活性。实践中常混合使用——确定性主流程用配置，决策节点用 LangGraph。

### Q5 ★ 怎么避免 LangGraph 死循环？

**考察点**：工程鲁棒性意识，"循环必须有边界，失败必须有出口"。

**参考答案要点**：
1. 设置**最大轮次**（如 recursion_limit），强制终止。
2. 将改进结果/失败结果**反馈给下一轮**，让模型感知进展而非原地重复。
3. 给模型**明确的退出条件**（含服务挂掉等异常场景）。
4. 对工具失败设置**兜底分支**（如拒答、转人工）。
- +扩展：还可加状态去重/环路检测（发现 state 重复即中断）、超时控制、循环节点单独监控告警。

## 模块二：Agent 与 RAG 基础

### Q6 ★★ Agent 是什么？和纯提示词、RAG、套壳大模型有什么区别？

**考察点**：对 Agent 本质的定义能力——"有没有完整执行闭环"。

**参考答案要点**：
- **Agent**：带目标、规划、工具调用和状态管理能力的 LLM 应用，能拆解任务→调用工具→读写状态→根据结果继续决策。
- **纯提示词**：一轮输入输出，无外部执行能力。
- **RAG**：重点是检索增强回答，核心是"找资料"，复杂决策依赖额外编排。
- **套壳大模型**：只是聊天界面接模型，无执行闭环。
- 成熟 Agent 核心七要素：**模型、工具、状态、流程控制、记忆、校验、兜底**。

### Q7 ★ 一个成熟的 Agent 架构包含哪些部分？

**考察点**：架构分层能力。

**参考答案要点**：
- **脑**：LLM/ChatModel——理解问题、推理下一步。
- **手**：Tools——搜索、数据库、API、计算器、RAG 检索等。
- **记忆**：Memory/State——上下文、历史对话、中间步骤、业务状态。
- **流程**：Agent Executor/Runtime——执行循环：接收任务 → 模型思考 → 选工具 → 执行 → 观察结果 → 再决策 → 输出。
- +扩展：生产级还需权限控制、日志追踪（如 LangSmith）、评测与灰度。

### Q8 ★★ RAG 是什么？完整链路是什么？

**考察点**：能否完整复述端到端链路，漏环节是常见扣分点。

**参考答案要点**：
- RAG = Retrieval-Augmented Generation，检索增强生成：把外部知识检索出来作为上下文交给模型生成答案。
- 完整链路：**文档解析 → 清洗 → 切分（chunking）→ 向量化 → 索引入库 → 查询处理 → 召回 → 融合重排（rerank）→ 上下文组装 → 答案生成 → 评测监控**。
- +扩展：常见追问——chunk 大小权衡（上下文完整性 vs 召回精度）、混合检索（向量+BM25）、查询改写/HyDE。

### Q9 ★ 大模型为什么需要外挂知识库？RAG 和微调有什么区别？

**考察点**：两大知识注入路线的取舍判断。

**参考答案要点**：
- 外挂知识库的价值：补充**时效性知识、私有领域知识、可追溯来源**，降低训练/微调成本。
- **RAG**：解决外部知识接入，知识存在数据库/向量库/文档库，更新知识=更新知识库，成本低。
- **微调**：改变模型行为、表达风格、任务格式或垂直任务能力，知识进入参数，更新成本高。
- +扩展口诀："知识用 RAG，能力用微调"；两者可结合（微调教会格式与风格，RAG 提供事实）。

## 模块三：任务执行与流程编排

### Q10 ★ Workflow、ReAct、Plan-and-Execute 有什么区别？

**考察点**：三种主流 Agent 组织方式的适用边界。

**参考答案要点**：
- **ReAct**：推理与行动交替，适合动态工具调用、逐步探索、开放性任务。
- **Workflow**：预定义节点和边，适合确定性强、稳定性要求高的生产链路。
- **Plan-and-Execute**：先生成整体计划再逐步执行，适合长任务、可拆解目标。
- 一句话：ReAct 适合开放探索，Workflow 适合稳定生产，Plan-and-Execute 适合复杂长任务。
- +扩展：Plan-and-Execute 的缺点——计划可能失真，常配 replanner；ReAct 的缺点——token 消耗大、易绕圈。

### Q11 ★ ReAct 的结构是什么？Action 的职责是什么？

**考察点**：对 T-A-O 循环的掌握。

**参考答案要点**：
- 基本结构循环：**Thought**（当前如何理解问题）→ **Action**（决定调用哪个工具：查知识库、调接口、跑 SQL、检索）→ **Observation**（工具返回结果）→ 进入下一轮 Thought。
- 价值：让模型围绕"思考—查找—执行—观察"持续推进任务。
- 代价：更依赖**工具质量**和**循环控制**（呼应 Q5 死循环问题）。

## 模块四：工具调用与能力封装

### Q12 ★★ Function Calling 是什么？执行机制是什么？

**考察点**：必须澄清"模型不执行函数"这一常见误解。

**参考答案要点**：
- 定义：让模型按约定格式**选择**并输出要调用的函数名和参数；**模型本身不执行外部函数**，执行由程序完成。
- 机制本质：**装饰器 + 工具映射表**。

```python
tools = {}

def tool(func):
    tools[func.__name__] = {
        "function": func,
        "name": func.__name__,
        "description": func.__doc__,
        "parameters": func.__annotations__,
    }
    return func

@tool
def add(a: int, b: int) -> int:
    """计算两个数的和"""
    return a + b
```

- 执行闭环：模型输出函数名+参数 → 程序查映射表执行 → 结果回传模型 → 生成最终回复。

### Q13 ★ Function Calling、MCP 和 Skill 有什么区别？

**考察点**：三个层次的概念辨析（机制 / 协议 / 封装）。

**参考答案要点**：
- **Function Calling**：一次工具调用的**机制**。
- **MCP**（Model Context Protocol，模型上下文协议）：一组工具或资源的**标准接入方式**。
- **Skill**：一类可复用的**能力封装**，形态不限——文本、脚本、应用程序或网络服务。
- 类比：Function Calling 是"打电话的动作"，MCP 是"统一的电话接口标准"，Skill 是"一整套办事能力包"。

### Q14 ★ 普通 HTTP 接口怎么包装成 MCP？

**考察点**：工程落地能力，最好能手写骨架。

**参考答案要点**：
- 步骤：按能力拆分接口 → 为每个工具定义名称、描述、参数 schema、返回结构 → 服务端处理认证、超时、重试、错误 → 通过 MCP server 统一暴露 → 客户端/Agent 运行时加载工具。
- 关键收益：模型侧看到标准化工具，接口细节由 MCP server 屏蔽。

服务端（FastMCP）：
```python
mcp = FastMCP("business-api", stateless_http=True, json_response=True)

@mcp.tool()
async def query_order(order_no: str) -> dict:
    """根据订单号调用订单系统HTTP接口，查询订单详情。"""
    async with httpx.AsyncClient(base_url=BUSINESS_API_URL, timeout=10.0) as client:
        response = await client.get(f"/api/orders/{order_no}")
        response.raise_for_status()
        return response.json()["data"]

mcp.run(transport="streamable-http")
```

调用端（LangChain 适配器）：
```python
client = MultiServerMCPClient({
    "business_api": {"transport": "http", "url": "http://127.0.0.1:8000/mcp"}
})
tools = await client.get_tools()
agent = create_agent(model=model, tools=tools,
    system_prompt="你是订单客服。查询具体订单时必须调用query_order工具，不能编造订单信息。")
```

### Q15 ★ 单个 Agent 挂载大量工具时，如何解决上下文超限和工具误调用？

**考察点**：多 Agent 拆分与路由的架构思路。

**参考答案要点**：
- 核心方案：**拆分成多个小 Agent**，每个只带自己的工具；通过**意图识别路由**选择对应 Agent。
- +扩展：工具层也可做检索式选择（tool RAG：先按语义召回 top-N 工具再注入）；工具描述写清晰、参数加约束、加调用前确认也能显著降低误调用。

### Q16 ★★ 大模型无法稳定输出结构化 JSON 时如何解决？

**考察点**：结构化输出的三板斧，高频工程题。

**参考答案要点**：
1. **预定义结构**：给模板让模型"完形填空"。
2. **官方 JSON Schema 输出**：部分模型原生支持，注意正确配置（如 response_format）。
3. **校验+回炉**：校验不通过时，把错误信息和上下文重新发给模型让其改正（self-repair / retry loop）。
- +扩展：也可用 Outlines/Guidance 等约束解码库、Function Calling 代替自由 JSON、低 temperature、few-shot 示例。

## 模块五：记忆、上下文与输出控制

### Q17 ★ Agent 记忆怎么设计？短期记忆和长期记忆分别解决什么问题？

**考察点**：记忆分层设计。

**参考答案要点**：
- **短期记忆**：存在对话状态对象中，保存当前窗口/最近几轮上下文；解决代词指代、条件延续、当前任务连续性。
- **长期记忆**：存 MongoDB/MySQL/向量库；保存用户偏好、历史事实、长期画像、可复用知识，支持跨会话复用。
- +扩展：长期记忆写入前要过滤与总结，读出时按相关性召回，避免噪声污染。

### Q18 ★★ LangChain 中常见记忆类型有哪些？如何选择？

**考察点**：五种 Memory 的特性与选型，纯背诵高频题。

**参考答案要点**：

| 记忆类型 | 机制 | 适用 |
|---|---|---|
| ConversationBufferMemory | 保存完整历史 | 短对话；token 消耗高 |
| ConversationBufferWindowMemory | 只留最近 N 轮 | 多轮任务、控制长度 |
| ConversationSummaryMemory | 历史压缩成摘要 | 长对话 |
| VectorStoreRetrieverMemory | 向量化，按语义召回 | 历史跨度大、按需召回 |
| ConversationKGMemory | 抽取实体关系 | 关系推理/矛盾检测（不推荐，维护成本高） |

### Q19 ★ Token 优化怎么做？

**考察点**：成本与上下文工程意识。

**参考答案要点**：
1. 改写问题，去除寒暄、重复内容、无效确认。
2. 控制历史对话数量；长期记忆向量化总结+按需召回。
3. 优化提示词模板，删减冗余词句。
4. 在保证召回率前提下优化 top-k 策略（注意风险）。
5. 利用 FAQ 和缓存，减少 LLM 调用次数。
- +扩展：还可做提示词压缩（LLMLingua）、系统提示词与可变部分分离以命中 KV cache、小模型预处理+大模型精答的分级调用。

### Q20 提示词如何管理和热更新？

**考察点**：提示词工程化（PromptOps）。

**参考答案要点**：
- 提示词放**变量/缓存**中，缓存 miss 时从配置（DB/配置中心）读取。
- 通过**页面控制台**维护更新。
- 更新数据库后**使缓存失效**，实现热更新。
- +扩展：生产环境还应做版本管理、灰度发布、A/B 评测、回滚机制。

## 附：高频考点速记卡

1. LangGraph 四要素：State / Node / Edge / Conditional Edge。
2. 防死循环：最大轮次 + 结果反馈 + 退出条件 + 失败兜底。
3. Agent 七要素：模型、工具、状态、流程、记忆、校验、兜底。
4. RAG 链路：解析→清洗→切分→向量化→入库→查询处理→召回→重排→组装→生成→评测。
5. RAG 管知识，微调管能力。
6. Function Calling：模型只"选函数、给参数"，不执行；机制=装饰器+映射表。
7. MCP 是协议标准，Skill 是能力封装，FC 是调用机制。
8. 工具过多 → 拆小 Agent + 意图路由。
9. JSON 不稳定 → 模板填空 / Schema 输出 / 校验重试。
10. 记忆选型：短 Buffer、多轮 Window、长 Summary、按需 Vector、图谱慎用。
