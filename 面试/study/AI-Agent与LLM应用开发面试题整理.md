## 一、LangChain 与 LangGraph

### Q1. 什么是 LangGraph？状态（State）、节点（Node）、边（Edge）、条件边（Conditional Edge）分别是什么？

**参考答案**

LangGraph 是「面向 Agent 和复杂工作流的状态机框架」，适合处理多步骤、可分支、可循环、可恢复的流程。四大核心概念：

| 概念 | 含义 | 作用 |
|------|------|------|
| **State** | 整个流程共享的数据上下文 | 跨节点传递信息，是流程的「记忆」 |
| **Node** | 一个执行步骤 | 可以是模型调用、工具执行、检索、判断逻辑 |
| **Edge** | 节点之间的固定流转关系 | 确定 A 执行完一定走 B |
| **Conditional Edge** | 根据状态或节点输出决定下一步走向 | 实现分支与动态路由 |

如果说 LangChain 更像「链」，LangGraph 更像「图」。它适合复杂编排，支持分支、循环、重试、暂停和恢复；在 LangGraph 中可以直接复用 LangChain 的组件。

**扩展加分点**

- **State 常用 `TypedDict` 定义**，配合 `Annotated` + reducer（如 `operator.add`）实现消息追加、结果合并，避免多节点并发写状态时互相覆盖。
- **Checkpointer（检查点）** 是 LangGraph 的杀手锏：把每个节点执行后的状态持久化（内存 / SQLite / Postgres / Redis），从而支持 **断点续跑、暂停恢复、人机交互（interrupt）、时间旅行回放**。
- **子图（Subgraph）** 和 **Send API** 支持并行分支、Map-Reduce 模式，是构建复杂多 Agent 系统的关键。
- 版本上 `StateGraph` 是常用入口，`Command` 对象可显式控制状态更新与下一步路由。

**面试追问**

1. LangGraph 的 checkpointer 是怎么实现「暂停 / 恢复」的？
2. 状态里多个节点并行写同一个字段，怎么避免覆盖？（reducer）
3. 怎么在一个图里实现「循环直到满足条件」？（条件边 + 终止节点）

### Q2. 什么是 LangChain？有哪些核心组件？在项目里起什么作用？

**参考答案**

LangChain 是面向 LLM 应用编排的开发框架，重点解决提示词组织、模型调用、工具调用、检索增强、输出解析和链式执行这些问题。常见组件：

| 组件 | 职责 |
|------|------|
| **Models** | 统一封装不同大模型的调用 |
| **Prompts** | 管理提示词模板和变量注入 |
| **Output Parsers** | 把模型输出转成结构化结果 |
| **Tools** | 让模型调用外部能力 |
| **Retrievers / VectorStores** | 接检索、向量库、RAG |
| **Chains** | 把多个步骤串起来 |
| **Memory** | 管理对话上下文 |

在项目里，LangChain 更适合线性流程、单次问答、RAG 链路、工具封装这类结构稳定的场景，优势是上手快、组件化强、开发效率高。

**扩展加分点**

- **LCEL（LangChain Expression Language）**：用 `|` 管道符把组件串联成 Runnable，天然支持 `invoke / batch / stream / astream`，还能自动获得并发、重试、流式、可观测性。
- **Runnable 接口统一抽象**：Chain / Retriever / Prompt / Model 都实现 Runnable，可自由嵌套组合。
- 面试常见认知：LangChain 的价值在于**快速落地标准化链路 + 生态组件**；缺点是抽象层多、版本变动快、复杂流程调试困难——这正好是 LangGraph 的互补点。
- 新项目里常被追问「LangChain 会不会过重」：可回答「按需取用，重组件化，轻框架绑定」，用 LCEL / 原生 SDK 兜底。

**面试追问**

1. LCEL 是什么？用 `|` 串联有什么好处？
2. 为什么很多团队从 Chain 转向直接用原生 SDK + 自研编排？LangChain 的坑有哪些？

### Q3. LangChain 和 LangGraph 的区别是什么？分别适合什么场景？

**参考答案**

核心区别在于**抽象层级和流程复杂度**。

| 维度 | LangChain | LangGraph |
|------|-----------|-----------|
| 形态 | 线性「链」 | 状态驱动的「图」 |
| 流程 | 固定、分支少 | 多分支、多轮决策、可循环 |
| 状态管理 | 较弱 | 显式 State + 持久化 |
| 典型场景 | RAG、工具链、单轮问答 | Agent 工作流、复杂编排 |
| 控制能力 | 弱 | 循环、回退、重试、暂停恢复 |

适用关系：简单链路优先 LangChain；复杂工作流、Agent 编排优先 LangGraph。

实战例子：电商小二偏单轮问答、工具链固定 → LangChain 够用；掌柜智库涉及多路检索、判断、反复修正、状态流转 → LangGraph 更合适。

**扩展加分点**

- 二者不是互斥的：LangGraph 内部可以调用 LangChain 的组件（Model、Retriever、Tool），是「编排层」与「组件层」的分工。
- 另一个竞品维度是 **Workflow 引擎（如 Dify、Coze、n8n、Temporal）**，偏可视化/工程化，适合非研发或确定性流程；LangGraph 偏代码级、强状态与强控制，适合需要复杂决策和动态路由的 Agent。

**面试追问**

1. 什么时候 LangChain 反而比 LangGraph 更合适？
2. LangGraph 和 Dify / Coze 这类可视化编排平台怎么选？

### Q4. LangGraph 和 YAML 配置工作流有什么不同？

**参考答案**

YAML 更适合「固定流程编排」——节点、顺序、参数预先写死，配置化、可读、易维护；LangGraph 更适合「有状态的动态决策流程」——每一步走向由运行时的状态和模型输出决定。

**扩展加分点**

| 维度 | YAML 配置工作流 | LangGraph |
|------|----------------|-----------|
| 决策时机 | 配置期静态确定 | 运行期动态路由 |
| 状态 | 弱，多为数据透传 | 显式 State，可持久化 |
| 循环/重试 | 需额外约定 | 原生支持 |
| 可编程性 | 低，靠 DSL | 高，直接写 Python |
| 适用 | 确定性、流程化业务 | Agent 动态决策 |

**面试追问**

1. 如果一个流程 90% 固定、10% 需要动态判断，你会怎么选？

### Q5. 怎么避免 LangGraph 死循环？

**参考答案**

从多个层面设防：

1. **设置最大轮次**（max iterations / recursion limit），超限强制终止。
2. **把改进结果 / 失败结果反馈给下一轮处理**，让模型「带着上次结论」继续，而不是原地重复。
3. **给模型明确退出条件**（例如服务挂掉、目标达成即结束）。
4. **对工具失败设置兜底分支**（如拒答），保证失败有出口。

核心思想：**循环必须有边界，失败必须有出口。**

**扩展加分点**

- LangGraph 自带 `recursion_limit` 参数，超限会抛 `GraphRecursionError`，可以捕获后走兜底节点。
- 防止「原地打转」：在 State 里记录已尝试的策略 / 已访问节点，重复出现时强制跳出。
- 路由条件要**显式定义「终止」分支**，不要只有「继续」分支；工具返回值里带明确成功/失败标记，让模型能判断是否收敛。
- 超时兜底：给每次模型调用 / 工具调用加 timeout，防止单步卡死。

**面试追问**

1. LangGraph 的 `recursion_limit` 触发后抛什么异常？怎么优雅兜底？
2. 怎么判断一个 Agent 是在「合理迭代」还是「死循环」？

## 二、Agent 与 RAG

### Q6. Agent 是什么？和纯提示词、RAG、套壳大模型有什么区别？

**参考答案**

**Agent** 是带有目标、规划、工具调用和状态管理能力的 LLM 应用。它能围绕目标拆解任务、调用工具、读写状态，并根据执行结果继续决策。

| 形态 | 核心能力 |
|------|----------|
| **纯提示词** | 只靠一轮输入输出，无外部执行能力 |
| **RAG** | 重点是检索增强回答，核心是「找资料」，复杂决策依赖额外流程编排 |
| **套壳大模型** | 只是把聊天界面接到模型上，无完整执行闭环 |
| **Agent** | 目标 + 规划 + 工具 + 状态 + 决策循环 |

成熟 Agent 的核心要素：模型、工具、状态、流程控制、记忆、校验和兜底。

**扩展加分点**

- 判断「是不是真 Agent」的关键：**是否有「观察 → 决策 → 行动」的自主闭环**，而不是单次问答。
- Agent 能力边界受制于：模型推理能力、工具质量、状态管理、循环控制与评测体系——面试常追问「Agent 为什么在生产中容易翻车」。

**面试追问**

1. 一个「调了搜索工具的问答机器人」算不算 Agent？为什么？
2. Agent 和 RAG 是互斥的吗？两者怎么结合？

### Q7. 一个成熟的 Agent 架构通常包含哪些部分？

**参考答案**

1. **脑 —— LLM / ChatModel**：理解问题、推理下一步该做什么。
2. **手 —— Tools 工具**：可调用的外部能力（搜索、数据库、API、计算器、RAG 检索等）。
3. **记忆 —— Memory / State**：保存上下文、历史对话、中间步骤或业务状态。
4. **流程 —— Agent Executor / Runtime**：执行循环 `接收任务 → 调用模型思考 → 选择工具 → 执行工具 → 观察结果 → 再次决策 → 输出答案`。

**扩展加分点**

成熟 Agent 的完整分层还可以补充：

```
┌─────────────────────────────────────┐
│  UI / 对话入口                        │
├─────────────────────────────────────┤
│  Orchestrator（编排 / 路由 / 循环控制）│
├──────────────┬──────────────────────┤
│  脑 (LLM)     │  记忆 (Memory/State)  │
├──────────────┼──────────────────────┤
│  手 (Tools)   │  检索 (RAG/Knowledge) │
├──────────────┴──────────────────────┤
│  校验 / 兜底 / 评测 / 可观测性          │
└─────────────────────────────────────┘
```

- 生产级 Agent 还必须有：**输入输出校验、权限控制、成本控制、失败兜底、可观测性（trace/log）和评测**。

**面试追问**

1. 除了脑/手/记忆/流程，生产级 Agent 还缺什么？
2. Agent Executor 的执行循环具体怎么落地？

### Q8. RAG 是什么？完整链路是什么？

**参考答案**

RAG = **Retrieval-Augmented Generation（检索增强生成）**：把外部知识库中的内容检索出来，作为上下文交给大模型生成答案。

完整链路：

```
文档解析 → 清洗 → 切分 → 向量化 → 索引入库 → 查询处理 → 召回 → 融合重排 → 上下文组装 → 答案生成 → 评测监控
```

**扩展加分点**

- **切分策略**：按固定长度 / 语义 / 结构（标题、段落）切分，含 overlap 防止语义截断；chunk 大小直接影响召回质量。
- **召回环节**常做**混合检索（Hybrid Search）**：稠密向量（语义）+ BM25（关键词）结合，取长补短。
- **重排（Rerank）**：用 Cross-Encoder 对召回结果二次打分，显著提升 top-k 精度。
- **查询处理**：查询改写、多路召回、HyDE（假设文档嵌入）等优化手段。
- **评测**：召回率 / 准确率 + 答案忠实度（faithfulness）、相关性（relevance），常用 RAGAS 等框架。
- 进阶话题：**RAG vs 长上下文**（百万 token 是否还需要 RAG）、**GraphRAG**（用知识图谱提升多跳推理）、**Agentic RAG**（检索过程由 Agent 动态决策）。

**面试追问**

1. 为什么要做混合检索？BM25 和向量检索各擅长什么？
2. chunk 大小怎么选？过大过小各有什么问题？
3. 长上下文模型时代，RAG 还有必要吗？

### Q9. 大模型为什么需要外挂知识库？RAG 和微调有什么区别？

**参考答案**

外挂知识库用于补充 **时效性知识、私有领域知识、可追溯来源**，同时降低训练和微调成本。

| 维度 | RAG | 微调（Fine-tuning） |
|------|-----|---------------------|
| 知识存放 | 数据库 / 向量库 / 文档库 | 进入模型参数 |
| 更新成本 | 低，更新知识库即可 | 高，需重新训练 |
| 主要作用 | 解决外部知识接入 | 改变行为、风格、任务格式、垂直能力 |
| 可追溯 | 强，可给出来源 | 弱，难以溯源 |

**扩展加分点**

- 一句话总结：**RAG 改「知识」，微调改「能力/风格」**。
- 微调适合：稳定的格式输出、特定语气、领域术语、小模型蒸馏；不适合频繁变动的知识。
- 常见组合拳：**微调打底 + RAG 补知识**，各取所长。
- 追问点：微调的代价不只是算力，还有数据标注、灾难性遗忘、持续维护成本。

**面试追问**

1. 什么情况下应该微调而不是 RAG？给一个具体业务场景。
2. 知识频繁更新（如每天变化的商品库），选 RAG 还是微调？

### Q10. Workflow、ReAct 和 Plan-and-Execute 有什么区别？

**参考答案**

| 方式 | 特点 | 适用 |
|------|------|------|
| **ReAct** | 推理和行动交替进行，动态工具调用、逐步探索 | 开放探索 |
| **Workflow** | 预定义节点和边 | 确定性强、稳定性要求高的业务链路 |
| **Plan-and-Execute** | 先生成任务计划，再逐步执行 | 较长任务、可拆解目标 |

ReAct 适合开放探索，Workflow 适合稳定生产流程，Plan-and-Execute 适合复杂长任务。

**扩展加分点**

- **ReAct**（Reasoning + Acting）源自论文，核心是 Thought-Action-Observation 循环，灵活但可能不稳定、token 消耗大。
- **Plan-and-Execute** 把「规划」和「执行」解耦：先列计划，再交给 executor 逐步执行，可中途重规划（Re-plan），适合多步长任务，但规划错误会整体偏离。
- **Workflow** 最可控、最省 token、最易评测，但灵活性最差。
- 实际系统常用**混合策略**：外层 Workflow 保证主链路稳定，内层用 ReAct 处理局部不确定任务。

**面试追问**

1. Plan-and-Execute 的「计划」错了怎么办？
2. 一个复杂任务，你怎么决定用 ReAct 还是 Workflow？

### Q11. ReAct 的结构是什么？action 的职责是什么？

**参考答案**

ReAct 的价值在于让模型围绕「思考、查找、执行、观察」持续推进任务，因此更依赖工具质量和循环控制。

基本结构（循环）：

1. **Thought**：当前如何理解问题
2. **Action**：决定调用哪个工具（查知识库、调接口、跑 SQL、做检索等）
3. **Observation**：工具返回的结果
4. 再进入下一轮 Thought，直到得出最终答案

**扩展加分点**

- Action 的职责是**把「思考」转化为「具体的工具调用」**：选对工具 + 生成正确的入参，是 ReAct 成败关键。
- ReAct 常见格式：通过提示词约束模型输出 `Thought / Action / Action Input / Observation` 固定结构，配合解析器驱动工具执行。
- 与 Function Calling 的关系：Function Calling 是 ReAct 中「Action」环节的工程化实现（模型输出结构化工具调用而非自由文本）。

**面试追问**

1. ReAct 和 Function Calling 是什么关系？
2. 如果工具返回结果很长，ReAct 怎么避免上下文爆炸？

## 三、工具调用与能力封装

### Q12. Function Calling 是什么？执行机制是什么？

**参考答案**

Function Calling 是让模型**按约定格式选择并调用函数**。关键点：**模型本身不会执行外部函数，只会输出要调用的函数名和参数**，真正执行由应用侧完成。

执行机制的本质是 **装饰器 + 工具映射表**：

```python
tools = {}

def tool(func):
    tools[func.__name__] = {
        "function": func,
        "name": func.__name__,
        "description": func.__doc__,
        "parameters": func.__annotations__,
    }
    return func

@tool
def add(a: int, b: int) -> int:
    """计算两个数的和"""
    return a + b

# 等价于把 add 注册进工具表：tools["add"] = add
```

**扩展加分点**

- 完整闭环：**定义工具 schema → 注入模型 → 模型输出函数名+参数（JSON）→ 应用侧执行函数 → 结果回填模型**，如此循环。
- 现代 API 支持 **tool_choice**（强制/禁止调用工具）、**并行工具调用（parallel tool calls）**、**严格 JSON schema**。
- 工具 schema 质量决定调用成功率：名称、描述、参数类型/枚举/必填项要清晰，描述越准确误调用越少。

**面试追问**

1. 模型「调用函数」时，函数是在模型内部执行的吗？
2. 怎么强制模型必须调用某个工具？（tool_choice）
3. 工具参数校验失败怎么处理？

### Q13. Function Calling、MCP 和 Skill 有什么区别？

**参考答案**

| 概念 | 定位 |
|------|------|
| **Function Calling** | 一次工具调用机制（模型层能力） |
| **MCP** | 一组工具/资源的标准接入方式；全称 **Model Context Protocol（模型上下文协议）** |
| **Skill** | 一类可复用的能力封装，形式可以是文本、脚本、应用程序或网络服务 |

**扩展加分点**

- 三者层级关系：**Function Calling 是「单次调用动作」，MCP 是「工具的标准接入协议」，Skill 是「能力的封装单元」**。
- MCP 三大原语：**Tools（可调用函数）、Resources（可读取的数据/文件）、Prompts（可复用提示词模板）**。
- MCP 架构：**Host（宿主应用，如 Claude/IDE）→ Client → Server**，一个 Host 可连多个 Server，实现工具生态复用。
- MCP 传输方式：**stdio（本地进程）、SSE（HTTP）、Streamable HTTP**。
- Skill 相比 MCP 更偏「带指令的能力包」，可包含工作流、专业知识、脚本等，不限于单个工具。

**面试追问**

### Q14. 普通 HTTP 接口怎么包装成 MCP？

**参考答案**

常见步骤：

1. 按能力拆分 HTTP 接口
2. 为每个工具定义名称、描述、参数 schema 和返回结构
3. 在服务端处理认证、超时、重试和错误
4. 通过 MCP server 统一暴露工具
5. 在客户端 / Agent 运行时加载 MCP 工具

这样模型侧看到的是标准化工具，接口细节由 MCP server 屏蔽。

**服务端示例**：

```python
import os
import httpx
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("business-api", stateless_http=True, json_response=True)

BUSINESS_API_URL = os.getenv("BUSINESS_API_URL", "http://127.0.0.1:8080")

@mcp.tool()
async def query_order(order_no: str) -> dict:
    """根据订单号调用订单系统HTTP接口，查询订单详情。"""
    async with httpx.AsyncClient(base_url=BUSINESS_API_URL, timeout=10.0) as client:
        response = await client.get(f"/api/orders/{order_no}")
        response.raise_for_status()
        result = response.json()
    return result["data"]

if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

**调用端示例**：

```python
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "business_api": {
        "transport": "http",
        "url": "http://127.0.0.1:8000/mcp",
    }
})

tools = await client.get_tools()

agent = create_agent(
    model=model,
    tools=tools,
    system_prompt=(
        "你是订单客服。查询具体订单时必须调用query_order工具，不能编造订单信息。"
    ),
)
```

**扩展加分点**

- 包装核心是把**「HTTP 细节」抽象成「模型友好的工具描述」**：认证、超时、重试、错误码翻译都在 Server 侧消化。
- 安全与治理：MCP Server 需要鉴权、限流、审计；错误应转成模型能理解的语义（而非裸 500）。
- 生产建议：接口变更时只改 MCP Server 内部实现，对模型侧 schema 保持稳定，实现「接口解耦」。

**面试追问**

1. 为什么要用 MCP 而不是让 Agent 直接调 HTTP？
2. MCP Server 里的错误（如 404）怎么优雅返回给模型？

### Q15. 单个 Agent 挂载大量工具时，如何解决上下文超限和工具误调用？

**参考答案**

把大 Agent 拆成多个小 Agent，每个 Agent 只带自己的工具，再通过**意图识别路由**选择不同的 Agent。

**扩展加分点**

- **工具描述本身占上下文**：几十上百个工具会挤占 token，且让模型选错工具的概率上升——这是「多工具」和「单 Agent」的根本矛盾。
- 优化手段（由轻到重）：
  1. **精简工具描述**，只保留必要信息；
  2. **动态/按需注入**：先路由意图，只给相关工具子集；
  3. **拆多 Agent + 路由（Router/Master）**：每个子 Agent 职责单一；
  4. **工具检索（Tool Retrieval）**：把工具向量化，按需召回相关工具；
  5. **分层编排**：Master 规划 + Worker 执行。
- 关键权衡：拆 Agent 降低单点复杂度，但引入路由错误、多 Agent 通信开销，需配合评测保证路由准确率。

**面试追问**

1. 拆多 Agent 后，路由错误了怎么办？
2. 「工具检索」和「意图路由」有什么区别？

### Q16. 大模型无法稳定输出结构化 JSON 时如何解决？

**参考答案**

1. **预定义好结构给模型做「完型填空」**：给模板/骨架，让模型填空而非自由生成。
2. **部分官方模型支持 JSON Schema 输出**，注意配置（如 `response_format`、`tool_choice` 等）。
3. **增加校验环节**：校验不通过时，把错误和上下文重新发给模型让它改正（重试 + 纠错）。

**扩展加分点**

- 完整策略链：**约束输出格式（JSON Schema / 正则 / 模板）→ 解析 → 校验 → 失败重试（带错误反馈）→ 兜底**。
- 兜底手段：换更强的模型、降级为自由文本 + 后解析、用 Pydantic 做 schema 校验与自动修复。
- 也可以**用 Function Calling 输出结构化参数**，天然比裸 JSON 更稳。
- 校验闭环的细节：把「解析失败原因」回传给模型，比「重新生成」更有效。

**面试追问**

1. 用 Function Calling 输出结构化数据，和用 JSON Schema 约束有什么区别？
2. 校验失败重试最多几次？重试还失败怎么办？

## 四、记忆、上下文与输出控制

### Q17. Agent 记忆怎么设计？短期记忆和长期记忆分别解决什么问题？

**参考答案**

| 记忆类型 | 存储位置 | 解决的问题 |
|----------|----------|-----------|
| **短期记忆** | 对话状态对象 | 保存当前对话窗口和最近几轮上下文，解决代词指代、条件延续、当前任务连续性 |
| **长期记忆** | MongoDB / MySQL / 向量存储 | 保存用户偏好、历史事实、长期画像、可复用知识，支持跨会话复用 |

**扩展加分点**

- 记忆分层可进一步细化为：**工作记忆（当前任务）→ 会话记忆（当前对话）→ 长期记忆（跨会话）**。
- 长期记忆又分 **语义记忆**（事实、偏好，可结构化存储）和 **情景记忆**（历史对话片段，向量化按需召回）。
- 记忆设计核心三问：**存什么、怎么存、怎么召回**；以及遗忘机制（过期/重要性衰减）和隐私合规。

**面试追问**

1. 短期记忆和长期记忆分别用什么技术方案？
2. 长期记忆怎么保证「该记得的记得、该忘的忘」？

### Q18. LangChain 中常见记忆类型有哪些？

**参考答案**

| 记忆类型 | 特点 | 适用 |
|----------|------|------|
| **ConversationBufferMemory** | 保存完整对话历史，简单直接 | 短对话，但 token 消耗高 |
| **ConversationBufferWindowMemory** | 只保留最近 N 轮 | 控制上下文长度、多轮任务 |
| **ConversationSummaryMemory** | 历史对话压缩成摘要 | 长对话 |
| **VectorStoreRetrieverMemory** | 历史内容向量化，按语义召回 | 历史跨度大、按需召回 |
| **ConversationKnowledgeGraphMemory** | 抽取实体和关系 | 关系追踪（不推荐，成本高） |

选择方式：短对话用 BufferMemory；多轮任务用 WindowMemory；长对话用 SummaryMemory；历史跨度大用 VectorStoreRetrieverMemory；关系推理用 KnowledgeGraphMemory（一般不推荐）。

**扩展加分点**

- 真实项目常**组合使用**：Window（近期原话）+ Summary（远期摘要）+ Vector（历史长尾召回）。
- 用 LangGraph 后，很多团队直接用 State + Checkpointer 自管记忆，比 LangChain 传统 Memory 更灵活可控。
- 图谱记忆（KnowledgeGraph）能支持实体关系推理和矛盾检测，但构建成本高、易出错，所以「不推荐」作为首选。

**面试追问**

1. SummaryMemory 的摘要丢失细节怎么办？怎么和 Window 结合？
2. 用 LangGraph 后还需要 LangChain 的 Memory 吗？

### Q19. Token 优化怎么做？

**参考答案**

1. **去除寒暄、重复内容和无效确认**，通过改写问题完成。
2. **控制获取历史对话数量**，长期记忆通过向量总结并向量召回。
3. **优化提示词模板**，减少无用冗余词句。
4. **在保证召回率的情况下优化 top-k 策略**（有风险，需权衡）。
5. **利用 FAQ 和缓存减少调用 LLM 的次数**。

**扩展加分点**

- **减少 token 的三个维度**：① 减少输入（压缩历史、精简提示词、动态注入）；② 减少调用次数（缓存、FAQ、规则兜底）；③ 降低单次成本（小模型分流、分级路由）。
- **Prompt Caching / 前缀缓存**：把稳定的 system prompt / 工具 schema 放前面命中缓存，显著降成本。
- **结构化输出 / 约束输出** 也能减少无谓的冗长生成。
- **top-k 优化是「召回率 vs 成本」的权衡**，砍太多会漏关键信息，需用评测数据验证，不能拍脑袋。

**面试追问**

1. Prompt Caching 的原理是什么？怎么让它命中？
2. 砍 top-k 降成本的风险是什么？怎么评估？

### Q20. 提示词如何管理和热更新？

**参考答案**

1. **提示词放在变量或缓存中**，缓存不存在时从配置中读取。
2. **通过页面控制台更新维护提示词**。
3. **更新数据库中的提示词后，失效缓存**，实现热更新。

**扩展加分点**

- 完整提示词管理体系：**版本管理（可回滚）→ 配置中心存储 → 缓存 + 失效 → A/B 测试 → 效果评测 → 灰度发布**。
- 热更新关键：**配置与代码解耦**，改提示词不重新发版；缓存失效策略（主动失效 / TTL / 版本号比对）。
- 提示词要**模板化 + 变量注入**，区分「稳定骨架」和「动态变量」。
- 生产实践：提示词变更必须有评测回归，避免「改了提示词把线上效果改坏」。
- 进阶：提示词可结合「动态拼接」——按用户画像、场景、历史召回结果动态组装。

**面试追问**

1. 提示词热更新时，缓存怎么保证一致性？
2. 怎么验证一个新提示词比旧的好？（A/B 测试 + 评测）
