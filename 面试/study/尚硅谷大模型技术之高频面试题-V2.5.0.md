### 2.闭包三要素

存在函数嵌套（内部函数定义在外部函数中）；内部函数引用了外部函数的变量；外部函数返回内部函数的引用。

### 4.什么并发并行，同步和异步

并发：多个任务在同一时间段内交替推进。在单个 CPU 核上，靠时间片切换就能实现，所以是“看起来同时”。
并行：多个任务在同一时刻真正同时执行。必须有多个核或多台机器，所以是“确实同时”。

同步：发起调用后原地等结果，拿到才继续。
异步：发起后立即返回，结果靠回调/通知送达。

*协程*：用户态、可挂起和恢复的执行单元**

**进程优缺点**：**操作系统分配资源的独立单元**，隔离好、稳定、并行强，	但开销大、通信复杂

**多线程优缺点**：开销小、共享数据方便，	但隔离差、一个线程崩溃可能影响整个进程。

**多协程适合**“高并发、I/O 等待多、任务轻量”的场景

## 二、langchain,graph

### 1.什么是

- **LangChain**：是一个面向 LLM 应用编排的开发框架，重点解决提示词、模型调用、工具调用、RAG、输出解析、上下文管理等能力封装问题。
- **LangGraph**：是面向 **Agent 和复杂工作流的状态机/图编排框架**，用“状态 + 节点 + 边 + 条件边”来编排多步骤、可分支、可循环、可恢复的流程。

yaml用户拖拉拽流程存储；LangGraph 更适合“有状态的动态决策流程”

### 2.二者区别

> **LangChain 解决“把 LLM 应用组件串起来”的问题；LangGraph 解决“让复杂流程按状态动态流转”的问题。**

所以：

- **线性流程、单次问答、RAG 链路、工具封装这类结构比较稳定的场景，优势是上手快、组件化强、开发效率高。** → 用 LangChain 更合适；
- **多分支、多轮决策、需要循环/重试/恢复** → 用 LangGraph 更合适。

### 3.graph死循环

设置最大轮次，讲改进结果/失败结果反馈给下次的处理，给模型明确退出条件（服务挂掉），对工具失败设置兜底分支（拒答）

## 三、Agent 与 RAG

langchainAPI-->`create_agent()``create_deep_agent()`

将模型的一次性判断，组织成有状态、可控制、可恢复的持续任务过程

### 1. 基础概念与架构

#### 1.1 Agent 是什么，和纯提示词、RAG、套壳大模型有什么区别

Ø **Agent** 是带有目标、规划、工具调用和状态管理能力的 LLM 应用。它能够围绕目标拆解任务、调用工具、读写状态，并根据执行结果继续决策。

Ø **纯提示词：**只靠一轮输入输出，没有外部执行能力

Ø **RAG****：**重点是检索增强回答，核心是找资料，复杂决策能力依赖额外流程编排

Ø **套壳大模型：**只是把聊天界面接到模型上，没有完整执行闭环

成熟 Agent 的核心是模型、工具、状态、流程控制、记忆、校验和兜底。

#### 1.2 一个成熟的 Agent 架构通常包含哪些部分

-->agent=llm+harness

1.2.1 脑：LLM / ChatModel

负责理解问题、推理下一步该做什么。

1.2.2 手：Tools 工具

Agent 可调用的外部能力，比如搜索、数据库、API、计算器、RAG 检索等。

1.2.3 记忆：Memory / State

保存上下文、历史对话、中间步骤或业务状态，让 Agent 能连续处理任务。

1.2.4 流程：Agent Executor / Runtime

负责执行循环：

接收任务 -> 调用模型思考 -> 选择工具 -> 执行工具 -> 观察结果 -> 再次决策 -> 输出答案。

#### 1.3 RAG 是什么，完整链路是什么

RAG 是 Retrieval-Augmented Generation，检索增强生成。它把外部知识库中的内容检索出来，作为上下文交给大模型生成答案。

完整链路包括文档解析、清洗、切分、向量化、索引入库、查询处理、召回、融合重排、上下文组装、答案生成和评测监控。

#### 1.4 大模型为什么需要外挂知识库，RAG 和微调有什么区别

大模型外挂知识库用于补充时效性知识、私有领域知识和可追溯来源，也用于降低训练和微调成本。

RAG 主要解决外部知识接入问题，知识保存在数据库、向量库或文档库中，更新知识时更新知识库即可。

微调主要改变模型行为、表达风格、任务格式或垂直任务能力，知识和模式会进入模型参数，更新成本更高。

### 2. 任务执行与流程编排

#### 2.1 Workflow、 ReAct和 Plan-and-Execute 有什么区别

ReAct、Workflow 和 Plan-and-Execute 是常见的 Agent 或工作流组织方式。

Ø **ReAct****：**推理和行动交替进行,动态决策，适合动态工具调用和逐步探索-->通用agent

Ø **Workflow****：**预定义节点和边，适合确定性强、稳定性要求高的业务链路

Ø **Plan-and-Execute****：**先生成任务计划，再逐步执行，适合较长任务和可拆解目标

ReAct 适合开放探索，Workflow 适合稳定生产流程，Plan-and-Execute 适合复杂长任务。

> 全局workflow编排,其中一小步(一个节点)可以用上面的动态决策

#### 2.2 ReAct 的结构是什么，action 的职责是什么

**ReAct** 的价值在于让模型围绕“思考、查找、执行、观察”持续推进任务，也因此更依赖工具质量和循环控制。

ReAct 的基本结构：

Ø **Thought****：**当前如何理解问题

Ø **Action****：**决定调用哪个工具（比如查知识库、调接口、跑 SQL、做检索。）

Ø **Observation****：**工具返回的结果

### 3 工具调用与能力封装

#### 3.1 Function Calling 是什么，执行机制是什么？

Function Calling 是让模型按约定格式选择并调用函数。模型本身不会执行外部函数，只会输出要调用的函数名和参数。

执行机制的本质是 装饰器 + 工具映射表

#### 3.2 Function Calling、MCP 和 Skill 有什么区别

Ø **Function Calling****：**一次工具调用机制

Ø **MCP****：**一组工具或资源的标准接入方式(MCP 的全称是 **Model Context Protocol****（模型上下文协议**)

Ø **Skill****：**一类可复用的能力封装，而能力可以是各种形式可能是文本，可能是脚本、应用程序或者网络服务。

> skill,渐进式加载
>
> 调用工具幂等处理，避免多次调用的错误结果；
>
> 工具误调用:调整描述信息；

#### 3.3 普通 HTTP 接口怎么包装成 MCP

常见步骤：

1.按能力拆分 HTTP 接口

为每个工具定义名称、描述、参数 schema 和返回结构

2.在服务端处理认证、超时、重试和错误

通过 MCP server 统一暴露工具

3.在客户端或 Agent 运行时加载 MCP 工具

这样模型侧看到的是标准化工具，接口细节由 MCP server 屏蔽。

#### 3.4 单个 Agent 挂载大量工具时，如何解决上下文超限和工具误调用

可以把大Agent拆成多个小Agent每个Agent只带自己的工具即可，然后通过意图识别路由的方式选择不同的Agent。

#### 3.5 大模型无法稳定输出结构化 JSON 时如何解决

**1）**预定义好结构给大模型让模型模型做完型填空

**2）**部分官方模型支持json schema输出 ，注意配置

**3）**增加校验环节，校验如果不通过，把错误和上下重新发给模型让它改正。

### 4 记忆、上下文与输出控制

#### 4.1 Agent 记忆怎么设计，短期记忆和长期记忆分别解决什么问题

短期记忆：存储在对话状态对象中。

长期记忆：存储MongoDB或MySQL或向量存储。

Ø **短期记忆：**保存当前对话窗口和最近几轮上下文，解决代词指代、条件延续和当前任务连续性

Ø **长期记忆：**保存用户偏好、历史事实、长期画像和可复用知识，支持跨会话复用

#### 4.2 LangChain 中常见记忆类型有哪些

Ø **ConversationBufferMemory****：**保存完整对话历史，简单直接，token 消耗高

Ø **ConversationBufferWindowMemory****：**只保留最近 N 轮对话，适合控制上下文长度

Ø **ConversationSummaryMemory****：**把历史对话压缩成摘要，适合长对话

Ø **VectorStoreRetrieverMemory****：**把历史内容向量化，需要时按语义召回

Ø **ConversationKnowledgeGraphMemory****：**抽取实体和关系，适合需要实体关系追踪的复杂对话

##### 选择方式：

Ø 短对话用 BufferMemory

Ø 多轮任务用 WindowMemory

Ø 长对话用 SummaryMemory

Ø 历史跨度大、需要按需召回用 VectorStoreRetrieverMemory 向量存储

Ø 需要关系推理和矛盾检测用 KnowledgeGraphMemory 图谱记忆（不推荐）

### 5. 多智能体协作与状态管理

#### 5.1 什么是多智能体，什么场景下需要多智能体

多智能体是把复杂任务拆给多个角色化 Agent 协同完成。每个 Agent 负责自己擅长的一段，比如规划、检索、执行、审核、总结。

适合多智能体的场景：

Ø **职责不同：**提示词定位不同

Ø **技能不同：**各自的工具集

Ø **能力不同：**需要不同能力级别的模型

Ø **进程不同：**需要并行处理。

#### 5.2 多智能体之间怎么通信，消息里通常包含什么

通信方式：函数调用x、**共享状态**或消息队列传递信息。

共享状态--->加一个父graph

消息一般包含：任务 ID、任务目标、必要资料、执行状态，以及返回的结论、依据和不确定性(置信度)。

#### 5.3 多智能体如何做任务规划、协调和编排

可以从两个方面理解：

**1****）谁来协调任务：

·    **路由式**：根据任务类型，分配给合适的 Agent。

·    **`主控式`**：主 Agent意图识别, 拆解和分派任务，子 Agent 执行后返回，由主 Agent 汇总。

·    **交接式**：当前 Agent 将处理权交给另一个 Agent，由接收方继续负责。

**2****）任务如何执行：

·    **流水线**：有依赖的任务按顺序执行，例如“收集 → 撰写 → 审核”。

·    **并行汇总**：独立任务同时执行，最后合并结果。

这些方式可以组合使用。核心是明确**任务怎么拆、谁来做、先后关系、结果交给谁**，并由程序管理任务状态、异常处理和结束条件。

#### 5.4 多智能体和并发怎么考虑

**1）**拆分多线程, 也可以做多进程

**2）**状态隔离(提示词,state)，不能出现并发写入同一状态的问题

**3）**超时等待处理，不能永久等待

**4）**结果汇总合并

#### 5.5 多Agent如何做全局状态管理

核心共享状态，推荐交给主Agent或者某个专职Agent管理。其他子Agent只维护自己部分的状态。

#### 5.6 子Agent故障如何隔离和降级

每个子Agent 应设置超时、重试、异常捕获和独立日志，失败不应阻断整个系统。

降级方式包括：

1. 使用备用模型（如果调用模型超时）

2.  简化工具链（绕过有问题的工具）

3. 跳过非关键子任务

主 Agent 需要在全局状态中记录失败原因和降级结果。

#### 5.7 多Agent系统如何监测和打破死循环

最大轮数、最大工具调用数。langsmith工具

增加退出策略

#### 5.8 多Agent如何共享上下文？

采用“公共资料按需共享，各自保留工作记录”的方式。给子 Agent 提供目标、相关证据和必要约束，返回时带上结论与来源；不必把全部聊天记录复制给所有 Agent。

> 可以用队列rabbit

#### 5.9 多agent和单agent的区别和优势

多 Agent 的优势是专业分工、权限隔离和并行处理，但沟通成本、耗时和费用也可能更高，简单任务用单 Agent 往往更合适。**任务可以拆分**

#### 5.10 多Agent系统运行结果的可靠性怎么保证的🛫

靠证据核对、程序校验、测试评估和必要的人工审核共同提高可靠性。关键结果要检查真实数据和执行记录，不能因为多个 Agent 都说“成功”就认为一定正确。

> 主agent调用tools，审核子agent的结果和依据

#### 5.11 多Agent调用的过程中有异常怎么办？比如死循环？

先记录现场，再按异常类型处理：临时网络问题有限重试，参数错误限次修正，权限问题停止或转人工，死循环强制终止。写操作超时后要先查是否已经成功，避免重试造成重复执行。

#### 5.12 多Agent并发调用同一工具或数据库时，如何处理争抢问题？

### 7. 检索、召回与重排

1.1.1.1 什么是向量，维度和相似度怎么理解

Ø **向量**：把一段文字变成一串数字，相当于文字的“语义坐标”。意思越接近，坐标越接近。

Ø **维度**：这串数字的长度。例如 768 维，就是用 768 个数字描述语义特征。维度越高，表达通常越细致，但计算和存储成本也越高。

Ø **相似度：**衡量两个向量有多接近。分数越高，表示两段文字的含义越相似。

## 四、OpenClaw & Hermes & Loop Engineering

1.1.1 Loop Engineering工程和Hermes的关系是什么

1.1.1.1.1 Loop工程是把智能体执行任务设计成持续闭环

Ø 输入目标

Ø 规划任务

Ø 调用工具

Ø 观察结果

Ø 校验输出

Ø 沉淀记忆或技能

Ø 进入下一轮优化

Hermes这类 Agent 框架强调任务执行后的记忆沉淀、技能复用和反馈闭环，属于 Loop 工程的一种落地形态。

1.1.1.1.2 OpenClaw 和 Hermes 的关注点

Ø **OpenClaw****：**更偏智能体编排、任务入口、工具生态和人工控制

Ø **Hermes****：**更偏长期记忆、执行反馈、技能沉淀和闭环学习

Ø **Loop****工程：**关注整个“执行、反馈、沉淀、复用”的工程闭环

1.1.1.1.3 落地时要看四个能力：

Ø 状态是否可持久化

Ø 工具调用是否可观测

Ø 错误是否能进入反馈闭环

Ø 经验是否能沉淀为规则、记忆或 Skill



1.1.2 怎么理解 Claude Code Hooks 和 Software Development Vibe

Claude Code Hooks 是 Claude Code 生命周期里的自动化机制，可以在特定事件发生时执行脚本、HTTP 调用或模型判断。

1.1.2.1.1 典型用途：

Ø **PreToolUse****：**工具执行前检查权限、阻止危险命令

Ø **PostToolUse****：**工具执行后自动格式化、跑测试、记录日志

Ø **Notification****：**需要用户输入时发送提醒

Ø **SessionStart****：**会话开始时注入项目上下文

Ø **Stop****：**任务结束时生成报告、更新记录

Hooks 的价值是把工程规则变成稳定执行的自动动作，减少只依赖模型自觉执行规则的问题。

Software Development Vibe 指的是 AI 参与开发时的整体协作方式，包括需求描述、上下文组织、任务拆解、代码生成、测试验证、代码审查和持续迭代。

1.1.2.1.2 两者关系：

Ø Vibe Coding 更偏自然语言驱动开发和快速探索

Ø Software Development Vibe 更偏完整软件工程协作流程

Ø Hooks 是把这种流程工程化、自动化和可控化的机制

成熟的 AI 开发流程通常是“清晰需求 + 足够上下文 + 自动校验 + Hooks 控制 + 人工审核”组合使用。



1.1.3 Harness

1.1.3.1 什么是 Harness 工程

Harness 工程是围绕智能体或 AI 编程工具搭建的一套“约束、上下文、工具、反馈和评测环境”。它关注模型之外的工程控制层，让智能体在明确边界内完成任务。

常见组成：

Ø **上下文：**需求文档、架构说明、接口规范、代码规范、业务规则

Ø **工具：**测试命令、格式化命令、代码扫描、日志查询、检索工具、MCP 工具

Ø **约束：**权限控制、禁止危险操作、输出格式要求、代码边界

Ø **反馈：**单元测试、集成测试、lint、类型检查、评测集、人工审核

Ø **闭环：**失败案例沉淀成规则、脚本、测试或新的文档



1.1.3.2 Harness 和 RDD、DDD、TDD 的关系是什么

RDD、DDD、TDD 都可以放进 Harness 里，作为智能体执行任务时的输入和反馈。

Ø **RDD****：**需求或文档驱动开发，先把目标、边界、验收标准写清楚

Ø **DDD****：**领域驱动设计，用领域模型、实体、聚合、服务边界约束系统结构

Ø **TDD****：**测试驱动开发，用测试定义功能行为和验收条件

Ø **Harness****：**把需求、领域模型、测试、规范、工具和反馈机制组合成智能体可用的工作环境

在项目里，RDD 提供任务目标，DDD 提供业务边界，TDD 提供可验证反馈，Harness 把这些内容组织成智能体能执行、能校验、能回滚的工程流程。



1.1.3.3 Harness 工程怎么用，应用中靠谱吗

1.1.3.3.1 Harness 的使用方式：

Ø 给智能体提供项目说明、目录结构、接口文档和业务规则

Ø 用测试、lint、类型检查、静态扫描约束输出质量

Ø 用 hooks 或脚本在关键节点自动执行校验

Ø 对高风险操作加入审批、白名单和回滚机制

Ø 对失败案例沉淀规则、测试用例和补充文档

Harness 工程适合多人协作、长期维护、质量要求高的项目。它能降低 AI 输出的不确定性，提高代码、流程和业务结果的可控性。

1.1.3.3.2 应用中的边界：

Ø 需求模糊时，Harness 只能约束执行，不能替代需求澄清

Ø 测试覆盖不足时，反馈信号会不完整

Ø 业务规则没有文档化时，智能体仍然容易误判

Ø 高风险场景需要人工审核和权限控制



1.1.3.4 如果用 Harness 工程重构 AI 客服，哪些地方能做得更好

AI 客服适合用 Harness 工程做重构，因为它涉及知识检索、工具调用、权限控制、回复质量、人工兜底和持续评测。

1.1.3.4.1 重构方向：

Ø **场景与规则：**沉淀客服场景、意图分类、话术边界、禁答规则、转人工规则

Ø **知识库治理：**规范文档导入、chunk 切分、召回评测、来源引用和知识更新流程

Ø **工具接入：**封装订单查询、退款查询、物流查询、工单创建等工具

Ø **安全控制：**敏感信息脱敏、危险操作审批、退款等高风险动作拦截

Ø **质量评测：**建立 FAQ 测试集、bad case 集、幻觉检测、转人工率和满意度指标

Ø **运行观测：**记录意图识别、检索结果、工具调用、模型输入输出和耗时

1.1.3.4.2 重构后的 AI 客服流程：

Ø 用户输入进入意图识别

Ø 根据意图选择知识库、工具或固定流程

Ø 检索或工具调用后做结果校验

Ø 生成回复时引用来源并遵守话术边界

Ø 低置信度、高风险或多次失败时转人工

Ø bad case 回流到测试集、规则和知识库

这种方式能让 AI 客服从“能回答”提升到“可观测、可评测、可控制、可持续优化”。

Ø 是否有重复造轮子

Ø 是否和现有业务规则冲突

发现可疑代码时，要回到源码、接口文档、测试结果和运行日志验证，不能只看 AI 的解释。



1.1.6 AI 没有按公共类或公共方法调用怎么办

处理方式：

Ø 明确告诉 AI 先检索项目已有实现

Ø 在提示里指定必须复用的类、方法和模块

Ø 提供相关文件路径和接口签名

Ø 让 AI 先输出调用方案，再写代码

Ø 生成后检查是否重复造轮子

Ø 把错误示例反馈给 AI 重新修改

Ø 把公共能力整理进项目文档或规则文件

团队使用时，把常用公共类、异常规范、返回格式、日志规范写进项目说明，让 AI 每次任务都能读取。



1.1.7 AI Coding 出现幻觉怎么处理

1.1.7.1.1 常见幻觉：

Ø 编造不存在的 API

Ø 编造依赖库方法

Ø 错用业务字段

Ø 忽略权限和异常

Ø 生成看似合理但不可运行的代码

1.1.7.1.2 处理方式：

Ø 要求 AI 引用真实文件和方法

Ø 让 AI 先搜索代码再修改

Ø 运行测试和静态检查

Ø 缩小任务范围

Ø 给出报错信息让 AI 修复

Ø 对关键逻辑人工复核

Ø 把幻觉案例沉淀为规则或测试



1.1.8 AI 生成代码后开发者还要做什么

开发者要负责最终质量。

后续工作：

Ø 读懂生成代码

Ø 检查业务逻辑

Ø 补充异常处理

Ø 补充测试用例

Ø 运行测试和本地验证

Ø 做性能和安全检查

Ø 对关键逻辑做 code review

Ø 调整命名、结构和风格

Ø 提交前确认没有无关改动

AI 负责提升初稿速度，开发者负责判断、取舍、验证和交付。



1.1.9 为什么选择 Claude Code、Cursor 或 Codex

1.1.9.1.1 工具选择要看场景。

Ø **Claude Code****：**适合命令行代理、跨文件修改、长上下文理解、自动执行任务

Ø **Cursor****：**适合 IDE 内联编辑、代码补全、快速改局部文件

Ø **Codex****：**适合代码库任务、补丁生成、测试驱动修复、协作式开发

Ø **Copilot****：**适合日常补全和小段代码生成

1.1.9.1.2 选择标准：

Ø 是否能理解整个仓库

Ø 是否能安全执行命令

Ø 是否方便 review diff

Ø 是否支持团队工作流

Ø 成本是否可控

Ø 输出是否稳定



1.1.10 Claude Code 的工作原理是什么

Claude Code 是面向代码任务的代理式工具。它通过读取项目文件、理解上下文、规划任务、编辑代码、执行命令和根据结果继续修正来完成开发任务。

基本流程：

Ø 读取用户需求

Ø 扫描项目结构和相关文件

Ø 制定修改计划

Ø 编辑代码

Ø 运行测试或命令

Ø 根据报错继续修复

Ø 输出变更说明

关键能力是工具调用和上下文管理。它会结合本地仓库、命令输出和测试结果完成开发闭环。



1.1.11 AI Coding的使用程度、费用和价值怎么评估

使用程度按任务占比说明，比如需求分析、代码初稿、重构、测试、排错、文档各占多少。

费用要按真实情况说明，包括订阅费、API token、公司额度或个人开销。

价值评估：

Ø 节省开发时间

Ø 提升方案探索速度

Ø 减少重复劳动

Ø 提高测试和文档覆盖

Ø 加快排错和重构

Ø 降低新人理解代码成本

成本是否值得，要看节省的人力时间、交付速度、代码质量和返工率。



1.1.12 怎么查看 token 消耗和历史会话

不同工具查看方式不同。

常见方式：

Ø 在工具控制台查看用量统计

Ø 在 API 平台查看 token、请求数和费用

Ø 在本地 CLI 查看历史会话或日志

Ø 在团队管理后台查看成员用量

Ø 对重要任务记录输入、输出、模型和耗时

团队使用时要设置预算、额度、模型选择规则和高成本任务审批
