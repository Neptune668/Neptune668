平台图（多工作流平台编排）

POST /workspaces/{workspace_id}/agent/tasks 接口全链路分析

接口定位：这个接口是 Agent 平台工作台「创建任务」的入口，路由在 agent_platform.py，函数名 create_task()，同步返回 202 + AgentTaskRead。整条链路分三段：同步创建 → 异步投递 → Worker 执行。其中有一处关键分流：Worker 拿到任务后先检查 workflow_key，若为 product_diagnosis_optimization（关键词路由的兜底值，也是默认任务），就转调基础图 graph.py，不构建平台图；只有显式指定其余六条工作流之一，才走 platform_graph.py 的平台图。以下按完整链路依次说明创建与投递、平台图拆解，并对照两条图的差异。

一、同步创建阶段：从提交任务到 202 返回

前端在 Agent 工作台提交任务（自然语言意图，或选模板指定工作流）后，一次请求在同一个数据库事务里写四张表。与商品工作台入口不同，这条入口的四表写入无条件成立——没有「工作区没启用就跳过」的分支。整体流程：

二、异步投递阶段：Outbox 可靠投递

三、Worker 分流：默认走基础图，其余才走平台图

这是整条链最关键的分叉。Worker 拿到任务后，run_registered_agent_workflow() 先查 workflow_key：等于 product_diagnosis_optimization 就转调基础图并直接返回；只有其余工作流才认领运行、构建平台图。由于意图路由的兜底值正是前者，所以「一句自然语言、没点模板」创建的任务默认走基础图。

四、平台图执行：动态装配与审批门

五、审批与恢复：人工决定怎么回到工作流

六、平台图与基础图差异对照

两张图共用同一套 Harness 约束，但在装配方式、审批门设置、返修能力和可观测实现上有明显差别。逐项对照如下：

七、五个容易搞错的点

  1. 路由文件与入口函数别记混。平台任务在 routes/agent_platform.py 的 create_task()，不在 routes/agent_tasks.py；后者是服务层所在。返回码是 202，不是 201。
  2. 默认任务根本不走平台图。意图路由没命中就兜底 product_diagnosis_optimization，Worker 命中这个 key 直接转基础图；要真正跑平台图，前端得用模板表单显式提交其它 workflow_key（或意图命中对应关键词）。
  3. 平台任务一定有 AgentTask。与商品工作台的 task 可空不同，这里 AgentRun.task_id 必填，_claim_run() 还会强制校验 task_id 非空；同事务写四张表无条件成立。
  4. 审批恢复入口不是 /agent-runs/{run_id}/review。那是基础图的入口；平台图走 /agent/approvals/{approval_id}/decision，且二次 Outbox 幂等键结尾是 approval-{approval_id}（基础图是 legacy-review）。
  5. 幂等键分段要分清。创建 agent-run:{run_id}:start、审批恢复 agent-run:{run_id}:approval-{id}、落库 platform-finalize-v1 或 finalize-v1。三者分别管投递、恢复、落库，不在同一层。
链路结论同步创建 → 异步投递 → Worker 按 workflow_key 分流（默认基础图，其余平台图）。
