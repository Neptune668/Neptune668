POST /products/{product_id}/agent-runs 接口全链路分析

接口定位：这个接口是商品工作台里「开始分析」动作的入口。它和平台任务入口不是同一条链——这里把工作流硬编码成 product_diagnosis_optimization，Worker 执行时命中特例直接转调基础图 graph.py，不构建平台图。整条链路分三段：同步创建 → 异步投递 → Worker 执行。

一、同步创建阶段：从点击到 202 返回

前端点击后，一次请求在同一个数据库事务里写四张表（有前提：工作区启用了该工作流）。路由层只做编排和异常转换，服务层负责主要业务逻辑。整体流程：

二、异步投递阶段：Outbox 可靠投递

提交之后进入异步段。这里有一个分叉：关联了 task 的走 Outbox 可靠投递（本接口的正常路径）；没关联 task 的直接投 Celery（旧直投路径）。Beat 的定时调度是真正的兜底。

三、Worker 执行阶段：LangGraph 基础图

Worker 拿到任务后还有一个关键分流：run_registered_agent_workflow() 一看 workflow_key 是 product_diagnosis_optimization，就直接转调基础图那条链，不构建平台图。随后按写死的节点链执行，中途有返修回路和人工审核门。

四、四个容易搞错的点

  1. 这条链没走意图路由。route_intent() 关键词匹配是 agent_tasks.py 那条「平台任务」入口用的；这个商品工作台入口把 workflow 硬编码成 product_diagnosis_optimization。
  2. 跑的是基础图不是平台图。因为 workflow_key 命中特例，platform_graph.py 在这里不执行。
  3. 同步返回的是 run 对象，不是结果。HTTP 202 返回完整 AgentRunRead（status=queued），分析在后台跑；前端靠每 2 秒轮询 GET /agent-runs/{runId} 推进度。
  4. 「同事务写四张表」有条件。agent_tasks 和 outbox_events 只在 workspace 启用了该工作流时才写；没启用就只有 agent_runs + agent_run_events，且投递改走直投 Celery。
