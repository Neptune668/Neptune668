AgentTask、AgentRun 与 OutboxEvent 的关系与流转

从对象关系到可靠投递的完整说明

三个对象的定位：AgentTask 是一次业务任务的工单，AgentRun 是这张工单下的一次具体执行，OutboxEvent 是把这次执行可靠送进队列的信使。三者不是并列关系，而是工单 → 执行 → 投递凭据的串联。POST /products/{product_id}/agent-runs 这条链路的核心，是三个对象在不同阶段各自记录的字段变化。

一、三个对象各自负责什么

AgentTask
agent_tasks
业务层的工单。用户的一次分析请求对应一条 Task，记录「要做什么」：workflow_key 指向工作流定义，input_payload / context_scope 保存输入，risk_level 标风险，result_summary 存结果摘要。它的生命周期跨越整次业务办理，状态走 queued → running → awaiting_approval → completed。
AgentRun
agent_runs
执行层的运行实例。真正被 Worker 认领、被 LangGraph 执行的是它。thread_id 是检查点恢复的钥匙，lease_owner / lease_expires_at 是执行租约，draft_output / final_output 分别存草稿与终稿。它通过 task_id 外键指向 Task——方向是 Run 指向 Task，且可空。
OutboxEvent
outbox_events
投递层的可靠信使。它不参与业务计算，只保证「该跑的消息最终一定送出去」。用 aggregate_type="agent_run" + aggregate_id=str(run.id) 逻辑关联 Run，payload 里带上 run_id 和恢复载荷，idempotency_key 防重复投递。状态只有 pending / published / failed 三态，没有中间态。

二、发件箱机制：从写入到执行

发件箱的构成：发件箱不是一个孤立的「投递动作」，而是把写入触发扫描投递执行四个环节串起来的可靠送达机制。其工作内容是：业务数据落库时，事件在同一个事务写进发件箱；Beat 定时发消息触发扫描，真正扫库并把消息写进 Redis 的是 maintenance Worker；最后由 agent.workflow Worker 消费消息、执行工作流。Outbox 只保证消息可靠送达，不负责执行。

完整链路：五个环节

一次诊断或平台任务的运行请求经历五个环节。图中左侧是环节名称，中间是主体动作，右侧是该环节的关键点。触发侧有两条路径汇到同一个任务，扫描与执行分属两个不同的 Worker 与队列。

三层角色与分工

五个环节由三个角色承担主要职责：Beat 负责定时触发，扫描者负责扫库投递，执行者负责消费消息并运行工作流，三者分工明确。

maintenance.dispatch_outbox
Beat 每 5 秒投递的定时任务，只往 maintenance 队列发一条「去扫描」的消息。它是闹钟，不碰数据库，也不执行工作流。
dispatch_pending_outbox_events()
扫描与投递的核心，由 maintenance Worker 调用。用 FOR UPDATE SKIP LOCKED 捞 pending 且到期的事件，每批 50 条，避免多个 Worker 抢同一批。
_publish_event() → apply_async()
只认 workflow.run.requested 这一种事件，把 run_id 投进 agent.workflow 队列。成功后事件改 published，Outbox 这条路到此结束。
kick_outbox_dispatcher()
创建 run 之后主动催一次扫描，让首次投递不必等 Beat 那 5 秒。它是加速路径，Beat 是兜底路径，两者投的是同一个任务。
run_registered_agent_workflow_task
消费 agent.workflow 队列的消息，真正执行工作流。它带租约 lease_owner 和心跳 fencing，失败按 2ⁿ 秒退避重试。租约与进度保存属于执行层，与 Outbox 无关。

两次写入与幂等键

一条 Run 一生可能写两条 Outbox 事件：首次启动时一条，人工审批通过后恢复执行时再写一条。两条用不同的幂等键隔开，恢复消息不会和首次投递撞车；载荷里多出来的 resume_payload 携带审核决定，Worker 据此续跑。

写入场景幂等键载荷
平台任务首次创建agent-run:{id}:startrun_id
平台任务审批通过agent-run:{id}:approval-{approval.id}run_id + resume_payload
基础图人工审核通过agent-run:{id}:legacy-reviewrun_id + resume_payload
巡检回收卡死任务agent-run:{id}:recovery:{attempt}run_id + resume_payload

四、逐阶段字段变化详解

阶段 1 · 创建：同一事务里落四张表

入口 create_agent_run_record() 先用 with_for_update() 查同商品有无活动 run，有就抛 409；接着判断工作区是否启用了 product_diagnosis_optimization。只有启用了才创建 Task 和 OutboxEvent，否则 task 为 None，后面投递改走直投 Celery。

AgentTask（新建）
字段赋值表达的含义
status→ queued工单刚建立，还没被 Worker 认领。
AgentTaskStatus 取值：queued · running · awaiting_approval · completed · failed · cancelled
workflow_key / version→ 工作流定义来自注册表 get_workflow("product_diagnosis_optimization")，决定后面跑哪张图。
risk_level→ R2诊断优化按执行类风险登记，因此后面会走人工审批。
AgentRiskLevel 取值：R0 · R1 · R2 · R3
context_scope→ {product_id, store_id}把业务上下文固定下来，恢复时不用重新拼。
input_payload / result_summary→ {}输入与结果先留空，结果在 finalize 时回填。
AgentRun（新建）
字段赋值表达的含义
thread_id→ str(uuid4())整次执行的唯一标识，也是 LangGraph 检查点恢复的钥匙。
task_id→ task.id 或 None指向工单。它同时是投递方式的开关：非空走 Outbox，为空走直投。
status→ queued等待 Worker 认领。
AgentRunStatus 取值：queued · running · awaiting_review · resume_queued · completed · rejected · failed · cancelled
attempt / queue_name→ 1 / agent首次尝试；记录计划投递的队列。
budget→ {max_total_tokens: 12000}token 预算上限，运行前会算余量、归零熔断。
usage / draft_output / final_output 等→ {}用量、草稿、终稿、质量报告、上下文快照全部先置空。
timeout_at→ now + 30min整体超时上限，心跳时会被检查。
lease_owner / lease_expires_at保持 None还没人认领，自然没有租约。
AgentRunEvent 与 OutboxEvent（新建）
对象 · 字段赋值表达的含义
RunEvent.event_type→ "queued"事件流的第一条，标记「已进队列」。
event_type 为固定字符串（非枚举类），常见取值：queued · workflow_started · workflow_resumed · human_review_requested · resume_queued · revision_requested · agent_step_completed · task_failed · dispatch_failed
Outbox.event_type→ "workflow.run.requested"扫描器只认这一种类型，其他类型一律拒绝投递。
Outbox.payload→ {run_id, resume_payload: None}首次投递没有恢复载荷；恢复时会再写一条带载荷的。
Outbox.idempotency_key→ agent-run:{id}:start唯一键，保证同一次启动只投一次。
Outbox.status / attempts / available_at→ pending / 0 / now待投递、零次尝试、立即可见。

阶段 2 · 投递：只有 OutboxEvent 在变

dispatch_pending_outbox_events() 用 status=pending 且 available_at <= now 筛选，FOR UPDATE SKIP LOCKED 加锁，一次最多 50 条。状态机中没有 pending→processing 的中间态，状态直到循环结束才落定，整个批次最后一次性 commit。

结果字段变化表达的含义
投递成功status → published；attempts 0→1；published_at → now；error → None消息已安全交给 Celery，Outbox 的使命完成。
OutboxEventStatus 取值：pending · published · failed
投递失败（可重试）attempts +1；error=异常前 2000 字；available_at=now+min(2^attempts,300)s；status 仍 pending指数退避，2/4/8…秒，封顶 300 秒；状态不改成 processing。
OutboxEventStatus 取值：pending · published · failed
投递失败（超限）attempts ≥10 时 status → failed放弃自动投递，留待人工排查。
OutboxEventStatus 取值：pending · published · failed

_publish_event() 把 run_id 和 resume_payload 作为参数，投递任务 run_registered_agent_workflow_task 到 agent.workflow 队列。这一步 Task 和 Run 的字段完全不动。

阶段 3 · 认领执行：AgentRun 拿到租约

_claim_agent_run() 用 with_for_update() 锁住 Run，只接受 QUEUED（恢复时是 RESUME_QUEUED），并拒绝已请求取消的任务。

对象 · 字段变化表达的含义
Run.statusqueued → running正式开始执行。
AgentRunStatus 取值：queued · running · awaiting_review · resume_queued · completed · rejected · failed · cancelled
Run.lease_ownerNone → "celery:{task_id}"标记「谁在跑」，后续每步都校验这个身份。
Run.lease_expires_atNone → now + 5min租约五分钟，心跳每 60 秒续期；过期可被巡检回收重排。
Run.started_at / error→ now（首次）/ None记录开始时间，清空上次可能残留的错误。
Task.status / errorqueued → running / None工单同步进入执行态。
AgentTaskStatus 取值：queued · running · awaiting_approval · completed · failed · cancelled
RunEvent.event_type→ "workflow_started"恢复时则是 "workflow_resumed"。

运行中每执行一个节点，_record_harness_event() 都会先校验租约有效，再续期、写事件，并把 current_agent 更新成当前节点名——所以这个字段相当于「跑到哪一步」的游标。

阶段 4 · 中断挂起：三个对象一起进入等待

基础图跑到 human_review_gate 时 interrupt() 挂起，_sync_agent_run_state() 把中断翻译成可审核状态。

对象 · 字段变化表达的含义
Run.statusrunning → awaiting_review前端轮询到这个态就切换成审核界面。
AgentRunStatus 取值：queued · running · awaiting_review · resume_queued · completed · rejected · failed · cancelled
Run.lease_owner / lease_expires_at→ None / None主动释放租约：等待期间不该有人持有执行权。
Run.current_agent→ "human_review_gate"明确停在人审门，不是卡在某个 Agent。
Run.draft_output / quality_report→ 草稿与质检结果草稿写进 Run 但没有落成正式业务对象，此时对商品主表零副作用。
Task.statusrunning → awaiting_approval工单停在待审批。
AgentTaskStatus 取值：queued · running · awaiting_approval · completed · failed · cancelled
AgentApproval（新建）run_id + task_id 双挂；action_key="workflow.accept_result"；status=pending；expires_at=now+24h审批单把 Run 和 Task 串起来；request_payload 存脱敏后的草稿与质检报告，24 小时过期。
AgentApprovalStatus 取值：pending · approved · rejected · expired · cancelled
RunEvent.event_type→ "human_review_requested"事件流记下等待审核。

阶段 5 · 审核恢复：再写一条 Outbox

POST /agent-runs/{run_id}/review 先校验状态必须是 awaiting_review、未请求取消、无重复审核，然后改状态并再写一条 Outbox 事件——这是很多人容易漏掉的一步。

对象 · 字段变化表达的含义
Run.statusawaiting_review → resume_queued不是直接回 queued，用独立状态区分「恢复」与「首次」。
AgentRunStatus 取值：queued · running · awaiting_review · resume_queued · completed · rejected · failed · cancelled
Task.statusawaiting_approval → queued工单回到排队，等 Worker 重新认领。
AgentTaskStatus 取值：queued · running · awaiting_approval · completed · failed · cancelled
Approval.statuspending → approved / rejectedreject 决定也记下来；同时记 decided_by、decision_payload、decided_at。
AgentApprovalStatus 取值：pending · approved · rejected · expired · cancelled
AgentRunReview（新建）decision / edited_output / note审核意见独立留痕，编辑后再通过时带 edited_output。
AgentReviewDecision 取值：approve · edit_and_approve · reject
Outbox（新建第二条）event_type="workflow.run.requested"；payload.resume_payload=审核载荷；idempotency_key=agent-run:{id}:legacy-review；status=pending用不同的幂等键避开首次那条，把审核决定可靠送回 Worker。
OutboxEventStatus 取值：pending · published · failed
RunEvent.event_type→ "resume_queued"事件流记下等待恢复投递。

随后 Worker 重新 _claim_agent_run(is_resume=True)，Run 从 resume_queued 再进 running，拿新租约、按同一个 thread_id 从检查点续跑——前面已完成的节点不重算。

阶段 6 · 终局落库：草稿变正式对象

_finalize_agent_run() 先建一条 AgentRunOperation，operation_key="finalize-v1"，靠 (run_id, operation_key) 唯一约束防重复；若该 operation 已 completed 就直接返回旧结果，这是 Celery 至少一次投递下的幂等保障。

对象 · 字段变化表达的含义
Run.status→ completed（通过）/ rejected（驳回）运行进入终态。
AgentRunStatus 取值：queued · running · awaiting_review · resume_queued · completed · rejected · failed · cancelled
Run.final_output{} → 审核后的结果draft_output 保留不删，草稿与终稿并存，便于追溯改了什么。
Run.current_agent / lease / finished_at→ None / 清空 / now执行权彻底释放，运行收尾。
Task.status→ completed / cancelled（驳回时）工单跟着收尾。
AgentTaskStatus 取值：queued · running · awaiting_approval · completed · failed · cancelled
Task.result_summary{} → 结果摘要列表页直接展示这个摘要，不用去翻 Run。
业务产出新建 ProductDiagnosis + CreativePlan带 agent_run_id 回指 Run，正式业务对象到这一步才产生。

五、状态机速查

对象中间态终态
AgentTaskqueued / running / awaiting_approvalcompleted / failed / cancelled
AgentRunqueued / running / awaiting_review / resume_queuedcompleted / rejected / failed / cancelled
OutboxEvent只有 pendingpublished / failed

三者的关系是同一个业务动作在三层各自的投影：Run 在 awaiting_review 时 Task 是 awaiting_approval；Run 有 rejected 终态而 Task 对应的是 cancelled。

六、几个容易踩的坑

  1. Task 可能根本不存在。工作区没启用 product_diagnosis_optimization 时，task 为 None，Run 的 task_id 也是 None，此时不写 Outbox，直接投 agent 队列。所以「同事务写四张表」是有条件的。
  2. Outbox 没有 processing 态。它只有 pending / published / failed，失败靠 attempts 和 available_at 表达重试节奏，别在文档或代码里臆造中间态。
  3. 恢复会写第二条 Outbox。首次幂等键结尾是 :start，恢复是 :legacy-review。两条事件类型相同、载荷不同。
  4. finalize 的幂等键不在 Outbox 上。它是 AgentRunOperation 的 finalize-v1，拦的是重复落库，和 Outbox 拦的重复投递是两道不同的闸门。
  5. 前端看到的是 Run，不是这三个对象的全貌。GET /agent-runs/{run_id} 返回 AgentRunRead，几乎全量暴露 Run 字段（含事件和审核列表），但不包含 AgentTask、OutboxEvent、AgentApproval 对象。
数据模型AgentTask 记录任务，AgentRun 记录执行，OutboxEvent 负责可靠投递，三者共同支撑商品诊断与优化链路。
