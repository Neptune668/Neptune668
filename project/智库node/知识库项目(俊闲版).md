## 一、项目整体与架构（Q1–Q12）

#### Q1. [基础] 用一分钟介绍这个项目，它解决什么问题，整体分哪两条链路？

**参考要点：**

- 定位：面向商品手册、说明书、维修资料、FAQ 的**文档型**知识库问答，解决客服、运营、业务人员查资料效率低、资料分散、人工翻文档成本高、回答不稳定的问题；导入的是切片后的手册内容，不是人工整理的 QA 对。
- 导入链路：`POST /upload` → 本地落盘 + MinIO 归档 + 计算 sha256 → `BackgroundTasks` 起 `run_graph_task` → `KBImportWorkflow` 的 7 节点：入口 → PDF 转 MD → 图片处理 → 切分 → 商品名识别 → BGE-M3 向量化 → Milvus 入库。
- 查询链路：`POST /query` → 建 SSE 队列 + 后台跑 `KBQueryWorkflow` → 商品名确认 →（分叉节点扇出**两路**检索：普通向量、HyDE）→ 汇合 → RRF → Rerank → 答案生成；商品不确定时条件边直接短路到答案节点。
- 存储分工：Milvus 存 `kb_chunks` 与 `kb_item_names` 两个集合，MinIO 存原始文件与图片，MongoDB 存多轮会话，任务状态是**进程内字典**。
- 代码依据：`atguigu/services/import_file_service.py:27-80`、`import_process/main_graph2.py:68-88`、`query_process/main_graph.py:89-118`、`.env.example:55-67`。

**易错提醒**：这是**两个独立 FastAPI 应用**（导入 `0.0.0.0:8000`、查询 `127.0.0.1:8001`），不是一个服务里的两组路由。

#### Q2. [进阶] 项目用了哪些模型？分别落在哪些节点？

**参考要点：**

- 文本 LLM：`qwen-flash`（`LLM_DEFAULT_MODEL` / `ITEM_MODEL`），用于商品名抽取与问题改写、HyDE 假设文档生成、导入侧商品名识别、最终答案生成；统一走 `llm_utils.get_llm_client()`，按 `(model, json_mode)` 缓存客户端，`enable_thinking=False`、`stream_usage=True`。
- VLM：`qwen3-vl-plus`（`VL_MODEL`），在图片节点给图片生成中文摘要，图片以 base64 data URL 送入；该节点直接 new `ChatOpenAI`，未走客户端缓存。
- Embedding：本地 `BAAI/bge-m3`（`BGE_M3_PATH`，`cuda:0`，FP16），由 `pymilvus.model.hybrid.BGEM3EmbeddingFunction` 加载，一次 `encode_documents` 同时产出 dense 与 sparse。
- Rerank：DashScope 远端 `qwen3-rerank`（`TEXT_RERANK_MODEL`），通过 `dashscope.TextReRank.call` 调用。
- PDF 解析：MinerU 云端 API，`model_version="vlm"`，负责版面识别；业务上同时支持 Word、Markdown 文档统一进入后续链路。
- 项目初期文本 LLM 与 VLM 都走成熟云端服务：调用量可控、运维成本低；优先独立部署的是调用频率高、成本更可控的 BGE-M3 与 reranker，后续量上来再评估独立部署大模型。
- 代码依据：`.env.example:6-7,17-23,43-49,78-80`、`utils/llm_utils.py:12-51`、`utils/embedding_utils.py:11-45`、`utils/reranker_http_utils.py:10-37`、`import_process/nodes/node_pdf_to_md.py:107-112`。

#### Q3. [基础] 为什么用 LangGraph 编排，两张图的节点与分支是怎么定义的？

**参考要点：**

- 导入图 `KBImportWorkflow`（`import_process/main_graph2.py`）：`node_entry` 后按文件类型走条件边——PDF 进 `node_pdf_to_md`，MD 直接进 `node_md_img`，其它后缀抛异常；之后固定顺序 `node_md_img → node_document_split → node_item_name_recognition → node_bge_embedding → node_import_milvus → END`。
- 查询图 `KBQueryWorkflow`（`query_process/main_graph.py`）：入口 `node_item_name_confirm`；条件路由 `_route_after_item_name_confirm` 判断 `state.get("answer")`，有值（澄清/拒识）直接去 `node_answer_output`，否则去分叉节点。
- 扇出/扇入靠 `add_node("node_multi_search", lambda x: x)` 与 `add_node("node_join", lambda x: {})` 两个**虚拟节点** + 从分叉节点挂出两条检索边、再由两路各挂一条边回到汇合节点实现；LangGraph 会等两条入边都完成才执行 `node_join`。没有用 `Send` API，也没有并行子图。
- 状态是纯 `TypedDict`（`import_process/state.py`、`query_process/state.py`），**不带 reducer / `Annotated` 累加通道**，所以两路并行节点必须各写各的字段：`embedding_chunks`、`hyde_embedding_chunks`，否则会触发 `InvalidUpdateError`。
- 节点基类 `NodeBase.__call__` 统一做进度埋点（进/出节点写 running/done 列表并推 SSE progress），异常记日志后向上抛。
- 代码依据：`import_process/main_graph2.py:59-88`、`query_process/main_graph.py:51-118`、`query_process/base.py:28-53`。

#### Q4. [基础] 系统里有哪几类资产？分别存在哪里？

**参考要点：**

- Milvus `kb_chunks`：切片正文 + `dense_vector` + `sparse_vector` + `document_id / chunk_order / title / parent_title / file_title / item_name`。
- Milvus `kb_item_names`：商品名向量集合，字段 `file_title / item_name / dense_vector / sparse_vector`，用于查询时把口语化商品名对齐到库内标准名。

- 代码依据：`import_process/nodes/node_import_milvus.py:101-140`、`node_item_name_recognition.py:223-299`、`services/import_file_service.py:113-136`、`import_process/nodes/node_md_img.py:308-397`、`utils/mongo_history_utils.py:110-121`。

#### Q5. [进阶] 为什么选 Milvus + MinIO + MongoDB 这套组合？分别在链路上起什么作用？

**参考要点：**

- Milvus 承担混合向量检索：同一集合上建 dense `AUTOINDEX/COSINE` 与 sparse `SPARSE_INVERTED_INDEX/IP` 两套索引，用 `WeightedRanker` 融合，且支持 `item_name in [...]` 标量过滤——这是把「商品范围」约束下推到检索层的关键；存算分离也便于弹性扩容。
- MinIO 承担大对象：MinerU 产出的图片、用户上传的原件；既能存向量库依赖的对象数据，也能直接给前端提供图片，避免组件重复；同时通过前缀白名单在答案生成时校验图片 URL 真伪。
- MongoDB 承担会话：商品名确认节点读最近历史做指代消解，并把确认结果回填到历史消息；答案节点写助手消息。
- 三者按「向量检索 / 对象存储 / 会话状态」分工；配置全部走 `.env`（`MILVUS_URL`、`MINIO_*`、`MONGO_*`）。
- ES 更偏全文精确匹配，Milvus 更偏语义匹配；本项目两类问题都有，因此以 Milvus 混合检索为主，全文检索能力由 BGE-M3 的 sparse 向量覆盖。
- 代码依据：`utils/milvus_utils.py:60-123`、`import_process/nodes/node_import_milvus.py:118-133`、`query_process/nodes/node_answer_output.py:255-277`、`utils/mongo_history_utils.py:103-160`。

#### Q6. [综合] 如果让你讲「一次提问从前端到答案」的完整时序，你会怎么串？

**参考要点：**

1. 前端 `chat.html` 用 localStorage 生成 `sessionId`，`POST /query` 只带 `query` 与 `session_id`（`user_id` 由后端默认 1）；后端生成 `task_id = uuid4()`、`request_id = task_id`、创建 SSE 队列，把 `run_query_graph` 丢进 `BackgroundTasks`，立即返回 task_id。
2. 前端用 `EventSource` 连 `GET /stream/{task_id}`；后台线程里图以 `stream=True` 逐节点执行，每个节点进出都推 `progress` 事件。
3. 商品名确认节点：读 MongoDB 最近 10 条 → LLM（JSON 模式）产出 `item_names` + `rewritten_query` → BGE-M3 向量 → `kb_item_names` 混合检索对齐 → 三档判定，澄清/拒识直接短路。
4. 两路并行召回：普通混合向量检索、HyDE 检索；各写各的 state 字段，汇合节点等待两路完成。
5. RRF 融合两路结果（按 `chunk_id` 去重）→ 候选交给远端 `TextReRank` 打分 → 断崖截断 → 组装带预算的 prompt → `llm.stream` 逐块推 `delta` → 写 MongoDB → 推 `final`。
6. `finally` 里做指标汇总并异步上报查询日志。
- 代码依据：`query_router.py:125-177,58-122`、`chat.html:757-887`、`query_process/nodes/*`。

#### Q7. [综合] 这个项目的设计难点在哪里？请结合实现说，而不是泛泛而谈。

**参考要点：**

- **格式统一**：PDF 先经 MinerU 云端 API 转成带标题/图片引用的 Markdown，Word/Markdown 也统一到同一条内容结构化链路，后续节点才有一致的处理对象。
- **商品维度隔离**：手册相似型号多，靠「导入时 LLM 抽 `item_name` 并回填每个 chunk」+「查询时先对齐商品名再做标量过滤」两级控制，避免串型号。
- **两路召回的协同**：普通向量检索覆盖常规语义与关键词，HyDE 补足用户表达不完整、缺主语的场景；两路结果结构一致，都带 `chunk_id`，因此可以先 RRF 融合再统一精排。
- **上下文预算与噪声**：`MAX_CONTEXT_CHARS=12000`，参考文档与历史共享递减预算；Rerank 断崖 + 最低分控制送入 LLM 的片段数量。
- **长任务的可见性**：导入靠 `/status/{task_id}` 轮询，查询靠 SSE 的 `progress / delta / final / error` 四类事件；任务状态是内存态，重启即丢，这是当前实现的边界。
- 代码依据：`import_process/nodes/node_entry.py`、`node_item_name_recognition.py:171-221`、`query_process/nodes/node_rrf.py:28-41`、`node_rerank.py:53-89`、`node_answer_output.py:26,121-186`、`utils/task_utils.py:12-29`。

#### Q8. [基础] 项目的用户量、访问量和数据规模大概是多少？压测口径怎么讲？

#### Q10. [进阶] 初期技术选型是怎么定的？为什么是 Milvus + MinIO？

**参考要点：**

- 选 Milvus 主要看重存算分离与语义/混合检索能力；选 MinIO 是因为一个组件既能承载向量库的对象数据，又能保存图片与原始文件，减少重复建设。
- 项目里其它业务线有 Qdrant + ES 的组合，主要源于既有系统的改造路径；如果再次统一选型，企业级场景用 Milvus 更稳。
- Milvus 与 ES 的取舍不看数据量本身（当前体量不构成瓶颈），而看匹配方式：Milvus 偏向向量与语义匹配，ES 全文匹配更精确；本项目通过 BGE-M3 的 dense + sparse 一次覆盖两类需求。
- 代码依据：`utils/milvus_utils.py:60-123`（`WeightedRanker` 混合检索）、`import_process/nodes/node_import_milvus.py:118-133`（双索引）、`.env.example:55-59`。

#### Q11. [综合] 如何应对日千万/亿级访问量？大模型宕机或线上异常怎么办？

**参考要点：**

- 高并发：多级缓存减少用户请求直接打到大模型；引导用户命中 FAQ；用 Nginx 做多副本负载均衡；用 MQ 增加排队机制、削峰填谷。
- 文档体量：一般不会成为瓶颈，Milvus 存算分离、MinIO 可弹性扩容。
- 模型侧：设定并发与每分钟 token 上限，通过多线程 + 消息队列做控流，避免接口限流或系统过载。
- 宕机降级：切换备用小模型、返回预设兜底话术；检索侧的两路并行也让单路异常不至于拖垮主流程。
- 代码依据：现有基础是 `utils/query_metrics_utils.py` 的 token 统计、`services/query_log_reporter.py` 的异步上报与 fail-open、`query_process/nodes/node_search_embedding.py:36-38` 的单路异常返回空结果；上述缓存、MQ、Nginx 属于生产部署方案。

## 二、导入链路：上传、解析与任务（Q13–Q24）

#### Q13. [基础] 一次文档导入的 HTTP 流程是怎样的？前端怎么知道进度？

**参考要点：**

- `POST /upload`（`import_router.py:42-60`）只接收一个 `UploadFile`，`process_upload_file` 生成 `task_id` 与独立的 `document_id`（都是 uuid4）、按日期建本地目录、1MB 缓冲写盘、算 sha256、把原件 `fput_object` 到 MinIO。
- 随后 `background_tasks.add_task(service.run_graph_task, upload_context)`，接口立即返回 `{message, task_id}`，不等待解析完成。
- `run_graph_task` 是**同步函数**，由 Starlette 放到线程池执行；它把图以 `stream=True` 跑完，专门捕获 `node_import_milvus` 的输出快照，据此写 `result`（`document_id / item_name / original_file_download_url / file_sha256 / chunk_count / total_text_length`），成功置 `completed`，异常置 `failed`。
- 状态来自 `utils/task_utils.py` 的内存字典：`processing / completed / failed`，含 running/done 节点列表与中文名映射；`GET /status/{task_id}` 仅在 `completed` 时返回 result。
- 前端 `import.html` 每 1500ms 轮询一次，PDF 按 8 个进度节点、MD 按 7 个（少一个 `node_pdf_to_md`）。
- 代码依据：`import_router.py:42-72`、`import_file_service.py:27-150`、`utils/task_utils.py:27-53,190-208`、`import_process/base.py:20-48`。

**易错提醒**：不是 Celery / MQ，也没有持久化和重试；服务重启后任务状态丢失。

#### Q14. [进阶] PDF 是怎么解析和提取内容的？MinerU 在链路里扮演什么角色？

**参考要点：**

- PDF 不直接检索：先用 MinerU 转成 Markdown，转完以后文本、标题、表格、图片引用都比较结构化，后续所有格式统一走 Markdown 图片处理和切片链路。
- 用的是 MinerU **云端 HTTP API**（`node_pdf_to_md.py`）：先 `POST /file-urls/batch` 申请批量上传，body 里固定 `model_version="vlm"`，拿 `batch_id` 与预签名 URL 后 PUT 上传原 PDF。
- 然后轮询 `GET /extract-results/batch/{batch_id}`，`timeout_seconds=600`、`poll_interval=3`、单次请求 `timeout=5`，`state=="done"` 取 `full_zip_url`，`failed` 抛错。
- 下载 zip 解压到 `{local_dir}/{file_title}/`，把 `full.md` 重命名为 `{file_title}.md`，只把 `md_path` 写回 state；`md_content` 实际由下一个节点读文件得到。
- MinerU 解决的是版面结构还原：PDF 文本顺序乱、表格难抽、图片引用难保留、跨页表格合并；它内部也有 VLM 用于识别版面信息。
- 代码依据：`import_process/nodes/node_pdf_to_md.py:93-237`、`.env.example:6-7`。

#### Q15. [基础] 支持哪些文档格式？Word 和扫描件怎么处理？

**参考要点：**

- 项目支持 **PDF、Word、Markdown** 三类商品资料；Word 文档在导入前统一转换成 Markdown，之后与 PDF 转换结果走同一条「图片处理 → 切分 → 商品名识别 → 向量化入库」链路。
- 代码入口按后缀做类型分发：`.pdf` 走 `node_pdf_to_md`，`.md` 直接走 `node_md_img`，`file_title` 取去后缀的文件名（`node_entry.py:31-59`）；前端 `import.html` 的 `accept` 与之一致。
- 扫描件/图片型 PDF 不是独立分支：由 MinerU 的 `vlm` 模型版本做 OCR 与版面识别，转成带结构的 Markdown；多栏、左文右图、图文错位这类版式也由版面分析还原阅读顺序。
- 「大片图片 + 简短编号」的工业文档，靠图片节点取上下文 + VLM 生成摘要补足语义（见 Q16）。

#### Q16. [进阶] 图片内容是怎么处理的？图片信息如何进入知识库？

**参考要点：**

- `node_md_img` 读 MD 全文，扫描同目录 `images/` 下的 6 类图片后缀，用正则 `!\[.*?\]\(.*?文件名\)` 找引用（只取第一个匹配），取前后各 **100 字符**作为上下文。
- 提示词 `IMAGE_SUMMARY` 把文件名、上文、下文一起交给 `qwen3-vl-plus`，要求「用中文简要总结，用于 Markdown 图片标题」；结果去掉换行。图片摘要就是多模态生成的 Caption。
- 工程保护：图片 > 4MB 跳过摘要返回「图片描述」；VLM 调用有 deque 滑动窗口限速（20 次 / 60 秒）；VLM 异常也兜底「图片描述」。
- 图片上传到 `upload-images/{file_title}/`（路径去空格，上传前先按目录清理旧对象），用明文 URL；随后 `pattern.sub` 把 MD 中的 `![...](本地路径)` 替换为 `![摘要](MinIO URL)`，另存为 `*_new.md`，原文件不动。
- 摘要与 URL 一起成为 chunk 正文的一部分，因此**图片信息是被当作文本向量化**的；答案里带图片 URL 时前端也能展示。
- MinerU 只负责把图片从 PDF 里抽出来并保留引用，VLM 才负责「看懂」图片——这是两者的分工。
- 代码依据：`import_process/nodes/node_md_img.py:102-160,190-286,288-450`、`import_process/prompt.py:3-4`、`query_process/nodes/node_answer_output.py:255-277`。

#### Q17. [进阶] 表格内容是怎么提取和处理的？

**参考要点：**

- MinerU 会把 PDF 里的表格转成 HTML `<table>`，并支持跨页表格合并，保留行列结构。
- 为了让 LLM 更好识别，切片阶段会对 HTML 表格做**行列交叉合并的线性化处理**：把「表头 + 行」组合成自然语言描述（例如「型号 HAK180 / 额定电压 220V」），避免模型面对原始标签时丢字段。
- 线性化后的文本与标题、商品名一起进入 embedding；代码侧对含 `<table` 的章节采取保护策略：`_split_long_section` 遇到表格直接 `return [section]`，保证一张表不被拆到两个 chunk 里（`node_document_split.py:247-249`）。
- 表格与图片是两类最容易丢信息的资产：表格靠线性化 + 整表保留，图片靠 VLM Caption，二者最终都作为文本参与检索。
- 代码依据：`import_process/nodes/node_document_split.py:238-249`、`node_pdf_to_md.py:107-112`、`import_process/nodes/node_md_img.py:411-431`。

#### Q18. [进阶] 为什么把各类文档统一转 Markdown，而不是直接对原文切片？

**参考要点：**

- Markdown 提供标题层级，切分节点才能用 `r'^\s*#{1,6}\s+.+'` 按 1–6 级标题做语义边界划分，并保留 `title / parent_title / file_title`；直接抽文本拿不到这些结构信息。
- Markdown 里的 `![...]()` 让图片定位、上下文提取、URL 替换成为可正则化的操作。
- 代码还处理了 CRLF 归一化、代码围栏内的 `#` 不当标题等细节，说明切分器是围绕 Markdown 语法写的。
- 代价是链路依赖 MinerU 云端服务（600s 超时、3s 轮询），失败会让整个导入任务置为 `failed`。
- 代码依据：`import_process/nodes/node_document_split.py:81,106-154`、`node_md_img.py:411-431`、`node_pdf_to_md.py:147-199`。

#### Q20. [综合] 新增文档或原文档更新后，切分和索引如何更新？

## 三、切分、商品名识别与向量化（Q25–Q36）

#### Q25. [基础] 文档切分具体怎么做的？切片带哪些元数据？

**参考要点：**

- 第一步按标题粗切：`title_pattern = r'^\s*#{1,6}\s+.+'`，逐行扫描，遇标题先 flush 上一节，产出 `{file_title, title, content}`；无标题文档兜底为 `title="无标题"`。
- 第二步精细化：先 `_split_long_section` 再 `_merge_short_sections`，最后给缺 `parent_title` 的片补值；太长的章节递归再切，太短的同父标题下合并。
- **代码里的阈值是类常量**：`DEFAULT_MAX_CONTENT_LENGTH = 500`、`MIN_CONTENT_LENGTH = 100`、`DEFAULT_WINDOW_OVERLAP = 50`（都是字符数）。
- 超长章节用 `RecursiveCharacterTextSplitter(chunk_size=500-len(prefix), chunk_overlap=50, separators=["\n\n","\n","。","！","？","；",".","!","?",";"," "])` 递归切；子片标题为 `{title} - {idx}`，`parent_title` 指向原标题。
- 每片元数据最终是：`file_title / title / parent_title / content`（切分节点）+ `item_name`（商品名节点回填）+ `document_id / chunk_order / chunk_id`（入库节点回填）+ 两种向量（embedding 节点回填）。
- 向量化时会拼 `item_name + content`，让商品相关性更强；每个切片都有 `item_name` 字段用于过滤，避免相似设备混淆。
- 代码依据：`import_process/nodes/node_document_split.py:24-28,67-154,215-354`、`node_bge_embedding.py:65-80`。

---

#### Q26. [进阶] 文档切分长度阈值是怎么控制的？为什么是这个量级？

**参考要点：**

- 项目里设置最大长度、最小长度和重叠策略：最大长度控制单个 chunk 不要太大，避免检索和 rerank 时关键信息被稀释；曾设置 2000 字符，发现 rerank 经常忽略关键信息，后按 **1200 字符**收敛。
- 最小长度控制 chunk 不要太小、避免缺上下文，按 **300 字符**起步；过长内容递归切分，过短内容向前后合并，并保留少量句子重叠（**1 个 `overlap_sentences`**）。
- 当前代码把同一策略收紧为 `500 / 100 / 50` 字符（`node_document_split.py:24-28`）：即最大 500、最小 100、字符级 `chunk_overlap=50`，与「小 chunk + 前置标题 + 商品名」的设计一致。
- 为什么小 chunk 更稳：rerank 把每片 `content` 作为一条 document 打分，文档越长相关性判断越容易被无关内容干扰；答案生成端还有 `MAX_CONTEXT_CHARS=12000` 的总预算，片越长能塞进 prompt 的片数越少。
- 参数是经验值起步，再按 RAGAS 评估（context_recall / context_precision）与 bad case 回归微调，见 Q26、Q69、Q71。
- 代码依据：`import_process/nodes/node_document_split.py:24-28,253-273`、`query_process/nodes/node_rerank.py:91-109`、`node_answer_output.py:86-163`。

#### Q27. [进阶] 商品名是怎么识别出来的？失败怎么办？

**参考要点：**

- `node_item_name_recognition` 取 `chunks[:5]`（`DEFAULT_ITEM_NAME_CHUNK_K=5`），按「【切片i】标题 / 内容」拼上下文，累计超 `MAX_CHARS=2500` 即截断。
- 用 `NAME_RECOGNITION` 模板把 `file_title` 与该上下文交给 `qwen-flash`（`item_model`），要求只返回「品牌+型号+名称」的字符串，识别不到返回空串；解析后经 `normalize_item_name` 做 NFKC 全角转半角与空白压缩。
- **兜底**：LLM 返回空或调用异常时，直接用 `file_title`（去后缀文件名）作为商品名。
- 识别结果回填到**每一个 chunk** 的 `item_name` 字段，同时单独向量化商品名，写入 `kb_item_names`（按 `file_title` 先删后插）。

#### Q28. [基础] 为什么要单独建一个商品名向量集合？

**参考要点：**

- 用户口语里的「P60」「这个机器」与库里标准名（如「华为 P60 128G」）不完全一致，`kb_item_names` 提供一层「实体对齐」：把 LLM 抽出的名称向量化后做混合检索，取回库内标准 `item_name`。
- 对齐后的标准名用于后续 `kb_chunks` 检索的 `item_name in [...]` 标量过滤，把召回范围锁在具体商品，避免相似型号串味。
- 集合字段较少：`pk / file_title / item_name / dense_vector(1024) / sparse_vector`，dense 用 `IVF_FLAT/COSINE/nlist=128`，sparse 用 `SPARSE_INVERTED_INDEX/IP`。
- 检索参数与切片检索不同：Top5、权重 `(0.8, 0.2)`、`norm_score=True`。
- 代码依据：`node_item_name_recognition.py:223-299`、`query_process/nodes/node_item_name_confirm.py:186-208`、`node_search_embedding.py:64-85`。

#### Q29. [进阶] BGE-M3 的 dense 和 sparse 是怎么生成并写入的？为什么要归一化稀疏向量？

**参考要点：**

- `embedding_utils.get_bge_m3_ef()` 用本地模型路径单例加载 `BGEM3EmbeddingFunction`（`cuda:0` + FP16）；`generate_embeddings(texts)` 调 `encode_documents`，dense 转 list，sparse 从 scipy 稀疏行转成 `{token_id: weight}` 字典。
- `normalize_sparse_vector` 对稀疏向量做 L2 归一化（范数 < 1e-9 时原样返回），保证写入和检索两侧的向量尺度一致——查询侧同样用 `generate_embeddings` 生成向量。
- 切片向量化的文本是 `f'{item_name} \n {content}'`，把商品名前置增强商品相关性；`batch_size=3` 分批推理防显存溢出，dense/sparse 一起写回每个 chunk。
- 商品名自身也用同一函数单独向量化（**不含 content**）。
- 代码依据：`utils/embedding_utils.py:11-69`、`import_process/nodes/node_bge_embedding.py:55-83`、`node_item_name_recognition.py:178-183`。

#### Q30. [进阶] dense 和 sparse 为什么都要？项目里的权重是怎么定的？

**参考要点：**

- dense 擅长语义改写与近义表达，sparse 擅长型号、参数、接口名和专有名词的精确字面匹配；企业文档两类问题都有，BGE-M3 一个模型同时产出两者，混合检索更稳。
- 工具层 `milvus_utils.hybrid_search` 的默认值是 `ranker_weights=(0.5,0.5)`、`norm_score=False`、`limit=5`；链路上三处调用显式覆盖：商品名确认、普通切片检索、HyDE 检索都用 `(0.8, 0.2)` + `norm_score=True`，切片检索 `limit=10`。
- 权重确定方法：准备测试集（常规问题 + 期望匹配的切片），按多组权重跑同一批问题，观察 context_recall / context_precision 与最终答案正确率，取分值更高的一组；业务上也有「两种索引各一半」的基线口径。
- 效果话术：只用 dense 的 Recall@5 约 78.4%，dense/sparse 按 0.8/0.2 混合后提升到 86.9%，再加 HyDE + RRF 到 90.8%；具体数值以评估集为准。
- `create_hybrid_search_request` 为 dense / sparse 各构造一个 `AnnSearchRequest`，**同一个 `item_name in [...]` 过滤表达式同时作用于两路**，最终由 `WeightedRanker` 融合。
- 代码依据：`utils/milvus_utils.py:48-123`、`query_process/nodes/node_item_name_confirm.py:190-197`、`node_search_embedding.py:71-86`、`node_search_embedding_hyde.py:94-116`。

#### Q31. [综合] 文档切分导致语义丢失时，怎么定位和优化？

**参考要点：**

- 定位路径：先从 bad case 入手，看原文里是否有答案，再查召回结果中有没有包含关键切片；原文有答案但召回没命中，就按链路顺序检查 embedding 评分、RRF 融合前后、reranker 筛选前后的日志。
- 借助 `fetch_chunks_by_chunk_ids` 按 `chunk_id` 回捞原文，对照 `chunks.json` 备份与 Milvus 里的 `content / chunk_order / parent_title`，确认是切碎了还是没召回。
- 优化手段：调小 chunk、增加 overlap、保留更多 RRF 候选、提高 rerank TopK、增加标题和商品名上下文；若召回结果高度重复、多样性不足，用 MMR 策略筛选（见 Q34）。
- 优化后用同一批问题集复测 `context_recall`、`context_precision` 与 `answer_correctness`，确认不是把噪声一起放大。
- 代码依据：`node_document_split.py:184-213,269-293`、`utils/milvus_utils.py:240-272`、`node_rrf.py:34`、`node_rerank.py:23-33`。

#### Q32. [综合] 同一段落或语义超过最大块长度、关键信息分布在多个块里，怎么保证召回完整？

**参考要点：**

- 当前实现：切分时尽量按标题、段落、句子边界切，避免从句子中间硬切；通过 `overlap` 增加边界冗余；表格章节整表保留不被二次切分。
- 上下文被切碎不全时，可以用**文本回填**：每个切片保留 `parent_chunk_id`，命中子块后回填父章节或相邻块；弊端是回填也会带来噪音，手册型文本段落比较清晰，需要保留超大文本完整语义的场景并不多。
- 长文本材料也可以先用大模型提取摘要放在靠前位置，但会有额外 token 与时间消耗；数千 token 的规章制度类文档尤其适合「回填 + 摘要」组合。
- 检索侧配合：查询改写补齐主语、商品过滤锁定范围、两路召回互补、RRF 保留更多候选、rerank 提高 TopK。
- 代码依据：`node_document_split.py:238-296`、`query_process/nodes/node_rrf.py:28-41`、`node_rerank.py:23-33`、`query_process/prompt.py:3-33`。

#### Q33. [进阶] 「向量化 + 文档切块」这套框架有什么问题？向量相似度等于语义相近吗？

**参考要点：**

- 框架实现简单，但切块会破坏上下文完整性、导致语义断裂，也难以建立跨文档的实体关联；改进方向是切片回填、结构化抽取与更细的元数据治理。
- 向量相似度与语义相近**不完全等同**：embedding 把一篇文章的含义压缩成向量，这个过程会丢失大量细节，就像把两幅油画变成 8 位像素图再比较相似程度。
- 因此不能只靠向量分数排序：项目用 dense + sparse 混合、商品名标量过滤、RRF 融合、rerank 精排和答案生成的 Prompt 约束共同兜底。
- 代码依据：`utils/embedding_utils.py:47-69`、`utils/milvus_utils.py:48-123`、`query_process/nodes/node_rrf.py:43-73`、`query_process/prompt.py:48-69`。

#### Q34. [进阶] 仅依靠相关度排序会导致切片重复、多样性不足，怎么解决？

**参考要点：**

- MMR（Maximal Marginal Relevance，最大边际相关性）：在按相关度评分排名时，对与已选切片过于相近的候选做权重惩罚，把高度重复的切片剔除，保留信息多样性。
- 适用场景：同一参数在手册里多处重复、相邻切片因 overlap 高度重合、长表格被切成多片时，TopK 容易被同质内容占满。
- 与断崖截断的分工：断崖检测决定「保留多少条」，MMR 决定「保留哪几条」；先按分数粗筛，再做去冗余，最后送进 prompt。
- 代码依据：`query_process/nodes/node_rerank.py:111-150`（分数排序与截断）、`node_answer_output.py:86-163`（按序号组装上下文）。

#### Q35. [进阶] 商品名确认这一步有性能优化空间吗？

**参考要点：**

- 当前每次提问都要读历史 → 调 LLM 抽商品名与改写 → 生成商品名向量 → 到 `kb_item_names` 做混合检索对齐，链路较长。
- 优化方向：对商品名称建立缓存，先对问题分词与缓存做匹配，命中则直接确定商品，跳过 LLM 与 embedding 比对；未命中再走完整确认链路。
- 同样适合缓存的还有高频 FAQ 的标准答案，减少大模型调用并削峰（见 Q11、Q80）。
- 注意缓存键要带商品名归一化结果（`normalize_item_name` 做 NFKC 与空白压缩），并处理别名与新型号上线后的失效。

#### Q36. [进阶] 召回的 chunk 超过 ReRanker 上下文窗口怎么处理？重排后相关度依然不高怎么办？

**参考要点：**

- `bge-reranker-large` 的上下文窗口是 512 token，所以切片主要控制在 500 量级；代码里 `chunk_size=500-len(prefix)`、`chunk_overlap=50`，与窗口约束是对齐的。
- 超长内容优先按标题/句子边界递归切，超长表格整表保留并做线性化，避免一个文档把 reranker 窗口占满。
- 如果相关度依然不高，先查原因：原文是否有答案、embedding 与 sparse 权重是否合适、商品过滤是否过窄；再考虑用 HyDE 补一路假设文档、增加标题与商品名上下文、或补结构化抽取提高匹配信息密度。
- 低分文档处理：按经验阈值（rerank 分数低于 0.3）可以淘汰上下文；若上下文都被淘汰，则触发拒答，返回资料不足的提示（见 Q52）。
- 代码依据：`import_process/nodes/node_document_split.py:24-28,253-273`、`query_process/nodes/node_rerank.py:23-33,111-150`、`node_answer_output.py:113-118`。

#### Q38. [进阶] Milvus 的混合检索在代码里是怎么发起的？

**参考要点：**

## 五、查询链路：确认、两路召回、融合与精排（Q44–Q60）

#### Q44. [基础] 商品名确认节点的完整流程是什么？

**参考要点：**

1. 校验 `session_id / original_query`，`get_recent_messages` 取最近 10 条历史，先插入一条占位用户消息拿 `message_id`。
2. 用 `SystemMessage + HumanMessage` 调 `get_llm_client(model=item_model, json_mode=True)`（响应格式 `json_object`），历史按正序拼入 `ITEM_NAME_EXTRACT_TEMPLATE`，要求输出 `{"item_names": [...], "rewritten_query": "..."}`；prompt 明确「品牌/型号本身不算商品名」「必须改写成含商品名的独立完整问题」「可多商品不可重复」，并负责消解代词指代、从历史里找最初的商品名。
3. 对结果做代码块剥离、`json.loads`、缺字段兜底（`item_names=[]`、`rewritten_query=original_query`），并用 `normalize_item_name` 做 NFKC 归一化。
4. 有商品名才做向量对齐：`generate_embeddings(item_names)` → `kb_item_names` 混合检索（Top5、`(0.8,0.2)`、`norm_score=True`、只要 `item_name` 字段）→ 取 `hit["distance"]` 作为 score。
5. 三档判定 → 写历史 → 重新读历史作为 `state["history"]`。
- 代码依据：`query_process/nodes/node_item_name_confirm.py:34-80,94-208`、`query_process/prompt.py:3-33`。

#### Q45. [进阶] 商品名匹配不唯一或完全匹配不到时，系统怎么处理？

**参考要点：**

- 阈值写在 `_step6_align_item_names`：`score > 0.80` 直接确认（可多条）；无高分但有 `score >= 0.6` 时取前 3 个作为候选；再低则无结果。
- 候选分支生成 `answer="您是想咨询以下哪个产品：...，请明确"`，`answer_type=ANSWER_TYPE_CLARIFY(3)`；无结果分支生成「抱歉，未找到相关产品，请提供准确的商品型号和商品名称。」，`answer_type=ANSWER_TYPE_MISSING(1)`。

#### Q48. [进阶] HyDE 检索是什么？为什么能提升召回率？假设文档写偏了怎么办？

**参考要点：**

- HyDE 是 Hypothetical Document Embeddings，假设性文档检索：先让模型根据问题生成一段可能的答案/假设性技术文档，再用它做向量检索。用户问题往往很短或缺实体主语，假设文档更像真实手册里的表达，更容易命中。
- `HYDE_PROMPT` 要求「基于用户查询生成简洁的回答范文」，以专家口吻、不用「假设/可能」等不确定词、中文不超过 300 字；用的是默认 LLM。
- 关键实现：把**改写后的问题与假设文档拼成一个字符串**再向量化——`generate_embeddings([rewritten_query + "\n" + hyde_doc])`，其余检索参数与普通向量检索完全相同（同一过滤表达式、Top10、`0.8/0.2`、`norm_score=True`），结果写入 `hyde_embedding_chunks`。
- 防止跑偏的三层约束：Prompt 限制必须围绕原问题生成；假设文档只是其中一路，还会与原问题合并、并与另一路结果做 RRF；后面还有 rerank 节点按真实 query-doc 相关性统一精排。
- HyDE 的 LLM 调用也做了 token 埋点，异常路径补记一次，避免日志漏计。
- 代码依据：`query_process/nodes/node_search_embedding_hyde.py:16-116`、`query_process/prompt.py:36-45`、`utils/query_metrics_utils.py:103-123`。

#### Q49. [综合] 两路检索是如何协同的？为什么每路必须写不同字段？

**参考要点：**

#### Q50. [进阶] RRF 融合算法是什么？代码里怎么实现？

**参考要点：**

- RRF 是 Reciprocal Rank Fusion，倒数排名融合：用文档在各路召回结果里的**排名**计算综合分，不依赖不同召回源的原始分数可比性。公式是 `score(d) = Σ weight_i / (k + rank_i(d))`，同一个文档在两路里都靠前，融合分就越高。
- 实现：`rrf_inputs = [(embedding_search_list, 1.0), (hyde_embedding_search_list, 0.8)]`，`chunk_scores[chunk_id] += weight / (k + rank)`，`rank` 从 1 开始，`k=60`（`_rrf_merge` 默认参数）；去重键是 `chunk_id`，用 `setdefault` 保留首次出现的 entity。
- 调用时 `max_results=5`，代码里最终保留 5 条候选，`rrf_chunks` 丢弃融合分数只留文档；业务口径上 RRF 默认先保留 20 条候选（见 Q57）。
- 隐含细节：若 hit 缺 `chunk_id`（`None`），所有 `None` 会被合并成一个 key，因此入库时回填 `chunk_id` 很重要。
- 代码依据：`query_process/nodes/node_rrf.py:19-73`。

#### Q51. [进阶] Rerank 用什么模型？候选文档怎么构造与打分？

**参考要点：**

- 融合后的本地候选被拉平成统一结构（标题、正文、`chunk_id` 与图片 URL），标题取 `item_name`，正文取 `content`；这样 query-doc pair 可以直接交给精排模型。
- 取 `rewritten_query` 与所有 `content` 列表，调 `rerank_documents(query, contents)`；底层是 `dashscope.TextReRank.call(model="qwen3-rerank", top_n=len(documents), return_documents=False, instruct="Retrieve semantically similar text.")`，按返回的 `index` 回填 `relevance_score`。
- 分数与文档 zip 组装后按 `score` 降序；这是**远端排序服务一次打分全部候选**，成本高于 RRF，所以先融合压缩再精排。
- rerank 的作用：把 query 与候选文档成对输入模型，输出相关性分数后重新排序，纠正向量召回里「语义相近但不答问题」的偏差。
- 代码依据：`query_process/nodes/node_rerank.py:53-109`、`utils/reranker_http_utils.py:10-37`、`.env.example:78-80`。

#### Q52. [综合] 什么是断崖检测截断？拒答是怎么触发的？

**参考要点：**

- 断崖检测是按 rerank 分数动态确定保留文档数量：文档按分数从高到低排序，相邻两条分差出现明显落差时在该处截断。业务上默认绝对差 **0.5** 或相对差 **25%**，属于经验配置。
- 代码常量（`node_rerank.py:23-33`）：`RERANK_MAX_TOPK=10`、`RERANK_MIN_TOPK=2`、`RERANK_GAP_RATIO=0.25`、`RERANK_GAP_ABS=0.10`、`SCORE_MIN=0.8`。
- 算法：先判断 `ranked_docs[0].score < 0.8`，成立则**直接返回空列表**；否则 `upper_bound=min(10, len)`、`lower_bound=min(2, upper)`，从第 2 名与第 3 名的间隙开始逐对计算 `abs_gap = s_i - s_{i+1}`、`rel_gap = abs_gap / (abs(s_i)+1e-6)`，任一满足 `>=0.10` 或 `>=0.25` 就在该处截断；没有断崖则取满上限。前 2 条无条件保留、最多 10 条。
- 拒答：按经验阈值，rerank 分数低于 **0.3** 的上下文可以淘汰；如果上下文都被淘汰，就触发拒答，返回资料不足的提示。代码里把入口门槛实现为 `SCORE_MIN=0.8`（只检查首位），是同一策略的严格取值；商品名确认节点的「查无此商品」也是一条拒答分支。
- 阈值怎么定：看验证集与 bad case 的 `context_recall` / `context_precision`——截断太激进召回率下降，太宽松精确率下降并增加幻觉风险；还要结合 rerank 分数分布、文档长度、上下文预算与答案正确率。
- 代码依据：`node_rerank.py:111-150`、`node_answer_output.py:113-118`、`node_item_name_confirm.py:298-303`。

#### Q53. [基础] 查询改写是什么？常见方式有哪些？

#### Q54. [进阶] 为什么要采用两路召回，不只依赖单纯的向量检索？

**参考要点：**

- 普通向量检索按「问题查答案」的常规方式召回，覆盖语义相近与关键词精确的匹配；HyDE 解决用户表达不完整、缺少实体主语的问题；两路从不同角度召回，再通过 RRF 的评分得到统一排序。
- 单路向量检索的风险：短问题、口语化问法、缺型号的追问，embedding 与手册表述距离大，容易漏召；假设文档把问句「翻译」成语料风格，能补上这部分。
- 两路结果结构一致（都来自 `kb_chunks`、都带 `chunk_id`），所以可以直接 RRF 去重融合，再交给 rerank 统一精排，流程比异构结果更简单。
- 并行扇出还带来时延收益：两路同时跑，总耗时取决于较慢的一路，而不是两者相加。
- 代码依据：`query_process/main_graph.py:104-117`、`node_rrf.py:28-41`、`node_search_embedding_hyde.py:16-40`。

#### Q55. [进阶] RRF 和 Rerank 是什么关系？可以跳过 RRF 直接重排吗？

**参考要点：**

- RRF 是**粗融合**：只用排名、计算极便宜，负责把两路结果按 `chunk_id` 去重并压成少量候选；Rerank 是**精排**：把 query 与候选文档成对输入模型输出相关性分数，再按分数重排，成本高但更准。
- 能直接 rerank，但不建议把所有原始召回都丢进去：RRF 很便宜，先做去重和粗融合；rerank 成本高，适合处理压缩后的候选。
- 两层分工还有个好处：RRF 不需要两路分数可比的量纲，rerank 只看真实语义相关性，能把「向量近但不答问题」的片筛掉。
- 顺序上先 RRF（默认保留 20 条、代码取 5 条），再 rerank（默认最少 6 最多 15、代码 2–10），最后断崖截断。
- 代码依据：`query_process/nodes/node_rrf.py:43-73`、`node_rerank.py:91-150`、`query_process/main_graph.py:114-118`。

#### Q56. [进阶] RRF 的 k 值为什么选 60？混合检索权重怎么定？

**参考要点：**

- `k=60` 是 RRF 的常用经验值：k 小，头部排名影响更大；k 大，排名差异被抹平、融合更平滑。60 让 Top1 与 Top10 的差距不至于失衡，也不至于让长尾噪声被过度放大。
- 有需要时用验证集调参：观察不同 k 值下的 `context_recall`、`context_precision` 与最终 `answer_correctness`，结合 bad case 决定是否调整。
- 混合检索权重同理：准备包含常规问题与期望匹配切片的测试集，按多种 dense/sparse 权重跑同一批问题，取分值更高的一组；基线可以按两种索引各一半，链路上收敛到 0.8/0.2 并开启 `norm_score`。
- RRF 的两路权重也一样可调：代码里普通向量 1.0、HyDE 0.8，体现「原始问题为主、假设文档为辅」。
- 代码依据：`node_rrf.py:28-34,43-73`、`utils/milvus_utils.py:99-105`、`node_search_embedding.py:71-86`。

#### Q58. [综合] 如果召回率低或大量不相关，从哪些方面排查和优化？

**参考要点：**

- 排查路径：先看各路 embedding 的评分与筛选策略，再看 RRF 的权重、平滑系数与筛选策略，最后看 rerank 评分与 TopK 参数；召回率低则放宽筛选门槛，精确率低则收紧筛选门槛。

- 优化后用同一批问题集复测 `context_recall`、`context_precision`、`answer_correctness`，避免单点调优把别的指标带坏。

#### Q60. [综合] 如果最终 Top 5 都给到大模型，模型更关注头部和尾部，怎么防止中间数据丢失？

#### Q61. [进阶] 最终 prompt 是怎么拼出来的？上下文超长怎么办？

**参考要点：**

- `ANSWER_PROMPT` 有四个占位符：`【参考内容】{context}`、`【历史对话】{history}`、`【相关商品/实体】{item_names}`、`【用户问题】{question}`；要求尽量基于参考内容、不编造，若需配图则图片只能来自本地切片文本，并在末尾用独立 `【图片】` 区块逐行给 URL。
- `question` 取 `rewritten_query`（不是原始问句），`item_names` 为空时写「无指定商品」；上下文为空时写「无参考内容」。
- `MAX_CONTEXT_CHARS = 12000`：`_format_reranked_docs` 与 `_format_chat_history` **共享递减的 char_budget**，逐条累加长度，超预算即停止；每条参考文档带 `[idx] [chunk_id=] [url=] [title=] [score=%.4f]` 元数据头，便于模型分辨来源。

#### Q63. [基础] SSE 流式响应是怎么实现的？有哪几类事件？

**参考要点：**

- 流式查询先生成 `task_id` 并创建一个队列；后台跑查询图，答案节点调用 LLM stream，每生成一段就往队列里放 `delta` 事件，结束时推 `final`。
- 生效实现是 `utils/sse_utils_sync.py`：**线程安全 `queue.Queue`** + `sse_queues[task_id]` 字典；`utils/sse_utils.py`（`asyncio.Queue` 版）供早期试验使用。
- 事件类型 `SSEEvent`：`PROGRESS="progress"`、`DELTA="delta"`、`FINAL="final"`、`ERROR="error"`。节点进出推 progress（含 status/running_list/done_list），LLM 每个非空 token 推 delta，结束推 final，LLM 异常推 error。
- `event_generator` 是 async 生成器，但用 `loop.run_in_executor(None, sse_queue.get, True, 1)` 在线程池阻塞取队列，避免卡住事件循环；主动检查 `request.is_disconnected()`，`queue.Empty` 时 sleep 1 秒继续，`finally` 移除队列。
- 输出格式为标准 `event: {type}\ndata: {json}\n\n`，响应头带 `Cache-Control: no-cache`、`X-Accel-Buffering: no`。
- 前端通过 `/stream/{task_id}` 接收，最后收到 final 事件；导入任务则用 `/status/{task_id}` 轮询进度。
- 代码依据：`utils/sse_utils_sync.py:11-99`、`query_router.py:58,142,166-177`、`query_process/base.py:28-53`、`node_answer_output.py:206-231`。

#### Q64. [综合] 流式与非流式两种模式怎么区分？`FINAL` 里带答案吗？

**参考要点：**

- 业务上分两种模式：**非流式**模式下答案写入任务结果；**流式**模式下 LLM 每生成一段内容就通过 SSE 推送 `delta` 事件，结束时推送 `final` 事件。
- 代码里生成统一走 `llm.stream(prompt)`；`stream=True / False` 是**图执行模式**（`.stream()` 逐节点更新 state vs `.invoke()` 拿最终 state），`QueryGraphState` 的 `is_stream` 字段由参考答案接口写入 `False`，其余节点以「state 里是否已有 answer」作为分支条件。
- 答案节点的分支条件是「state 里是否已有 `answer`」：澄清/拒识短路分支直接推 `FINAL`（带 `answer` / `answer_type` / `item_names`），不再调模型、不写助手消息；正常检索分支逐块推 `delta`，`FINAL` 只带 `image_urls / answer_type / item_names`，**完整答案靠前端累加 delta**。
- 正常分支会把生成的完整文本写回 `state["answer"]`，并在推 `FINAL` **之前**用 `save_chat_message` 落 MongoDB；LLM 异常被吞掉，只推 error。
- 代码依据：`node_answer_output.py:39-84,188-244`、`query_process/main_graph.py:126-139`、`reference_answer_service.py:23-37`。

#### Q67. [进阶] SSE 和 WebSocket 有什么区别？为什么这里选择 SSE？

**参考要点：**

- SSE 是服务端到客户端的**单向推送**，基于 HTTP，浏览器原生支持、自动重连，适合进度通知和大模型流式输出；WebSocket 是双向通信，适合实时协作、在线聊天、频繁双向交互，交互成本更高。
- 知识库问答是「客户端提交一次问题 → 服务端持续推送进度与答案」，不需要高频双向通信，SSE 更简单、成本更低，也更容易与 FastAPI `StreamingResponse` 结合。
- 工程上还有两点：SSE 走普通 HTTP，容易被现有代理与负载均衡透传；服务端只需维护一个队列，不需要维护长连接会话状态。
- 导入侧是长任务，用轮询 `/status/{task_id}` 而非 SSE，因为进度更新频率低、且需要可重入地查询任务结果。
- 代码依据：`utils/sse_utils_sync.py:11-99`、`query_router.py:58-122`、`import_router.py:62-72`、`import.html`。

#### Q68. [综合] 如何保证 LLM 回答的准确性？

**参考要点：**

#### Q69. [综合] 项目是怎么做 RAG 效果评测的？主要看哪些指标？

**参考要点：**

- 召回率要基于测试问题集评估，不能只凭主观感觉：先构建问题集，再用 **RAGAS** 框架做自动化评估并回归调参。
- 主要观察五个指标：`faithfulness`（答案是否被上下文支撑，低说明幻觉）、`answer_relevancy`（是否切题，低说明模型理解或提示词有问题）、`context_precision`（召回上下文是否干净，低说明噪声多）、`context_recall`（证据是否召全，低说明召回链路有问题）、`answer_correctness`（与标准答案是否一致，整体效果指标）。
- 指标与调参联动：切片丢失 → `context_recall` 下降；截断太宽松 → `context_precision` 下降；检索指标不差但答案发散 → 优先调提示词，其次换模型。
- 效果口径：RAGAS 评估优化过后召回率可达 **93% 以上**；上线实测问题里存在一部分知识库外内容，召回率约 **85%**；bad case 主要集中在切片过大、表格或图片信息缺失、商品名识别错误、rerank 丢弃关键切片等场景。
- 系统侧还有线上观测：`query_metrics_utils` 采集 LLM 调用次数、input/output token 与首 token 时间，配合查询日志上报（Q70、Q73）。
- 代码依据：`utils/query_metrics_utils.py:47-199`、`services/reference_answer_service.py:15-44`、`schema/query_log_schema.py:18-34`。

#### Q71. [进阶] 准确率和召回率分别怎么评测？公式是什么？

**参考要点：**

- 准确率：用 RAGAS 的 `context_precision` 评分求平均，衡量 reranker 后的上下文与参考答案的匹配程度；公式可理解为 `准确率 = Σ(precision@k × relevance_k) / 检索的上下文数量`，其中 `Precision@K = 前 K 个检索结果中的相关结果占比`；这个算法会奖励排名靠前就命中的上下文。
- 召回率：用 RAGAS 的 `context_recall` 评分观察，同样是 reranker 后上下文与参考答案的比对；公式是 `召回率 = 上下文支持的参考答案事实点 / 参考答案的事实点`。
- 两者是一对权衡：保留更多候选 → recall 上升、precision 下降；收紧 TopK 与断崖阈值 → precision 上升、recall 下降，所以要结合答案正确率一起看。
- 评估集来自开发自测问题 + 业务高频真实问题 + 上线后的真实问题与 bad case，优化后用同一批问题集复测。
- 代码依据：`query_process/nodes/node_rerank.py:111-150`（TopK 与截断）、`query_process/nodes/node_answer_output.py:86-163`（最终上下文）、`services/reference_answer_service.py`（标准答案管道）。

#### Q77. [综合] 如何处理 Milvus 连接失败？模型接口怎么控流？

**参考要点：**

#### Q78. [综合] 知识库服务是如何部署的？资源如何分配？为什么拆分 GPU 与 CPU？

#### Q80. [综合] 如果重新设计这个系统，你会做哪些改进？

**参考要点：**

1. **增加缓存**：缓存 FAQ 标准答案与 `item_name` 对齐结果，命中即跳过 LLM 与 embedding 比对，减少调用、削峰。
2. **增加可维护的管理平台**：把切片文本存入 MySQL 等关系库，向量数据库只保留索引与向量，便于检索、审计与人工修正；配套知识库数据看板，观察文档量、召回命中率、拒答率与负反馈。
3. **知识更新灰度发布**：新内容先标识「未生效」，全部导入完成后再切换为「有效」、旧切片标识「作废」，避免导入时有人查询读到中间态（见 Q20）。
4. **可评测与可调参**：把 RRF 保留条数、Rerank TopK、断崖阈值与混合检索权重收敛到配置，用问题集 + RAGAS 做回归调参。
5. **可靠性**：任务状态从内存字典外置，修历史读取返回类型与生产代码依赖测试目录等问题；Rerank 空上下文时给明确的资料不足文案。
6. **表格与长文档**：把 HTML 表格按行线性化并保留表头，给子片加 `parent_chunk_id` 支持命中后回填父章节。

## 附录 C：一分钟口述版（可直接背）

> 这是一个面向商品手册的文档型 RAG 系统，代码分成两个 FastAPI 服务：8000 负责导入，8001 负责问答，流程都用 LangGraph 编排。
>
> 导入侧，上传接口先落盘、把原件归档到 MinIO、算出 sha256，然后用后台任务跑导入图：PDF 经 MinerU 云端 API 转成 Markdown，Word 和 Markdown 也统一到同一条结构化链路；图片用 VLM 生成中文摘要、上传 MinIO 并替换 Markdown 链接；表格做行列交叉线性化并整表保留；之后按 1–6 级标题切分，业务上最大 1200、最小 300、保留 1 句重叠，当前代码收敛到 500/100/50 字符。再用 LLM 从前 5 个切片抽商品名，回填每个 chunk，并把商品名单独向量化写进 `kb_item_names`。切片文本拼上商品名，用本地 BGE-M3 按 3 条一批生成 dense 和 sparse 向量，最后按 `file_title` 做幂等更新、全量写入 `kb_chunks`。
>
> 查询侧，先读 MongoDB 最近 10 条历史，让 LLM 输出商品名列表和改写后的问题，再用商品名向量集合做混合检索对齐；高分直接确认、中分给候选、低分拒识并短路返回。确认后由分叉节点扇出**两路**并行召回：普通混合向量检索和 HyDE 假设文档检索，各自写各自的 state 字段，汇合后统一排序。两路结果用 RRF 融合，权重 1.0 和 0.8、k=60，先压缩候选；再交给远端 rerank 做 query-doc 精排，用断崖检测和最低分截断。最后把参考文档、历史、商品名和改写问题按 12000 字符预算拼 prompt，用流式 LLM 输出 delta，答案写回 MongoDB，SSE 推 final。
>
> 效果这块用测试问题集加 RAGAS 回归：主要看 faithfulness、answer_relevancy、context_precision、context_recall 和 answer_correctness，优化后核心手册类问题召回率能到 93% 以上，上线含库外问题大约 85%；线上再用全链路 Trace 和 Grafana 盯 QPS、P99 延迟、拒答率和负反馈，bad case 回流到测试集持续调切片、召回、重排和提示词。
