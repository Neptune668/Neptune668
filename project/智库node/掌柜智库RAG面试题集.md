## 一、项目背景与整体介绍（开场必答）

### Q1. 简单介绍一下这个项目 ⭐
**题目**：请简单介绍一下你做的这个 RAG 知识库项目。

**应答思路（30s 电梯陈述版）**
- **一句话定位**：面向商品资料的文档型知识库问答系统，服务客服、运营、业务人员。
- **解决什么问题**：产品手册/说明书/维修资料分散、格式复杂，人工翻文档效率低、回答不稳定。
- **两条链路**：
  - 存储侧：PDF/Word/Markdown → MinerU 转 Markdown → 图片/表格处理 → 切片 → 商品名识别 → BGE-M3 向量化 → Milvus/MinIO。
  - 查询侧：商品名确认 → 多路召回（向量/HyDE/MCP）→ RRF 融合 → Rerank 精排 → 断崖截断 → LLM 生成 → SSE 流式返回。
- **技术栈**：FastAPI + LangGraph；存储 Milvus / MongoDB / MinIO；模型 BGE-M3（Embedding）、BGE-reranker-large（精排）、千问（生成/VLM）。

**加分点**：主动点出「你在其中负责的部分」——后端 RAG 核心链路（导入 + 查询），体现 ownership。

**工程侧难点补充**：异步导入、任务进度、流式输出、向量库一致性、导入与查询互不干扰。

## 二、核心技术难点及解决方案

### 2.1 文档解析（PDF / 图片 / 表格）

### Q6. PDF 是怎么解析和提取内容的？ ⭐⭐
**应答思路**
- PDF **不直接检索**，先 MinerU 转 Markdown。
- 转完文本、标题、表格、图片引用结构化，后续所有格式统一走 Markdown 链路。
- MinerU 解决：PDF 文本顺序乱、表格难抽、图片引用难保留。

### Q7. MinerU 和 VLM 图片识别的区别？ ⭐⭐
**应答思路（一句点破职责边界）**
- **MinerU**：把 PDF 拆出来转 MD，图片只做**引用**不做解读。
- **VLM**：看懂图片，生成图片摘要（Caption），用户提问时引用图片、回答问题。

### Q8. 表格内容是怎么提取和处理的？ ⭐⭐
**应答思路（有具体动作才加分）**
- MinerU 把 PDF 表格转为 HTML `<table>`。
- 为了让 LLM 好识别，切片时把 HTML 表格做**行列交叉合并的线性化**处理，变成自然语言。

### Q9. 图片内容是怎么处理的？ ⭐⭐
**应答思路（五步闭环）**
1. 扫描 Markdown 里的图片引用。
2. 取图片前后标题、上文、下文作为**上下文**。
3. 调 VLM 生成图片标题/摘要。
4. 上传 MinIO。
5. 把 Markdown 里的本地图片链接替换成**远程 URL + 摘要**；摘要作为文本参与检索，答案带图片 URL 前端可展示。

### Q10. 如何处理多栏格式、图文错位、左文右图、大片图片+简短编号？ ⭐⭐⭐
**应答思路**：MinerU 内部自带 VLM 识别版面信息，处理复杂版面；工业文档「大片图+简短编号」靠 VLM 生成 Caption 补全语义。

### Q11. 跨页大表格/图片切片后检索差如何处理？ ⭐⭐⭐
**应答思路**
- MinerU 支持**跨页表格合并**；HTML 表格线性化。
- 图片用 VLM 生成说明文字，把图片语义落成文本参与检索。

### Q12. RAG 中的噪声是怎么处理的？ ⭐⭐
**应答思路（三阶段过滤）**
- **导入阶段**：去页眉、页脚、乱码、无意义字符。
- **检索阶段**：相似度阈值过滤低分、Rerank 提升相关性。
- **生成阶段**：Prompt 指示模型过滤噪声信息。

### 2.2 文档切片与上下文完整性

### Q13. 文档切片是怎么做的？ ⭐⭐
**应答思路（四要点）**
1. 按 Markdown 1–6 级标题切。
2. 太长章节递归切，太短同父标题下合并。
3. 每个 chunk 保留 title / parent_title / file_title / item_name。
4. 向量化时拼 `item_name + content`，增强商品相关性；每个切片带 item_name 用于标量过滤，避免相似设备混淆。

### Q14. 文档切分长度阈值怎么控制？ ⭐⭐⭐
**应答思路（有具体数字 + 有理由 = 高分）**
- 最大长度 1200 字符（之前设 2000 时发现 rerank 经常忽略关键信息）；最小长度 300 字符；`overlap_sentences = 1`。
- 逻辑：max 控制 chunk 别太大（避免检索/rerank 稀释关键信息）；min 控制别太小（避免缺上下文）；过长递归切、过短前后合并、保留少量句子重叠。

### Q15. 同一段落/语义超过最大块长度，如何保证语义完整？ ⭐⭐⭐
**应答思路（当前实现 + 进阶方案）**
- **当前**：按标题/段落/句子边界切，不硬切句子中间；`overlap_sentences` 增加边界冗余。
- **进阶**：
  - 文本回填：chunk 保留 `parent_chunk_id`，命中子块后回填父章节/相邻块（弊端：可能引入噪声，手册型文本段落清晰，需求场景不多）。
  - 知识图谱：实体关系建立跨切片语义关联，图谱关系作为补充信息交给 LLM（弊端：需 LLM 抽取，额外 token/时间损耗）。

### Q16. 切片导致语义丢失，怎么定位和优化？ ⭐⭐⭐
**应答思路（从 bad case 出发的排查闭环）**
1. RAGAS 评估，context_recall 低 = 明显切片丢失。
2. bad case 入手：看原文有没有答案 → 召回结果有没有关键切片。
3. 原文有答案但没召回：检查 embedding / rrf / reranker 筛选前后日志。
4. 优化手段：调小 chunk、增加 overlap、保留更多 RRF 候选、提高 rerank TopK、增加标题和商品名上下文。
5. 用同一问题集复测 context_recall / context_precision / answer_correctness。

### Q17. 数千 token 规章文档切块后简短提问只能召回局部，怎么办？ ⭐⭐⭐
**应答思路**：上下文切碎 → 回填补充；长距离跨切片 → 知识图谱提取核心实体关系。

### 2.3 向量化与混合检索

### Q18. dense 和 sparse 为什么都要？ ⭐⭐
**应答思路（一句话 + 数据背书）**
- dense 擅长语义改写，sparse 擅长型号、参数、接口名、专有名词；企业文档两类问题都有，BGE-M3 混合更稳。
- **数据话术**：dense only Recall@5 = 78.4%；dense/sparse 0.8/0.2 → 86.9%；HyDE+RRF 后 → 90.8%。

### Q19. 什么是混合检索？BM25 和向量权重怎么定？ ⭐⭐
**应答思路**：当前两种索引权重各一半；确定方法是准备「常规问题 + 期望命中切片」的测试集，多组权重对比测试取分值更高者。

### Q20. 什么是查询改写？ ⭐⭐
**应答思路**：把原始问题转成更适合检索的表达，并把历史对话信息提炼进本次问题。常见方式：纠错、标准化（简称/别名转标准术语）、补充主语、拆解复杂问题。

### Q21. 向量相似度和语义相近是否等同？ ⭐⭐
**应答思路（打个比喻）**：不等同。向量模型把文章含义压缩成向量，丢失大量细节——就像把两幅油画压成 8 位像素图再比相似度。

### Q22. RAG 向量化 + 切块的框架有什么问题？有没有更好方式？ ⭐⭐⭐
**应答思路**：实现简单，但切块破坏上下文完整性、语义断裂，无法建立跨文档实体关系；改进方向是回填切片或知识图谱。

### 2.4 商品名识别（项目特色点，容易被深挖）

### Q23. 商品名确认机制是怎么做的？ ⭐⭐⭐
**应答思路（四步分级决策，重点）**
1. LLM 从当前问题 + 历史对话抽商品名。
2. 商品名向量化 → 商品名向量集合混合检索。
3. 分级决策：高分直接确认 / 中间分返回候选（"您是在询问哪款产品"）/ 低分让用户补型号。
4. 确认后商品名作为后续 Milvus 检索的**标量过滤条件**。

**加分点（待优化）**：未来可对商品名做缓存，问题分词后与缓存匹配直接命中，跳过 LLM + embedding 比对。

### Q24. 多轮对话后才确认商品名，历史记录缺失怎么办？ ⭐⭐⭐
**应答思路**
- 问题改写会带上之前的对话记录（含已有商品名）。
- LLM 基于本次问题 + 历史抽取商品名，存进本次会话。
- 确认成功后**回填**之前未确定商品的历史对话。

### 2.5 多路召回

### Q25. 三路召回分别是什么？各自解决什么问题？ ⭐⭐
**应答思路（记住"两本地 + 一网络"）**
- 普通向量检索：常规语义 + 关键词匹配。
- HyDE 检索：解决用户表达不完整、缺实体主语。
- MCP 网络检索：额外网络补充，补本地缺失信息 + 实时信息。

### Q26. 为什么要多路召回，不只用单纯向量检索？ ⭐⭐
**应答思路**：单路召回维度单一，召回不全；多路从不同角度召回后经 RRF + Rerank 统一排序，召回更全、答案更稳。

### Q27. 多路检索之间如何协同（LangGraph 实现）？ ⭐⭐⭐
**应答思路（体现编排能力）**
- LangGraph 里一个虚拟 `multi_search` 节点把多路检索**并行**发出去。
- 每一路只写自己的结果字段，互不干扰。
- join 后本地两路进 RRF（无图谱则两路），网络结果在 Rerank 阶段合并。
- 好处：并行提速 + 统一排序。

### Q28. HyDE 是什么？为什么能提升召回？偏了怎么办？ ⭐⭐
**应答思路**
- HyDE = Hypothetical Document Embeddings，先让模型根据问题生成一段假设性答案/技术文档，再用假设文档做向量检索。
- 用户问题短/缺实体，假想文档更接近真实手册表达，召回更易命中。
- 防偏：提示词限制必须围绕原问题生成；HyDE 只是一路，与原问题合并；后面还有 rerank 兜底。

### 2.6 RRF 融合与 Rerank 重排

### Q29. RRF 是什么？为什么需要 RRF？ ⭐⭐
**应答思路**：Reciprocal Rank Fusion 倒数排名融合，不依赖各召回源原始分数可比性，只按文档在各路结果中的**排名**算综合分。

$$score(d)=\sum_i \frac{1}{k + rank_i(d)}$$

- `rank_i(d)`：文档在第 i 路的排名；`k` 常用 60；排名越靠前融合分越高。同一文档多路都靠前 → 分数累加。

### Q30. RRF 的 k 值为什么选 60？ ⭐⭐
**应答思路**：60 是经验值；k 小头部排名影响更大，k 大排名差异更平滑；可经验证集调参（观察不同 k 下的 context_recall / context_precision / answer_correctness）。

### Q31. RRF 和 rerank 有什么区别？重排怎么做？ ⭐⭐
**应答思路**
- RRF：**粗融合**，便宜，做去重和初步排序。
- rerank：**精排**，把 query 和候选文档成对输入 rerank 模型，输出相关性分数再排序。
- 定位差异：rerank 成本高，适合处理 RRF 压缩后的候选。

### Q32. 能否直接用 rerank 模型重排，跳过 RRF？ ⭐⭐⭐
**应答思路（能，但不建议）**
- RRF 便宜，先做去重粗融合。
- Rerank 成本高，适合处理压缩后候选。
- 网络结果没有本地 chunk_id，放到 rerank 阶段统一精排更方便。

### Q33. 检索重排后返回 Top 多少？ ⭐⭐
**应答思路（不是固定 TopK，体现"动态"）**
- RRF 默认先保留 20 条本地候选。
- Rerank 后默认最少 6 条、最多 15 条，中间用**断崖检测**截断。

### Q34. 什么是断崖检测截断？阈值怎么定？ ⭐⭐⭐
**应答思路**
- rerank 后按分数降序，用「绝对差 0.5 或相对差 25%」检测断崖，动态确定保留数量（当前为经验配置）。
- 调阈值观察两指标：截断太激进 → context_recall 下降；太宽松 → context_precision 下降、幻觉风险增加。
- 最终结合 rerank 分数分布、文档长度、上下文预算、答案正确率定。

### Q35. Top5 都给到大模型，但模型更关注头部和尾部，中间数据丢失怎么办？ ⭐⭐⭐
**应答思路（排序 + 提示词 + 摘要三招）**
- 排序：Rerank 分数最高的切片放最前。
- 提示词：要求模型逐条阅读参考资料。
- 摘要：长文本用 LLM 提摘要放靠前位置（有额外消耗）。

### Q36. 召回 chunk 超过 reranker 上下文窗口怎么办？重排后相关度仍不高怎么办？ ⭐⭐⭐
**应答思路**
- bge-reranker-large 上下文窗口 512 token，切片也控制在 500 左右，天然对齐。
- 相关度仍不高：查原因，用 HyDE 或知识图谱增加信息匹配。

### Q37. 仅靠相关度排序导致切片重复、多样性不足怎么办？ ⭐⭐⭐
**应答思路**：用 MMR（Maximal Marginal Relevance）筛选——按相关度排名时对与其他切片相近的切片做权重惩罚，删除过近切片保留多样性。

### Q38. 拒答的触发条件和实现方式？ ⭐⭐
**应答思路**：Rerank 评分低于 0.3 时淘汰上下文；上下文全被淘汰则拒答。

## 三、代码实现细节

### Q41. LangGraph 是怎么编排导入和查询流程的？ ⭐⭐⭐
**应答思路**
- 导入侧：`ImportGraphState` 携带 `task_id / file_dir / import_file_path`；入口节点判文档类型，PDF 走 MinerU、MD 直接读。
- 查询侧：`QueryGraphState` 携带 `original_query / session_id / task_id / is_stream`。
- 节点化带来的好处：每步可追踪、可单测、节点耗时可观测、失败可定位到具体节点。

### Q42. 导入接口与任务状态怎么设计？ ⭐⭐
**应答思路**
- FastAPI 导入接口创建 `task_id`；ImportFileService 先存本地任务目录，再归档 MinIO。
- TaskService 记录状态机：上传 → 处理中 → 完成 / 失败。
- 前端通过任务状态/节点列表看进度。

### Q43. Milvus 入库节点做了什么？ ⭐⭐
**应答思路**：创建 chunks 集合、稠密向量索引、稀疏向量索引、标量字段；chunk 批量插入。同时商品名向量单独一个集合。

### Q44. 最终形成哪三类核心资产？ ⭐
**应答思路**：MinIO 的原文件/图片对象；Milvus 的商品名向量、切片向量（+实体名向量）。后续查询围绕这些资产做召回、融合、生成。

### Q45. 文档去重 / 唯一性怎么保证？ ⭐⭐⭐
**应答思路（三级演进）**
1. 当前：按**设备名**幂等（删除旧的重导）。
2. 进阶：按文件 **SHA 码**识别，提醒导入用户已有重复文档。
3. 未来：不覆盖，做版本管理。

### Q46. 新增/更新文档后，切分和索引怎么更新？ ⭐⭐⭐
**应答思路（当前 + 更优做法，体现思考深度）**
- 当前：幂等更新——按商品名清旧向量 → 重新切片、向量化、入 Milvus。
- 更优（灰度发布思路）：新内容先导入标"未生效"不删旧，导入完成后标"有效"、旧切片标"作废"，避免导入中途有人查询。

### Q47. SSE 流式响应怎么实现？ ⭐⭐⭐
**应答思路（完整链路）**
1. 流式查询生成 `task_id`，创建一个 queue。
2. 后台跑查询图，答案节点调 LLM stream。
3. 每出一段往队列放 delta 事件。
4. 前端 `/stream/{task_id}` 接收，最后收到 final 事件。

### Q48. SSE 和 WebSocket 区别？为什么选 SSE？ ⭐⭐
**应答思路**
- SSE：服务端→客户端单向推送，基于 HTTP，浏览器原生支持、自动重连，适合进度通知 + 大模型流式输出。
- WebSocket：双向通信，适合实时协作/聊天，交互成本高。
- 本项目客户端提交问题后服务端持续推进度/答案，无高频双向需求，SSE 更简单、低成本，且易与 FastAPI StreamingResponse 结合。

### Q49. 文件导入这种长任务，前端如何感知进度？ ⭐
**应答思路**：上传接口返回 task_id → 后台跑导入 → 前端轮询 `/status/{task_id}` 看状态和节点列表。

## 四、模型、评测与优化

### Q50. 项目用了哪些模型？分别用在哪？ ⭐
**应答思路（四类模型对号入座）**
- 文本 LLM（千问 Flash）：商品名抽取、问题改写、HyDE、图谱抽取、答案生成。
- VLM：图片摘要（兼容 OpenAI/DashScope 配置）。
- Embedding（BGE-M3）：生成 dense + sparse。
- Rerank（BGE-reranker）：远端 HTTP 服务精排。

### Q51. VLM 和文本大模型为什么没独立部署？ ⭐⭐⭐
**应答思路（成本 + 调用频率权衡）**
- 初期访问量不高、调用频率可控，用成熟云端模型更稳、运维成本低。
- 独立部署 VLM/大模型需要高显存、服务治理、推理优化，投入大。
- 优先独立部署的是 BGE-M3 和 reranker（调用频率高、本地部署成本可控）。
- 后续调用量上升再评估独立部署文本模型/VLM。

### Q52. 召回率大概怎么样？ ⭐⭐
**应答思路（区分口径，体现严谨）**
- RAGAS 评估优化后达 93% 以上（测试集）。
- 线上实测问题含知识库外内容，召回率 85%。
- 口径话术：核心产品手册类问题稳定；bad case 集中在切片过大、表格/图片缺失、商品名识别错、rerank 丢关键切片。

### Q53. RAGAS 主要观察哪些指标？高低分别代表什么？ ⭐⭐
**应答思路（五个指标含义要背）**
- faithfulness：答案是否被上下文支撑，低 = 幻觉。
- answer_relevancy：回答是否切题，低 = 模型理解或提示词问题。
- context_precision：召回上下文是否干净，低 = 噪声多。
- context_recall：证据是否召全，低 = 召回链路问题。
- answer_correctness：最终答案与标准答案一致性，整体效果指标。

### Q54. 准确率 / 召回率具体怎么用 RAGAS 评测？ ⭐⭐⭐
**应答思路**
- 准确率：`context_precision` 求平均，即 reranker 后上下文与参考答案评分；`Precision@K = 前 K 检索结果中相关结果占比`，奖励排名靠前命中。
- 召回率：`context_recall`，即 reranker 后上下文 vs 参考答案；`召回率 = 上下文支持的参考答案事实点 / 参考答案事实点`。

### Q55. 测试问题集怎么来的？ ⭐
**应答思路（三来源）**：开发按文档整理自测问题 → 业务补高频真实问题 → 上线后收集真实用户问题 + bad case。

### Q56. bad case 主要分析什么？步骤？ ⭐⭐⭐
**应答思路（按评分分诊，重点）**
- 召回率低：先查原文有无答案 → 查淘汰证据节点（embedding / rrf / reranker）。
- 上下文准确分低：调 topk 保留数量。
- 正确性低、其他高：优先调提示词，其次换模型。

### Q57. 项目里有哪些优化案例？ ⭐⭐
**应答思路（四类案例，各背一个）**
1. 切片/重排：答案在原文后半段但 rerank 不敏感 → 调小 chunk、加 overlap、提高候选保留。
2. 提示词：检索指标不差但答案发散 → 只基于资料回答、控制长度、按对象分组。
3. 脏数据：mineru 转出的特殊符号公式 → 加规则过滤清洗。
4. 性能：多用缓存和 FAQ，减少 LLM 调用。

### Q58. 审计机制 / 系统观测怎么实现？ ⭐⭐
**应答思路**：LangSmith/Langfuse/自研日志记录全链路 Trace（Query、召回 Chunks、Rerank 分数、Prompt、LLM 输出、耗时）；Grafana 观测 QPS、P99、拒答率、负反馈率。

## 五、性能、稳定性与部署

### Q59. 响应时间从 3s 变 12s，怎么排查节点耗时？ ⭐⭐⭐
**应答思路**
- 查询每环节进度可见、日志有节点耗时，可追踪。
- 延迟一般出在 LLM 节点和 MCP 节点。
- MCP：排查网络访问阻塞；LLM：用缓存策略绕过 LLM。

### Q60. 如何保证知识库系统高可用？ ⭐⭐
**应答思路**：多路召回（单路故障不影响主流程，容错）、重试机制、多副本、兜底策略。

### Q61. Milvus 连接失败怎么处理？ ⭐⭐⭐
**应答思路**
- 客户端单例 + 连接检查，避免重复连接。
- 失败记日志，给上层节点返回可控错误/空结果，不让服务崩。
- 导入场景：任务标 failed，前端看到失败原因。
- 查询场景：降级到其他召回源（图谱/历史/MCP）。
- 生产配健康检查、重试、超时、告警。

### Q62. 如何做模型接口控流，避免限流/过载？ ⭐⭐
**应答思路**：设定并发 + 每分钟 token 参数；多线程 + 消息队列削峰。

### Q63. 项目怎么部署的？资源怎么分配？ ⭐⭐
**应答思路（按 0.5–1 QPS 规划）**
- 两台服务器：4C16G 应用机 + 8C32G 中间件机。
- 大模型用千问服务；Embedding + Reranker 部署在一台 4090（24G 显存）GPU 云服务器。
- （压测数据可作加分）16/32/64 并发 → 14.8/25.6/38.9 QPS，TPOT P95 38/46/63 ms/token，GPU 61%/78%/91%。

### Q64. 为什么拆分 GPU 和 CPU 服务器？ ⭐⭐
**应答思路**：CPU 服务负责 API、流程编排、DB 读写、SSE；GPU 服务负责 embedding、rerank 推理；拆开互不抢资源，方便单独扩模型服务。

### Q65. 为什么没用 Kubernetes 部署？ ⭐⭐⭐
**应答思路**：当前规模不大，Docker Compose 更易交付排查；K8s 适合多副本、弹性伸缩、灰度发布、复杂运维；先把链路跑稳，流量上来再迁移。

### Q66. 如果重新设计这个系统，你会做哪些改进？ ⭐⭐⭐
**应答思路（四条，体现架构思维）**
1. 加缓存（FAQ、item_name）。
2. 加可维护管理平台，文本存 MySQL、向量库只留索引。
3. 加知识库数据看板。
4. 知识更新做灰度发布，避免导入时有人查询。

## 六、常见追问应答思路（话术模板）

### 模板 A：召回率低 / 大量不相关怎么排查 ⭐⭐⭐
> 排查路径：先看各路 embedding 评分与筛选策略 → 再看 RRF 各路权重、平滑系数、筛选策略 → 再看 rerank 评分、topk 筛选参数。原则：召回率低则放宽筛选门槛，精确率低则收紧筛选门槛。

### 模板 B：涉及"数值口径"的问题（用户量/召回率/文档规模）
> 用"规划口径 vs 实际口径"分开表述，避免被追问打脸；文档 3000–6000 份，有 PDF/Word/MD，几页到上百页不等；知识库是文档切片存储，不是 QA 对。

### 模板 C：关于"模型选型依据"
> Milvus 看重存算分离，MinIO 同时存向量数据、图片、原始文件；问数项目用 Qdrant+ES 是承接京东 DataAgent 改造；再选一次可以统一，企业级用 Milvus 更稳。

### 模板 D：关于"技术方案对比"
> 任何"为什么用 A 不用 B"的问题，回答结构：A 的优势 → B 的劣势/成本 → 本项目场景为什么匹配 A → 什么情况下会切换 B。
